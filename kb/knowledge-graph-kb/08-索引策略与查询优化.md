# 08 索引策略与查询优化

## 1. 索引是为查询付费

每一个索引会消耗写入吞吐、磁盘、内存、恢复时间和运维复杂度。因此先收集真实 query template，再设计索引。为每个模板写下：入口过滤、连接顺序、排序、返回上限、权限维度、目标 p95 延迟和数据基数。

## 2. 索引工具箱

| 索引 | 擅长条件 | 典型用途 | 成本/限制 |
| --- | --- | --- | --- |
| 邻接/边标签 | 已知起点后的扩展 | `作者→论文` 两跳遍历 | 高度节点会变热 |
| B-tree/range/composite | 等值、范围、前缀、排序 | 规范 ID、日期、状态 | 写放大；组合顺序重要 |
| 哈希 | 高选择性等值 | 外部 ID 去重 | 不支持范围/排序 |
| 倒排全文 | 词项、短语、布尔检索 | 标题、正文、别名 | 分词器和语言必须匹配 |
| 位图 | 低基数过滤 | 租户、状态、类型 | 高基数会膨胀 |
| 向量 ANN | 高维相似 | 文档块、实体描述候选 | 近似结果、需过滤策略 |
| RDF 排列 | S/P/O 各种绑定模式 | SPARQL 三元组连接 | 存储与更新放大 |

## 3. 向量 ANN 的工程取舍

HNSW 常在召回、延迟和内存之间取得好平衡，适合频繁查询；IVF 系列用聚类降低比较量，通常需要调节探测桶数；量化和磁盘索引用召回换成本。无论算法如何，必须单独评估 `recall@k`、延迟、索引构建时间、内存和过滤后的结果质量。

向量索引的元数据过滤（租户、语种、时间、文档类型）不是装饰：如果先全局 ANN 再过滤，既可能泄露数据也可能得到不足 k 个可用结果。能在索引阶段执行的过滤优先下推。

## 4. 图和三元组查询优化

1. 从最选择性的已索引条件出发，而不是从全图扫描。
2. 在扩展路径前应用类型、时间、权限和边类型过滤。
3. 将常用的 (S,P,O) 绑定排列或属性组合交给相应索引。
4. 维护基数统计；统计过期会令优化器选错连接顺序。
5. 分析执行计划，确认实际走索引而非碰巧跑通。

对于 JanusGraph 一类系统，复合索引适合确定的等值组合；混合索引适合全文、地理、范围等搜索后端能力。对 Neo4j，一般让 Cypher 优化器选择 range、text、full-text、vector 等索引；不同检索器的分数不应直接比较。

## 5. 混合排序与缓存

一个清晰的初始策略：

```text
hard filters → lexical Top-100 + vector Top-100 → RRF → graph re-rank → evidence checks → Top-10
```

缓存优先放在权限安全且高重复的层：词表、实体详情、短 TTL 热门查询、预计算邻域。不要缓存没有版本键的最终答案；图谱、索引、权限或模型变更后它会悄悄陈旧。

## 6. 上线前检查

- 对每种查询跑 `EXPLAIN/PROFILE` 或等价计划分析。
- 压测冷热缓存、超级节点、空查询、跨租户过滤和索引重建。
- 监控索引滞后、失败率、碎片、召回率抽样和成本。
- 给索引取可读名称，并写明所有者、查询模板、重建方式和回滚步骤。
