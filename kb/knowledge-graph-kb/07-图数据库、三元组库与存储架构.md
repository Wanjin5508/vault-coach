# 07 图数据库、三元组库与存储架构

## 1. 选择存储前先列出约束

至少明确规模（节点/边/文本量）、读写比例、峰值并发、延迟 SLO、事务要求、推理/标准互操作、部署模型和数据主权。不存在“最好的图数据库”，只有对主查询最匹配的组合。

## 2. 工具定位

| 工具/类别 | 模型与接口 | 强项 | 注意点 |
| --- | --- | --- |
| Neo4j | 属性图、Cypher | 开发体验、图遍历、事务与一体化索引 | 评估版本、部署和规模边界 |
| Apache Jena TDB2/Fuseki | RDF、SPARQL、HTTP 服务 | 标准语义、命名图、SHACL 与本地三元组存储 | 需按查询和数据规模压测 |
| Eclipse RDF4J 等 RDF 栈 | RDF、SPARQL | Java 生态和可组合 RDF 组件 | 选择具体存储实现 |
| JanusGraph | 属性图、Gremlin、可插拔后端 | 分布式存储和搜索后端组合 | 模式与索引生命周期更需严谨运营 |
| OpenSearch/Elasticsearch 类 | 文本/过滤/向量检索 | 大规模召回与搜索排序 | 不替代权威关系存储 |
| Milvus 等向量库 | ANN 向量检索 | 高维近邻召回 | 无法替代实体、关系与证据治理 |

这些工具可在一个系统中共存。将所有数据复制到每一个引擎通常会造成一致性和成本问题；应确定一个权威写入层，并通过事件或批处理构建派生索引。

## 3. 三元组库的物理思路

三元组模式查询需要快速绑定 `S`、`P`、`O`。常见实现维护 SPO、SOP、PSO、POS、OSP、OPS 的若干排列或压缩变体，使不同绑定模式可以从合适前缀开始。它提升读性能，但带来更多写放大和存储开销。

命名图也是物理设计问题：它能提供来源/版本隔离，却会增加四元组过滤和统计复杂度。只有在确实查询或治理来源边界时，才把细粒度来源建成命名图；否则可使用断言元数据。

## 4. 属性图的物理思路

遍历主要依赖邻接表：从一个节点拿到按边类型、方向、时间或属性排序的邻居。高出度“超级节点”会造成热点、分区倾斜和宽行问题，需要：

- 分桶/分片邻接表；
- 对常用边类型建立 vertex-centric 索引；
- 为公共入口使用预聚合或缓存；
- 限制无界多跳查询，并为在线与离线分析分流。

## 5. 推荐的分层数据面

```text
对象存储/湖仓（原始文件、快照、训练集）
        ↓
规范化记录与实体目录（权威 ID、变更日志）
        ↓
规范知识图/断言图（事务与证据）
        ↓                   ↘
全文/过滤索引             向量 ANN 索引
        ↓                   ↙
      查询编排层、缓存、审计与可观测性
```

图数据库或三元组库保存可解释的关系真相；检索索引是从它和文档派生出的、可重建的加速层。下一章将从查询模式反推各层索引：[[08-索引策略与查询优化]]。
