# 团队协作模板与新人训练

## 1. 新人进入项目时先建立三张地图

### 1.1 产品地图

新人应能回答：

- Vault Coach 为谁解决什么问题？
- 当前 Product Goal 和 Sprint Goal 是什么？
- 本地优先、隐私和离线能力有哪些不可破坏的约束？
- 当前 PBI 为什么比其他工作优先？

入口：

- [[01-项目总览与面试叙事]]
- [[02-需求分析与产品设计]]
- 当前版本产品优化与开发里程碑文档
- Product Backlog 与当前 Sprint 记录

### 1.2 架构地图

新人应能画出：

```text
presentation → application API/services → domain ports/rules
                                  ↓
                           infrastructure adapters
```

并能解释：

- 为什么 `domain` 不依赖 Obsidian、DOM 和日志实现；
- 为什么组合根负责创建有状态服务；
- 为什么持久化事实、派生视图和运行诊断的生命周期不同；
- 为什么兼容适配器要传播 context，而不是重复创建 root trace。

入口：[[15-重构后软件架构]] 与 [[06-VaultCoach可观测性架构与接口]]。

### 1.3 交付地图

```text
Backlog → Sprint Goal → Task → Commit → PR → CI → Obsidian 验收
        → Review → Release/用户反馈 → Retrospective → Backlog
```

新人不仅要知道怎样提交代码，还要知道每个证据在何处产生、由谁检查、失败后怎样恢复。

## 2. 新人四周训练计划

| 周次 | 学习重点 | 实际任务 | 完成证据 |
| ---: | --- | --- | --- |
| 第 1 周 | 产品、架构、构建、测试 | 本地安装；跟踪一个 command 到 domain/infrastructure | 架构图、基线命令、疑问清单 |
| 第 2 周 | Agile/Scrum、Story、DoD | 改进一个文案/小缺陷，走完整 PBI→PR | 验收标准、PR、手工验证 |
| 第 3 周 | 结构化日志与 trace | 用 fake sink 为一个低风险应用流程加 span | trace 树、单测、隐私检查 |
| 第 4 周 | 故障注入、CI、Review/Retro | 完成索引 trace 的一个子阶段 | 失败证据、Review 演示、Retro 行动 |

### 学习原则

- 第一次改动要走完整交付链，而不是追求功能规模；
- 每周至少由导师做一次代码/设计走查；
- 新人先解释现有契约，再提出修改；
- 自动化通过后必须做与改动相关的真实 Obsidian 验证；
- 只把已验证结果写成事实，计划与待验证项明确标记。

## 5. Daily 检查模板

Daily 的中心是 Sprint Goal，不是工时报告：

```markdown
## YYYY-MM-DD
- Sprint Goal 状态：on track / at risk / blocked
- 昨日新增证据：测试、trace、评审或用户反馈
- 今日最小可完成动作：
- 当前阻塞与需要谁处理：
- 是否需要调整 Sprint Backlog：
```

如果连续两天只有“仍在开发”，应把任务拆小，明确未知项，或创建 timeboxed spike。

运行故障先保存事实，再提出原因：

```markdown

## 用户可见现象

## 环境
- plugin/Obsidian/OS：
- relevant settings categories：
- test Vault scale：

## 时间线
| 时间 | 事实 | traceId/spanId/证据 |
| --- | --- | --- |

## 影响与边界
- 受影响：
- 保持可用：
- 数据完整性：

## 复现
1. …

## 已确认事实
- …

## 假设（尚未验证）
- …

## 修复与恢复
- immediate recovery：
- code change：
- data repair：

## 验证
- regression test：
- manual：
- negative test：

## 防止再次发生
- backlog item / DoD / alert / docs：
```

不要根据一条 error log 直接写根因。trace 也只描述已记录路径；缺失 span 可能来自采样、容量、埋点或执行未到达。

## 12. 代码评审检查表

### 产品与 Agile

- [ ] PR 关联 PBI 和 Sprint Goal；
- [ ] 验收标准可从变更和证据中核对；
- [ ] 修改范围形成可用纵向切片；
- [ ] 非目标工作没有偷偷混入。

### 架构

- [ ] Domain 保持纯净；
- [ ] app 定义端口，infrastructure 实现 adapter；
- [ ] presentation 只通过应用 API；
- [ ] 有状态实例由组合根管理；
- [ ] 兼容层没有重复业务或 root span。

### 日志与 trace

- [ ] root span 与用户意图/任务一致；
- [ ] span 名称稳定、低基数；
- [ ] attributes 使用 allowlist；
- [ ] error/cancel/degraded 语义一致；
- [ ] 日志带相关 context；
- [ ] 没有每 chunk/每 token 高频记录；
- [ ] sink 失败不影响业务。

### 隐私与生命周期

- [ ] 无正文、prompt、回答、凭据、绝对路径；
- [ ] 默认无远程遥测；
- [ ] buffer 有界且可清除；
- [ ] 卸载清理 listener/timer/exporter；
- [ ] audit/domain facts 没有混入诊断缓冲。

### 验证

- [ ] 测试覆盖实际风险，不只是镜像实现；
- [ ] lint/test/build/diff check 结果齐全；
- [ ] 真实 Obsidian 场景与环境已记录；
- [ ] 文档、事件目录和接口同步。

## 13. 用 trace/span 思想改善团队协作

Trace/span 是运行时模型，也能帮助新人理解工作分解，但二者不能混成同一数据系统：

| 运行时 | 协作类比 | 使用价值 |
| --- | --- | --- |
| Trace | 一条 PBI 从需求到交付 | 保持端到端目标 |
| Root span | Sprint 中的一次纵向实现 | 找到负责边界 |
| Child span | 可独立验证的工程阶段 | 明确依赖和耗时 |
| Context | Issue/PR/commit/证据链接 | 保持跨工具追溯 |
| Event | 关键决策或阻塞时间点 | 形成时间线 |
| Status/outcome | Done/cancelled/degraded/failed | 不把“代码写了”当完成 |
| Link | 非树形依赖或触发关系 | 记录跨 PBI 因果 |

类比只用于思考和追溯。不要把人员、工时或绩效写入运行时 trace。

## 14. 导师带教节奏

### 任务开始前

导师检查：问题、价值、边界、依赖和验收。新人复述调用链和风险，导师不要直接给完整实现。

### 开发中

每次走查聚焦一个主题：

1. 第一次：依赖方向和接口；
2. 第二次：失败、取消、降级；
3. 第三次：测试与可观测字段；
4. 第四次：真实环境与发布影响。

### 合并前

新人负责演示和证据包。导师询问“这个证据能证明什么、不能证明什么”，帮助形成工程判断。

### 合并后

在 Review 收集产品反馈，在 Retro 选一个流程改进。导师检查文档是否能让下一位新人重复工作。

## 15. 新人毕业 Gate

新人能够独立完成以下任务后，可承担中等规模 PBI：

- [ ] 从 Product Goal 写出一条可验收 Story；
- [ ] 画出当前调用链和依赖方向；
- [ ] 识别内部/外部依赖与风险；
- [ ] 设计成功、取消、降级和失败；
- [ ] 为关键路径设计低基数 trace/span；
- [ ] 用 fake clock/ID/sink 写确定性测试；
- [ ] 通过 lint、test、build 和 diff check；
- [ ] 在真实 Obsidian 中完成并记录手工验证；
- [ ] 做一次隐私字段审查；
- [ ] 主持一次 Review 演示并提交一个 Retro 改进行动。

## 16. 术语速查

| 术语 | 本教程含义 |
| --- | --- |
| Product Goal | 产品的长期目标 |
| Product Backlog | 改进产品所需工作的有序单一来源 |
| Sprint Goal | 一个 Sprint 的单一价值目标 |
| Increment | 满足 DoD、可用且累积的产品成果 |
| Definition of Done | 判断 Increment 达到质量要求的正式描述 |
| Telemetry | 用于理解系统行为的 traces、metrics、logs 等数据 |
| Trace | 一次端到端操作的相关 spans |
| Span | 有开始、结束和上下文的工作单元 |
| Context | 跨执行边界传播关联值的不可变载体 |
| Attribute | span/log 上的类型化元数据 |
| Span event | span 生命周期中的结构化时间点 |
| Sink | 接收本地诊断记录的目标 |
| Exporter | 把遥测发送到某个消费者的 adapter |
| Cardinality | 字段可能出现的不同值数量 |
| Audit fact | 必须按业务契约保留的用户/治理事实 |
