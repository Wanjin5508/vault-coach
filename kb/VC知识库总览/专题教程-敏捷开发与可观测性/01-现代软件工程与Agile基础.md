# 现代软件工程与 Agile 基础

## 1. 现代软件工程在管理什么

软件项目的困难通常不在于“能否写出某个函数”，而在于以下不确定性同时存在：

- 用户真正需要什么会随反馈变化；
- 方案可行性要通过代码、设备和真实数据验证；
- 多个模块和贡献者会产生依赖、冲突与返工；
- 发布以后仍会遇到兼容、性能、隐私和恢复问题；
- 团队必须在有限时间里决定什么先做、什么暂不做。

现代软件工程用需求管理、架构边界、版本控制、自动化测试、CI/CD、可观测性和复盘，把这些不确定性转成小批量、可验证的决策。

## 2. Agile 是价值取向，不是单一流程

[Agile Manifesto](https://agilemanifesto.org/) 提出了四组价值取向。它没有否定右侧事项，而是当两者发生取舍时，更重视：

| 更重视 | 对 Vault Coach 的含义 |
| --- | --- |
| 人与互动 | Issue、PR 和短讨论要帮助贡献者形成共同理解 |
| 可工作的软件 | 里程碑文档最终要落到可运行、可验证的增量 |
| 与用户协作 | 论坛反馈、真实 Vault 使用和可用性观察进入 Backlog |
| 响应变化 | 新证据出现后调整顺序，同时保护稳定接口和用户数据 |

“重视可工作的软件”不等于不写文档。当前项目的架构文档、迁移规则、ADR、测试说明和发布记录能减少协作成本，它们直接支持工作软件。

## 3. 十二项原则怎样落到工程动作

[Agile Manifesto principles](https://agilemanifesto.org/principles.html) 强调早期持续交付、欢迎变化、频繁交付、技术卓越、简洁、可持续节奏和定期反思。对本项目可转换为以下动作：

| 原则方向 | 工程动作 | 可检查证据 |
| --- | --- | --- |
| 早期交付价值 | 每个 Sprint 完成一个可演示的纵向切片 | Obsidian 演示、验收清单 |
| 欢迎变化 | Backlog 可重排；Sprint Goal 稳定，范围可协商 | 变更原因和重新排序记录 |
| 频繁交付 | 小 PR、小提交、短分支 | PR 周期、合并频率 |
| 技术卓越 | 分层、测试、类型、构建、隐私和恢复设计进入 DoD | CI 和评审证据 |
| 简洁 | 只实现当前 Gate 需要的能力 | ADR 中的暂不实现清单 |
| 可持续节奏 | 限制 WIP，不靠连续加班补偿过大范围 | Sprint 容量与未完成项处理 |
| 定期反思 | 每个 Sprint 复盘一项最值得改进的工作方式 | Retrospective 行动项 |

## 4. 需求从想法变成反馈循环

以“加入日志系统”为例，以下描述过大：

> 为项目接入企业级 OpenTelemetry、云端平台和全部日志。

它混合了用户价值、技术选型、远程服务和全量迁移，无法在短周期内验证。可以先写成价值假设：

> 当索引重建失败时，开发者能在本地诊断视图中找到同一 trace 的阶段、耗时、降级和错误码，从而在不查看用户笔记内容的前提下定位失败阶段。

再拆成第一条纵向切片：

```text
用户动作
  → index.rebuild 根 span
  → scan / parse / persist 子 span
  → 脱敏字段
  → 有界内存 sink
  → 本地诊断视图
  → 单元测试与 Obsidian 手工验收
```

它覆盖 UI、Application、Infrastructure 和测试，但范围仍足够小，能得到真实反馈。

## 5. User Story、验收标准与工程任务

### 5.1 Story 表达价值

推荐格式：

> 作为维护者，当索引重建失败时，我希望按一次执行查看关联的阶段和错误码，以便在不读取用户内容的情况下定位问题。

Story 描述角色、需要和价值。它不应该写成“新增 `tracer.ts`”，因为文件是方案，不是价值。

### 5.2 验收标准定义可观察结果

使用 Given/When/Then：

```gherkin
Given 本地诊断已启用且向量索引持久化被注入失败
When 用户执行一次索引重建
Then 诊断缓冲区包含一个 index.rebuild 根 span
And 根 span 的状态为 error
And vector persist 子 span 与根 span 共享 traceId
And 记录不包含笔记正文、prompt、API key 或绝对路径
And 关键词索引仍按既定降级策略保持可用
```

### 5.3 Task 描述实现动作

同一 Story 可拆为：

- 定义 trace/span 端口与安全属性类型；
- 实现有界内存 sink；
- 在索引编排边界接入根 span；
- 为 scan、parse、persist 增加子 span；
- 添加失败注入和脱敏测试；
- 添加本地诊断读取 API；
- 在 Obsidian 中完成手工验收。

Story 可独立验收，Task 单独完成通常没有用户价值。

## 6. 快速反馈的工程基础

### 6.1 小批量变更

小批量指一个 PR 围绕一个清楚的目标，而不是简单追求行数少。收益包括：

- 评审者能理解意图和风险；
- 失败时更容易定位和回滚；
- 合并冲突更少；
- trace 与测试证据能对应到具体行为。

### 6.2 持续集成

每次准备合并前至少执行当前仓库提供的 Gate：

```bash
npm run lint
npm test
npm run build
git diff --check
```

这些命令分别检查静态规则、行为契约、类型与打包、空白错误。它们不能替代真实 Obsidian 手工验证。

### 6.3 架构边界

敏捷不鼓励为了速度破坏边界。短期把 `console.error` 写进 Domain 看起来更快，但会让领域逻辑难测、难复用，也阻碍未来替换 sink。持续关注技术卓越，正是为了保持后续改变的能力。

### 6.4 可观测性

测试回答“预先想到的场景是否符合预期”，日志与 trace 帮助调查“真实运行中究竟经过了什么路径”。两者互补，不能相互替代。

## 7. 常见误区

| 误区 | 造成的问题 | 修正方式 |
| --- | --- | --- |
| Agile 就是不做计划 | 目标和依赖不透明 | 做短周期、可调整的计划 |
| Agile 就是每天开会 | 会议很多，反馈仍然很慢 | 围绕可用增量与检查调整组织事件 |
| 文档越少越敏捷 | 决策反复、接手困难 | 保留支持协作和风险控制的活文档 |
| Sprint 中不断插入新需求 | 目标失焦、永远无法验收 | 保护 Sprint Goal，范围与 PO 协商 |
| 速度等于价值 | 完成大量低价值 Task | 用可工作的增量和用户反馈衡量进展 |
| 加日志等于可观测 | 输出很多字符串仍无法关联 | 使用稳定结构、context 和诊断问题驱动埋点 |
| 所有错误都记录后继续 | 数据损坏被掩盖 | 明确可降级错误和必须失败的错误 |

## 8. 新人练习

选择 Backlog 中一个小需求，完成以下材料：

1. 一句话价值假设；
2. 一条 User Story；
3. 3–6 条 Given/When/Then 验收标准；
4. 纵向调用路径；
5. 内部依赖和外部依赖；
6. 自动化验证与手工验证；
7. 失败时的恢复策略；
8. 哪些运行证据应成为日志或 span。

### 完成 Gate

- [ ] Story 没有把具体文件名当成用户价值；
- [ ] 验收标准能由第三方重复验证；
- [ ] 依赖、隐私和降级行为已写明；
- [ ] 工作量能在一个 Sprint 中形成可用增量；
- [ ] 没有把构建通过写成真实 Obsidian 可用的证明。
