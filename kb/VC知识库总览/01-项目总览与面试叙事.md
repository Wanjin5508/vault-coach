# 项目总览与面试叙事

## 面试讲法

可以把这个项目讲成一个“个人知识库 RAG 助手”的完整工程：先解决 Obsidian Markdown 知识的解析和索引，再接入本地或用户配置的模型，最后在问答之外增加考试模式，把知识检索能力扩展到主动训练。

项目不是单纯调用 LLM，而是在插件环境中实现了从数据准备、检索、重排、prompt 构造、流式 UI、持久化、隐私配置到发布流程的一整套闭环。

## 当前能力

- 扫描 Obsidian vault 内 Markdown 文件，支持整个 vault 或指定目录。
- Heading-aware chunking，把文档按标题和自然段切分。
- 关键词检索、向量检索和 hybrid 融合检索。
- Query rewrite、rerank、长期记忆、来源展示。
- 支持 Ollama 本地模型，也支持 OpenAI-compatible 云端或自托管服务。
- 支持考试模式：生成题目、提交答案、LLM 评分、隐藏目录保存、历史查看、手动导出。
- 支持 GitHub Actions 构建、lint 和 tag release。

## 面试问答

### 1. 这个项目解决什么问题？

它解决的是用户有大量 Obsidian Markdown 笔记，但很难快速从个人知识库中找到答案、复习知识和准备面试的问题。Vault Coach 把笔记转成可检索 chunk，通过 RAG 检索相关内容，再交给 LLM 生成回答，并展示来源，降低“翻笔记”和“复习”的成本。

### 2. 为什么选择做 Obsidian 插件，而不是独立 Web 应用？

因为目标用户的知识资产已经在 Obsidian vault 里。插件可以直接复用 Obsidian 的文件系统、Markdown 渲染、内部链接跳转和侧边栏 UI，避免用户再导入数据。代价是运行环境受 Obsidian 插件 API 限制，不能随意使用 Node/Electron 能力，移动端也要更谨慎。

### 3. 项目的核心技术难点是什么？

核心难点不是简单调用 LLM，而是在插件内稳定实现 RAG：包括 Markdown 切块、中文英文混合检索、向量索引、hybrid 融合、rerank、prompt 设计、来源溯源、索引持久化和增量同步。考试模式又额外要求 LLM 输出稳定 JSON、评分口径一致、结果可追溯。

### 4. 为什么默认本地优先？

Obsidian 笔记通常包含个人知识和隐私内容。默认使用 Ollama，可以让聊天和 embedding 请求只发送到用户本机服务。云端模型能力保留给有需求的用户，但必须显式配置，并在 README 和设置中说明会发送哪些数据。

### 5. 这个项目和普通 ChatGPT 插件有什么区别？

普通聊天插件主要处理对话本身，而 Vault Coach 的核心是围绕 vault 建立检索层。它会先找到相关笔记片段，再让模型基于上下文回答。回答下方有来源，可以回到原笔记。考试模式也不是凭空出题，而是基于当前知识库范围生成和评分。

### 6. 项目里有哪些比较能体现工程能力的点？

- 索引和向量快照持久化，避免每次启动都全量重建。
- 文件事件监听、debounce、最大等待时间和文件阈值组合，实现增量同步。
- embedding 模型切换后通过索引签名判断旧向量是否失效。
- 远程服务失败时降级到关键词检索或启发式 rerank。
- 考试模式用 JSON schema、低温度、修复重试和本地归一化降低 LLM 不稳定性。

### 7. 如果面试官问项目边界，应该怎么说？

当前项目重点是 Obsidian 插件内的轻量 RAG 和考试训练，不追求企业级多用户系统、复杂工作流 Agent 或数据库级向量检索。它更像一个本地优先的个人知识助手，工程目标是在插件约束下做到可用、可配置、可发布。

### 8. 项目的主要演进方向是什么？

项目计划分为几个阶段：第一阶段是 Advanced RAG 问答；第二阶段计划做知识图谱增强检索；第三阶段是多角色面试 Agent；第四阶段是独立应用，支持更完整的前后端、语音和多会话管理。
