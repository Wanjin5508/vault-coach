# 高频追问速记

## 项目亮点

- 在 Obsidian 插件约束中实现完整轻量 RAG。
- 支持本地 Ollama 和 OpenAI-compatible 服务。
- 支持中文友好的关键词检索和向量检索。
- 支持 hybrid RRF 融合和 rerank fallback。
- 支持流式输出、Markdown 来源渲染和可点击溯源。
- 考试模式实现生成、作答、评分、保存、历史和导出闭环。
- 通过 CI/CD 自动 build、lint、release。

## 高频问答

### 1. 如果 vault 很大，当前方案会有什么瓶颈？

主要瓶颈是 embedding 构建成本、内存中线性向量扫描、MarkdownRenderer 渲染大量内容和插件环境下的 UI 阻塞。当前通过快照持久化、增量同步、top k 限制和批量 embedding 缓解，但不是企业级大规模向量数据库方案。

### 2. 为什么不用现成向量数据库？

Obsidian 插件强调轻量、本地优先和移动端潜在兼容。引入向量数据库会增加安装、运行和隐私复杂度。当前规模下内存 Map 和线性扫描足够简单可控，后续如果 vault 极大，可以再抽象向量存储层。

### 3. 你的 RAG 结果如何评估？

可以从召回质量、来源准确性、回答忠实度和用户体验四个角度评估。工程上可以构造一组标准问题和期望来源，检查 top k 是否包含目标 chunk；再人工或 LLM-as-judge 评估回答是否基于来源。

### 4. 如果模型回答和来源不一致，怎么排查？

先看 query rewrite 是否偏离问题，再看 keyword/vector/hybrid 召回结果，接着看 rerank 后进入 prompt 的 chunk，最后检查 prompt 是否约束不够。项目保留 retrieval mode、query rewrite 和 sources，有利于定位问题。

### 5. 为什么来源展示不直接让模型生成？

来源必须由程序根据真实检索结果生成。如果让模型生成来源，可能伪造文件名或标题。项目让模型只生成正文，来源由 `buildAnswerSources()` 从候选 chunk 转换，保证可点击和可追溯。

### 6. 本地 LLM 噪音和性能问题怎么优化？

可以降低默认模型规模、减少 contextTopK、降低 embedding 批次、关闭向量检索或改用云端服务。用户体验上可以加入忙碌指示、流式输出和索引进度。移动端方向可以考虑 Transformers.js embedding，但聊天模型仍需要云端或远程服务。

### 7. 考试评分是否可靠？

它是 LLM 辅助评分，不是标准化考试系统。项目通过参考答案、评分标准、低温度、百分制约束和本地归一化提高一致性，但仍应把结果定位为学习反馈，而不是绝对权威评分。

### 8. 如何处理 LLM 输出非法 JSON？

先要求严格 JSON 和 schema；解析时去掉代码块并截取 JSON 对象；失败后调用同一模型进行 JSON 语法修复；修复后仍失败才抛出用户可理解的错误。最后用本地 normalize 保证字段和分数合法。

### 9. 如果要支持移动端完整体验，最大障碍是什么？

embedding 可以用 Transformers.js 或云端服务解决，但本地聊天 LLM 在移动端难度更高。还要考虑模型文件下载、缓存、内存占用、WebGPU/WASM 能力差异和 Obsidian 移动端插件 API 限制。

### 10. 面试中如何讲项目不足？

可以主动说：当前向量检索是内存线性扫描，不适合超大规模；考试上下文抽样不保证完整覆盖；长期记忆检索还不是语义检索；CI 还可以增加版本一致性校验；README 和文档需要随功能持续更新。这样显得你了解边界，而不是只讲亮点。
