# 03：模型路径、下载与缓存设计

## 1. 学习目标

完成本章后，你应能：

1. 区分模型来源与模型缓存；
2. 理解浏览器模式下 `localModelPath` 为什么通常是 URL base；
3. 设计显式下载、完整性检查、断网暖启动和目标清除；
4. 区分 artifact cache、WASM cache、pipeline、KV cache 和知识索引；
5. 避免在 Obsidian 插件中依赖任意操作系统路径或 CDN runtime 代码。

## 2. 五种容易混淆的存储

| 名称 | 生命周期 | 典型内容 | 清除后的影响 |
| --- | --- | --- | --- |
| 模型 artifact cache | 跨重启持久化 | ONNX、tokenizer、config | 下次需要重新下载/准备模型 |
| WASM runtime cache | 跨重启持久化 | ONNX Runtime `.wasm` 与相关 factory | runtime 可能需重新加载资产 |
| pipeline/session | 进程/Worker 内存 | 已解析模型、CPU/GPU buffer | 当前生成能力消失，磁盘缓存仍在 |
| KV cache | 单次或单会话生成内存 | 历史 token 的 Key/Value | 当前生成上下文失效 |
| Vault Coach knowledge index | Vault 内持久化 | chunks、BM25、vectors、graphs | 影响检索，不等于删除模型 |

设置页中的“清除内置模型”只应清理 Vault Coach 管理的目标模型 artifact/WASM namespace，并先释放相关 pipeline。它不应删除用户笔记、考试、图谱、文字索引或其他插件缓存。

## 3. 模型来源与缓存是两个轴

### 3.1 远程模型源

默认模式通常从 Hugging Face Hub 获取文件：

```text
model ID + revision + subfolder + filename
  → remote URL
  → fetch
  → cache put
  → Transformers.js/ONNX Runtime 使用响应
```

首次使用需要网络。之后能否离线取决于：

- 所需文件是否全部缓存；
- cache origin/key 是否相同；
- WASM runtime 是否也可用；
- 系统是否驱逐缓存；
- 代码是否意外请求另一个 revision/dtype；
- Worker 与主线程是否使用相同资源定位策略。

### 3.2 本地模型源

Transformers.js `env` 提供 `allowLocalModels` 和 `localModelPath`。官方文档同时说明浏览器与文件系统环境有不同默认行为。[Transformers.js env](https://huggingface.co/docs/transformers.js/api/env)

关键区别：

```text
Node/可用 FS 环境：localModelPath 可以映射文件系统路径
浏览器环境：localModelPath 通常作为 fetch 可以访问的 URL 路径前缀
```

因此下面代码在普通网页/renderer 中不等于获得任意磁盘读取权限：

```ts
env.localModelPath = "/Users/name/models/";
```

它可能被解释为当前 origin 下的 URL。Obsidian Desktop 虽基于 Electron，但插件还要支持 Mobile，而且项目规则要求避免依赖 Node/Electron 私有路径。不能把开发机绝对路径写入正式设置或构建产物。

### 3.3 本项目的推荐路径

| 需求 | 推荐方式 |
| --- | --- |
| 默认 Built-in 模型 | 用户显式下载固定 Hub revision，存入 Vault Coach 专属浏览器/custom cache |
| 完全离线暖启动 | 验证模型、tokenizer 和 WASM 所需资源都已缓存 |
| 高级用户自定义本地大模型 | 使用现有 Ollama provider，更适合管理外部模型目录与 runtime |
| 开发期本地 fixture | 开发服务器或受控 adapter 提供 URL；不进入正式设置 |
| 社区插件 runtime 代码 | 随插件构建固定版本，不在运行时获取远程 JS/WASM |

不建议把数百 MB 模型权重放进用户 Vault：它会污染知识目录、可能触发同步、备份和移动端下载。也不建议让插件访问 Vault 外任意路径。

## 4. Transformers.js 环境配置

环境配置应在创建任何 pipeline 之前只初始化一次：

```ts
import { env } from "@huggingface/transformers";

export function configureTransformersEnvironment(): void {
  env.allowRemoteModels = true;
  env.allowLocalModels = false;
  env.useBrowserCache = false;
  env.useCustomCache = true;
  env.cacheKey = "vault-coach-transformers-v1";
  env.useWasmCache = true;
}
```

这只是教学骨架。`customCache` 还需要 adapter，字段应以 spike 锁定版本的类型为准。不要在多个模块中反复修改全局 `env`，否则不同 pipeline 的资源策略会互相影响。

正式策略还应控制：

- `remoteHost` 与路径模板；
- 是否允许远程模型；
- 自定义 cache；
- WASM 资产路径；
- runtime 日志级别；
- 开发/生产配置差异。

## 5. 自定义 Cache adapter

### 5.1 为什么需要

默认浏览器 cache 便于原型，但产品需要：

- 独立 namespace；
- 查看目标模型是否完整；
- 显示大致占用；
- 只清除 Vault Coach 自己的缓存；
- 识别 partial/corrupt/missing；
- 在 policy/revision/dtype 变化时区分旧资产。

官方 `env.customCache` 要求对象提供类似 Web Cache API 的 `match` 与 `put`。[Transformers.js env](https://huggingface.co/docs/transformers.js/api/env)

### 5.2 adapter 骨架

```ts
interface TransformersCacheLike {
  match(request: RequestInfo): Promise<Response | undefined>;
  put(request: RequestInfo, response: Response): Promise<void>;
}

export class VaultCoachModelCache implements TransformersCacheLike {
  constructor(private readonly namespace: string) {}

  private async open(): Promise<Cache> {
    return caches.open(this.namespace);
  }

  async match(request: RequestInfo): Promise<Response | undefined> {
    const response = await (await this.open()).match(request);
    return response ?? undefined;
  }

  async put(request: RequestInfo, response: Response): Promise<void> {
    await (await this.open()).put(request, response.clone());
  }

  async clear(): Promise<boolean> {
    return caches.delete(this.namespace);
  }
}
```

这个示例说明边界，不保证与未来 Transformers.js 的 `CacheInterface` 类型完全一致。实现时从固定依赖版本导入或对照公开类型写 contract test。

### 5.3 namespace

建议：

```text
vault-coach:model-cache:v1:<policy-id>
```

namespace 不应包含用户 Vault 名称、绝对路径或 prompt。`policy-id` 映射固定 model/revision/dtype/runtime policy。

不要把所有模型共用一个不可区分的 cache，然后用“清缓存”删除整个 origin。Obsidian 和其他插件可能共享宿主 origin 行为，清除范围必须经过实机验证。

## 6. 完整性 manifest

### 6.1 Ready 不能只是一个布尔值

下载到一半关闭 Obsidian时，Cache 可能已有部分 response。单独保存 `isInstalled: true` 会产生假阳性。

推荐 manifest：

```ts
interface BuiltinModelManifestV1 {
  schemaVersion: 1;
  policyId: string;
  modelId: string;
  revision: string;
  dtype: string;
  transformersJsVersion: string;
  completedAt: string;
  files: Array<{
    url: string;
    expectedBytes: number | null;
    sha256: string | null;
  }>;
}
```

manifest 只在以下条件后写 complete：

1. pipeline 所需资源下载结束；
2. 每个已知资源能从目标 cache 读出；
3. pipeline 创建成功；
4. 固定 warm-up 成功；
5. manifest 自己成功持久化。

### 6.2 启动验证

```text
读取 manifest
  → policy/model/revision/dtype/runtime version 匹配？
  → 所列文件都能读取？
  → 已知大小/hash 是否匹配？
  → 创建 pipeline
  → warm-up
  → Ready
```

如果资源探测失败，状态回到 `not-installed` 或 `partial`，显示恢复动作。不要反复自动下载形成循环。

Hash 只有在项目为固定 revision 建立可信清单时才有意义；如果没有可信期望值，写 `null` 并明确只做存在/大小/加载验证。不要把下载后的自算 hash 当作供应链真实性证明。

## 7. 下载进度

Transformers.js 的 `progress_callback` 会提供带状态的加载事件，可包含文件和字节进度。把第三方事件先转换成项目类型：[ProgressInfo](https://huggingface.co/docs/transformers.js/api/utils/core)。

```ts
type ModelLoadProgress =
  | { phase: "resolving"; file?: string }
  | { phase: "downloading"; file: string; loaded: number; total: number | null }
  | { phase: "loading" }
  | { phase: "ready" };
```

聚合原则：

- 只在 total 已知时显示百分比；
- 多文件总进度需要已知完整文件集合，否则显示当前文件；
- 文件名可以展示模型资源名，但日志不要写带用户路径的完整 URL；
- 下载完成不等于 pipeline/warm-up ready；
- 过期 job 的 callback 不能覆盖新任务状态。

## 8. 显式下载流程

```text
用户选择 Built-in Chat
  → UI 显示来源、license、预计体积、设备要求
  → 用户点击“准备模型”
  → runtime 创建 prepare job
  → 下载/缓存资源并显示真实进度
  → 创建 pipeline + warm-up
  → Ready
```

普通 Ask 遇到未准备状态时：

```text
返回 MODEL_NOT_READY
  → UI 提示“准备模型”或选择 Ollama/云服务
```

不要在一次 Ask 中暗中下载数百 MB 模型。

## 9. 断网暖启动

测试顺序：

1. 干净 cache，联网 prepare；
2. 关闭并重启 Obsidian；
3. DevTools/系统断网；
4. 加载相同 policy；
5. 确认没有网络请求；
6. 创建 pipeline 并完成固定 warm-up；
7. 生成短回答；
8. 记录启动时间和实际后端。

只看到 cache entry 不足以说明离线可用。WASM runtime、tokenizer、generation config 或 external model data 缺失都会让启动失败。

## 10. 清除顺序

```text
阻止新请求
  → 取消当前 generation/prepare
  → 终止或通知 Worker dispose
  → 释放 pipeline/session/GPU buffer
  → 删除目标 artifact/WASM namespace
  → 删除该 policy manifest
  → 重新 inspect
  → 状态变为 not-installed
```

若直接先删 Cache，内存中的 pipeline 仍可能工作，UI 会错误地以为清除失败或模型仍安装。清除操作必须幂等；重复执行应安全返回已清除。

设置页文案应说明：

- 删除多少估计空间；
- 下次使用需要重新下载；
- 不删除笔记和知识索引；
- 当前生成会停止。

## 11. Cache 状态机

```ts
type ModelCacheStatus =
  | { kind: "missing" }
  | { kind: "partial"; cachedBytes: number | null }
  | { kind: "complete"; manifest: BuiltinModelManifestV1 }
  | { kind: "incompatible"; reason: "policy" | "runtime-version" }
  | { kind: "corrupt"; reasonCode: string };
```

恢复策略：

| 状态 | 动作 |
| --- | --- |
| missing | 用户显式 prepare |
| partial | 显示重试或清除；是否续传由 fetch/cache 行为实测决定 |
| complete | 创建 pipeline 并 warm-up |
| incompatible | 不加载旧资产；允许清除或并存迁移 |
| corrupt | 清除目标 policy 后重新 prepare |

## 12. 存储容量与驱逐

`navigator.storage.estimate()` 只能提供估计：

```ts
const estimate = await navigator.storage?.estimate?.();
const usage = estimate?.usage ?? null;
const quota = estimate?.quota ?? null;
```

不能把 origin 总 usage 全部归因于 Vault Coach，也不能把 quota 当作一定可用空间。Cache Storage 可能被系统驱逐，因此每次启动都要 inspect，不把设置中的 `ready` 当事实。

在下载前可做预算检查，但最终写入仍可能因 quota 或 I/O 失败。错误应分类为可恢复状态，并保留 keyword、Ollama 和云 provider 的正常路径。

## 13. runtime 资产与远程代码边界

Transformers.js 自定义使用文档允许设置 WASM 路径。[Custom usage](https://huggingface.co/docs/transformers.js/custom_usage)

对 Vault Coach：

- 模型 ONNX/tokenizer 是用户显式下载的数据资产；
- Transformers.js、ONNX Runtime JS、Worker 和 WASM 属于运行时代码；
- 运行时代码必须固定版本并随插件正式构建提供；
- 不依赖 CDN 的 `latest` JS/WASM；
- 不能 fetch 后 `eval`；
- release smoke test 要在断网和干净 Vault 中验证 runtime 资产存在。

如果当前社区安装流程无法携带额外 WASM 文件，必须通过 spike 验证内联/Blob/受支持的单文件定位方案，或记录 NO-GO。不能把开发目录中的 `node_modules` 当成用户安装环境。

## 14. 故障注入

| 实验 | 操作 | 预期 |
| --- | --- | --- |
| 下载中断 | 下载一半断网 | partial；不写 complete manifest |
| 缺文件 | 删除一个 cache response，保留 manifest | inspect 判 corrupt/missing，不进入 ready |
| revision 改变 | policy 换 commit | 旧 cache 不被误认为新模型 |
| dtype 改变 | q4 → q8 | namespace/fingerprint 改变 |
| quota 不足 | mock `put()` 失败 | prepare 失败可重试，旧 provider 不受影响 |
| cache 驱逐 | 删除 namespace 后重启 | 状态回 missing |
| 清除中关闭插件 | clear 中 unload | 下次 inspect 得到确定状态，不假装 ready |
| 断网暖启动 | complete 后断网 | 无网络依赖且 warm-up 成功 |

## 15. 常见误区

| 误区 | 正确理解 |
| --- | --- |
| `localModelPath` 就是 macOS 绝对目录 | 浏览器模式常作为 URL 路径，需要宿主和 fetch 证明 |
| 浏览器 cache 有文件就 Ready | 还需完整性、pipeline 和 warm-up |
| 模型 cache 与 KV cache 是一回事 | 一个跨重启保存资产，一个在生成内存中保存注意力状态 |
| 清模型要删除向量索引 | 聊天模型与 embedding index 独立 |
| `storage.estimate()` 是插件精确占用 | 它通常是 origin 级估计 |
| CDN WASM 只是数据 | WASM 是 runtime 代码，生产来源必须受控 |
| Hub `main` 足够稳定 | 正式 policy 要固定不可变 revision |

## 16. 本章练习

1. 实现 fake custom cache，覆盖 hit/miss/put failure；
2. 写 `inspect()`：manifest 存在但缺一个文件时返回 corrupt；
3. 模拟 q4/q8 policy，断言 namespace 和 fingerprint 不同；
4. 做一次联网冷启动与断网暖启动，保存 Network 面板证据；
5. 清除目标 namespace，确认没有删除其他 cache；
6. 在构建后的 `main.js` 中搜索 CDN、`.wasm` 和开发绝对路径。

## 17. 本章完成标准

- [ ] 能区分模型来源与缓存位置；
- [ ] 不把浏览器 `localModelPath` 当作任意文件系统权限；
- [ ] 完成状态由 manifest、资源探测和 warm-up共同决定；
- [ ] 下载由用户可见动作触发并显示真实进度；
- [ ] cache namespace 可单独 inspect/clear；
- [ ] 断网暖启动经过真实验证；
- [ ] 清模型不删除知识索引；

- [ ] 缓存损坏、驱逐和 quota 失败有恢复路径。
