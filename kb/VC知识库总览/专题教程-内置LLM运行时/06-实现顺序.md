# 4个LLM调用本地运行时的实现顺序
是的，但从你现在这版代码看，我会稍微修正一下“4 个 LLM”的说法：更准确地说，是 **4 类模型职责**：

**Embedding → Reranker → 小型辅助 LLM → 主生成 LLM**

其中 Query Rewrite 和长期记忆抽取目前实际上共用了 `chatModel`；最终回答也共用这个 `chatModel`。你的代码已经把这些职责分得比较清楚：Embedding 单独配置，Rerank 单独配置，而 Query Rewrite、长期记忆抽取、最终回答走聊天模型。

如果你的最终目标是 **“用户安装 Vault Coach 后，尽可能不需要 Ollama，只配置一个可选的 LLM API 就能用”**，我建议按下面顺序本地化：

**① Embedding → ② Reranker → ③ Query Rewrite / Memory 小模型 → ④ 最终生成 LLM**

而且我认为前三步和第四步的产品意义完全不同。

### 1. 第一优先级：Embedding

这个应该毫无疑问最先做。

你现在默认：

`embeddinggemma → Ollama → /api/embed`

而整个 vector/hybrid RAG 都依赖它：构建索引时所有 chunk 要 embedding；用户每次查询也要先生成 query embedding。你的 `AdvancedRagEngine` 目前就是先调用 `embedTexts([query])`，再进入 vector search。

所以它实际上是目前 Vault Coach 最大的“外部基础设施依赖”。

我会把目标设计成：

> Vault Coach 自带一个轻量 Embedding 模型，首次使用自动下载/初始化，用户完全不需要知道什么叫 Embedding。

这与你之前确定的产品方向完全一致。

而且 embedding 非常适合本地化：它是 encoder，不需要自回归生成，模型可以很小，推理确定性高，而且可以批处理。你现在代码也已经实现了批量 embedding。

完成这一步以后，产品体验会从：

**安装 Vault Coach → 安装 Ollama → pull embedding 模型 → 配 URL → 配模型名 → 建索引**

变成：

**安装 Vault Coach → 建索引**

这是最大的一次 UX 提升。

---

### 2. 第二优先级：Reranker

Embedding 完成以后，我甚至建议**紧接着做 Reranker，而不是先做本地生成 LLM**。

因为你的 RAG 已经是：

**Keyword + Vector → RRF → Rerank → Context → LLM**

你的默认参数甚至已经体现这个架构：Hybrid Top-K 12 → Rerank Top-K 8 → Context Top-K 8。

现在的问题是：Reranker 还不是 Vault Coach 真正内置的能力。如果没有配置 rerank 服务，你会回退到 heuristic rerank。

真正的小型 cross-encoder reranker 很适合内置。Reranking 本身就是“召回后提高 precision”的阶段，尤其适合你这种 Hybrid Retrieval；微软的 RAG 架构文档也明确建议在 hybrid/multi-search 后使用 reranking。([Microsoft Learn](https://learn.microsoft.com/azure/architecture/ai-ml/guide/rag/rag-information-retrieval?utm_source=chatgpt.com "Develop a RAG Solution on Azure - Information-Retrieval Phase - Azure Architecture Center | Microsoft Learn"))

这样第二阶段完成后：

> **整个 Retrieval Pipeline 已经 100% 本地化。**

也就是：

`Markdown`  
→ chunk  
→ keyword index  
→ **内置 embedding**  
→ vector index  
→ hybrid/RRF  
→ **内置 reranker**  
→ Top-K Context

到这里甚至还没有调用 LLM。

这对于 Vault Coach 是一个非常漂亮的架构边界。

---

### 3. 第三优先级：小型辅助 LLM

这里我建议你未来把现在的 `chatModel` 概念进一步拆开。

因为现在一个 `Gemma 3 4B` 同时在干三件完全不同的事情：

**Query Rewrite**

你的 Prompt 要求它只返回：

```text
{"rewritten_query": "..."}
```

而且 temperature=0。

**Memory Extraction**

也只是结构化抽取：

```text
{"memories": [...]}
```

同样 temperature=0。

**Final Answer**

这才是真正需要强生成能力的任务。

所以从工程上，我不认为 Query Rewrite 和 Memory Extraction 值得长期占用一个 4B 生成模型。

未来可以变成：

```text
Vault Coach

Built-in models
├── Embedder
├── Reranker
└── Utility SLM
      ├── Query Rewrite
      ├── Memory Extraction
      ├── Intent Classification
      └── 后续 Agent Routing

External / Optional
└── Main LLM
      ├── RAG Answer
      ├── Exam generation
      └── Complex reasoning
```

这里的 **Utility SLM** 可以非常小，因为任务输出空间高度受限。

而且这一层以后会越来越重要。你如果把 Vault Coach 往 Agent 方向扩展，它还可以负责：

`rewrite / memory / routing / tool selection / query classification / retrieval decision`

所以我会把它定义成 **Vault Coach Local Intelligence Model**，而不是简单叫 Query Rewrite Model。

---

### 4. 最后才考虑：主生成 LLM

这个我反而建议你**暂时不要急着内置**。

因为你的最终回答模型承担的是最复杂的工作。代码里最终会把检索 Context、Conversation、Memory 等组装以后交给生成模型。

用户对于这个模型的需求差异也最大：

有人有 Mac M4 32GB；

有人 Windows 16GB；

有人只想用 DeepSeek API；

有人已经有 Ollama；

有人想用 OpenAI-compatible 服务。

因此把一个 3B/4B LLM 强塞给所有用户，反而会破坏你现在逐渐形成的“低配置门槛”。

你现在已经实现 `ollama | openai-compatible` Provider 抽象，这其实就是正确方向。

最终可以让：

**RAG 基础设施 = Vault Coach 管**

**生成模型 = 用户选择**

---

```text

               │ Query Rewrite   │
               └────────┬────────┘

                        │

                        │
                     Top-K
                        │

                        │
                ┌───────▼───────┐
                │   Main LLM    │
                │               │
                │ Cloud API     │
```

因此开发顺序我会定得非常明确：

**V1：内置 Embedding → V2：内置 Reranker → V3：内置 Utility SLM → V4：可选内置生成 LLM。**

前三个做完之后，我认为你甚至可以**不做 V4**。因为这时 Vault Coach 已经从“需要用户自己搭一套本地 AI 环境的 Obsidian 插件”，变成了：

> **RAG 基础设施全部开箱即用，用户只需要选择自己喜欢的 LLM。**

这其实比“4 个模型全部本地化”更有产品价值。

另外还有一个重要的工程决策：**Embedding 和 Reranker 不应该照搬你现在的 Ollama HTTP 架构来内置。** 你下一步真正需要确定的是“Obsidian/Electron 环境中模型放在哪里跑”：ONNX Runtime Web、Transformers.js、WASM/WebGPU，还是 sidecar。这个选择会直接决定桌面端、移动端支持、插件包大小和模型下载机制。我建议你下一步先把 **内置 Embedding 的 runtime 技术路线**定下来，再写代码；这是整个本地化路线最关键的架构决策。


# 内置 Utility SLM
可以，而且我认为 **Utility SLM 是 Vault Coach 里非常适合用 Transformers.js 内置的那一个模型角色**。

[Transformers.js](https://huggingface.co/docs/transformers.js/en/index?utm_source=chatgpt.com) 官方已经支持 `text-generation`、`text2text-generation`、分类、embedding 等任务，并通过 ONNX Runtime 在 JS 环境直接执行；2026 年的 Transformers.js v4 又进一步强化了 WebGPU，并明确覆盖浏览器、Node 和桌面应用。([Hugging Face](https://huggingface.co/docs/transformers.js/en/index?utm_source=chatgpt.com "Transformers.js · Hugging Face"))

### 为什么 Utility SLM 特别适合

你现在的 `LocalModelClient` 实际把三类任务都压在 `chatModel` 上：

```text
chatModel
├── Query Rewrite
├── Memory Extraction
└── Final Answer Generation
```

但前两个任务与最终回答的计算需求完全不同。Query Rewrite 本质上更接近：

```text
用户问题
↓
小模型
↓
固定 JSON
{
  "queries": [...]
}
```

Memory Extraction 同样如此：

```text
对话
↓
小模型
↓
固定 JSON
{
  "memories": [...]
}
```

以后做 Agent 后还可以继续让它负责：

```text
Intent Classification
Query Rewrite
Memory Extraction
RAG / Tool Routing
Knowledge Graph Relation Extraction
```

这些任务通常输出短、上下文短、temperature≈0、格式高度受约束，所以没有必要每次启动 Gemma 3 4B 这样的主生成模型。

因此我会把你的架构改成：

```text
                 Vault Coach
                     │
        ┌────────────┴────────────┐
        │                         │
 Built-in AI Runtime         Main LLM
 Transformers.js             用户配置
        │                         │
 ┌──────┼───────┐          ┌──────┴──────┐
Embedding   Reranker   Utility SLM     Answer
   │          │           │
   │          │     ┌─────┼─────┐
   │          │   Rewrite Memory Router
```

这样 **Utility SLM 不再属于 `LocalModelClient` 的“用户 LLM”概念，而属于 Vault Coach 自己的推理基础设施。**

### Transformers.js 怎么做

技术上可以直接：

```ts
import { pipeline } from "@huggingface/transformers";

const utilityModel = await pipeline(
    "text-generation",
    MODEL_PATH,
    {
        dtype: "q4",
        device: "webgpu",
    }
);
```

Transformers.js 官方支持量化模型，例如 `q8`、`q4`，因此你完全没有必要内置 FP16/FP32 SLM。([Hugging Face](https://huggingface.co/docs/transformers.js/en/index?utm_source=chatgpt.com "Transformers.js · Hugging Face"))

而且它支持设置本地模型路径以及：

```ts
env.allowRemoteModels = false;
env.localModelPath = "...";
```

也就是说，**首次下载模型后可以完全离线运行**。([Hugging Face](https://huggingface.co/docs/transformers.js/en/custom_usage?utm_source=chatgpt.com "Use custom models · Hugging Face"))

这对 Vault Coach 很重要，因为你不应该把几百 MB 的模型直接塞进 Obsidian Community Plugin 的 `main.js`。更合理的是：

```text
安装 Vault Coach
      ↓
第一次启用 Local AI
      ↓
下载模型
      ↓
Obsidian 本地模型缓存
      ↓
以后离线加载
```

### 真正的问题不是“能不能”，而是模型多大

这里我反而建议你**不要一开始就选 1B–3B Utility Model**。

Utility SLM 的目标不是“回答得聪明”，而应该是：

> **在尽可能低的计算成本下，稳定完成结构化的小任务。**

我会优先实验 **200M–600M 量级的 instruct model，Q4/Q8 ONNX**。

例如你未来甚至可以做到：

```text
Embedding     ~100 MB
Reranker      ~100–300 MB
Utility SLM   ~200–500 MB
─────────────────────
Built-in AI   < 1 GB
```

而主 LLM 完全不需要跟着内置。

这样 Vault Coach 的产品体验会变成：

> 安装插件 → 下载一次 AI Runtime → 只配置自己的主 LLM → 所有 RAG 基础设施自动工作。

这比现在要求用户理解：

```text
Ollama
Embedding model
Chat model
Rerank endpoint
Rerank model
TopK
Hybrid retrieval
...
```

成熟很多。

### 还有一个非常关键的工程优势

Transformers.js 默认可以 CPU/WASM 执行，也可以在支持的平台切换到 WebGPU；官方同时提醒 WebGPU 并非所有环境都可靠，因此你可以设计成：

```text
启动
 ↓
检测 WebGPU
 ↓
┌──────────────┐
│ 支持         │ 不支持
↓              ↓
WebGPU        WASM
GPU inference CPU inference
```

这会比把 Ollama 当作插件的强依赖更适合普通 Obsidian 用户。([Hugging Face](https://huggingface.co/docs/transformers.js/guides/webgpu?utm_source=chatgpt.com "Running models on WebGPU · Hugging Face"))

而且 Transformers.js v4 在 2026 年已经把 WebGPU runtime 扩展到了桌面和 Node 等 JS 环境，这一点对 Obsidian/Electron 尤其值得你验证。([Hugging Face](https://huggingface.co/blog/transformersjs-v4?utm_source=chatgpt.com "Transformers.js v4: Now Available on NPM!"))

**所以我的结论很明确：可以，而且值得。** 甚至我现在会进一步修改之前的方案——你未来真正应该做的不是“内置四个 LLM”，而是做一个统一的 **`LocalAIRuntime`**：

```text
LocalAIRuntime
│
├── EmbeddingService
│     └── Transformers.js
│
├── RerankerService
│     └── Transformers.js / ONNX
│
└── UtilityModelService
      └── Transformers.js
      ├── rewriteQuery()
      ├── extractMemory()
      ├── classifyIntent()
      ├── routeQuery()
      └── extractRelations()

ModelClient
│
├── Ollama
└── OpenAI-compatible
      ↓
 Final Answer LLM
```

这实际上可以成为你下一次架构重构非常清晰的一条边界：**`LocalAIRuntime` 是 Vault Coach 自带的 AI 基础设施，`ModelClient` 是用户选择的生成模型。**

下一步最值得做的是直接根据你现在上传的 `model-client.ts / rag-engine.ts / knowledge-base.ts / settings.ts`，设计出这个 `LocalAIRuntime` 的 TypeScript 接口和目录结构，同时选出 **Embedding + Reranker + Utility SLM 三个实际适合 Transformers.js 的候选模型**，再比较下载体积、中文能力、内存和移动端可行性。
