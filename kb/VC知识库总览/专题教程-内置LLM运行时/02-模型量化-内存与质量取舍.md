# 02：模型量化——体积、内存、速度与质量的取舍

## 1. 学习目标

完成本章后，你应能：

1. 说明 fp32、fp16、q8、q4 表示什么；
2. 区分权重存储精度、计算精度、激活和 KV cache；
3. 估算模型权重与 KV cache 的内存量级；
4. 设计 dtype 对照实验，而不是默认“越小越好”；
5. 为 Vault Coach 的引用问答和结构化任务建立质量 Gate。

## 2. 什么是量化

神经网络权重最初通常用浮点数表示。量化用更少的 bit 表示权重或中间值，并配合 scale、zero point、分组信息等元数据，把离散整数映射回近似数值。

直观示例：

```text
浮点权重：[-0.91, -0.28, 0.05, 0.43, 0.88]
量化后：  [-7,    -2,    0,    3,    7  ] + scale
```

位数减少通常会：

- 减少模型文件下载量；
- 减少权重驻留内存；
- 改善缓存和内存带宽压力；
- 引入数值近似误差；
- 依赖后端是否有高效对应 kernel；
- 可能增加反量化或类型转换开销。

因此 q4 不保证比 q8 在所有设备上更快，也不保证所有模型和模块都适合相同 dtype。

## 3. Transformers.js 中常见 dtype

官方 dtype 指南列出的常见选择包括：

| dtype | 典型位宽 | 直观含义 | 主要取舍 |
| --- | ---: | --- | --- |
| `fp32` | 32 bit | 单精度浮点 | 文件和内存大，通常作为高精度参考 |
| `fp16` | 16 bit | 半精度浮点 | WebGPU 常见，设备需支持相应能力 |
| `q8` / `int8` / `uint8` | 8 bit | 8 位量化家族 | 体积明显降低，通常比 q4 更保守 |
| `q4` | 约 4 bit 权重 | 4 位量化 | 体积更小，误差与 kernel 兼容性更需验证 |
| `q4f16` | 模型定义相关 | 4 位权重配合 fp16 路径 | 需要具体模型和后端支持 |
| `bnb4` | 模型定义相关 | 4 位量化方案 | 不能仅根据名字推断兼容性 |

可用 dtype 取决于模型仓库实际包含的 ONNX 文件。官方提供 `ModelRegistry.get_available_dtypes()` 查询能力，但产品策略仍应使用经过验证的 allowlist，不应每次启动根据网络结果自动选择“最小 dtype”。参考：[Transformers.js dtype guide](https://huggingface.co/docs/transformers.js/en/guides/dtypes)。

## 4. 量化了什么，没有量化什么

### 4.1 权重文件

一个参数量为 $P$ 的模型，如果所有权重都理想地用 $b$ bit 存储，权重数据理论下限约为：

$$
\text{WeightBytes} \approx \frac{P \times b}{8}
$$

以 0.5B 参数为粗略例子：

| 形式 | 仅权重理论下限 |
| --- | ---: |
| fp32 | 约 2.0 GB |
| fp16 | 约 1.0 GB |
| q8 | 约 0.5 GB |
| q4 | 约 0.25 GB |

实际下载与内存不会精确等于这个表，因为还包括：

- tokenizer、config 和 generation config；
- scale、zero point、group metadata；
- 某些未量化层；
- 多个 ONNX 文件或 external data；
- runtime、WASM 和 JavaScript bundle；
- session 初始化的临时 buffer；
- 激活、logits 和 KV cache；
- GPU driver 与 buffer 对齐开销。

所以不要用参数量公式向用户承诺实际下载大小。真实大小应来自固定 revision 的文件清单和下载进度。

### 4.2 计算精度

“q4 模型”通常描述权重存储或特定算子的权重量化方式，并不代表所有计算都以 4 bit 进行。后端可能：

- 在 kernel 内解包 q4；
- 把权重转换到 fp16/fp32 参与计算；
- 让不同模块使用不同 dtype；
- 对不支持的算子采用其他路径。

因此需要分别记录：

```text
模型文件 dtype
实际 execution provider
设备能力
pipeline 初始化内存
生成时峰值内存
生成速度
```

不能从 `dtype: "q4"` 单独推断显存、速度或质量。

### 4.3 激活与 KV cache

自回归模型每生成一个 token 都需要保存历史注意力的 Key/Value。简化估算：

$$
\text{KVBytes} \approx 2 \times L \times S \times H_{kv} \times D_h \times B
$$

其中：

- $2$：Key 与 Value 两份；
- $L$：Transformer 层数；
- $S$：当前序列 token 数；
- $H_{kv}$：KV head 数；
- $D_h$：每个 head 的维度；
- $B$：每个 KV 元素的字节数。

如果 batch 大于 1，还要乘 batch size。具体实现可能使用 grouped-query attention、不同 KV dtype、预分配或动态 cache，因此公式只用于量级预估。

关键结论：

- 把权重量化为 q4 不代表 KV cache 也降为 4 bit；
- 上下文越长，KV cache 近似线性增长；
- 长聊天历史可能比短 prompt 明显增加峰值内存；
- 降低 `max_new_tokens` 只控制输出上限，仍需限制输入 token。

## 5. 为什么内置聊天比 Embedding 更难

Embedding 模型通常一次前向后得到固定向量；聊天 LLM 需要逐 token 生成：

```text
输入 prompt
  → forward 得到 next-token logits
  → 选择 token
  → 更新 KV cache
  → 再次 forward
  → 重复直到停止
```

因此聊天需要额外关注：

- 首 token 延迟；
- 持续 tokens/s；
- KV cache；
- 取消能否中断循环；
- streamer 是否及时释放 UI；
- 长上下文截断；
- 采样参数对可复现性；
- JSON 或引用格式在量化后的稳定性。

这也是 M2 要求 Built-in Chat 单独设置 Gate 的原因。

## 6. Vault Coach 的 dtype 策略

### 6.1 不让普通用户随意选每一种 dtype

设置页若直接列出 q4、q8、fp16、fp32，会把设备兼容和模型质量责任转给用户。推荐由不可变 policy 选择经过验证的组合：

```ts
interface BuiltinChatModelPolicy {
  id: string;
  modelId: string;
  revision: string;
  dtype: "q4" | "q8" | "fp16";
  preferredDevice: "webgpu" | "wasm";
  contextTokenLimit: number;
  maxNewTokens: number;
  implementationVersion: number;
}
```

不同设备档位应是经过验证的完整 policy，而不是自由组合：

```text
desktop-webgpu-q4
desktop-wasm-q8
mobile-safe（只有真机 Gate 通过后存在）
```

每个 policy 都要有独立 fingerprint 和 benchmark 结果。

### 6.2 fingerprint

至少包含：

```ts
const fingerprintInput = {
  modelId,
  revision,
  dtype,
  task: "text-generation",
  transformersJsVersion,
  runtimePolicyVersion,
  chatTemplateVersion,
  contextTokenLimit,
};
```

聊天 fingerprint 主要用于诊断、缓存完整性和结果可复现性。不要与 embedding fingerprint 共用，因为更换聊天模型不应使向量索引失效。

## 7. 质量 Gate 应测什么

### 7.1 测试集

为中文、英文、德文分别准备脱敏 prompt：

```json
{"id":"zh-cite-001","task":"cited_answer","messages":[...],"mustCite":["S1"],"forbiddenClaims":[...]}
{"id":"en-json-001","task":"structured_json","messages":[...],"schema":"exam-question-v1"}
{"id":"de-rewrite-001","task":"query_rewrite","messages":[...],"requiredTerms":[...]}
```

覆盖：

- 有依据的引用回答；
- 证据不足时不编造；
- query rewrite 保留意图；
- 考试题 JSON；
- Markdown；
- 长上下文截断；
- 多轮指代；
- 中英德混合术语；
- prompt injection 片段；
- 相同输入的稳定性。

### 7.2 指标

| 指标 | 说明 |
| --- | --- |
| 引用正确率 | 引用 ID 是否存在且支持对应陈述 |
| unsupported claim rate | 无来源支持的陈述比例 |
| JSON schema success | 一次生成即可解析并通过 schema 的比例 |
| task success | query rewrite、考试、概念抽取分别评测 |
| first-token p50/p95 | 暖启动首 token |
| tokens/s p50/p95 | 持续生成速度 |
| peak memory | WebGPU/WASM、短/长上下文分别记录 |
| cold/warm init | 首次下载与缓存命中 |
| cancel latency | 用户取消到生成停止的时间 |

总平均不能掩盖某一语言、设备或任务失败。Built-in Chat 可以只声明通过的 capability，例如基础引用问答通过，但考试 JSON 未通过时，考试继续要求 Ollama/云 provider。

## 8. dtype 对照实验

### 8.1 控制变量

同一模型比较 q4/q8/fp16 时固定：

- model ID 与 revision；
- Transformers.js 与 ONNX Runtime 版本；
- 设备与 execution provider；
- prompt、chat template 和上下文 token；
- generation 参数；
- warm-up 次数；
- 计时起止点；
- Obsidian/Electron/OS 版本。

不要拿 q4/WebGPU 与 q8/WASM 的结果直接归因于量化差异。

### 8.2 建议配置

为可复现质量测试先禁用采样：

```ts
const generationConfig = {
  do_sample: false,
  max_new_tokens: 128,
  repetition_penalty: 1.05,
};
```

具体参数必须以固定版本 API 和模型 generation config 为准。质量基线稳定后，再单独评估 temperature 和 sampling。

### 8.3 结果表

| model | revision | dtype | device | download MB | warm init ms | first token ms | tokens/s | peak MB | cite score | JSON success |

| teaching model | pinned | q4 | WebGPU |  |  |  |  |  |  |  |

不支持的组合写 `unsupported`，不要填 0。

## 9. 内存预算

### 9.1 分项记录

```text
baseline：只启用 Vault Coach，无 Built-in runtime
loaded：pipeline 创建且 warm-up 后
short：短 prompt 生成期间峰值
long：接近 context limit 时峰值
disposed：释放 pipeline、终止 Worker、等待 GC 后
```

关注：

- renderer JS heap；
- WASM linear memory；
- GPU memory 或可观察替代指标；
- Worker memory；
- Cache Storage 占用；
- Obsidian 整体进程内存。

浏览器指标不总能准确报告 GPU/进程内存，因此报告中要写测量工具和限制，不伪造精确数字。

### 9.2 预算失败时的顺序

1. 缩短上下文与最大输出；
2. 限制同时运行任务；
3. 验证更小模型；
4. 验证更低 dtype；
5. 更积极地 dispose；
6. 将该设备标记为不支持 Built-in Chat；
7. 提示用户选择 Ollama 或云服务。

不要通过吞掉 OOM 或崩溃后自动外发 prompt 来掩盖失败。

## 10. 常见误区

| 误区 | 正确理解 |
| --- | --- |
| q4 一定是模型体积的四分之一 | 还包含未量化层、metadata 和其他资产 |
| q4 一定比 q8 快 | 取决于后端 kernel、转换和设备 |
| 权重量化后所有内存都下降同样比例 | 激活和 KV cache 可能使用其他 dtype |
| 小模型更容易输出正确 JSON | 仍要按任务和语言测量 |
| 平均质量足够就能发布 | 引用错误或某语言失败可能是阻断项 |
| 用户可以自己选 dtype，所以无需支持矩阵 | 产品仍要对每个可见选项负责 |
