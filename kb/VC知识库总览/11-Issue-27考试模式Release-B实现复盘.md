# Issue 27 考试模式 Release B 实现复盘

## 背景

Issue 27 的目标是基于 v1.2.9 需求文档优化考试模式，让用户在创建测试前可以更精细地管理出题范围，并通过智能筛选排除空白、索引、任务清单、低正文量等不适合出题的内容。

需求文档拆成两步：

1. Release A：补齐考试创建页面和设置页的范围控制能力。
2. Release B：引入智能内容画像、蓝图规划、题目质量控制和缓存机制。

这次实现看起来是一个“考试模式增强”，实际涉及知识库范围解析、文件级 UI、设置持久化、LLM JSON 输出稳定性、局部缓存、异步进度、滚动位置保持和兜底生成策略。

## 最终效果

- 考试创建页支持管理文件、搜索文件、全选、全部排除、恢复默认。
- 设置页支持考试排除路径和智能筛选开关。
- 智能筛选会分析 Markdown 文件是否适合出题，并缓存分析结果。
- 范围分析完成后展示文件级筛选详情、缓存命中数、预计题量。
- 筛选详情中的 Markdown 文件名可以点击并跳转到对应 Obsidian 笔记。
- UI 重绘时保留考试区域滚动位置，避免点击按钮后跳回顶部。
- 题目生成改为单轮模型生成加本地兜底，不再反复出现“正在重新生成未通过题目”。
- 即使关闭智能筛选，考试生成也不再依赖智能筛选链路才能成功。

## 主要模块

### `ExamScopeService`

负责把用户选择的范围解析成候选文件、规则排除文件和可用 chunk。

关键点：

- 范围来源是当前已索引的知识库，而不是重新扫描 vault。
- 支持目录选择、文件排除、强制包含。
- 永久排除 `.vault-coach` 等插件运行目录，避免考试结果污染下一次出题。

### `ExamContentProfiler`

负责对 Markdown 文件做智能内容画像。

输出包括：

- `include`：完全适合出题。
- `partial`：部分标题或段落适合出题。
- `exclude`：整体不适合出题。
- `reasonCodes`：排除或部分可用的原因。
- `estimatedQuestionCapacity`：预计题量。

这里使用本地缓存，缓存 key 绑定文件路径、内容 hash、模型信息和 prompt 版本。文件内容没变时可以直接命中缓存，避免重复让模型分析。

### `ExamBlueprintService`

负责把可用 chunk 规划成考试蓝图。

蓝图项包含：

- 考察主题。
- 学习目标。
- 题型。
- 难度。
- 绑定的真实 `sourceChunkIds`。

如果模型规划失败，会回退到确定性蓝图：按文件和 chunk 分布选择代表性片段，保证后续仍能生成测试。

### `ExamQuestionGenerator`

负责根据蓝图生成题目。

最终策略从“多轮生成 + LLM 质量审查 + 重试”调整为：

1. 单轮模型生成题目。
2. 本地解析和结构校验。
3. 可用题直接保留。
4. 不可用题用来源 chunk 构造兜底题。

这个改动是体验上的关键修复。之前模型已经生成了内容，但因为字段名不稳定、审查模型过严或 JSON 结构偏差，题目会被全部打回，导致反复提示“正在重新生成 5 道未通过题目”，最后仍然失败。现在题目生成只做必要的本地校验，不再让二次 LLM 审查阻断创建流程。

### `ExamQuestionValidator`

负责本地确定性校验。

校验项包括：

- 题干是否为空或过短。
- 参考答案是否为空或过短。
- 评分标准是否为 100 分制。
- 来源 chunk 是否真实存在。
- 是否泄漏内部标签，例如 `SOURCE_PATH`、`CHUNK_ID`、`BLUEPRINT_ITEM`。
- 是否与已接受题目重复。

它不再调用 LLM 做质量审查。原因是审查模型带来的体验成本大于收益：慢、不稳定、容易误杀可用题。

## 实现过程

### 1. 先补 UI 能力

第一轮实现后，用户反馈考试创建页没有看到文件管理、搜索、批量操作、智能筛选开关和容量提示，设置页也缺少考试排除路径。

排查后确认前端入口不完整，于是补了：

- 考试文件管理面板。
- 文件搜索框。
- 全选、全部排除、恢复默认。
- 智能筛选开关。
- 当前范围文件数、排除数、实际参与数和预计题量。
- 设置页的考试排除路径配置。

这一步的重点不是算法，而是让需求文档里的用户路径能在 UI 上闭环。

### 2. 优化文件管理排版

后续发现文件展开后信息堆在一起，可读性差。于是把每个文件改成独立块：

- 文件名。
- 路径。
- chunk 数。
- 排除原因。
- 勾选状态。

这样用户能一眼判断某个文件是否被纳入考试范围。

### 3. 修复 UI 跳顶

多个按钮点击后页面会跳回顶部，包括：

- 全选。
- 全部排除。
- 恢复默认。
- 智能筛选开关。
- 选择目录。
- 分析考试范围。

根因是考试模式区域每次状态变化都会调用完整 `render()`，`contentEl.empty()` 后 DOM 重建，滚动位置丢失。

修复方式是增加 `renderPreservingExamScroll()`：

1. 重绘前读取 `.vault-coach-exam-area.scrollTop`。
2. 调用 `render()`。
3. 重绘后恢复 scrollTop。
4. 再用 `requestAnimationFrame` 二次恢复，处理浏览器布局延迟。

经验是：在 Obsidian 插件这种单视图重绘模式里，只要局部操作会触发完整 render，就要显式保护滚动位置，否则用户会感觉 UI 在跳。

### 4. 智能筛选 null 报错

用户点击智能筛选后报：

`Cannot read properties of null (reading 'replace')`

根因是模型返回或缓存数据中存在 `null`，但某些清洗函数默认按 string 处理并直接 `.replace()`。

修复策略：

- 所有模型输出字段先按 `unknown` 接收。
- `normalizeWhitespace()` 兼容 `string`、`number`、`boolean`、`null`、`undefined`。
- 解析 LLM payload 时不信任字段类型。

这个坑说明：只要数据来自模型或旧缓存，就不能把 TypeScript 类型当运行时保证。

### 5. 引入 Obsidian 文件跳转

范围分析详情里展示每个 Markdown 文件的分析结果，但最初只是纯文本。用户希望点击文件名后主页面跳转到对应笔记。

实现方式：

- 文件名渲染为 button，而不是普通文本。
- 点击后通过 `app.vault.getAbstractFileByPath()` 找到 `TFile`。
- 再用 `app.workspace.getLeaf().openFile(file)` 打开。

这里没有用外部链接，而是使用 Obsidian 原生文件 API，保证路径和 vault 内文件一致。

### 6. 处理题目生成反复失败

这是最关键的踩坑。

初始 Release B 设计是：

1. 生成题目。
2. 本地初步校验。
3. 调用 LLM 审查题目质量。
4. 未通过则定向重试。
5. 最多重试三轮。

理论上更严格，实际体验很差：

- 本地模型字段名不稳定，例如返回 `answer`、`referenceAnswer`、`参考答案`，而不是 `reference_answer`。
- 审查模型可能把确定性可用的题全部判失败。
- 重试会再次调用模型，耗时明显变长。
- 用户看到“正在重新生成 5 道未通过题目”，但最后仍然失败。
- 关闭智能筛选也无效，因为问题不在筛选，而在题目生成后的校验和重试链路。

最终改成更务实的策略：

- 保留模型生成，但只做一轮。
- 兼容常见字段别名和中文字段名。
- 移除 LLM 质量审查。
- 移除多轮重试。
- 本地校验失败时，基于蓝图和真实来源 chunk 构造兜底题。
- 批量大小从本地模型每批 2 道提升到 5 道，减少请求次数。
- prompt 中来源文本截断，降低长文档导致的响应耗时。

这让考试创建从“严格但不稳定”变成“稳定可用，质量由模型题和兜底题共同保证”。

## 关键踩坑

### 坑 1：LLM-as-judge 不适合阻断主流程

质量审查听起来合理，但它也是一次模型调用，本身同样会输出不稳定 JSON，也会误判。

在这个功能里，用户的第一诉求是“生成一份可用测试”。如果审查器把所有题都打回，体验比生成几道普通题更差。

最后的取舍是：审查可以作为离线诊断或可选增强，但不应该阻断创建考试。

### 坑 2：智能筛选不是生成失败的唯一变量

用户关闭智能筛选后仍然失败，说明问题不在筛选范围，而在后续生成链路。

排查时不能只看当前开关对应的模块，要沿完整链路看：

范围选择 -> 分析结果 -> 蓝图 -> 题目生成 -> 字段解析 -> 校验 -> UI 状态。

### 坑 3：模型 JSON schema 只能约束，不能保证

即使 prompt 写了 `reference_answer`，模型仍可能输出：

- `referenceAnswer`
- `answer`
- `标准答案`
- `参考答案`
- 嵌套对象或数组

所以解析层必须有字段别名、类型归一化和 fallback，不能只依赖 prompt。

### 坑 4：完整 render 会破坏滚动位置

Obsidian 插件 UI 常用手写 DOM 和完整重绘。完整重绘简单，但对长页面非常容易造成跳顶。

后续只要是考试页面局部交互，都应该优先使用保留滚动位置的重绘方法。

### 坑 5：缓存命中需要解释给用户

“缓存命中 10/10”对开发者很清楚，但用户会问它是什么意思。

这里的含义是：10 个文件的智能内容画像都从本地缓存读取，没有重新调用模型分析。它提升速度，但不等于题目生成也被缓存。

## 面试讲法

如果面试官问 Issue 27 做了什么，可以这样回答：

> Issue 27 是对考试模式的一次完整增强。我先把考试范围管理做成文件级可控，包括搜索、批量包含/排除和设置页默认排除路径；然后引入智能内容画像和本地缓存，用来过滤不适合出题的 Markdown；最后重构题目生成链路，从多轮 LLM 审查改成单轮生成加本地兜底，解决了生成慢和反复失败的问题。

如果面试官问最大的工程教训，可以这样回答：

> 最大教训是 LLM 链路要把“不稳定”当成常态。prompt schema 不能替代运行时校验，LLM-as-judge 也不能随便放在主流程里阻断用户。最后我把严格质量审查下沉成本地结构校验，把模型失败变成可恢复状态，这样功能才真正稳定。

## 后续可优化

- 把兜底题标记出来，让用户知道哪些题来自模型，哪些来自本地生成。
- 给题目生成增加可选的“严格模式”，由用户主动选择是否启用 LLM 质量审查。
- 在调试模式下展示题目生成失败原因统计。
- 对不同模型维护更细的字段兼容策略。
- 为考试生成链路增加单元测试，覆盖 JSON 字段别名、空输出、重复题、无效来源和兜底题生成。
