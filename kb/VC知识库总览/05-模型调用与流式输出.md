# 模型调用与流式输出

## 模型调用设计

项目通过 `LocalModelClient` 屏蔽不同模型服务差异。聊天模型和 embedding 模型可以分别选择：

- 本地 Ollama。
- OpenAI-compatible 云端或自托管接口。

聊天接口用于 query rewrite、回答生成、长期记忆抽取、考试出题和评分。Embedding 接口用于向量索引和向量查询。

## 流式输出

问答模式中，视图先创建临时助手气泡，然后通过 `StreamHandlers.onToken` 逐步追加模型输出。完整答案生成后，再使用 Obsidian MarkdownRenderer 渲染最终 Markdown。这样避免边生成边 Markdown 渲染带来的复杂性，同时降低用户感知延迟。

## 面试问答

### 1. 为什么要抽象 `ModelClient`？

因为业务层不应该关心 Ollama 和 OpenAI-compatible 的接口细节。RAG 引擎只需要“生成 JSON”“生成 Markdown”“生成 embedding”“rerank documents”等能力。抽象后新增 provider 或替换接口时，影响范围更小。

### 2. Ollama 和 OpenAI-compatible API 的差异如何处理？

Ollama 本地聊天默认走 `/api/chat`，embedding 优先走 `/api/embed`，404 时尝试旧版 `/api/embeddings`。OpenAI-compatible 聊天走 `/chat/completions`，embedding 走 `/embeddings`。代码会根据 base URL 自动拼接合理路径。

### 3. 为什么聊天模型和 embedding 模型要分开配置？

两者职责不同。聊天模型负责生成和推理，embedding 模型负责把文本转成向量。用户可能想用本地聊天模型，但用云端 embedding；也可能反过来。分开配置能提高灵活性，但设置页必须清楚显示当前实际使用哪个服务。

### 4. 流式输出如何提升用户体验？

本地 LLM 或低性能设备上生成答案可能很慢。如果等待完整答案再显示，用户会觉得插件卡住。流式输出让用户看到答案逐步出现，降低感知延迟，即使总耗时没有明显减少，体验也会更好。

### 5. 为什么完整答案生成后再渲染 Markdown？

流式阶段直接渲染 Markdown 容易遇到未闭合代码块、列表结构不完整、Mermaid 误渲染等问题。项目选择流式阶段显示纯文本，完成后统一渲染 Markdown，是实现复杂度和体验之间的折中。

### 6. 模型调用失败时如何提示用户？

`ModelRequestError` 会附带状态码和针对 URL 的提示。例如 Ollama `/api/embed` 404 时提示可能是旧版接口或 base URL 配错。向量失败会降级到关键词检索，避免用户完全不可用。

### 7. 为什么考试生成和评分要求 JSON？

考试模式需要结构化数据：题目、参考答案、评分标准、来源路径、逐题分数和反馈。如果只让模型输出 Markdown，后续 UI 和保存都难以稳定解析。JSON 更适合程序处理，但需要额外处理模型输出不合法的问题。

### 8. JSON 输出不稳定如何处理？

项目用了多层防护：低温度、明确 schema、要求不输出 Markdown 代码块、`parseJsonObject()` 去除代码块和截取 JSON 对象、失败后让模型执行“只修复 JSON 语法”的重试，最后再做字段归一化。

### 9. 如果要支持 Transformers.js embedding，应该怎么接入？

可以把 `EmbeddingProvider` 扩展为 `transformers-js`，新增懒加载的 embedding client，在 `ModelClient.embedTexts()` 中增加分支。它适合移动端本地 embedding，但首次需要下载模型文件，必须在设置和 README 中披露网络请求和隐私边界。
