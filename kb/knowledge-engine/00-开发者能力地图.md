# 00 开发者能力地图：通过 Knowledge Engine 能掌握什么

> 本文说明“需要掌握什么”；对应的渐进学习材料见 [Knowledge Engine 开发教程](./开发教程/README.md)。建议在每个 KE 阶段开始前阅读相应分支，并将“最小验收产物”落实为测试、基准或 Workbench Inspector 证据。

## 1. 这个项目的技术定位

Knowledge Engine 的基础仍然偏向**后端、数据基础设施与本地系统工程**，但现在不再是只有 API 的后端项目。它还包含一个独立 Web 工作台：用于导入资料、验证 chunk/revision、调试检索和图谱、完成考试，并以受控工具调用运行知识训练 Agent。

当前技术基线是 **TypeScript + Node.js/Fastify** 的 Engine Core、**React + TypeScript** 的 Web Workbench，以及 KE-9 中用于直装 macOS 应用的 Electron Desktop Host。它们共享 contracts、HTTP API 和测试资产；Mac App Store 沙盒版与 Tauri/Rust 不是当前主线，只有度量证明必要时才进入条件性评估。详见[语言、客户端与桌面发行策略](./05-语言、客户端与桌面发行策略.md)。

因此，完成这个项目后获得的不是单一框架熟练度，而是一套可迁移到 RAG 平台、搜索服务、知识图谱、全栈数据产品、训练系统和可信 Agent 的工程能力。GUI 不是“再做一个聊天壳”，而是 Engine 独立可验证性的第一个客户端。

~~~text
原始资料 / 用户事实
        ↓ revision、hash、幂等同步
可恢复的数据副本
        ↓ 索引 / ANN / 图查询 / 异步作业
有界、可追溯的查询与计算结果
        ↓ 版本协商、降级、隐私控制
Obsidian 插件或其他产品客户端
~~~

## 4. 按阶段获得的能力

| 项目阶段 | 核心交付 | 你真正练到的能力 | 最小验收产物 |
|---|---|---|---|
| KE-0 契约与基准 | schema、fixture、匿名 benchmark、独立/Connector 数据边界 | 把模糊需求写成可测试协议；定义可测指标与事实归属 | OpenAPI、fixture、基准报告、Lite 对照数据 |
| KE-1 服务与 Workbench 骨架 | health/version/config/migration/Docker/GUI | 从零部署可靠本地服务，并让 GUI 成为可验证 API 客户端 | 一键启动、健康检查、导入/任务诊断页面、升级/回滚说明 |
| KE-2 增量同步 | revision、幂等 ingress、delete、waterline | 一致性与数据生命周期，而不只是 CRUD | 重放/乱序/断点恢复集成测试 |
| KE-3 检索与 ANN | section/chunk、FTS、pgvector、filter、top-K | 检索系统设计、索引取舍和质量/延迟评估 | recall/latency 基准与增量索引实验 |
| KE-4 有界图查询 | adjacency、projection、cache、路径 | 图查询的性能边界与来源可追溯性 | 深度/节点/边受限 API 与负载测试 |

| KE-6 独立训练与考试 | exam mode、Assessment、mastery、训练建议 | 将检索/图谱转化为可验证学习闭环 | 有来源考试、评分版本、掌握度回归 |
| KE-7 受控训练 Agent | tool policy、预算、trace、评估、确认 | 在不放弃确定性的前提下实现多步骤知识任务 | 工具调用回归、越权/无证据/取消评估 |

## 5. 推荐学习顺序

不要一开始学习全部数据库和全部分布式系统。建议每一步都以一个可运行、可测试、可测量的产物收尾：

1. **先掌握服务骨架和 SQL**：HTTP、PostgreSQL、migration、Docker、healthcheck。此时不要接 LLM、向量库或图数据库。
2. **再做 revisioned sync**：这是项目的核心难点。主动构造重复、乱序、删除、重命名和服务重启，而不是只测试“正常新增”。
3. **实现词面检索后再加向量**：先有 metadata filter、来源与 top-K，再评估 pgvector。不要把 embedding 当成搜索系统的全部。
4. **先用关系表做图**：练习复合索引和有界 BFS；只有负载数据说明不足时，再研究 Neo4j 等专用图数据库。
5. **把重计算放进 job**：先有取消、进度、失败和恢复，再增加抽取、embedding、候选关系等重任务。
6. **先让独立 GUI 可验证，再做 Connector**：以匿名导入资料完成“索引—检索—图谱—考试”的闭环；连接 Vault Coach 是增强，不是 Engine 能运行的证明。
7. **最后加入 Agent**：先有受限工具、证据、取消和高影响动作确认，再追求多步骤智能性。

## 6. 能力等级自评

### Level 1：能启动和调用

你能运行 Docker Compose，理解 health endpoint、环境变量、HTTP 请求和 PostgreSQL 基础查询；能看懂 API schema，但还未处理失败、并发和版本变化。

### Level 2：能正确实现一个功能

你能为同步、检索或图查询写 migration、handler 和测试；知道要加索引、设 top-K/limit，能返回来源，但对重复消息、服务重启和性能尚未系统验证。

### Level 3：能交付可靠模块

你能实现 revision/idempotency、cancel/retry、版本兼容、数据删除、限额和可观测性；能在服务异常时维持 Lite fallback，并用基准解释索引/缓存选择。

### Level 4：能做架构取舍

你能用 p95、召回率、磁盘、内存、恢复时间与运维成本判断是否引入 HNSW、IVFFlat、Qdrant、Neo4j 或消息队列；能把事实、候选、派生索引和用户授权分层，不被“用了更多 AI/数据库”误导。

### Level 5：能领导知识基础设施设计

你能为多源数据、权限、审计、删除、版本迁移、性能和 AI 证据链建立统一规则，并将复杂系统拆成能独立验证的阶段。此时项目经验可迁移到企业检索、RAG 平台、数据/图谱平台和可信 Agent 基础设施。

## 7. 作品集与面试表达

不要把项目表述为“做了一个知识库聊天机器人”。更有价值的表达是：

> 设计并实现了一个 local-first Knowledge Engine：以 revisioned sync 保证增量数据一致性，以 PostgreSQL/pgvector 支持受范围约束的混合检索，以有界图投影避免全图查询，通过 durable jobs 处理可取消、可恢复的重计算；客户端在服务不可用时自动回退 Lite，并以最小数据传输、证据与删除语义保护用户知识库。

可以准备以下可展示证据：

- 一份 OpenAPI 与版本兼容 fixture；
- 一张“全量 vs 1% 增量”索引耗时、p50/p95、磁盘和内存对比图；
- revision 重放/乱序/delete/rename/restart 的自动化测试；
- 一个有 node/edge/depth budget、来源和 revision 的图投影响应；
- 一段取消 job、重启后恢复或标记 stale 的演示；
- 一份隐私边界与“断开 Engine 后 Lite 仍正常”的回归记录。

## 8. 不应从本项目错误学到的东西

1. 不要认为“引入向量库”就等于完成检索；范围、来源、过滤、评估和降级同样重要。
2. 不要把 LLM 或 embedding 相似度当作事实确认；候选、证据和用户治理必须分离。
3. 不要为了“架构先进”预装 Neo4j、Qdrant、Kafka、Redis 和微服务；每个组件都要由测量驱动。
4. 不要以 Engine 成功来掩盖 Lite 体验问题；local-first 产品应先保证无服务也能学习。
5. 不要把用户的笔记、聊天或密钥当作默认可同步数据；授权、范围、删除和审计是功能的一部分。
