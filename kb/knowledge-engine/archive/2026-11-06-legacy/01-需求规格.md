# Knowledge Engine Local：独立知识训练平台需求规格

## 1. 产品定义

Knowledge Engine Local（简称 **Engine**）是一个由用户主动部署在本机 Docker 环境中的、本地优先的**独立知识训练平台**。它提供自己的 Web GUI，用户不安装 Obsidian 也能导入资料、建立索引、检查检索/图谱证据、完成考试并运行受控的知识训练 Agent。

Engine 同时是 Vault Coach 与 AI Career Agent 的可选协同服务，但不是任何一方的运行前提。它支持两类互不混淆的工作区：

- **`managed` 独立工作区**：用户通过 GUI/CLI 明确导入资料；Engine 保存已导入 revision，并以该工作区完成自身的训练闭环；
- **`connector` Vault 工作区**：Vault Coach 通过用户授权的 revisioned DTO 同步副本；Vault 中的 Markdown/PDF、Assessment、M2/M3 图谱事实和用户治理决策仍为权威，Engine 不得反向覆盖。

无论工作区来源如何，Engine 的索引、embedding、ANN 候选、搜索投影、缓存和图算法结果均是可追溯、可删除的计算数据，而不是可以静默篡改用户知识事实的后门。

## 2. 用户价值与使用场景

| 用户情境 | Lite / 非 Engine 的边界 | Engine 的增益 |
|---|---|---|
| 401–650 个语义窗口 | 经用户确认后可以本地手动构建，但等待时间高 | 将批处理、进度、取消与恢复移出 Obsidian 主进程 |
| 超过 650 个语义窗口 | Lite 拒绝新的本地图谱重建 | 在用户部署并授权后处理增量抽取与图计算 |
| 大量 section/chunk 的搜索 | 浏览器内存和索引构建受限 | 以数据库索引和 ANN 提供带过滤的 top-K 查询 |
| 高连接度概念图 | Canvas 必须保持节点/边预算 | 在服务端计算有限邻域、路径和 revision-keyed 子图缓存 |
| 多次重建或模型失败 | 插件进程不适合作业恢复 | 持久化 job、检查点、取消、重试和可观察进度 |
| 未使用 Obsidian 的重度学习者 | 没有 Vault Coach 作为操作入口 | 通过 GUI 独立完成导入、检索、图谱、考试和训练 |
| 检索或图谱结果可疑 | 插件界面不应承担完整运维诊断 | Retrieval Inspector、任务历史、revision、来源和预算可直接验证 |
| 开放式学习目标 | 固定页面很难决定多步查询顺序 | Agent 只编排受控检索/图谱/训练工具，并保留可读执行 trace |

Engine 不是“因为知识库大就自动上传”的云功能。Connector 模式必须由用户先安装、启用、通过本机健康检查，并明确选择同步的数据类别和范围；独立模式也必须由用户显式选择导入来源，不能静默扫描本机文件。

## 3. 范围与非目标

### 3.1 首版必须具备

1. **本地服务与独立 GUI**：Docker Compose、健康检查、版本查询、配置校验、迁移、持久 volume、日志、完整删除，以及仅调用 API 的 Web 工作台。
2. **工作区与资料入口**：支持 `managed` 显式导入和 `connector` revisioned sync；在 GUI 展示 source/revision/hash、section/chunk、范围、体积与删除影响。
3. **内容检索**：保存被授权的 section/chunk 元数据，提供 lexical、metadata filter、ANN top-K 和可选混合检索；结果返回来源 revision、命中渠道与截断原因。
4. **有效图谱查询**：仅处理 effective Concept、已确认 typed relation、alias/redirect 与证据；提供深度/节点/边都受限的 projection、邻居和前置关系查询。
5. **异步作业与调试**：embedding、ANN 候选、投影预热、批量 Mastery 计算等必须经 durable job 执行；GUI 可检查进度、取消、错误、输入 revision 和 index lag。
6. **独立考试与训练闭环**：生成有来源的 simple/challenge 考试，保存 Assessment evidence，重算 mastery，并给出可解释的下一步训练建议。
7. **受控 Agent**：以工具调用编排有限检索、图谱、掌握度和训练计划；没有数据库直连、任意文件/HTTP/shell 权限，高影响操作必须交给确定性 workflow 与用户确认。
8. **Connector 协商与降级**：Vault Coach health/version/capability negotiation、协议兼容检查、超时、退避和清晰状态；任意失败都回退 Lite。
9. **选择性能力画像接口**：只在用户另行授权时导出选定 Concept、来源摘要及可选 Mastery 摘要，支持预览、发布、撤销和删除。

### 3.2 首版明确不做

- 不做云托管、多租户、账号体系、远程遥测、跨设备同步或 LAN 默认监听；
- connector 模式下不让 Engine 直接读 Vault、Obsidian 配置、聊天记录或 API key；managed 模式也不得未经用户操作扫描任意本地路径；
- 不自动确认语义候选、不自动合并 Concept、不覆盖 Assessment/Mastery/图谱治理事实；
- 不在首版引入 Neo4j、Qdrant/Milvus、Kafka、Redis 或微服务集群；它们需由基准证明为瓶颈后再决策；
- 不把 Engine 可用性作为 Ask、Exam、Learning Map、Recommendation 可用性的前置条件。
- 不让 Agent 自主修改 confirmed graph、mastery、Assessment、同步范围或资料；不暴露思维链、任意 SQL、ES DSL、文件系统或 shell 工具。

## 4. 功能需求

### FR-0：独立工作区、导入与 GUI

- Engine 必须通过 `GET /` 或单独 loopback Web 入口提供 GUI；GUI 只能调用公开的版本化 API，不得绕过 API 读写数据库。
- 用户可创建 `managed` 工作区，并通过明确的文件/目录选择操作导入资料；系统需显示待导入来源、hash、section/chunk 预览、预计体积和失败原因。
- `connector` 工作区只能由 Vault Coach 的已协商连接创建或更新；UI 必须明确其为 Vault 副本、显示同步水位，且不提供“覆盖 Vault”的写回动作。
- 用户可以导出、删除或完全清除 Engine workspace；删除的影响范围、保留/删除的审计信息和不会触碰的外部源必须可见。

### FR-1：连接、版本与能力协商

- Vault Coach Connector 只能连接用户配置的 loopback URL，默认建议 `127.0.0.1`，不得自动探测局域网或公网地址。
- `GET /health` 给出 readiness；`GET /v1/version` 返回 API/schema/index 算法版本与能力集合。
- 客户端必须在首次启用和版本变化后校验主版本兼容性；不兼容状态只能提示升级/降级，不能尝试“猜测解析”响应。
- 每个 Engine 请求都有超时、取消信号和有限重试；状态变化只影响 Engine 路径，Lite 读模型保持可用。

### FR-2：显式、最小化的同步

- 只有用户确认同步范围后，Vault Coach Connector 才能发送变更；首次同步前显示文件/section 数、预计字节、数据类别和取消入口。
- V1 允许的类别是：`content-change`、`confirmed-graph-facts`、`assessment-evidence`、`knowledge-profile-candidate`。
- 默认禁止内容正文；若用户只选择图谱或 Assessment，Engine 必须接受对应的最小 payload，而不能要求整库重传。
- 所有数据项必须带 stable id、revision、内容 hash、操作类型和 schema version。delete 是显式事件，不是静默漏同步。

### FR-3：可追溯检索

- 查询输入包含 workspace、scope filter、top-K、可选 lexical/vector/hybrid 模式与取消信号。
- 响应最多返回请求的 top-K，每项有 source id、section/chunk id、source revision、score kind、索引/模型版本和可打开的来源定位信息。
- 无索引、无匹配、索引过期、权限/范围拒绝、模型不可用和超出预算均为明确的状态，不得填充伪结果。

### FR-4：有界图谱

- API 只能返回有明确 `nodeLimit`、`edgeLimit`、`depth` 和 relation type filter 的 projection；服务端不得有“全图”捷径。
- 返回的 relation 必须包含方向、类型、证据引用、effective graph revision 和是否为 confirmed/user fact。
- pending/rejected/automatic display relation 不进入默认有效图谱。候选由任务生成时，也只能作为待审核数据返回。

### FR-5：作业、进度和恢复

- 作业状态为 `queued | running | succeeded | failed | cancelled | stale`，记录输入 revision、算法/模型版本、进度、错误摘要及完成时间。
- 大批 embedding、候选生成、中心性、投影预热及批量 Mastery 不得在 HTTP 请求中同步执行。
- 取消或 revision 变化不能发布半成品 effective relation；服务重启后作业须恢复或安全标记 `stale`。

### FR-6：用户数据控制

- Engine GUI 必须显示工作区 source mode、连接地址、服务版本、同步类别、范围、水位线、任务状态、存储占用、导出、断开与删除入口；Vault Coach 设置页只展示 Connector 所需的对应信息。
- Engine 提供 workspace 数据完全删除与确认状态；删除 Engine 副本不触及 Vault 文件或 `.vault-coach` 事实。
- 任何外部模型 endpoint、embedding provider 或能力画像发布都必须单独提示数据类别和目的。

### FR-7：独立考试、Assessment 与训练

- Engine GUI 可在任一工作区中选择范围、题数与 `simple | challenge` 模式，先完成范围/目标分析，再生成考试；分析完成后必须锁定这些输入，用户只能返回设置页后修改。
- simple 仅允许可在本地复现的客观题评分；challenge 可以使用受支持的自由文本题型，但必须保存 evaluator、模型与 prompt 版本。
- 每道题必须返回 source/chunk 或 Concept 证据；Concept binding 不安全时保存未绑定 Assessment，不得猜测。
- Assessment、mastery 和训练建议均有独立的版本化数据模型；Connector 工作区的跨端同步只允许使用显式兼容的 DTO，不能静默覆盖 Vault Coach 历史。

### FR-8：Agent 与工具调用

- Agent 请求必须绑定 workspace、用户允许的 source scope、调用轮数、时间、token/成本预算和取消 signal。
- 首版工具仅限 `search_chunks`、`get_graph_projection`、`get_concept_mastery`、`get_assessment_history`、`draft_training_plan` 和 `draft_exam_request` 等显式注册的受限工具。
- Agent 对每个结论返回来源；无证据、scope 不允许、工具超时或 revision 过期时应 abstain/降级，而不是编造补全。
- 每次运行保存可读 execution trace：目标、工具名、参数摘要、来源、revision、耗时、错误/拒绝原因；不保存或展示模型内部思维链。
- 创建考试、导入资料、启动大 job、发布 Knowledge Profile 和写入治理决定必须经过确定性 API 验证与用户确认，不能由 Agent 单独执行。

## 5. 质量、隐私与安全要求

| 编号 | 要求 |
|---|---|
| NFR-1 | 默认离线、loopback-only、无遥测、无外网回调；日志不得写入正文、密钥、完整聊天内容或 Agent 思维链。 |
| NFR-2 | 三个产品均可独立运行：Engine GUI 不依赖 Obsidian；Engine 未安装、停止、超时、升级或损坏时，Vault Coach 核心功能不退化为不可用。 |
| NFR-3 | 所有写入可按 revision 幂等重放；服务只保存可删除的副本和派生索引。 |
| NFR-4 | API、DTO、数据库 migration、embedding/索引/图算法均有版本；客户端不跨主版本解析。 |
| NFR-5 | 不做无界查询、无界图渲染、N² 相似度比较或在 Obsidian `onload` 中启动全库计算。 |
| NFR-6 | 每一个高影响结果能返回范围、版本和证据；没有足够证据是合法响应。 |
| NFR-7 | GUI、Connector 和 Agent 只能调用相同的有界 API；不得使用数据库直连、任意 ES DSL、任意文件系统或 shell 作为旁路。 |
| NFR-8 | Agent 必须有工具白名单、权限/scope 检查、调用预算、取消、执行 trace 与高影响动作确认；其输出不等于领域事实。 |

## 6. 推荐实现依赖（KE-0 的决策基线）

首版建议采用模块化单体，而不是一开始拆分多个容器。下表是建议依赖，任何替换必须附带基准和运维理由。

| 层 | 建议 | 原因与约束 |
|---|---|---|
| 服务运行时 | TypeScript + Node LTS + Fastify | 与插件契约和 fixture 语言接近；Fastify 适合 schema 校验和低开销 HTTP。可在 KE-0 比较其他运行时，但对外契约必须保持 OpenAPI/JSON Schema。 |
| 关系/向量存储 | PostgreSQL + pgvector | 单机事务、JSON、全文、HNSW/IVFFlat 可先统一运维；必须记录索引/embedding 版本。 |
| 迁移与访问层 | SQL migration 工具（如 node-pg-migrate/Drizzle migration）+ 参数化 SQL | migration 可重复、可审计；不要把 ORM 隐式 schema 变化当作迁移策略。 |
| 作业队列 | PostgreSQL job table + `FOR UPDATE SKIP LOCKED` | 首版无需 Redis/Kafka；具备持久化、重试和重启恢复。 |
| API 契约 | OpenAPI 3.1 + JSON Schema + shared fixture | 不从插件 TypeScript interface 直接推导线上协议。 |
| 独立 GUI | React + TypeScript Web App + API contract client | 首版作为 Engine loopback Web Workbench；不直接操作数据库，可在 Docker/浏览器中独立 E2E 验证。 |
| macOS 桌面 Host | Electron（KE-9 后置） | 包装同一 Web UI 与本地 API/worker，负责启动、诊断、签名、公证和升级；不是第二套业务逻辑。 |
| Agent 编排 | 受限 tool registry + policy layer + trace store | 不先引入通用多 Agent 框架；先将工具、预算、确认和评估做成可测试的确定性边界。 |
| 可观测性 | Pino 结构化本地日志 + OpenTelemetry-compatible metrics seam | 记录延迟、队列深度、索引版本和错误分类，不输出内容。 |
| 容器 | Docker Compose、Postgres 官方镜像、healthcheck、named volume | 单命令启动、升级、备份与删除；默认仅发布 loopback 端口。 |

首个面向普通 macOS 用户的发行物优先采用 Developer ID 签名、公证的 `.dmg`/`.pkg`；Mac App Store 沙盒版与 Tauri/Rust 桌面壳都属于后续由安装体积、内存、沙盒和维护成本基准触发的决策，详见《05-语言、客户端与桌面发行策略》。

只有满足以下条件才考虑增加组件：pgvector 在目标数据规模下的 p95、过滤能力或维护成本持续不达标才评估 Qdrant/Milvus；递归邻接查询/受限路径在测量后仍不达标才评估 Neo4j；队列吞吐或隔离已被测量证明不足才评估 Redis/Kafka。

## 7. 退出标准与验收

1. 不安装 Obsidian 时，空、小、中、大 `managed` 基准 workspace 均能启动 GUI、导入、迁移、索引、检索、图查询、考试、停止、重启和删除；基准不含真实私有笔记。
2. 同一 revision 流的全量与增量结果一致；重放、乱序、删除、重命名、取消和崩溃恢复不出现重复 section 或悬空 relation。
3. 所有 Engine 查询有有限预算，所有响应有 revision/来源；服务失败时插件自动回退 Lite。
4. 记录 Lite 与 Engine 的索引耗时、峰值内存、磁盘、p50/p95、取消时间和恢复时间；若没有可测收益，Engine 不作为推荐方案。
5. 用户能在 GUI 查看并删除 Engine workspace，确认日志不含正文/密钥；断开 Engine 后 Vault Coach 仍通过全部核心回归。
6. Agent 的越权 scope、无来源结论、工具循环、超预算、模型不可用、取消和高影响动作确认均有自动化测试与可读 trace。
7. Vault Coach、独立 Engine GUI 和 Career Agent 的协同只通过版本化 Connector/Profile DTO 验收，任一端不可用不会阻断另两端的独立核心路径。
