# Knowledge Engine Local：独立知识训练平台架构设计

## 1. 总体结构和责任边界

~~~text
┌────────────── Independent Knowledge Engine ──────────────┐
│ Workbench GUI (browser) → Versioned local HTTP API       │
│ managed workspace: explicit import → source revisions    │
│ retrieval · graph · training/exam · controlled agent     │
│ jobs: embedding / projection / batch calculation         │
│ PostgreSQL + pgvector: facts / revisions / jobs          │
│ optional ES: rebuildable Search Projection                │
└───────────────┬───────────────────────────┬──────────────┘
                │ explicit Connector DTO     │ consented Profile DTO
                ▼                            ▼
┌───────────────────────────┐    ┌───────────────────────────┐
│ Vault Coach / Obsidian     │    │ AI Career Agent            │
│ connector workspace source │    │ capability consumer        │
│ Lite fallback always works │    │ no arbitrary Vault access  │
└───────────────────────────┘    └───────────────────────────┘
~~~

Engine 的 GUI 是 API 的第一个客户端，且可在没有 Obsidian 时独立运行。Vault Coach 只通过版本化 Connector 调用 Engine；不能让插件 presentation/domain 代码直接 `fetch`。Connector 工作区中，Engine 只管理服务侧副本、索引、job 和缓存，不是 Vault 内容、插件治理决定或插件 Assessment 的权威写端；`managed` 工作区则只以用户显式导入的 revision 为本机训练事实。

## 2. 客户端、工作区与 Connector 接缝

### 2.1 独立 Workbench 与工作区来源

Workbench 通过 loopback HTTP API 创建、导入、检查和删除 `managed` workspace。导入适配器必须由用户选择文件/目录后才读取；它先生成 source/revision/hash 与 section/chunk 预览，再入队执行重索引。GUI 不拥有数据库写权限，也不以浏览器会话保存 job 真相。

`connector` workspace 只能接收 Vault Coach 的 `KnowledgeChangeV1`。服务层在每个 workspace 记录 `source_mode`，禁止把 managed 导入与 connector 同步写入同一 source revision 流，或提供“写回 Vault”的通用操作。

### 2.2 Vault Coach 能力协商

插件侧以三种状态工作：

| 状态 | 条件 | 行为 |
|---|---|---|
| `lite` | 用户未启用或没有配置 Engine | 所有调用使用 LiteEngineClient；不做网络请求。 |
| `available` | loopback health 成功、主协议兼容、能力满足请求 | 仅对用户选择的 Engine 功能创建请求。 |
| `unavailable` | 停止、超时、错误、认证失败或协议不兼容 | 记录可读诊断并立即回退 Lite；不阻断 Ask/Exam。 |

`KnowledgeEngineClient` 是窄 port：`getAvailability()`、`getCapabilities()`、`getDiagnostics()`。未来查询/sync 接口均基于它的显式 capability，而不是通过 `instanceof` 或 URL 是否存在猜测服务能力。`LiteEngineClient` 永远返回 `mode: "lite"`，不发请求。

### 2.3 V1 传输 DTO 原则

DTO 使用 JSON Schema/OpenAPI，且字段用 value objects 表达，而不是复用插件内部 `SemanticGraphState` 或 Obsidian 文件对象。所有 payload 有：

~~~ts
interface VersionedEnvelopeV1<T> {
  schemaVersion: 1;
  workspaceId: string;
  requestId: string;
  payload: T;
}
~~~

同步事件的最小形式：

~~~ts
interface KnowledgeChangeV1 {
  kind: "content-change" | "confirmed-graph-facts"
      | "assessment-evidence" | "knowledge-profile-candidate";
  operation: "upsert" | "delete";
  sourceId: string;
  revision: number;
  contentHash: string | null;
  occurredAt: number;
  payload: unknown; // each kind has a separate schema
}
~~~

接口必须验证 `kind` 对应 schema、workspace、payload 字节上限、revision 与 idempotency key。对同一 `workspaceId/sourceId/revision` 的重复请求返回原成功结果；旧 revision 返回冲突；删除保留最小审计记录并清除派生索引。

## 3. API 和任务设计

| API | 同步性 | 输出/约束 |
|---|---|---|
| `GET /health` | 同步 | liveness/readiness、数据库和 migration 状态；无内容。 |
| `GET /v1/version` | 同步 | API/schema、索引、算法版本和 capabilities。 |
| `POST /v1/workspaces`、导入预览/提交/删除 | 短事务 + job | 创建 `managed` workspace；必须显式 source mode、导入清单、revision、体积和删除影响。 |
| `POST /v1/workspaces/{id}/changes` | 短事务 | 幂等写 revision，派生工作入队；不在请求中批量 embedding。 |
| `POST /v1/retrieval/search` | 有限读 | filter 后 top-K、来源 revision、截断/降级信息。 |
| `POST /v1/answers` | 有限读 + 模型调用 | 仅基于有界 retrieval hits 的带引用回答；无足够证据时 abstain。 |
| `GET /v1/graph/projection` | 有限读 | depth ≤2、node/edge limit、relation/source filter、证据。 |
| `POST /v1/jobs`、`GET /v1/jobs/{id}` | 异步 | 状态、阶段、进度、revision、错误摘要；支持取消。 |
| Training / Exam API | 短事务 + 有界计算 | 范围分析、计划、生成、提交、评分、Assessment 与 mastery；保存题目来源和评分版本。 |
| `POST /v1/agent/runs`、`GET /v1/agent/runs/{id}` | 有限异步编排 | 仅允许注册工具、scope、轮数/时间预算与可读 execution trace；高影响动作不由该 API 直接执行。 |
| Profile 预览/发布/撤销 | 显式授权 | 只接收用户选择的 summary，支持完全删除。 |

作业表是初始队列：事务写入 `job`，worker 通过 `FOR UPDATE SKIP LOCKED` 提取；每个 job 存 `input_revision`、`attempt`、`lease_expires_at`、`algorithm_version`。服务重启时过期 lease 进入可重试或 `stale`，绝不把部分输出提升为 effective graph。

## 4. 数据模型与版本

### 4.1 PostgreSQL 核心表

~~~text
workspace(id, source_mode, schema_version, created_at, deleted_at)
source_revision(workspace_id, source_id, revision, hash, operation, payload_kind, received_at)
section(workspace_id, section_id, source_id, revision, locator, text?, metadata)
chunk(workspace_id, chunk_id, section_id, revision, ordinal, text?, token_count, metadata)
embedding(workspace_id, chunk_id, model_version, vector, revision)
concept(workspace_id, concept_id, effective_revision, display_name, aliases)
relation(workspace_id, relation_id, source_id, target_id, type, direction, evidence, revision)
assessment_evidence(workspace_id, event_id, concept_id, revision, normalized_score, occurred_at)
training_session(workspace_id, session_id, scope, exam_mode, revision, evaluator_version, status)
job(id, workspace_id, type, state, input_revision, progress, error_summary)
agent_run(id, workspace_id, goal, policy_version, state, input_revision, trace_summary, created_at)
profile_revision(workspace_id, profile_id, revision, consent, payload, deleted_at)
~~~

`source_revision` 与领域数据分开：它使同步幂等、waterline、重放和删除可验证。`section/chunk` 可以只保留用户已授权的正文；每条记录均保留能回到 managed source 或 Connector source 的 locator/稳定 id。`source_mode` 决定事实边界：connector 不得覆盖插件 M3 决策，managed 工作区的治理/Assessment 只在其自身 workspace 内生效。`agent_run` 只保存可审计的工具执行摘要，不能保存模型内部思维链。

### 4.2 索引策略

1. `source_revision(workspace_id, source_id, revision DESC)`：冲突检查与水位线；
2. `section/chunk(workspace_id, source_id, revision)`：增量删除、重命名和范围过滤；
3. `embedding(vector)`：先在基准上对比 HNSW 与 IVFFlat；记录 embedding 维度、模型和索引版本。HNSW 更适合低延迟、增量更新，IVFFlat 更适合大批量且允许训练/重建；不得无测量地二选一；
4. `relation(workspace_id, source_concept_id, type)` 和反向复合索引：一/两跳邻居与前置关系；
5. 词面索引：Postgres FTS（或后续经基准证实的独立搜索服务）与 folder/tag/type metadata 过滤共同使用；
6. job 部分索引：`state in (queued, running)`，保证 worker 不扫描历史任务。

候选关系管线固定为：规范化/alias blocking → 每个 Concept 取固定 top-K ANN → 元数据/来源过滤 → 小集合精确余弦或 rerank → `pending`。它的复杂度近似 `O(N × K)`，禁止 N² 两两比较；ANN 分数不是已确认关系的证据。

## 5. 查询、缓存和预算

### 5.1 检索

~~~text
scope / metadata filter
  → lexical candidate top-L
  → vector ANN candidate top-V
  → dedupe + reciprocal-rank/hybrid merge
  → bounded rerank top-R
  → source/evidence projection top-K
~~~

每一层有上限：`L`、`V`、`R`、`K` 由请求与服务 max 共同裁剪；响应包含截断原因。过滤应尽可能下推到 SQL/ANN metadata，而不是先从全库召回再在 Node 内过滤。查询按 request deadline 取消；超时返回明确降级而非阻塞 Obsidian UI。

### 5.2 图谱

有界 projection 的 cache key 是：`workspaceRevision + rootConcept + depth + relationFilter + sourceScope + nodeLimit + edgeLimit`。revision 变化时只失效该 workspace 的相应 key。服务端先从邻接索引做 BFS，再按稳定优先级裁剪节点/边；禁止把整图交给插件 Canvas。

## 6. Workbench、训练与 Agent 架构

### 6.1 Workbench 是 API 客户端

`apps/workbench` 采用 React + TypeScript，只依赖 `packages/contracts` 生成的 SDK；所有资料导入、任务、检索检查、图谱、考试和 Agent 页面均经 API 访问同一 workspace。Engine API/worker 采用 TypeScript + Node LTS + Fastify。这样可以对 API 做契约测试、对 Workbench 做端到端测试，且不会出现“只有 Obsidian 才能复现问题”的调试死角。

### 6.2 训练域保持确定性边界

Training 模块复用 versioned session、Assessment evidence、Concept binding、mastery 和 recommendation 的领域契约。`simple` 只走可复现的客观题评分；`challenge` 的模型评分记录 evaluator/model/prompt 版本。无论由 GUI、Connector 或 Agent 发起，创建考试、提交评分和写入 Assessment 都必须经过同一确定性 API。

### 6.3 Agent 是受策略控制的编排层

Agent module 由四部分组成：

```text
AgentRun → policy gate → tool registry → retrieval / graph / training query ports
                 ↓
       budget、scope、confirmation、trace、cancellation
```

- tool registry 初始只有只读 `search_chunks`、`get_graph_projection`、`get_concept_mastery`、`get_assessment_history` 和纯计算的 training/exam draft 工具；
- policy gate 在每次工具调用前检查 workspace、source scope、top-K/depth、调用轮次和 deadline；
- 高影响写入被分离为 GUI/Connector 的确定性 workflow，并要求用户确认；
- trace 记录工具名、参数摘要、revision、来源和耗时，绝不记录思维链或给予 agent 数据库/ES/文件系统直连。

## 7. 对 Obsidian 插件性能的具体提升

| 当前 Lite 风险 | Engine/插件实现方案 | 保持的用户体验 |
|---|---|---|
| 主进程长时间模型/embedding 工作 | Engine durable jobs + 检查点 + progress/cancel；插件仅订阅/有限轮询任务状态 | Obsidian 不冻结；服务停止时仍可用 Lite 已有结果 |
| Vault 全扫描和重复传输 | vault event → debounce → source revision/hash → 批量增量 change | 只同步变化文件/section；删除和重命名可恢复 |
| 浏览器内 ANN/大数组 | pgvector HNSW/IVFFlat + top-K filter | 插件只收到少量可解释结果和来源 |
| 大图 Canvas | 服务端 depth/node/edge budget、邻居/路径缓存、渐进展开 | 首屏有界，用户可继续聚焦而非一次加载全图 |
| N² 概念相似度 | blocking + ANN top-K + filter + rerank job | 候选仍进入人工审核，不自动生效 |
| 频繁读本地 JSON | revision-keyed DTO/cache + Lite snapshot 继续可重建 | 不改变事实源，失效精确、可诊断 |
| 插件启动重负载 | client 懒初始化；不在 `onload` health scan、同步或构建索引 | 打开 Obsidian 仍快速，用户显式打开功能才请求服务 |

## 8. 部署与安全

Docker Compose 首版包含 `engine-api`、`engine-worker`（可同镜像不同命令）、`workbench` 静态资源服务与 PostgreSQL+pgvector。使用 named volume，提供 `healthcheck`、升级 migration、备份、`down -v` 删除说明；端口绑定 `127.0.0.1`，不提供公网/局域网监听快捷开关。Workbench 与 API 可由同一 loopback origin 对外提供，避免 CORS 和公开端口复杂度。

KE-9 再增加 Electron Desktop Host：它打包同一 Workbench 静态资源，通过 localhost API 启动/监控 Node API 与 worker，并管理用户数据目录、签名、公证、升级和诊断。Electron 专属进程/文件 API 不能进入 Core domain；Docker 仍是可重复的开发与高级用户形态。Mac App Store 版必须另行适配 App Sandbox，不应被当成同一安装包的上传步骤。

插件保存的只是地址、可选启动 token 的 secret reference 和用户配置，不保存数据库密码到 Vault 文本。每次请求附 request id；Engine 日志只记录类别、长度、revision、耗时、错误码和 hash 前缀，默认不记录正文、向量、聊天或密钥。

## 9. 演进门槛

KE-0 先冻结独立 workspace、GUI/API、Connector 与 Agent tool 契约并建立基准；KE-1/2 再启动独立服务、Workbench 及 revision 写入，KE-3/4 后才允许插件使用 Engine 检索/图查询。引入额外图数据库、向量库或消息队列需同时满足：

1. 在匿名基准上明显超过 pgvector/关系邻接方案的 p95 或成本阈值；
2. 能维持 revision、证据、删除、备份和 Lite 降级；
3. 不将用户安装从一个 Docker Compose 变成多组件手工排障。

在任何阶段，若 Engine 没有带来可量化收益，插件应继续推荐 Lite，而不是以“服务已经存在”为理由转移复杂性给用户。

当全文检索、中文分析、highlight、复杂 metadata filter 与 lexical/vector RRF 在基准中有明确收益时，可在 PostgreSQL 事实层之后引入 Elasticsearch 作为可重建 Search Projection；详见《03-Elasticsearch检索加速层》。
