# 05 Knowledge Engine：语言、客户端与桌面发行策略

## 1. 已确定的技术决策

| 决策面 | 选择 | 原因 |
| --- | --- | --- |
| Engine Core | **TypeScript + Node.js LTS + Fastify** | 与 Vault Coach 的 DTO、契约、测试和 Agent 工具定义保持同一语言；适合 HTTP API、job 编排、模型 I/O 与本地服务诊断 |
| Workbench | **React + TypeScript Web App** | 适合 Retrieval Inspector、Graph Explorer、考试和任务控制台；可独立在浏览器运行与 E2E 验证 |
| 数据与重计算 | **PostgreSQL + pgvector + worker** | 事务、revision、job、索引与向量检索构成主要性能边界，不应由 UI 或 Node 内存数组承担 |
| macOS 直装版 | **Electron Desktop Host，后置引入** | 可以复用 TypeScript/Node，包装同一 Web UI 与 API，并负责启动/监控本地 Engine、数据目录、更新、签名和诊断 |
| 默认发行顺序 | **Docker/Web → Electron `.dmg/.pkg` → 可选 Mac App Store** | 先验证产品与 API；再降低普通用户安装门槛；最后才承担 Store 沙盒/审核限制 |

结论：**Engine 首先是 Web Workbench，不是先做原生 GUI；Electron 是其桌面发行壳，而不是第二套产品或第二套业务逻辑。**

## 2. 为什么 Core 不首选 Rust、Python 或 Go

Engine 的主要成本来自 PostgreSQL/pgvector、可选 Elasticsearch、embedding 模型、文件解析和可恢复 job，而不是普通 API handler 的 CPU 指令数。应优先用基准、索引、批处理、取消和缓存解决问题，不能为了“高性能”过早重写全部领域代码。

| 方案 | 当前决定 | 适用理由与边界 |
| --- | --- | --- |
| TypeScript / Node.js | 采用为主语言 | 复用现有知识、统一 contracts/GUI/Agent policy；长任务由 worker、数据库与模型服务承担 |
| Python | 不作为主系统 | 可在未来独立做模型实验或评估脚本；若作为主服务会增加 DTO、部署、日志和测试体系的分裂 |
| Go | 不作为首发 | 单二进制部署优秀，但无法抵消与现有 TypeScript 客户端/契约体系重新整合的成本 |
| Rust | 后置、局部采用 | 仅当图算法、文件解析、桌面体积或 CPU 热点经 benchmark 证明成为瓶颈时，作为独立 native module/sidecar 评估 |

这不是禁止 Rust 或 Python，而是要求它们解决已测量的问题，并保持 OpenAPI/JSON Schema、revision、证据和删除语义不变。

## 3. Web Workbench 与桌面壳的关系

```text
React + TypeScript Workbench
        │  typed HTTP / WebSocket
        ▼
TypeScript Engine API ──────► PostgreSQL + pgvector
        │                         │
        ├──► Engine worker         └──► 可选 Elasticsearch projection
        └──► 模型 / embedding provider

Electron Desktop Host（后置）
  ├── 打包同一 Workbench 静态资源
  ├── 启动、监控、停止本地 API / worker
  ├── 管理 Application Support 数据目录、升级与诊断
  └── 仍经 localhost API 使用 Engine，不绕过 domain 或数据库边界
```

Workbench 在 Docker、开发环境和桌面壳中使用同一 contracts SDK。业务页面不得因被 Electron 包装就直接访问数据库、文件系统或 worker 私有接口。

### 3.1 为什么 Electron 是首个桌面壳

Engine 已选择 TypeScript/Node。Electron 可以以同一语言处理窗口、打包、自动更新、日志和本地 service 生命周期；其 `utilityProcess` 可承载 Node 子进程，适合隔离不可信、CPU 较重或可能崩溃的任务。参见 [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model)。

Electron 的代价是 Chromium 运行时体积和内存。对 Knowledge Engine 而言，PostgreSQL、向量索引和模型通常已经是主要资源消耗，因此首要目标是缩短交付和调试路径；实际产品应仍测量启动时间、空闲内存和安装包大小。

### 3.2 为什么不先选 Tauri

Tauri 可以把 Node 服务作为 sidecar 打包，且通常有更小的桌面壳；但它同时引入 Rust、sidecar 构建、权限清单、签名和跨进程调试的新复杂度。官方的 Node sidecar 指南也明确要求打包独立二进制并配置 shell 权限。[Tauri Node sidecar](https://v2.tauri.app/learn/sidecar-nodejs/)

因此 Tauri 是一个 **KE-9 之后的再评估项**：只有当 Electron 的安装体积、内存或平台集成被基准证明不满足目标时，才对同一 Web/API 架构替换桌面壳；不影响 Engine Core、Workbench 或 Connector 的对外契约。

## 4. 发行渠道与优先级

| 渠道 | 目标用户 | 交付内容 | 当前优先级 |
| --- | --- | --- | --- |
| Docker Compose | 开发者、高级用户、设计伙伴 | API/worker/Workbench/PostgreSQL，完整诊断与可重复环境 | 第一阶段 |
| 浏览器 Workbench | 开发与独立验证用户 | loopback Web UI；可由 Docker 或本地 Engine 提供 | 第一阶段 |
| Electron `.dmg` / `.pkg` | 不愿使用 Docker 的 macOS 普通用户 | Desktop Host + 同一 Workbench + 本地 Engine 安装/诊断 | KE-9 设计伙伴阶段 |
| Homebrew Cask / CLI | 技术用户与自动化安装 | 指向已签名、公证的 macOS 产物 | 桌面稳定后 |
| Mac App Store | 希望通过 Store 安装的轻量用户 | 受沙盒约束的独立构建 | 最后评估 |

### 4.1 macOS 直装版

Mac App Store 外分发应使用 Developer ID 签名、Hardened Runtime 和 notarization；Apple 明确提供 macOS App 的 Direct Distribution 路径。[Apple：Direct distribution](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases/) [Apple：Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)

推荐先选择 `.dmg`（拖拽安装，适合 GUI）或 `.pkg`（需要更明确安装/服务管理时）。发布流水线需要验证签名、公证、staple ticket、首次启动、升级、卸载和数据保留/清除；不能只在开发机双击成功就发布。

### 4.2 为什么 Mac App Store 后置

Mac App Store 应用必须启用 App Sandbox。沙盒应用可通过用户选择的文件/目录获得访问，并需用 security-scoped bookmark 持久访问；它不适合把“扫描任意目录、管理外部 Docker、运行未受控外部程序”当成默认能力。[Apple：App Sandbox](https://developer.apple.com/documentation/security/app-sandbox) [Apple：访问沙盒外文件](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)

因此 Store 版需要单独设计：显式资料选择、bookmark 生命周期、沙盒数据容器、受限后台行为，以及与直装版分开的签名/测试。它可以成为未来轻量发行渠道，但不能反向驱动 Core 牺牲独立 Workbench、Connector 或重度本地训练能力。

## 5. 桌面 Host 的边界

Desktop Host 只负责宿主职责：

- 管理 API/worker 生命周期、崩溃重启和退出顺序；
- 提供本地数据目录、备份、诊断和更新入口；
- 将浏览器 Workbench 包装为应用窗口；
- 提示文件选择、模型外发、磁盘占用和破坏性删除；
- 处理签名、公证、自动更新和崩溃报告的 explicit opt-in。

它不得：

- 直接改写 PostgreSQL 表、图谱事实、Assessment 或 job 状态；
- 因桌面便利而给 Agent 任意 shell/文件/网络权限；
- 替代 Docker 的可重现开发环境；
- 让 Electron 专属 API 泄漏进 Core/Workbench 的领域代码。

## 6. 路线图调整与验收

| 阶段 | 技术交付 | 验收问题 |
| --- | --- | --- |
| KE-0 | TypeScript monorepo、OpenAPI/JSON Schema、React/Node build contract | GUI、Connector 与 API 能否共享 fixture？ |
| KE-1 | React Workbench + Node/Fastify API/worker + Docker | 不安装 Obsidian 时能否完成启动与诊断？ |
| KE-2～KE-8 | 继续使用同一 Web/API 架构完成导入、检索、图谱、训练、Agent、Connector | 是否存在桌面/插件专属的业务旁路？ |
| KE-9 | Electron `.dmg/.pkg` POC、Developer ID 签名、公证、升级/卸载测试 | 不用 Docker 的用户能否稳定安装、升级、备份和删除？ |
| KE-10（仅在需要时） | Mac App Store feasibility POC 或 Tauri 对照 benchmark | 沙盒/体积收益是否足以覆盖额外维护？ |

在 Electron POC 之前，不因桌面发行而改变数据库或领域模型。若本地 PostgreSQL 的无 Docker 打包成本过高，应先把“桌面 Host + 外部 Local Engine”的启动/诊断体验验证清楚，再决定是否打包数据库；不能为了一个 `.app` 在没有基准的情况下重写 Core。

## 7. 最终检查清单

- [ ] Core、Workbench、Connector 的主要代码均为 TypeScript，协议不依赖 Electron；
- [ ] Workbench 可在普通浏览器/Docker 中独立使用，并有 E2E 测试；
- [ ] Electron 仅为后置 Host，复用同一静态 UI 与 HTTP API；
- [ ] macOS 直装版具备 Developer ID 签名、公证、升级、卸载、备份/删除验证；
- [ ] Mac App Store 版被视为独立受沙盒约束的发行物，而非“上传同一包”；
- [ ] Tauri/Rust/其他数据库仅在明确 benchmark 和维护收益后评估。
