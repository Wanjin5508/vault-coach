# 03｜检索优化、受欢迎原因与 Vault Coach 借鉴

## 1. Neural Composer 已提供的检索杠杆

| 杠杆 | 源码/文档所见 | 要验证的效果 |
|---|---|---|
| `local/global/hybrid/naive/mix` 模式 | 插件把模式交给 LightRAG `/query`；服务端实现候选组合。[插件源码](https://github.com/oscampo/obsidian-neural-composer/blob/main/src/core/rag/ragEngine.ts)、[模式文档](https://github.com/HKUDS/LightRAG#selecting-query-modes) | 按“局部事实 / 跨文档关系”分组比较召回率、证据覆盖与延迟。 |
| 自定义实体类型 | 插件设置可提供领域 ontology。[插件 README](https://github.com/oscampo/obsidian-neural-composer#advanced-options) | 是否减少重复实体和关系歧义；需人工核对抽取。 |
| 重排 | 插件设置支持 Jina、Cohere 或自定义本地端点；LightRAG 官方说明重排增加查询时间。[插件 README](https://github.com/oscampo/obsidian-neural-composer#advanced-options)、[LightRAG 重排说明](https://github.com/HKUDS/LightRAG#enabling-reranking) | 在固定召回集合上测 `nDCG@k`、无证据回答率和 P95 延迟。 |
| 文档状态与按文件重摄入 | 监视文件夹、处理状态、失败重试；修改事件约 5 秒防抖。[插件 `main.ts`](https://github.com/oscampo/obsidian-neural-composer/blob/main/src/main.ts) | 降低索引过期和“以为已摄入”的问题；这是新鲜度和 UX 改进。 |
| 引用回链 | 请求 `include_references`，把服务返回的 `file_path/content` 显示给用户。[插件 `ragEngine.ts`](https://github.com/oscampo/obsidian-neural-composer/blob/main/src/core/rag/ragEngine.ts) | 用户能否打开准确来源、识别缺证据回答。 |

`similarity` 显示分数来自答案引用次数，不能拿来衡量检索质量，也不能用作重排训练标签。指定文件问答直接读取全文，不能用它的效果代替 Graph RAG 的效果。[插件 `processQuery()`](https://github.com/oscampo/obsidian-neural-composer/blob/main/src/core/rag/ragEngine.ts)

## 2. 建议的优化顺序：先建立证据，再调模型

以下是**针对 Vault Coach 的候选实验**，不是 Neural Composer 已实现的功能清单。

1. **建立查询集**：从真实 Vault 的已授权内容选局部事实、别名、跨文件关系、无答案、中文/英文混合问题；每题记录允许来源与最小支持证据。不要用生成模型自评取代人工 gold。
2. **固定基线**：记录当前 Vault Coach 的 keyword、vector、hybrid/RRF、可选 rerank 的 `Recall@k`、`MRR/nDCG@k`、引用命中率、无证据回答率、P50/P95 延迟与索引成本。现有机制见[本项目 RAG 笔记](04-RAG原理与检索实现.md)。
3. **先修召回缺口**：检查解析失败、标题/文件名/别名缺失、过大或过小 chunk、被排除文件、中文 token、过期索引。若 gold 块已在候选中而最终丢失，优先改排序与上下文预算。
4. **再试图增强**：对跨文件关系问题，做实体/关系候选召回并沿有界邻域找原文证据；与现有 hybrid 做并列测试。限制跳数、节点/边数、来源数量和 token 数，避免噪声路径挤掉直接证据。
5. **重排与路由**：在相同候选池上比较无重排、现有启发式、外部/本地 reranker；仅在能证明关系问题收益时让这类问题走图通道。简单事实题仍可走低成本路径。
6. **失败和隐私 Gate**：模型抽取错误、别名误合并、文档删除、权限范围变化、远端服务失联时，验证来源可追溯、事实可撤销、Ask/Exam 可继续使用。图边应区分提议与已确认事实。

LightRAG 官方提醒 embedding 模型需在索引和查询时一致；切换模型通常要求重建向量。查询重排可单独切换，但会增加延迟。高成本的图抽取也必须计入比较，不能只报查询时延。[官方模型与重排说明](https://github.com/HKUDS/LightRAG#embedding-models)、[论文成本分析](https://arxiv.org/html/2410.05779v3)

若瓶颈在**摄入**而非查询，LightRAG 官方把文件并行数、抽取 LLM 并发、embedding 并发与批量大小分开配置；先按失败率与资源使用量定位瓶颈，再逐项调参。若瓶颈在**查询上下文**，先检查实体/关系/总 token 预算和重排输出。提高并发不会修复错误实体、缺失来源或不合适的 chunk。[官方并发与查询配置](https://github.com/HKUDS/LightRAG#concurrency-optimization-for-file-processing)

## 3. 为什么它可能受欢迎：有根据的推断

社区页面在 2026-09-20 查阅时显示**约 1.3 万次下载**，并列出聊天、图可视化、本地 Ollama、监视文件夹、引用、远端服务及移动端等功能。[社区页面](https://community.obsidian.md/plugins/neural-composer) 这只能证明页面上的累计下载显示；不能推算独立用户、留存或满意度。以下是从产品路径作出的**推断**：

| 可观察设计 | 用户可能感受到的价值 | 证据与限制 |
|---|---|---|
| 在 Obsidian 内管理本地 LightRAG 服务 | 减少手动启动 Python 服务的步骤 | [插件 README](https://github.com/oscampo/obsidian-neural-composer#readme)；仍需用户安装 Python/LightRAG。 |
| 图谱、引用和处理状态在同一界面 | 能看到“是否处理、连到哪里、答案来自哪里” | [社区功能页](https://community.obsidian.md/plugins/neural-composer)；可见性不等于正确性。 |
| Ollama 本地路径及多提供商选择 | 兼顾隐私偏好与模型质量/速度选择 | [插件隐私说明](https://github.com/oscampo/obsidian-neural-composer#privacy--security)；云提供商配置会发送数据。 |
| 从 Smart Composer 借用成熟交互，再加入图功能 | 降低学习门槛，覆盖既有聊天使用习惯 | [项目 README 致谢](https://github.com/oscampo/obsidian-neural-composer#readme)；无法据此量化增长贡献。 |
| 跨笔记关系问题的明确定位 | 给研究、写作等场景一个易懂用例 | [社区功能页](https://community.obsidian.md/plugins/neural-composer)、[作者论坛帖](https://forum.obsidian.md/t/neural-composer-local-graph-rag-made-easy-lightrag-integration/109891)；尚无与 Vault Coach 的公开同条件对照。 |

## 4. 对 Vault Coach 的取舍

Vault Coach 当前已有可选向量召回、RRF hybrid、可选 rerank、结构图谱和用户审核的语义概念图谱，**不能说目前完全没有图能力**。但在当前问答路径中，图事实并非 LightRAG 式的主要候选召回通道；若要借鉴，应先用第 2 节基准证明跨文件问题存在稳定缺口。[本项目 RAG 说明](04-RAG原理与检索实现.md)、[本项目语义图谱服务](../../../src/app/semantic-graph/semantic-graph-service.ts)

优先借鉴的产品做法是：清楚展示摄入状态、来源和重试路径；对每条图关系保留原文证据；将图检索作为可测、可回退的候选通道。Neural Composer 的自动启动外部 Python 进程、Vault 外工作目录、远端服务和全自动抽取确认方式都涉及本项目的隐私与治理约束，不能直接照搬。本仓库规划中的 Knowledge Engine 是可选协作服务，当前插件版本尚未把它接成线上查询后端。[本项目 `README.md`](knowledge-engine/README.md)、[Knowledge Engine 需求规格](01-需求规格.md)
