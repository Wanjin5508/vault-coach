可行，而且 **Vault Coach 其实比一般的 RAG 插件更适合 Agent 化**。但我不建议把现有系统推倒重写成“LLM 自己决定一切”的通用 Agent，而应该把 Agent 放在最上面，作为**决策与编排层（orchestration layer）**。

你现在已经有 `VaultKnowledgeBase → AdvancedRagEngine → ModelClient` 的稳定链路，也有长期记忆、索引同步、来源跳转等能力。`streamAssistantTurn()` 本质上已经在协调知识库、记忆、RAG 和状态持久化；这些模块非常适合进一步封装成 Agent Tools。 当前 RAG 本身也已经被拆成 query rewrite、retrieval、rerank、context construction 等相对独立步骤。

更重要的是，你之前的路线图本身已经规划了知识图谱和“智能体面试助手”，所以 Agent 化实际上是现有方向的自然延伸，而不是突然换赛道。

---

# 一、最合理的架构不是 RAG → Agent，而是 Agent → Tools

现在大致是：

```text
User
 ↓
Vault Coach UI
 ↓
AdvancedRagEngine
 ↓
Retrieve → Rerank → LLM
 ↓
Answer
```

以后我建议变成：

```text
User Goal
   ↓
Learning Agent
   ↓
Planner / Router
   ↓
Tool Registry
   │
   ├── Search Vault
   ├── RAG Answer
   ├── Query Knowledge Graph
   ├── Generate Exam
   ├── Grade Exam
   ├── Read Mastery
   ├── Update Mastery
   ├── Read Memory
   ├── Create Review Plan
   ├── Open Source Note
   └── Write / Link Note
           ↓
        Obsidian
```

这里有一个非常重要的原则：

> **Agent 不替代 RAG。RAG 是 Agent 的一个 Tool。**

同样：

> Knowledge Graph 不是 Agent。

而是：

> Knowledge Graph 是 Agent 可以查询的一种结构化知识源。

Exam Engine 也是一样。

---

# 二、你目前其实已经拥有很多“Agent Tool”

例如现在代码里已经存在：

```text
ensureKnowledgeBaseReady()
streamAnswerQuestion()
openSource()
rebuildKnowledgeBase()
syncVectorIndex()
extractMemoryStatements()
```

这些已经是准 Tool 结构。

未来只需要把它们进一步抽象成：

```ts
interface AgentTool {
    name: string;
    description: string;
    execute(input: unknown): Promise<ToolResult>;
}
```

例如：

```text
search_vault
query_knowledge_graph
generate_exam
grade_exam
get_mastery
get_learning_history
create_review_plan
open_note
create_note
update_note
add_concept_relation
```

然后 Agent 不再直接操作底层数据库和 Obsidian API，而是只能通过这些受控 Tool 行动。

这样安全性和可测试性都会好很多。

---

# 三、Vault Coach 最有价值的 Agent 不是 Chat Agent，而是 Learning Agent

这是我认为最重要的产品定位。

现在大量产品已经在做：

> Chat with your notes.

即使做成：

> Agent with your notes.

也很容易再次落入 Copilot 的竞争区。

Vault Coach 真正有优势的目标应该是：

> **Autonomous Learning Agent / Personal Knowledge Coach**

它不仅回答：

> “什么是 PPO？”

而是能处理：

> “我准备两周后面试强化学习相关岗位，你根据我的知识库和历史考试情况帮我安排复习。”

这时候普通 RAG 就不够了。

Agent 可以执行：

```text
Goal:
两周后准备 RL 面试

        ↓

读取 Knowledge Graph

        ↓

读取 Mastery
PPO          0.82
DQN          0.76
TD Learning  0.41
MC           0.63
Policy Grad  0.38

        ↓

检查知识依赖

Policy Gradient
      ↓
Actor-Critic
      ↓
PPO

        ↓

生成学习计划

Day 1:
Policy Gradient

Day 2:
Actor-Critic

Day 3:
PPO

        ↓

自动生成 Exam

        ↓

根据考试结果更新 Mastery

        ↓

调整后续复习计划
```

这里才真正需要 Agent。

# 四、最值得扩展的 8 个 Agent 场景

## 1. Personal Learning Coach

这是我认为优先级最高的。

用户说：

> “我这周想复习强化学习。”

Agent 自动：

```text
get_mastery()
        ↓
query_knowledge_graph()
        ↓
find_weak_concepts()
        ↓
find_prerequisites()
        ↓
create_review_plan()
        ↓
generate_exam()
```

过去 Vault Coach 是：

> 用户自己决定问什么。

Agent 化以后变成：

> **Vault Coach 主动决定用户下一步应该学什么。**

这和你的 Learning Map / Mastery 系统天然匹配。

---

# 2. Weakness Diagnosis Agent

考试模式以后不要仅仅输出：

```text
7 / 10
```

而是让 Agent 分析：

```text
Question 3 错误
 ↓
涉及 TD Target
 ↓
Knowledge Graph:
TD Target → TD Error → DQN

 ↓

检查过去考试

TD Target：
过去 4 次错误 3 次

 ↓

诊断：
基础概念薄弱

 ↓

搜索相关笔记

 ↓

生成针对性解释

 ↓

生成 3 道新题
```

于是考试真正形成：

> **Assessment → Diagnosis → Intervention → Reassessment**

这是教育产品里面非常有价值的一条闭环。

---

# 3. Socratic Tutor Agent

这个场景和普通 Chat 很不一样。

例如用户问：

> “为什么 DQN 要使用 target network？”

普通 RAG 给答案。

Socratic Agent 可以说：

> “先不直接告诉你。你还记得 Bootstrap 中 TD Target 是怎么构造的吗？”

然后根据回答继续：

```text
User answer
 ↓
Evaluate
 ↓
Correct?
 ├─ yes → deeper question
 └─ no  → retrieve note → hint
```

直到用户自己推导出来。

这特别适合：

数学、机器学习、算法、医学、法律等知识库。

---

# 4. Knowledge Maintenance Agent

这是知识图谱完成后非常自然的一步。

现在知识图谱可能是：

```text
PPO
 ↓ based-on
Policy Gradient

PPO
 ↓ uses
Actor-Critic
```

Agent 可以周期性检查：

```text
孤立 Concept
缺失关系
重复 Concept
同义词
疑似错误关系
没有 source evidence 的 edge
长期没有更新的知识
```

然后给用户：

> 我发现 `Temporal Difference Learning` 和 `TD Learning` 可能是同一概念，是否合并？

或者：

> `PPO → Actor-Critic` 关系目前只由一篇笔记支持，要不要检查？

这个场景的价值非常高，因为用户最大的 Obsidian 问题之一就是：

> **知识库会逐渐变乱。**

---

# 5. Knowledge Graph Builder Agent

你原计划的 KG 构建本身也可以 Agent 化。

而不是一次性：

```text
LLM → entities → relations
```

可以变成：

```text
Extract candidate entities
 ↓
Search existing graph
 ↓
Check duplicates
 ↓
Retrieve source evidence
 ↓
Infer candidate relation
 ↓
Validate evidence
 ↓
Ask user if uncertain
 ↓
Commit edge
```

例如：

```text
新文档：
"PPO introduces clipping..."

Agent:

1. 找到 PPO
2. 找到 Policy Gradient
3. 找到 Actor-Critic
4. 检查已有 edge
5. 提取 evidence
6. 提议：

PPO --variant_of--> Policy Gradient
PPO --uses--> Actor-Critic
```

这会比简单 Information Extraction 稳定很多。

---

# 6. Research Agent

这是未来非常值得做的 Advanced 功能。

例如用户说：

> “看看最近有没有关于 GRPO 的论文，把和我当前知识库不同的新知识找出来。”

Agent：

```text
Web / arXiv Search
 ↓
Read Papers
 ↓
Search Vault
 ↓
Compare external knowledge
       vs
personal knowledge

 ↓

Identify knowledge gap

 ↓

Generate:
- summary
- new concepts
- conflicting information
- suggested notes
```

最终不是单纯总结论文，而是：

> **“这篇论文相对于你已经掌握的内容新增了什么？”**

这是普通 ChatGPT 很难做到的，因为它不知道用户真正的知识结构。

而 Vault Coach 有：

```text
Vault
+
Knowledge Graph
+
Mastery
+
Memory
```

这会成为很强的上下文。

# 7. Knowledge Writing / Note Refactoring Agent

这是 Agent 开始真正“行动”的地方。

例如：

> “把我关于 DQN 的笔记整理一下。”

Agent：

```text
search_vault("DQN")
 ↓
发现 7 篇相关笔记
 ↓
query_graph(DQN)
 ↓
发现重复内容
 ↓
提出 plan

1. 创建 DQN.md
2. 合并核心定义
3. 保留实验笔记
4. 建立 links
5. 更新 index note
```

然后：

> Apply?

用户确认以后才执行：

```text
create_note()
update_note()
add_link()
```

这里必须设计权限等级。

我建议：

```text

→ 自动执行

→ 自动执行

Write Tool
→ 默认请求确认

→ 必须确认
```

千万不要一开始就做 Fully Autonomous Vault Editing。

# 六、但不是所有功能都应该 Agent 化

这一点尤其重要。

我建议坚持：

### Deterministic Pipeline

继续负责：

```text
chunking
embedding
indexing
hybrid retrieval
RRF
reranking
persistence
grading calculation
mastery calculation
```

这些都应该尽量确定性。

Agent 不应该：

> “思考一下今天要不要用 vector search。”

RAG Engine 自己决定即可。

Agent 应该处理的是：

```text

search?
exam?
query graph?
review?
write note?
```

也就是**业务层决策**。

# 七、我建议采用 4 级 Agent 成熟度

不要一下做到 Autonomous Agent。

## Level 0 — 当前 Vault Coach

```text
Ask
→ RAG
→ Answer
```

## Level 1 — Tool Routing

用户：

> “帮我测试一下 DQN。”

LLM 自动调用：

```text
generate_exam
```

用户：

> “DQN 和 PPO 有什么关系？”

自动：

```text
query_graph
+
search_vault
```

这是第一版 Agent 最应该做的。

---

## Level 2 — Multi-step Agent

例如：

> “找出我强化学习最薄弱的地方。”

Agent：

```text
get_mastery
 ↓
query_graph
 ↓
search_exam_history
 ↓
search_vault
 ↓
analysis
```

开始出现 Tool Loop。

---

## Level 3 — Goal Agent

例如：

> “这个月帮我掌握强化学习基础。”

Agent维护：

```text
Goal
Plan
Progress
Mastery
Tasks
Review
```

持续多天甚至多周。

这时 Vault Coach 已经真正成为：

> Personal Learning Agent。

---

## Level 4 — Autonomous Knowledge Agent

系统主动：

```text
发现新笔记
↓
更新 KG
↓
发现薄弱知识
↓
重新安排 Review
↓
发现重复笔记
↓
提出修改建议
```

这个阶段再考虑更高自治。

# 九、这也会改变 Vault Coach 的市场定位

现在可以说：

> AI learning assistant for Obsidian.

未来则可以自然升级成：

> **A personal learning agent that understands your notes, tests your knowledge, tracks mastery and decides what you should review next.**

我认为这比：

> AI Agent for Obsidian

强很多。

后者会直接和 Copilot 竞争。

前者建立了自己的类别。

---

## 最终我会这样规划路线

**1.5：Zero-setup RAG**

内置 embedding，把安装门槛降下来。

↓

**1.6：Learning Graph + Mastery**

把 KG、考试结果和学习状态真正连起来。

↓

**1.7：Agent Tool Layer**

把 RAG / Exam / Graph / Mastery 封装成 Tools，先实现 Tool Routing。

↓

**1.8：Learning Agent**

支持：

> “我想学习 X。”

然后自动执行：

```text
Assess
→ Plan
→ Learn
→ Test
→ Diagnose
→ Review
```

↓

**2.0：Personal Knowledge & Learning Agent**

再加入：

Research Agent、知识库维护、长期 Goal、复习计划和跨应用接口。

所以我认为 **Agent 化不仅可行，而且很可能是 Vault Coach 最自然的长期终点**。但真正值得做的不是“让 LLM 多调用几个工具”，而是利用你已经逐渐拥有的 **RAG + Knowledge Graph + Exam Evidence + Mastery + Long-term Memory**，让 Agent 能够回答一个普通 RAG 无法回答的问题：

> **“根据我已经学过的内容、真正掌握的程度和知识之间的依赖关系，我下一步应该做什么？”**

一旦这一点实现，Vault Coach 和普通 Obsidian AI Chat 插件的产品差异就会非常明显。
