# 里程碑 5：能力地图工作区技术说明与踩坑复盘

## 1. 为什么需要 Progress read model

Learning Map 需要同时解释三个不同层次的数据：

~~~text
知识本身：effective Concept 与确认关系
学习证据：Assessment Event → Mastery snapshot
考试活动：结构化 Assessment Session history
~~~

让 View 同时读取多个 Store 会带来三个问题：UI 了解存储布局、同一统计在多个组件复制、以及未来 Local Knowledge Engine 接入时必须重写 View。因此 L5.1 新增位于【src/app/progress/】的 Progress read model。

它属于 Application 层，而不是 Domain 层：它只把既有领域事实投影为 UI 可读摘要，不增加新的业务事实、不计算新的掌握度算法，也不改变 Concept/Relation。

## 2. 技术设计

### 2.1 Facade + Read Model

【VaultCoachApplication】通过【ProgressApplicationApi.getSnapshot】暴露一个异步、只读的【ProgressSnapshot】。Presentation 只依赖这个接口，不能 import：

- 【LearningGraphQueryService】；
- 【MasteryService】；
- JSON Store；
- 图谱渲染器和 renderer projection。

这样的 Facade 让后续 L5 Dashboard、L6 自适应考试和未来 Engine adapter 可以复用相同的读取边界。

### 2.2 为什么使用 Concept catalog，而不是图谱投影

【LearningGraphProjection】是为 renderer 设计的有界子图，默认存在节点/边预算。若用它计算“知识总数”或“覆盖率”，大知识库会因为 UI 截断而得到错误统计。

L5.1 因此使用【LearningGraphQueryService.getConceptCatalog】。catalog 是不带布局数据的 effective Concept 全量列表，且排除了 pending/rejected candidate。这个选择保证：

- 能力地图计数不受图谱首屏显示数量影响；
- 未确认语义候选不会影响学习结论；
- 未来绘制子图时仍可独立限制 renderer 负载。

### 2.3 为什么只统计结构化 Assessment history

Markdown 考试报告是可再生投影，可能缺失、被重建或与 JSON session 同时存在。把它计入考试活动会重复计数，也可能把没有可追溯事件的旧文本误当成学习证据。

ProgressService 只调用【AssessmentSessionStore.listHistory】。这不意味着旧 Markdown 被删除：它仍可在历史兼容界面中打开；只是它不影响能力地图、覆盖率和后续自适应考试。

### 2.4 缺失值与数据新鲜度

“没有数据”与“得分为零”在学习产品中含义不同：

| 情况 | Progress 表达 | 不做的事 |
|---|---|---|
| 图谱未建立 | graph unavailable | 不显示 0 个知识点作为结论 |
| 尚无 Mastery snapshot | mastery missing，coverageRatio 为 null | 不显示 0% 掌握度 |
| 图谱/考试变化但 snapshot 未重算 | mastery stale | 不把旧快照说成实时状态 |
| 正在重算 | mastery calculating | 不阻塞 Ask/Exam，也不删除旧状态 |
| Assessment history 读取失败 | assessments unavailable | 不让整个 Progress 请求失败 |

局部数据源的错误被转换为摘要状态而不是直接抛给 Dashboard；这让未来 UI 能同时显示已有信息和可操作的恢复提示。

### 2.5 为什么 L5.1 不缓存

缓存本身不是性能优化的默认答案。当前读取来自内存中的 LearningGraphQueryService/MasteryService，以及紧凑的 Assessment history index；先建立正确的事实边界和可测试结果，比过早缓存更重要。

L5.2 才会定义缓存/失效策略。届时必须以 ApplicationEvent、版本或 revision 为依据，避免：

- 每次 View render 全量读取 history；
- 每个索引事件重复刷新；
- 用 renderer 的局部状态作为全局统计缓存键；
- 在 onload 进行昂贵的全 Vault 扫描。

### 2.6 为什么预留空 recommendations 字段

M7 才会实现 RecommendationService。提前在 snapshot 内稳定地返回空数组，能让 Dashboard 先完成布局与 loading/empty state，而不会在 M7 破坏 API shape。它不表示目前已经存在“零条推荐”的学习结论；UI 必须结合 RecommendationService 的可用状态解释该字段。

## 3. 本次踩坑与修复

### 3.1 Vitest 不支持 Jest 的 runInBand 参数

首次验证时误执行【npm test -- --runInBand】。项目使用 Vitest 0.34，CLI 不认识该 Jest 参数，直接报 Unknown option。该问题不是源码或依赖损坏。

修复方式是使用项目脚本【npm test】。在 L5.2 完成后的最终验证中，40 个测试文件、145 项测试均通过。后续如果需要控制并发，应查阅当前 Vitest 版本支持的参数，而不是复用 Jest 命令。

### 3.2 M0 测试把占位返回值写死为 false

原架构测试断言 ProgressController 中存在固定签名【isAvailable(): false】。这在 M0 合理，因为当时 Progress 是无数据的占位边界；但 L5.1 已在容器中注入 ProgressService，availability 必须反映实际服务是否装配。

修复为【isAvailable(): boolean】，并保留两条保护：

- 没有 ProgressService 的兼容测试构造路径仍返回 false；
- Presentation 仍只调用 ProgressApplicationApi，未 import 具体业务服务。

### 3.3 旧 Concept 不可混入当前统计

Mastery snapshot 是可恢复缓存，图谱合并、删除或重建后其中可能暂时含有已经不属于 current effective catalog 的 Concept。若直接遍历 snapshot，会让 Dashboard 显示过期的 weak/mastered 数量。

ProgressService 先以 catalog ID 集合过滤 snapshot states，再统计等级和覆盖。若 Mastery 标记为 dirty，仍提供最后一次快照供解释，但状态明确为 stale。

## 5. 后续实现注意事项

- L5.2 已实现惰性缓存、既有 Application 事件失效和 revision 保护。缓存依然是只读派生数据，不能因为刷新而写回 Mastery/Graph。
- L5.4 已实现按需 Dashboard：仅在 Progress View 打开后的生命周期读取 snapshot，并显示状态、生成时间和缺失数据，而不是渲染一个没有上下文的百分比。
- L5.5 图谱画布应使用 bounded projection，不能把 catalog 全量节点直接交给 renderer。
- L6 选择考试目标只能消费 effective Concept、confirmed relation 和带版本的 Mastery evidence。

## 6. L5.2：惰性缓存、事件复用与并发安全

### 6.1 为什么缓存位于 ProgressService

缓存放在 View 会让多个分屏、关闭/重新打开的叶子各自读取 Assessment history；缓存放在 Store 又会把 UI 投影误当作事实数据。ProgressService 位于 Application 层，正好能缓存“由多个事实源组合出的临时读模型”，同时不持久化它。

缓存状态只有：

~~~text
无快照（dirty）
  → 第一次 getSnapshot
  → 有快照（clean）
  → 源事件 invalidate
  → 保留旧快照但标记 dirty
  → 下一次 getSnapshot
~~~

【invalidate】没有 I/O 行为。它不会在 onload、Vault 文件事件或 index busy 状态变化时触发全量扫描，因而符合插件启动轻量和按需读取原则。

### 6.2 为什么复用已有 Application 事件

Runtime 已订阅 VaultCoachApplication 的 index、graph、semantic graph、mastery 和 exam history 事件，并安全刷新已打开 View。新增一个 Progress 专用 timer、Obsidian Vault listener 或 event bus 会引入重复刷新和卸载风险。

L5.2 的做法是：每个会改变 Progress 输入的既有应用操作都先调用【ProgressService.invalidate】，再发布原本就需要的源事件。这样：

- 现有 View 刷新机制保持不变；
- 未来 Progress View 只需在既有刷新中调用 getSnapshot；
- 不会在一次语义图谱操作中额外发布多个 Progress 专用通知；
- Progress 不依赖 Obsidian API，仍可在应用测试中使用 fake port。

### 6.3 revision 保护与 in-flight 合并

缓存带单调递增的内存 revision。多个读取请求共用一个 in-flight Promise；若计算期间收到 invalidate，旧结果不能写入缓存，调用方会继续读取新 revision。

这解决了典型竞态：

~~~text
View A 开始读 Progress
  → 用户保存考试或自动同步图谱
  → invalidate
  → View A 的旧 I/O 返回
  → 旧结果不缓存，重新读取并返回新结果
~~~

这不是数据库事务替代品，而是 UI 读模型的一致性保护：事实源仍分别由 Assessment JSON、Learning Graph 和 Mastery snapshot 管理。

### 6.4 L5.2 测试修复

新增应用事件测试时，MasteryService fake 最初没有实现【markDirty】。图谱重建的真实协调路径会标记 Mastery stale，因此测试抛出“markDirty is not a function”。

修复为在 fake 中提供【markDirty】。这说明应用层测试应模拟操作链实际使用的最小 port，而非只 mock 被最终断言的函数。

新增覆盖：

1. 缓存命中不重复读取 Assessment history；
2. 返回 snapshot 被调用者修改后，不污染缓存；
3. 失效后才惰性重读；
4. 并发读取合并为单个 I/O；
5. 读取中失效会自动重读；
6. index、图谱、Mastery、新 Assessment 事实触发 invalidate。

## 7. L5.3：为什么 Progress 必须是独立主工作区 View

### 7.1 侧栏不是图谱或 Dashboard 的容器

Ask/Practice 侧栏的核心任务是短回合问答与考试。若把能力卡片、筛选器和图谱画布直接放进同一滚动容器，会与输入框、会话历史和考试表单争夺空间，也使分屏、关闭和恢复图谱状态变得不符合 Obsidian 使用习惯。

L5.3 因此把【ProgressWorkspaceView】注册成普通【ItemView】。它使用稳定的【vault-coach-progress】View Type，Obsidian 可以将该类型保存在工作区布局中。用户可像使用笔记一样关闭、重新通过命令打开、或把它分屏；侧栏只保留一个紧凑启动按钮。

### 7.2 一个激活器，三种主工作区入口

【activateMainWorkspaceView】抽取了 Concept Review、Learning Map 与 Progress 共同的生命周期：

~~~text
查找既有同类 leaf
  ├─ 找到：聚焦既有 leaf
  └─ 未找到：workspace.getLeaf(true)
              → setViewState({ type, active: true })
              → 聚焦新 leaf
~~~

这里不能使用右侧栏 leaf；否则用户可能把 Dashboard 与 Ask/Practice 强行叠在同一侧栏区域。也不能每次命令都无条件新建 leaf；那会产生多个不同步的 Dashboard 标签页。该 helper 有独立单元测试，覆盖“复用已有 leaf”和“创建并初始化新 leaf”两条路径。

### 7.3 为什么 L5.3 shell 初始不读取 snapshot

L5.2 保证【getSnapshot】按需且可缓存，但“可缓存”不等于“每次打开 View 都应该读取”。工作区恢复、Ribbon 点击和 application-state refresh 都可能频繁发生。如果 L5.3 先读取 Assessment history，用户尚未看到 Dashboard 卡片便已经触发 I/O，也会让后续性能问题难以定位。

因此 L5.3 的初始 shell 只调用同步的【ProgressController.getState】来判断服务是否可用；不调用【getSnapshot】，也不创建 renderer、timer 或订阅。L5.4 在用户实际打开该 View 后才以明确的 loading/error/freshness 状态异步读取 snapshot；L5.5 才将预算内 Learning Graph projection 交给 renderer。

### 7.4 测试中的 lint 误报如何处理

首次测试使用【workspace.getLeaf】和【leaf.setViewState】属性直接进行 Vitest 断言。ESLint 的【unbound-method】规则正确地指出：若这些是真实实例方法，脱离对象引用可能丢失【this】；同时测试里的 Workspace 类型把一个旧方法签名带到了断言中。

处理方式是保存每个【vi.fn】的局部引用，再把它们放入 fake workspace，断言只引用 spy 变量。没有关闭 lint、没有强制转换过时方法，也没有改变产品的 Obsidian API 调用。这让测试更贴近“观察调用结果”的目的，并保留将来 API 类型升级时的诊断价值。

## 8. L5.4：Dashboard 的按需读取与不确定性表达

### 8.1 Dashboard 是 Presentation read model，不是新的事实层

【ProgressDashboardModel】位于 Presentation components，输入只有【ProgressSnapshot】、【ProgressStateView】和已有【GraphCapacityAssessment】。它把固定、已存在的值转化为五张状态卡与五级 Mastery 分布；不写 Store、不改变 Concept、不会触发考试、也不根据相似度猜测推荐。

这使 UI 的数字可沿以下链路追溯：

~~~text
effective Concept catalog ─┐
Mastery snapshot ──────────┼→ ProgressSnapshot → ProgressDashboardModel → Dashboard DOM
Assessment Session history ┘
semantic graph capacity ────────────────────────────────────────────────┘
~~~

容量评估仍来自【SemanticGraphApplicationApi.getState】。它只提示 Lite 本地容量状态，不会因为建议使用 Knowledge Engine 而禁用 Ask、Exam、已有图谱或 Dashboard。

### 8.2 为什么 "Not calculated" 比 0% 更重要

学习产品中三个状态不能混淆：

| 原始值 | Dashboard 文案 | 原因 |
|---|---|---|
| coverageRatio 为 null | Not calculated | 没有可比较的 catalog 或 Mastery snapshot，不是用户答错。 |
| Mastery missing/unavailable | Evidence quality: Not calculated | 没有证据时，0 个 unbound issue 不是“证据健康”。 |
| Assessment history unavailable | Structured assessments: Unavailable | JSON 读取失败不能显示为“尚无考试”。 |

模型的回归测试覆盖这三种 partial-data 情况，防止后续样式或文案修改把缺失值悄悄转成 0。

### 8.3 异步 View 的双重竞态保护

L5.2 的【ProgressService】保护“来源变化期间的 snapshot 读取”；L5.4 的 View 还需要保护“叶子已经关闭或用户已触发第二次刷新”的 DOM 生命周期：

~~~text
refresh #1 开始读取
  → 用户触发 refresh #2 或关闭 View
  → refresh #1 返回
  → View refresh revision 不匹配，#1 不再回写 DOM
~~~

View 保留最近一次成功 snapshot。下一次读取失败时，用户仍能看到带 warning 的旧卡片和 Retry；从未成功读取时才显示纯错误面板。这样既不把旧数据伪装成 current，又不会在暂时性读取失败时丢失全部上下文。

### 8.4 Promise lint 修复

L5.4 使【ProgressWorkspaceView.refresh】变为 Promise，因为它需要等待按需 snapshot。Plugin 的【refreshAllViews】是既有“通知式、不阻塞”的循环，因此使用【void leaf.view.refresh()】明确忽略已由 View 内部处理的后台 Promise。若改为 await，索引/图谱事件可能被 UI 读取拖慢；若完全不标记，则 ESLint 会正确报告未处理 Promise。

## 9. L5.4 补充：本地化与长任务可见性

### 9.1 不能把 Service 错误原文当作 UI 文案

应用服务的【message】与【lastError】服务于诊断和状态传播，来源可能是中文实现、英文 SDK、模型服务或未来的第三方 Knowledge Engine。把它们直接放进 Dashboard 或图谱页面会导致同一屏幕中英文混排，也会把不稳定的底层措辞变成用户可见契约。

本项目采用两层处理：Application/Domain 继续保存原始错误以便日志与调试；Presentation 只根据稳定的 status、busy、capacity 和是否有数据，选择【i18n.ts】中的本地化文案。这样错误发生时用户仍能得到可执行的“重试/检查设置”提示，而开发者不会失去原始诊断信息。

### 9.2 为什么构建开始也必须发事件

仅在 rebuild Promise 结束时发布事件，会造成典型盲区：耗时模型调用已经开始，但 View 仍显示旧的 0 节点状态。用户无法区分“没有数据”和“正在计算”，于是重复点击重建。

语义图谱协调器在第一个 await 之前同步设置 busy。Facade 在调用【service.rebuildAll】后立即发布状态事件，完成路径在 finally 再发布一次：

~~~text
rebuild command
  → coordinator.start()：busy = true
  → semantic-graph-state-changed（View 立即显示构建中）
  → 异步抽取 / embedding / 写入
  → finally：semantic-graph-state-changed（View 刷新最终图谱或错误状态）
~~~

这复用了既有 Runtime→View 刷新机制，不引入轮询、全局 interval 或额外 Vault listener；也保证失败与取消不会遗留“永远构建中”的页面。

### 9.3 动画是辅助，文字状态才是事实

旋转 spinner 和轻微脉冲边框用于吸引注意力，但不能是唯一反馈：减少动态效果、低性能设备或屏幕阅读器都可能看不到动画。状态条使用 `role=status` 与 `aria-live=polite`，始终包含“正在构建”及可用的章节进度文字；CSS 的 `prefers-reduced-motion` 会关停动画而不删除状态。

### 9.4 回归测试

- Dashboard display-model 测试显式传入中文翻译函数，验证卡片使用中文状态且不会泄漏英文 Service message；
- Application Facade 测试使用可控的未完成 rebuild Promise，验证 busy 变为 true 后立即发出第一条 semantic state event，完成后再发出第二条；
- 完整回归执行 build、lint、Vitest 和 diff check，最终为 42 个测试文件、151 项测试。

## 10. L5.4：为什么考试掌握度必须使用来源 Chunk，而不能猜主题

### 10.1 临时主题 ID 不能成为长期事实 ID

早期考试题使用【exam-topic:*】保存蓝图 topic。它能保证同一主题字符串得到稳定 ID，但并不表示该 ID 是语义图谱中的 Concept ID。蓝图 topic 往往是章节标题或教学目标，例如“TypeScript 基础与类型约束”；同一来源里的确认概念可能是“TypeScript”“类型收窄”等多个粒度不同的实体。将两者按字符串或 embedding 强行合并会让考试分数归到错误概念。

### 10.2 Source chunk 是共同的可审计锚点

题目和语义概念都持久化【sourceChunkIds】/evidence chunkId。它们来自同一确定性文本索引，因此可以建立如下完全本地、无需模型调用的连接：

~~~text
Exam question.sourceChunkIds
  → effective Concept evidence.chunkId
  → concept:* ID
  → Assessment event / Mastery state
~~~

这个连接的优点是可以解释、可以复算、可以用于旧记录；缺点是一个 chunk 可能支持多个概念。当前 Lite 策略宁可把题目分数应用到全部有直接 chunk 证据的概念，也不跨 chunk、跨关系或按相似度扩散。后续 Knowledge Engine 可以在保留该 provenance 的基础上，引入更精细的 section/claim 级绑定。

### 10.3 不迁移 Assessment JSON

已保存的 Assessment event 是用户学习事实，不能为了升级绑定算法而静默改写。修复使用读取时的最后一级 source-chunk-evidence resolver：旧 event 仍保留原始【exam-topic:*】和生成时来源；重建 Mastery snapshot 时用当前有效概念 catalog 重新解析。新生成题目则直接持久化 concept:*，两种记录能在同一算法下共存。

本次改变有效证据集合，故算法版本从【mastery/v1】递增为【mastery/v2】。这不是存储 schema 变更：旧快照仍可读取，但 MasteryService 会标记为 dirty，UI 必须提示用户重建，不能把旧绑定规则计算出的数值显示成 current。

### 10.4 实际 Vault 验证的限制

测试 Vault 的最新空白考试中，5 个题目来源 chunk 只有第 1 个能命中当前语义概念 evidence；该 chunk 同时支撑多个概念。这说明 source-chunk 绑定可以恢复可追溯性，但其粒度最多只能精确到 chunk，不能宣称它已经理解“题干只考察 chunk 中哪一个概念”。Lite 版会把该题分数作用于所有同源确认概念，并保留【source-chunk-evidence】bindingKind 供审计；未命中 evidence 的其余题目仍保持 unknown。

若后续要做到更细颗粒度，应在考试蓝图中保存“目标 concept ID + section/claim evidence”，并让出题模型从受限候选中选择；该方案属于后续 Knowledge Engine/考试规划升级，不能在当前版本用模糊字符串或 ANN 悄悄替代。

## 11. L5.5：为什么正式 Learning Map 使用一次性确定性力导向布局

### 11.1 图谱布局不等于语义图谱计算

`LearningGraphRenderer` 接收的是已经完成筛选、关系过滤和节点预算的 `LearningGraphProjection`，而不是 semantic catalog。力导向算法只根据“有哪些可见节点与边”生成二维坐标；它不会判断概念是否相似、不会新增关系、不会调用 embedding，也不会读写 Vault。

因此两类复杂度必须分开理解：

| 工作 | 输入规模 | 本地 Lite 策略 |
| --- | --- | --- |
| 语义候选/ANN | 原始 section 与概念证据 | M3 的有界候选流程和容量阈值控制。 |
| Learning Map 布局 | 已截断的 renderer projection，最多 150 节点 | 一次性 O(V² × iteration) 视觉计算。 |
| 用户平移、缩放、选择 | 当前 SVG DOM | O(1) 或与局部相邻边成正比，不重新布局。 |

### 11.2 为什么不是持续动画模拟

Obsidian 原生图谱的观感来自力导向布局，但插件不应在一个学习工作区中永久运行 `requestAnimationFrame` 或 interval。持续模拟会占用主线程、导致节点在用户阅读时漂移，并使同一数据在不同刷新后难以复现。

本实现使用稳定 ID hash 初始化，然后固定迭代次数完成排斥、碰撞、弹簧与居中力。结果具备三个产品属性：

- 相同 projection 产生相同坐标，便于截图、测试和问题复现；
- 关系节点自然拉近，孤立节点分散，不再形成调试网格；
- 布局结束后不再占用 CPU，用户手动拖动的节点也不会被下一帧拉回。

节点预算是安全前提：即使 150 个节点进行 150 轮两两排斥，也只是有限的同步 UI 计算。若将 catalog 全量输入，数千节点会使 `V²` 成为不可接受的主线程阻塞；这正是 renderer 必须只接受 projection 的原因。

### 11.3 标签、方向与邻域强调

在稠密图里让每个节点永久显示标签会比规则网格更难读。画布只默认显示连接节点的标签；用户选中或悬停任意节点时，会显示它及一跳邻域的标签，并淡化无关节点和边。完整名称仍保存在 SVG `title` 中，避免把 Obsidian 的 HTMLElement tooltip 机制应用到 SVG 后触发 `isShown()` 兼容问题。

有方向的边将箭头终点缩进目标节点圆周，防止箭头被圆覆盖；检查器沿用同一 `sourceNodeId → targetNodeId` 契约。无方向关系仍使用普通线段，不能因为显示层需要“方向感”而伪造领域事实。

### 11.4 可逆 Focus navigation

Focus neighbourhood 是一次 query 变换，不是页面导航。Controller 因此仅在内存保存上一个完整 `LearningGraphQuery`，让【Back】精确恢复原搜索和过滤条件；它不持久化到 Vault 或 Obsidian 工作区，不会在重启后还原可能已经过期的局部子图。新全局搜索和 Reset 会清空历史，明确开始新的探索分支。

## 12. L5.5 补充：事实关系与显示关系必须分层

### 12.1 两种关系不能混为一谈

语义图谱中的候选关系有模型、规则和相似度三种来源。候选的 `confidence` 不是用户确认，也不是掌握度证据；把它直接写成 confirmed relation 会污染后续 Mastery、考试和跨项目数据契约。

本项目因此把读取模型分为两层：

~~~text
SemanticGraphState
  ├─ decision log → project() → effective relations（学习事实）
  └─ 候选 + display policy → projectAutoDisplayRelations()（仅视觉提示）
                              ↓
                     LearningGraphProjection
                     trust = confirmed | automatic | structural
~~~

`automatic` 边不会持久化。候选一旦被确认，effective edge 以 `confirmed` 出现，自动边随即排除；候选一旦被拒绝，也不会继续展示。这个优先级同时避免同一关系双线重复，并保证用户决策永远覆盖模型建议。

### 12.2 为什么默认模型阈值是 0.95，而不是 0.70

模型置信度没有跨模型、跨 prompt 的统一校准含义。当前 Vault 的候选分布中，0.70 会带来大量模型候选，视觉上接近“几乎全部连线”；这会掩盖真正可信的结构，也会让用户误以为插件已经确认它们。

因此 Lite 默认把模型阈值定为 0.95：它是保守的视觉提示起点，而非事实判断阈值。规则 `same_as` 候选可单独显示，因为它来自相同的规范化名称；embedding similarity 默认关闭，因为“相似”不等于“同义或存在知识关系”。用户可在设置中显式调整这些显示策略，但任何设置都不会改变事实层。

### 12.3 为什么 cache key 必须包含 source revision

仅把 `LearningGraphQuery` 序列化为 cache key，会产生一个典型的 UI 一致性漏洞：用户保持同一搜索条件确认关系，query 未变，旧投影却继续返回。事件通知一般会调用 `invalidate()`，但不能把正确性完全交给每一条未来调用链。

`SemanticGraphService.getLearningMapRevision()` 组合 state 的时间戳、concept/candidate/decision 数量与自动显示策略。`LearningGraphQueryService` 把该 revision 与规范化 query 一起作为 cache key。于是即使只是 Setting 页保存了阈值、或决策在同一个时钟 tick 内连续写入，下一次读取也会建立新的投影。缓存仍然存在，但不能跨越事实或显示策略版本。

### 12.4 Canvas 而不是复用 Obsidian 内部 GraphView

Obsidian 的公开插件类型中没有可注入自定义概念节点与边的 `GraphView` API。复用内置 GraphView 的私有实现会把 VaultCoach 绑定到未承诺稳定性的内部 DOM/数据结构，版本升级时容易失效，也无法区分 confirmed、automatic 和 user relation。

因此 renderer 使用浏览器原生 Canvas 2D：没有第三方图库和额外 bundle 依赖，画布只接收已裁剪的 `LearningGraphProjection`。固定调色板（暗背景、蓝色 confirmed、紫色 automatic、青色 user）不依赖用户主题色，确保状态含义不会被主题覆盖。边箭头绘制在目标节点圆周前，方向语义仍由领域 relation 的 `source → target` 决定，而不是由布局猜测。

### 12.5 动画与复杂度预算

Canvas 的力导向 simulation 每次创建或明确 reheat 时最多运行 96 帧，然后停止。它对当前 projection 做 O(V²) 排斥、O(E) 弹簧计算；默认 150 节点适合 Lite 交互，完整模式虽允许 500 节点但仍受硬上限约束。动画期间节点会自然 settle，停止后坐标稳定，用户拖动节点会将其 pin 住，后续 simulation 不会再拉回。

这只是显示层计算：不读取文件、不调用 embedding、不执行候选两两比较。超过 500 节点或 2,000 边时，页面不提供“全部”按钮，改以搜索和邻域投影保护主线程；更大规模的全图布局应由后续 Knowledge Engine 提供。

### 12.6 本次修复的测试策略

1. `SemanticGraphProjector` 测试自动关系的候选选择与确认/拒绝优先级；
2. `LearningGraphQueryService` 测试 `automatic` trust、开关过滤和 revision 引起的重新读取；
3. 设置测试验证本地显示策略的保存和阈值钳制；
4. Canvas layout 测试验证相同输入得到相同坐标、节点留在安全边界且具有二维分布。

最终验证使用 `npm run build` 与 `npm test`，共 44 个测试文件、159 项测试。提交前还应运行 `npm run lint` 与 `git diff --check`。

## 13. L5.5 布局复盘：degree 不只是排序依据

### 13.1 只做全局排斥为什么不够

普通 force layout 给每一对节点相同的最小距离、给每条边相同的目标长度。对于低 degree 图足够；但语义候选图会出现 hub：一个概念连接许多自动候选，数十条线从同一个点射出。若仍按普通节点处理，弹簧会把邻居拉到 hub 周围，标签和箭头最终堆叠，即使节点圆形本身没有精确重合也不可读。

本实现的 degree 是当前投影中入边与出边的总数。它只服务布局，不回写 Concept/Relation，也不会影响关系置信度：

~~~text
degree(node)
  → visual radius（高连接点略大）
  → invisible collision radius（hub 周围留白更大）
  → desired edge length（hub 的边更长）
~~~

这样 hub 仍在局部结构的视觉中心，但它的关系扇区有空间展开；不是简单把 hub 和所有叶子挤在画布中心。

### 13.2 碰撞约束要有直接修正

仅靠力会受到阻尼、边界和弹簧拉力影响，密集星形图在有限迭代后仍可能留下重叠。每步积分后，本 renderer 进行两轮 pair-wise positional separation：若距离小于双方 layout radius 与安全间距之和，就将两个非固定节点沿连线反方向推开并重新钳制到画布边界。

这不是语义上的 N×N 概念比较，而是已受 150/500 节点预算约束的显示层 O(V²) 计算。它不使用 embedding、不触发 I/O，且有自适应 iteration budget。500 节点模式的迭代次数会显著小于 150 节点概览，避免打开 View 时冻结。

### 13.3 为什么取消打开时的位移动画

“有动态效果”不应等同于“页面加载后节点大范围移动”。首帧先完成确定性 solve，用户每次打开看到相同空间结构；悬停、选中、缩放、平移和拖动仍提供互动反馈。自动候选边也保持较低透明度，箭头只在被关注时显示，避免让候选建议视觉上压过 confirmed fact。

测试通过的两个关键不变量是：同一输入得到相同位置；高 degree hub 到最近叶子的距离保持在安全值以上。它们分别防止重新打开跳动和关系扇区塌缩再次回归。

## 14. L5.5 深化：从单一力图到知识星系

### 14.1 Canvas 是窗口，不是坐标边界

矩形 Canvas 只能限制用户看到的像素区域，不应限制图谱的世界坐标。把所有节点 `clamp` 到 `0..width / 0..height` 会在密图中人为压缩外围节点，最终形成矩形云团。现在布局世界坐标没有边界；【适配视图】根据所有节点的 bounds 计算 transform，平移与缩放只改变观察位置。

### 14.2 无监督社区近似

完整 Leiden/Louvain 社区发现对 Lite renderer 来说不必要，且会引入更多迭代、依赖或非确定性。当前采用可解释的 hub-seeded community approximation：

~~~text
degree 排序 → 选择彼此尽量超过两跳的 hub
            → 多源 BFS 分配最近 hub
            → 每个 hub/community 形成一个 galaxy
            → 跨 community 边保留为星系间桥
~~~

它不宣称发现严格的图论最优社区；目标是给用户一个稳定的阅读空间：高连接概念成为视觉中心，与它最直接相关的概念聚在周围，多个核心通过较长桥接边区分开。相同 projection 使用稳定 ID 排序和确定性初始坐标，因此结果可复现。

### 14.3 degree 同时决定三种视觉尺度

degree 不只用于选择 hub：

| 使用点 | 效果 |
| --- | --- |
| 节点半径 | 高连接概念更醒目，用户可快速识别知识枢纽。 |
| 碰撞半径 | 为 hub 的多条箭头及邻域留下更大空白。 |
| 同社区边长度 | hub 与叶子不被弹簧拉进同一个小圆，关系扇区更清晰。 |

跨社区边使用更长、更弱的弹簧；社区中心使用很轻的椭圆锚定力。两者共同避免“所有关系一股脑拉向中心”的矩形团块，同时不会把跨星系关系隐藏掉。

### 14.4 Hub 的视觉倍率

degree 进入平方根映射而不是线性映射：低 degree 的节点不会因一两条关系突然变成大圆，高 degree hub 仍能明显放大。本轮把额外半径上限从 18 提升为 32，并加入“degree 25 相比 degree 0 至少大 30”的回归断言。碰撞留白以此显示半径为基础同步增加，保证视觉重点不会换来重叠问题。

## 15. L5.5 交互密度与证据渐进披露

### 15.1 触控板 wheel 不是离散按钮

鼠标滚轮常产生较少、较大的 line delta；触控板会产生大量小的 pixel delta。为两者使用固定比例会导致后者累积成暴冲缩放。现在将 delta mode 归一化后使用指数缩放：单次增量的实际影响与移动距离连续相关，并在极大 delta 时钳制。世界坐标会围绕光标位置保持不动，用户在某个星系上缩放时不需要重新寻找目标。

### 15.2 为什么证据不应常驻图谱页

图谱的主任务是识别结构与选择节点；长 Markdown 摘要属于阅读任务。将全部证据正文放在右侧检查器会同时压缩 Canvas 宽度和抢占垂直空间，尤其在知识库段落较长时让图谱退化为狭窄缩略图。

因此检查器采用渐进披露：默认只保留选择节点所需的最小结构信息；来源被规范化为去重的 `filePath + heading` 项，用户点击【证据来源（N）】才看到菜单并打开原笔记。该方案不复制证据文本，不新增 Store，也不改变证据的可追溯性。

## 16. L5.5 视觉焦点与连续标签层级

### 16.1 Hover 必须覆盖 Selection 的局部强调

选择状态用于固定检查器上下文；悬停状态用于快速比较。若渲染器始终让 selected node 作为唯一 active node，用户选中 A 后悬停 B 时，B 的邻域仍会被 A 的淡化规则压低，无法进行比较。

渲染器现在按 `hoveredNodeId ?? selectedNodeId` 选择临时 active node。选择仍保留在检查器和节点颜色中；悬停 B 时，B 与一跳邻居使用高亮圆、glow、较粗关系线和完整标签，离开后再恢复 A 的视觉焦点。这是纯 render state，不会改变图谱事实或选择数据。

### 16.2 标签不是二元开关

概览需要隐藏标签，局部阅读需要显示标签。单一缩放阈值会造成“放大一点仍然没有、再一点突然全部出现”的认知跳变。使用 smoothstep 将 0.82 到 1.50 的 zoom 映射为 alpha：越接近阅读尺度，越多非局部标签逐渐可见；选中/悬停邻域则无条件显示。深色描边和较高字体权重让文字不受深色边线干扰。

### 16.3 图例应复用视觉语言

文字描述“蓝色实线”要求用户在文字与图中做额外映射。图例改为与 Canvas 相同的实线、虚线图示：蓝线代表 confirmed、青线代表 user、紫色虚线代表 automatic。标签仍说明事实状态，但颜色通过图示本身传达。

## 17. L5.5 沉浸式控制层与屏幕空间标签

### 17.1 世界空间与屏幕空间的分工

节点、边和布局在世界空间中绘制，随 transform 缩放；文字若使用相同字体单位，也会在放大时无限变大。标签改为在 transform 内使用 `screenFontSize / currentScale` 的字体大小，因此经 Canvas scale 后仍保持固定屏幕字号。这样 hover 标签在缩小全图时可正常阅读，深度放大时也不会遮住邻近节点。

标签透明度仍由 zoom smoothstep 控制：非焦点标签逐步显现，focus neighbourhood 无条件显示。深色描边使用同样的 inverse scale，避免在缩小/放大时变得模糊或过厚。

### 17.2 为什么工具应覆盖在画布内

图谱用户的主要视线在画布，连续的标题、统计、筛选器和告警横幅会把有效可视区域切成多段。当前控制层采用绝对定位的 HTML 按钮，Canvas 仍是唯一大面积内容区：

- `i` 按需打开统计与状态；
- 搜索使用按需 popover，而不是常驻输入框；
- Display/Filter 用 Obsidian `Menu` 的 checked 项表达当前开关；
- 原有的适配、返回、重置、完整图功能以图标按钮保留，不丢失功能。

这种 overlay 不进入 Canvas 的世界坐标，因此缩放/平移不会导致工具漂移；它也不改变 graph projection、决策或任何持久化状态。

### 17.3 缩放与状态切换

最小缩放放宽到 0.1、适配下限到 0.12，解决星系布局在当前窗口无法看到全貌的问题。自动边提高了颜色 alpha 和默认绘制 alpha，使低置信候选在深色背景仍可追踪。再次点击 selected node 清除 selection，是纯 Presentation state 切换，不会撤销关系或改变任何图谱事实。

## 18. L5.5 原生式图云：标签、来源结构与稳定空间

### 18.1 标签应是屏幕空间，而不是世界空间

Canvas 在绘制节点时已经应用了 `transform.scale`。若字体也直接使用世界坐标单位，用户放大图谱时字体会和节点一起无限增长；若把字体做得很小以避免该问题，全图视角又无法阅读。正确的折中是：

~~~text
Canvas 最终标签字号 = transform.scale × (screenFontSize / transform.scale)
                        = screenFontSize
~~~

普通标签取 20px，悬停、选中和一跳邻域取 24px；普通标签仍只在缩放到阅读尺度后以渐进透明度出现。这样全图不会被文字淹没，而用户把指针放在节点上时可获得接近原生图谱的稳定、清楚说明。

### 18.2 来源结构不是概念关系

Concept 节点和 confirmed/user/automatic relation 属于知识语义层；文档、章节和标签节点及其边属于来源追溯层。二者不能共享同一种颜色或被误认为掌握度事实。因此图例明确分为：蓝色概念圆点、灰色来源节点、蓝色/青色/紫色语义关系，以及带方向箭头的灰色来源连接。来源结构仍仅由显示开关控制，且不会参与 degree 的业务意义、掌握度或考试计算。

### 18.3 为什么从“椭圆环”改为“向日葵圆盘”

把所有社区中心均匀放到一个椭圆周上，会让每个 disconnected component 都被固定在外围。较多小组件出现时，主图像一个空心圆，桥接边也会过长。新算法以 degree 排序的 hub 为序，使用黄金角螺旋和平方根半径把中心填满：

~~~text
hub[0] → 圆心
hub[i] → maxRadius × sqrt(i / (count - 1))
angle  → i × goldenAngle + small deterministic jitter
~~~

平方根半径使圆盘面积近似均匀填充，稳定的小扰动避免完全规则的同心圈。局部社区锚定、跨社区较短弹簧与极弱全局向心力共同约束空间；它们是软力，不是画布边界，因此用户仍能平移、缩放与拖动固定节点。

### 18.4 固定高度比内容驱动高度更适合检查器

检查器的功能是提供当前选择的摘要，而非承载长证据正文。若容器高度依内容变动，首次选择节点会使整张图向上或向下跳动。固定约四行高度后，未选择、选择节点、选择关系三种状态共享同一个 layout slot；简介截为两行，证据列表改由按钮菜单按需打开。这是“渐进披露”与稳定空间的组合，不丢失来源跳转能力。

## 19. 让 Canvas 标签与 CSS 图例精确同尺度

“固定 16px”只在 Canvas 的 CSS 宽度恰好等于内部逻辑宽度时才等于页面上的 16px。插件画布会随 split pane 改变宽度，浏览器会把内部 `920` 坐标压缩或放大到实际 CSS 宽度；因此同一 Canvas font 在窄栏中会显得更小。图例则是正常 DOM 文本，使用 `0.78rem`。

本实现把图例的目标 CSS 像素 `rootFontSize × 0.78` 转换为 Canvas 世界单位：

~~~text
worldFont = (rootFontSize × 0.78) × (logicalCanvasWidth / displayedCanvasWidth)
drawFont  = worldFont / graphTransform.scale
~~~

最后一次 Canvas scale 与前面的除法抵消，浏览器把 Canvas 压缩到显示宽度后，用户实际看到的字号仍是 `0.78rem`。这比猜测“20px 或 24px 看起来合适”更可靠，并会自然遵从 Obsidian 的界面字体大小设置。

## 20. L5.6：为什么定向考试必须退化为来源文件范围

Learning Map 中的 Concept 是 M3 的 effective semantic fact，而当前 ExamEngine 的可靠输入仍是已索引的文件和 chunk。直接把一个 Concept label 或 alias 丢给题目生成模型，会出现三类不可审计风险：同名概念可能对应多个实体、别名可能跨文件歧义、模型也可能从范围外资料补全问题。

所以 L5.6 使用一条可追溯的降级链：

~~~text
effective Concept
  → sourcePaths + Concept evidence 的 Markdown/PDF 文件路径
  → 去重、排除空路径与永久规则排除项
  → ExamController 的明确 file scope
  → 既有 ExamScopeService / ExamEngine
~~~

`forceIncludedFilePaths` 的含义仅是“用户从图谱明确选择的文件不能被智能内容画像悄悄移除”；它不能绕过永久排除规则，也不突破当前知识库索引范围。其他文件被写入内存中的 manual exclusion，考试 setup 会显示文件管理器，用户可恢复或扩大范围。此状态不保存到图谱、不写到设置，在下一次普通考试操作时仍由用户控制。

这使“按此知识考试”成为一个可靠入口，而非对未来自适应考试的虚假承诺。真正按 Mastery、前置关系、复习到期和历史覆盖选择 Concept 的算法必须等待 L6 的版本化 `ExamPlan`。

### 20.1 UI 选择必须与实际 Scope 一致

仅使用“全库 + 排除非来源文件”可保证 ExamEngine 的最终 chunks 正确，却会让目录选项仍显示为全库，用户自然会认为功能没有定位到 Concept 来源。修复采用最深共同目录：在现有 folder scope 中筛选能包含每个来源路径的目录，并按路径长度逆序取第一个。若来源都在 `notes/database/`，该目录会被选中；若来源分布在不同根目录或包含根目录文件，则没有可表达的共同 folder scope，才显式使用全库回退。

目录范围只负责表达用户可见的起点；同目录中的非来源文件仍进入 manual exclusion，因此“目录正确”不会牺牲“文件精确”。

## 21. 画布的可用空间不等于固定纵横比

图谱容器是 flex item，主工作区变高时它可以增长；Canvas 若只设置宽度与 `aspect-ratio`，则其 CSS 高度只由宽度决定，剩余容器空间不会被画布占用。背景颜色相同会掩盖这个事实，但坐标系、节点和边确实在较矮的 Canvas 中结束了。

Canvas 改为显式填满父容器。renderer 的逻辑坐标保持 `920 × 640`，但 pointer 事件已使用 `rect.width` 与 `rect.height` 分别换算，因此 CSS 纵横比变化只改变最终显示比例，不会将点击位置映射到错误节点。`fit()` 仍按照完整世界 bounds 计算中心和缩放，故额外高度会用于显示更多垂直图空间。

## 22. “完整”应是硬上限内的默认，而非隐藏操作

150 / 300 是为了保护大图而设置的概览预算，却不应迫使中小 Vault 用户先发现一个图标按钮，才能看到自己的全部知识。现在初始 projection 使用 renderer 已有的 500 节点 / 2,000 边硬上限：这是可预测的 local Canvas 成本边界，而不是无界图谱承诺。用户仍可主动切回概览；超过硬上限时继续显示截断说明，并不伪装成可完整展示。

## 23. CSS 盒子、Canvas backing store 与世界坐标必须同步

Canvas 有三层尺寸：CSS 盒子的显示宽高、`canvas.width/height` 的 backing store 像素，以及 renderer 用来进行 `fit()`、平移和命中测试的逻辑 viewport。只修改 CSS 高度会让前两者的 X/Y 映射不一致：圆形经非等比缩放变为椭圆，而逻辑世界仍认为自己只有旧高度。

当前 renderer 使用 `ResizeObserver` 监听画布 CSS 尺寸，并按以下顺序同步：

~~~text
actual CSS width / height
  → logical viewport width / height
  → backing store = viewport × devicePixelRatio
  → fit() 重新计算统一 scale 与中心
  → pointer / pan / zoom / grid 统一使用新 viewport
~~~

节点仍在世界空间中用统一 `context.scale(scale, scale)` 绘制，故半径不会因容器比例变化而变形。容器变高后，`fit()` 能使用真实垂直边界容纳完整图；它不会重新运行力导向模拟，因此不会引入重新打开时的随机跳动。

## 24. L5.7：工作区状态不是图谱事实

Obsidian 工作区会为每个 `ItemView` leaf 保存 `getState()` 返回的数据。Learning Map 利用这项机制保存用户的阅读上下文，而不是创建新的 VaultCoach 数据文件。状态 schema 包含 query、focus history、选中项和 pinned node positions；它不包含 Concept、Relation、Mastery score、Assessment 或 source evidence。

只持久化 pin 而不持久化全部节点坐标有两个好处：

1. 未被用户手动调整的节点仍从当前 projection 的确定性 layout 得到位置，图谱事实变化后不会恢复一组过期的全量坐标。
2. 用户明确拖动的节点不会在 refresh 或重开 leaf 后丢失；若 Concept 已被删除，则恢复时自然忽略其 pin。

所有 workspace state 都必须视为不可信输入。恢复过程会检查版本、限制 history 数量，过滤无效 relationship type、非字符串选择 ID、非有限坐标和不在当前投影的节点；损坏状态退化为默认学习图，而不是阻断插件加载。

## 25. Canvas 生命周期的三类资源

Canvas 组件没有网络或业务 timer，但仍有三类需要显式回收的 Presentation 资源：Canvas DOM/event closure、`ResizeObserver` 和 search popover 的延迟 focus timer。前两者由 renderer `destroy()` 与 DOM 清理释放；View 在关闭、刷新失败和重绘前调用 destroy。后者由 View 保存 timer id 并在任何重新渲染/关闭前 `clearTimeout`。

异步读取还需要 revision guard：每次 refresh 递增 revision，Promise 解析后只有 revision 仍匹配且 View 未关闭才可更新 DOM。这样文件事件密集到来、用户关闭标签页或快速重开时，旧请求既不会重建已经销毁的 renderer，也不会覆盖更新后的投影。

## 26. 来源结构、证据与学习关系必须分层

学习图的节点并不全是学习事实。文档、章节和标签是确定性解析得到的来源结构；Concept 与 Concept 之间的边才是已确认、用户创建或满足阈值的自动语义关系。因此图例使用不同的节点符号：蓝色空心圆为 Concept，灰色实心圆为文档/章节，橙色实心圆为标签；灰色箭头是来源结构边。

Concept 当前通过 `evidence` 保存其出处，而没有在完整视图中画出 `Concept → Section` 边。这是一个刻意的可读性/性能取舍：一个概念可能由多个 section 佐证，一个 section 也会支持多个概念，完整展开会以多对多的 provenance 边主导图形布局，并让用户误把“出现在同一笔记里”理解为“存在学习关系”。

若未来需要在画布追溯，应定义独立的 `evidenced_by` 只读边：它不能被确认、拒绝或用于掌握度传播；只在选中或聚焦 Concept 后的局部视图中展开，并设置每个 Concept 的证据节点/边预算。这样既能从概念回到来源，又不污染 Learning Map 的核心关系层。
