# 里程碑 5.8：知识域变更与派生数据生命周期技术说明

## 1. 为什么“缓存文件存在”不等于“缓存仍可用”

Vault Coach 会把可以从当前笔记重新计算的数据保存到本地：文本 chunk、向量、文档结构图、语义 Concept 图和掌握度快照。这样再次启动时无需重新读取全部 Markdown/PDF 或调用模型。

问题出现在插件关闭期间：用户可能删除原有资料，再向同一个 Vault 导入另一套资料。旧的 `index-snapshot.json` 仍然存在，但它描述的不是现在的知识库。若直接加载，会造成三种错误：

1. 问答检索到旧 chunk；
2. Learning Map/Dashboard 暂时展示旧领域的节点和掌握度；
3. 用户误以为新资料已经被索引。

因此 5.8 的原则是：**派生数据只有在能证明来源仍一致时才允许读取。**

## 2. Source inventory：低成本的一致性门

每次成功保存文本索引时，snapshot 都记录当前范围内文件的有序清单：

```ts
interface SourceInventoryV1 {
  schemaVersion: 1;
  scopeSignature: string;
  files: Array<{ path: string; size: number; modifiedAt: number }>;
  fingerprint: string;
  generatedAt: number;
}
```

它的工作方式：

1. 从当前扫描范围获得 `TFile`，仅使用路径、大小和 mtime；
2. 按路径排序，计算稳定 fingerprint；
3. 启动时再次生成一份 inventory；
4. 仅当 settings signature 和 inventory 都匹配，才 hydrate text/vector/graph/semantic/mastery。

它不是内容安全哈希。保留 `size + mtime` 的原因是启动轻量：无需读取全文，也不需要把资料发给任何模型。真正重建时仍由内容 hash 与解析结果决定最终 chunk。

旧版本 snapshot 没有 inventory 时，采取保守策略：不恢复派生读模型，提示用户重建。这比“假定旧快照仍正确”更安全。

## 3. 如何区分普通修改和疑似换域

以路径为键比较前后 inventory：

| 情况 | 结果 |
| --- | --- |
| 新清单独有 | added |
| 旧清单独有 | removed |
| 同路径但 size/mtime 变化 | modified |
| 路径、size、mtime 相同 | unchanged |

`changedRatio = (added + removed + modified) / max(oldCount, newCount, 1)`。

- 普通不一致：`source-sync-required`；
- `changedRatio >= 0.70`，或双方都有文件但共同路径为 0：`possible-domain-switch`。

阈值只决定提示强度，不会触发自动删除。离线重命名会被视为删除 + 新增；因此它可能提高比例，但不会让插件删除用户数据。

## 4. 两阶段恢复为何比“检测后立刻删文件”更稳妥

### 阶段 A：安全隔离

发现不一致时，运行时不加载旧 snapshot，也不加载 M2/M3/M4 派生读模型。旧文件可以暂时留在磁盘，以便用户取消或排查重建；但是它们不会进入问答、考试范围、Learning Map 或 Dashboard。

### 阶段 B：用户明确重建

用户点击重建后，按顺序完成：

```text
当前文件 → Text chunk → Vector shard → Deterministic graph
                                 ↓
                    semantic source reconciliation
                                 ↓
                     clear Mastery snapshot
                                 ↓
                   写入新 Source inventory（解除 gate）
```

`semantic source reconciliation` 不调用 LLM 或 embedding 模型。它只保留仍与当前 `sectionId + inputHash` 对齐的抽取记录，再从这些记录重新派生 Concept、候选和 embedding。新 Section 的概念抽取必须由用户显式执行语义图重建，符合“离线变化不会自动把笔记发送给外部服务”的隐私约束。

Assessment Session、考试报告、聊天与长期记忆不是可再生缓存，所以不在此流程中删除。

## 5. 为什么语义 embedding 使用 Float32 binary shard

JavaScript JSON 会将每个浮点数编码成多个字符；768 维向量写成 `number[]` 时，磁盘体积和解析开销都明显高于其原始二进制表示。

Float32 的成本可近似为：

```text
conceptCount × dimension × 4 bytes
```

例如 1,000 个 768 维 Concept 向量约为 `1000 × 768 × 4 ≈ 2.93 MB` 原始数据；JSON 通常远大于此值。

现在 JSON 元数据只保存 `conceptId`、模型签名、输入 hash、更新时间、维度和 binary path；向量本体按顺序写入 `.bin`，加载时根据 `index × dimension` 切片恢复。

### 内容寻址与 manifest 提交顺序

不能把每次更新直接写到固定的 `vectors.bin`：如果写到一半中断，旧 manifest 仍指向该文件，却读到半新半旧内容。

正确顺序是：

```text
write new content-addressed .bin
  → write metadata JSON
  → commit manifest last
  → delete unreferenced old shards
```

文件名 hash 包含向量实际值而非仅 metadata。原因是同一输入在模型升级、非确定性服务或异常重试下可能得到不同数值；若路径复用，就可能覆盖旧 manifest 正在使用的 shard。

## 6. GC 的白名单原则

语义 GC 只处理 `.vault-coach/graph/semantic` 中可精确识别的路径：

- `sections/<hex>.json`
- `concepts/<hex>.json`
- `candidates/<hex>.json`
- `embeddings/records-v1.json`
- `embeddings/vectors-<hash>.bin`
- `decisions-v1.json`

`.tmp`/`.bak` 是原子 JSON 写入的恢复材料，GC 不会抢先删掉。它也不会递归删除 `.vault-coach` 根目录，因此不会误伤 Assessment、导出或用户文件。

## 7. 人工治理为何单独重置

确认/拒绝关系、概念合并、别名和手工关系表达用户判断，不应因一次普通文件修改被悄悄删除。来源对齐后，指向不存在 Concept 的旧 decision 会保留在 audit 中，但不再影响有效图。

当用户确认 Vault 主体已经换域时，可以使用命令面板中的 **重置语义图谱人工决策**。确认框先展示 decision 数和当前受影响 Concept 数，确认后只清空治理 overlay；抽取、embedding、考试记录和原始笔记都保留。

## 8. Storage footprint 的边界

命令面板中的 **查看 VaultCoach 派生数据存储用量** 只读统计 VaultCoach 已知数据根，按文本索引、向量、结构图、语义事实、语义向量、Mastery、Assessment 与隐藏考试报告分组。

手动导出到任意用户自选文件夹的 Markdown 不会被扫描：插件既不应遍历用户全部 Vault 来猜测哪些文件属于导出，也不应将这种诊断变成文件清理器。该限制会在 UI 中明确说明。

## 9. 新人排查清单

1. Learning Map/Dashboard 显示“需要更新”时，先看 `sourceInventoryStatus`，不要先怀疑渲染器。
2. 重建后语义图没有新概念是预期行为：来源对齐不会调用模型；执行“重建语义概念图谱”。
3. 磁盘空间异常时，先打开 storage footprint；若 semantic embedding 远大于预期，检查 Concept 数量、维度与是否存在遗留旧版 shard。
4. 不要用宽泛的 `rmdir('.vault-coach', true)` 作为修复方案。Assessment 和用户历史在其中。
5. 如果修改 manifest/schema，必须保留旧 JSON embedding 的读取路径，并验证下一次写入会安全迁移到 binary shard。
