# 里程碑 3：语义概念图谱技术说明

## 1. 本文目标

这是一份给新开发者的培训资料。它不只说明“代码在哪里”，更说明为什么项目要这样设计、哪些看似简单的方案会在真实 Vault 中失效，以及后续改动时不能破坏哪些边界。

阅读本文后，应能回答：

1. 为什么 M2 的结构图谱不能直接扩展成“模型说什么就存什么”的图谱；
2. 为什么概念抽取以 Section 而不是全文或单个 Chunk 为单位；
3. 为什么相似概念不能做全量 `N × N` 比较；
4. ANN、Top-K 与本项目 LSH 实现分别解决什么问题；
5. 用户确认、拒绝、合并为什么必须与模型候选分层保存；
6. 如何安全地调试、测试和替换语义图谱中的组件。

## 2. 项目背景：从“结构事实”到“语义候选”

里程碑 2 已经实现了确定性知识图谱。它只使用可以从 Vault 和 Obsidian metadata 直接证明的事实：

```text
Document / Section / Tag
contains / links_to / embeds / tagged_with
```

例如，笔记 `a.md` 链接 `b.md`，这是可重建的结构事实；不需要模型猜测。因此它被保存在：

```text
.vault-coach/graph/graph-snapshot-v1.json
```

这份快照必须保持确定性：相同 Vault 输入应得到相同节点、边和排序。它也是文本索引、问答和考试能够继续稳定工作的基础。

语义概念图谱解决的是另一类问题。例如，模型可以从不同笔记中提出：

```text
“RRF” 可能是 “Reciprocal Rank Fusion” 的别名
“检索” 可能用于 “排序”
“向量检索” 可能是 “混合检索” 的前置知识
```

这些并不是确定事实，而是 **候选（candidate）**。它们受模型版本、提示词、语言、上下文以及用户理解影响。因此，M3 不能污染 M2 快照，而是使用独立目录：

```text
.vault-coach/graph/semantic/
├── semantic-manifest-v1.json
├── sections/       # Section 抽取结果分片
├── concepts/       # Concept 分片
├── candidates/     # 关系候选分片
├── decisions-v1.json
└── embeddings/     # 可重建的 Concept embedding 缓存
```

核心原则是：

```text
确定性结构事实（M2）    ≠    模型候选（M3）    ≠    用户决策（M3）
```

## 3. 总体数据流

```text
当前 Document Index + M2 GraphSnapshotV1
                │
                ▼
   SectionExtractionInput（direct Chunk + E1/E2 证据映射）
                │
                ▼
      聊天模型：Concept / 受限关系候选
                │
                ├──────────────► Section extraction cache
                ▼
  SemanticConcept + model relation candidates
                │
                ├── 规则名称 / Alias 精确匹配
                └── Concept embedding → ANN Top-K → same_as candidates
                │
                ▼
      Candidate layer（默认不作为已确认语义）
                +
      用户 Confirm / Reject / Merge / Alias / Manual relation
                │
                ▼
      Effective semantic graph（Concept review 与未来 M4 消费）
```

相关代码位置：

| 责任 | 位置 |
|---|---|
| 领域类型与 schema | `src/domain/semantic-graph/semantic-graph-types.ts` |
| 名称归一化、候选指纹 | `src/domain/semantic-graph/` |
| 投影与完整性检查 | `semantic-graph-projector.ts`、`semantic-graph-integrity.ts` |
| Section 输入与模型抽取 | `src/app/semantic-graph/section-extraction-input.ts`、`concept-extraction-service.ts` |
| 调度、相似性、主服务 | `src/app/semantic-graph/` |
| JSON 分片持久化 | `src/infrastructure/storage/json-semantic-graph-store.ts` |
| 审核视图 | `src/presentation/views/concept-review-view.ts` |

## 4. 为什么以 Section 抽取概念

### 4.1 三种粒度的比较

| 粒度 | 优点 | 问题 | 结论 |
|---|---|---|---|
| 全文档 | 上下文最完整 | 长文超上下文、调用昂贵、证据难定位 | 不使用 |
| 单个 Chunk | 输入短、易处理 | 标题语义丢失、同一概念被重复抽取 | 不作为语义单元 |
| Section | 有标题上下文、正文范围明确、可定位 Chunk | 超长 Section 需分窗口 | M3 使用 |

M2 的 `SectionGraphNode` 已拥有稳定 ID、标题路径、文档路径和 **直接拥有的 `chunkIds`**。M3 利用它避免再次发明一套文档结构。

### 4.2 direct Chunk 的含义

父标题通常包含多个子标题。若父 Section 把所有后代 Chunk 都发送给模型，会有两个问题：

1. 子标题正文会在父、子两个 Section 中被重复抽取；
2. 一个概念的证据归属变得含混，无法回答“它到底出现在哪一节”。

因此 `createSectionExtractionInputs()` 只读取当前 Section 的 `chunkIds`，不递归合并子 Section。没有直接正文的标题仍会保留在 M2 图中，但不会生成无证据 Concept。

### 4.3 Excerpt 映射与可追溯性

模型不会直接返回任意文本位置，而只能引用输入中的编号摘录：

```text
Document: notes/retrieval.md
Section: Retrieval > Ranking

E1 [chunk-101]: RRF combines ranked lists ...
E2 [chunk-102]: Ranking selects the final evidence ...
```

模型输出必须是严格 JSON：

```json
{
  "concepts": [
    {
      "name": "Reciprocal Rank Fusion",
      "aliases": ["RRF"],
      "description": "一种按排名融合多个检索结果的方法。",
      "source_excerpt_ids": ["E1"]
    }
  ]
}
```

代码会把 `E1` 还原成 `sectionId + chunkId + locator + inputHash`。如果模型引用了不存在的 `E9`、漏掉证据、增加未知字段或返回自由文本，结果会被拒绝，不会写入 JSON Store。

### 4.4 超长 Section 的窗口化

模型输入不是无限的。一个 Section 过长时，输入按 **Chunk 边界** 切为连续窗口，而不是按字符硬切：

```text
Section S
├── Window 1: Chunk 1, Chunk 2
├── Window 2: Chunk 3, Chunk 4
└── Window 3: Chunk 5
```

这样不会把一个 Chunk 从中间截断；每个窗口都有独立 `inputHash` 和 `E1...En` 映射。相同 Section 中名称相同的候选会在后续确定性合并中去重。

### 4.5 缓存为何需要 inputHash

抽取缓存不能只按 Section ID 命中，因为以下变化都可能使旧结果无效：

- Chunk 内容或顺序变化；
- 标题路径变化；
- prompt/schema 版本变化；
- 聊天模型或提供商变化。

所以缓存身份包含 Section、正文哈希和抽取器签名。这样修改一节笔记只会重跑对应 Section，而不是重跑整个 Vault。

## 5. Concept、候选与决策：为什么必须分层

### 5.1 Concept ID 不是显示名称

Concept 采用类似 `concept:<hash>` 的持久 ID。名称、Alias 和描述可以修改，ID 不应随之改变。这样未来 Assessment Event 或掌握度数据可以长期引用它。

注意：两个名字相同的 Concept 也不能自动合并。例如“网络”在不同课程中可能指计算机网络或神经网络。M3 让它们先作为不同的来源概念存在，最多生成 `same_as` 候选。

### 5.2 Candidate layer

模型、规则和向量近邻产生的边都先进入候选层：

```text
same_as / part_of / prerequisite_of / used_for / contrasts_with / related_to
```

其中模型关系必须有 Chunk 证据；关系类型白名单避免模型自由发明难以维护的 ontology。`same_as` 只是“可能相同”，绝不自动 merge。

### 5.3 Decision layer

用户操作不会改写模型 cache，而是追加决策记录：

```text
confirm-candidate
reject-candidate
merge-concepts
undo-merge
add-alias / remove-alias
create-manual-relation / remove-manual-relation
```

这样做有三个好处：

1. **可审计**：知道某条关系为何成立、谁确认过它；
2. **可逆**：合并不删除旧 Concept，而是建立 redirect；撤销合并可重新投影；
3. **抗重跑**：重新抽取不会覆盖用户判断。拒绝相同候选后，它不会反复在审核图中出现。

`SemanticGraphProjector` 负责把候选和决策投影为有效图。审核 UI 和未来 M4 只能消费这个投影，不能绕过它读取原始候选。

## 6. 为什么不能做 N² 相似度比较

### 6.1 朴素方案

最直观的相似概念计算如下：

```ts
for (const conceptA of concepts) {
  for (const conceptB of concepts) {
    cosineSimilarity(conceptA.vector, conceptB.vector);
  }
}
```

若有 `N` 个 Concept，需要大约 `N × (N - 1) / 2` 次比较：

| Concept 数 | 比较对数 |
|---:|---:|
| 1,000 | 499,500 |
| 10,000 | 49,995,000 |
| 50,000 | 1,249,975,000 |

若 embedding 维度为 768，一次余弦相似度需要约 768 次乘加。10,000 Concept 的朴素方案会造成数百亿级别运算；更糟糕的是，每次笔记变化都可能重复这项工作。这对本地 Ollama、移动端和 Obsidian 主线程都不可接受。

需要区分两件事：

- 为每个 Concept 生成一个 embedding 是约 `O(N)` 次模型输入；
- 把所有 Concept 两两比较是约 `O(N²)` 次向量比较。

M3 允许前者做批处理与缓存，但禁止后者作为默认路径。

## 7. ANN 是什么

ANN 是 **Approximate Nearest Neighbour，近似最近邻**。它回答的问题不是“找出全库绝对最相似的所有概念”，而是：

```text
给定一个新/变化的 Concept 向量，快速找到少量“很可能相近”的 Top-K 邻居。
```

“Approximate” 的意思是允许漏掉少量真实最近邻，换取显著更低的计算量和延迟。对于本项目，这个取舍合理，因为结果只是待审核候选；漏掉一条候选不会自动造成知识事实错误，而全量比较会拖垮插件。

### 7.1 Top-K 的作用

Top-K 是每次查询最多返回的邻居数。M3 将其限制在 `1–50`，默认值来自设置 `semanticGraphSimilarityTopK`。

这意味着新增一个 Concept 时，最多只产生有限数量的相似候选；即使知识库有 10,000 个 Concept，也不会因此生成 5,000 万条候选边。

### 7.2 阈值的作用

Top-K 只限制数量，阈值限制质量。M3 还要求：

```text
cosine similarity >= semanticGraphSimilarityThreshold
```

默认阈值为 `0.86`。阈值越高，候选越少但更保守；阈值越低，召回更多但审核负担更大。它只影响候选展示，不能替代用户确认。

## 8. 本项目的 ANN 实现：有界 LSH

### 8.1 为什么当前不直接引入 HNSW 库

HNSW（Hierarchical Navigable Small World）是常见且效果优秀的 ANN 方案。但给 Obsidian 插件直接引入一个实现需要额外评估：

- 是否纯浏览器/移动端兼容；
- 是否引入 Node 原生二进制依赖；
- bundle 体积、初始化内存和资源释放；
- 索引序列化格式的版本兼容性。

在没有引入不合规大依赖前，M3 采用一个可审计的 **有界 LSH（Locality-Sensitive Hashing，局部敏感哈希）** 实现：

```text
src/app/semantic-graph/concept-similarity-index.ts
BoundedLshConceptSimilarityIndex
```

它实现了 `ConceptSimilarityIndex` 端口，因此未来替换为 HNSW 不需要改动抽取、决策、存储或 UI。

### 8.2 LSH 的核心直觉

LSH 让相似向量更可能落入同一个桶（bucket），不相似向量更可能落入不同桶。查询时只比较同桶中的有限候选，而不是比较全库。

M3 的实现流程：

```text
Concept embedding
     │
     ▼
4 个确定性签名表，每表 12 个符号位
     │
     ▼
bucket key，例如：0:101101...、1:001011...
     │
     ▼
查询时取这几个 bucket 中的候选（总数硬上限 512）
     │
     ▼
只对候选计算余弦相似度，排序并返回 Top-K（最大 50）
```

关键点：

- LSH 不是“精确最近邻”，可能漏掉真实近邻；
- 若没有命中 bucket，返回空结果，**不会退化为扫描全库**；
- 即使某个 bucket 异常大，候选集合也被硬限制为 512；
- 向量先 L2 归一化，因此点积等价于余弦相似度。

这些限制正是避免 N² 计算爆炸的安全阀。

### 8.3 与 HNSW 的对比

| 项目 | 当前有界 LSH | 后续可替换 HNSW |
|---|---|---|
| 实现复杂度 | 低、易审计 | 较高 |
| 依赖 | 无额外依赖 | 通常需要专用实现 |
| 查询质量 | 依赖桶命中，可能漏召回 | 通常更稳定 |
| 构建成本 | 较低 | 中等 |
| 删除/更新 | 直接更新 bucket | 取决于实现 |
| 本项目适用性 | M3 候选 MVP | 大规模生产优化 |

替换 HNSW 时必须继续满足以下端口约束：

```ts
interface ConceptSimilarityIndex {
  upsert(items): Promise<void>;
  remove(conceptIds): Promise<void>;
  findNearest(vector, limit): Promise<ConceptSimilarityHit[]>;
  rebuild(items): Promise<void>;
  clear(): Promise<void>;
}
```

不能为了提高召回率而增加“LSH miss 时精确扫描全部 Concept”的回退逻辑；这会重新引入 N² 风险。

## 9. Embedding 缓存与增量更新

Embedding 不是事实，而是可重建性能缓存。每条缓存记录包含：

```text
conceptId
embedding provider / model signature
concept text hash
vector
updatedAt
```

只有 Concept 名称、Alias 或描述变化，或者 embedding 模型变化时，才重新生成向量。Section 变化的增量路径是：

```text
文件变更
  → M2 增量文本/结构同步
  → 受影响 Section 重抽取
  → 受影响 Concept 重建或移除
  → 仅变化 Concept 重新 embedding
  → 仅变化 Concept 执行 Top-K ANN 查询
  → 更新局部候选与有效投影
```

因此，稳定的旧 Concept 不会因修改另一篇笔记而重新发送给 Ollama，也不会再次与全库所有 Concept 比较。

## 10. 隐私与失败隔离

语义图谱必须显式开启，原因是它会调用用户配置的模型：

- 使用 Ollama 时，内容发送到用户配置的本地地址；
- 使用 OpenAI-compatible 服务时，相同范围的内容会发送到该服务；
- 模型调用内容仅限 Section excerpt，或用于相似检索的简短 Concept 文本；
- `.vault-coach/graph/semantic/` 可能包含路径、标题、摘录、Concept、embedding 与用户决策，必须视为私有 Vault 数据。

失败隔离规则：

```text
语义抽取失败 / embedding 失败 / ANN 失败
        ↓
仅影响 SemanticGraph 状态与候选质量
        ↓
不得回滚或禁用 M2 图谱、文本索引、Ask、Exam、Assessment
```

例如 embedding 服务不可用时，模型关系和规则名称匹配仍然可以存在；相似候选会暂时减少。此时不应把错误修复为“全库精确比较”。

## 11. Concept review 的交互原则

大量概念不能要求用户逐条阅读长列表。因此审核视图只请求局部投影：

```text
搜索匹配的 Concept
+ 用户显式 Focus 的节点一跳关系
+ 有上限的待确认候选
```

它不应默认向 DOM 或 SVG 传递整个 Vault 图。当前默认最多渲染 36 个局部节点，并使用可拖拽、可平移、可缩放的力导向布局。普通点击只选择节点，不会改变当前投影或重置视图；用户可通过 **Focus local neighbourhood** 明确切换局部簇，并用 **Reset local graph** 返回默认投影。关系含义为：

| 显示 | 含义 | 可做操作 |
|---|---|---|
| 虚线边 | 未确认 candidate | Confirm、Reject、查看证据；通过 Recent reversible changes 撤销 |
| 实线边 | 已确认有效关系 | 查看证据；模型/规则关系可恢复为 candidate，手工关系可删除 |
| 多选节点 | 用户准备处理的局部簇 | Merge、手工关联 |

`part_of`、`prerequisite_of` 与 `used_for` 是有向关系，在 SVG 中显示箭头；`same_as`、`related_to` 与 `contrasts_with` 是无向关系，不显示箭头。所有撤销均追加新的 Decision，而不覆盖旧记录。合并不会删除旧 Concept。旧 ID 通过 redirect 指向 canonical Concept，保留历史证据与未来 Assessment 引用的可追溯性。

## 12. 新开发者调试清单

### 12.1 先看哪个文件

1. M2 图谱是否存在：`.vault-coach/graph/graph-snapshot-v1.json`；
2. M3 manifest 是否存在：`.vault-coach/graph/semantic/semantic-manifest-v1.json`；
3. manifest 指向的 Section/Concept/candidate 分片是否可解析；
4. Concept 是否有 `evidence`，并且证据 Chunk 是否仍在当前索引；
5. UI 展示的是 candidate、decision 还是 effective relation。

### 12.2 常见问题

| 现象 | 优先检查 |
|---|---|
| 没有任何 Concept | 功能是否开启、M2 快照是否存在、Section 是否有 direct Chunk、聊天模型是否返回合法 JSON |
| 模型有回答但没有结果 | 是否引用有效 `E1...En`、是否包含未知字段或关系类型 |
| 没有相似候选 | embedding 模型是否可用、阈值是否过高、LSH bucket 是否没有命中；这不应触发全库扫描 |
| 候选反复出现 | candidate fingerprint 是否稳定、Reject decision 是否正确保存 |
| 合并后关系异常 | 检查 redirect 是否形成环、是否用 `SemanticGraphProjector` 查询有效图 |
| 清除索引后仍有语义文件 | 检查 `SemanticGraphService.clear()` 与 `JsonSemanticGraphStore.clear()` 调用路径 |

### 12.3 自动化验证

```bash
npm ci
npm run build
npm run lint
npm test
```

M3 至少覆盖：

- direct Chunk / Section 窗口化；
- Concept 候选、关系证据与 schema 拒绝；
- LSH Top-K、删除和硬上限；
- candidate + decision → effective graph；
- 分片 JSON Store 不写入 M2 快照；
- 显式 rebuild 后的端到端候选与 Confirm 行为；
- domain/presentation/import 边界。

## 13. 修改前必须遵守的规则

1. 不要把 M3 节点或边写进 `GraphSnapshotV1`；
2. 不要让 `onload`、普通索引重建或 Ask/Exam 隐式调用语义模型；
3. 不要删除 evidence 来“简化” Concept schema；
4. 不要把 embedding 相似直接变成自动 merge；
5. 不要添加未受限的模型 relation type；
6. 不要为了改善 ANN 召回而加全库精确回退；
7. 不要让 presentation 直接读取 JSON Store、ANN 索引或模型 client；
8. 不要把 `.vault-coach/graph/semantic/` 提交到插件仓库。

遵守这些规则，才能让语义能力在大型 Vault 中保持可控，同时不损害当前插件最重要的本地优先、可解释和可维护边界。
