# 三个项目协同架构与责任边界

## 1. 决策摘要

项目不应在 **AI Career Agent** 中重新实现一套高性能 Vault Coach，也不应将 Knowledge Engine 永远限制为 Obsidian 的隐形后端。推荐目标是建立一个可独立部署、可被两个产品复用的 **Knowledge Engine**：它是高性能知识计算核心，也是用户可直接使用和验证的知识训练工作台。

它先以可抽取边界清晰的模块化单体实现，并有四种清晰的运行方式：

```text
A. Lite：仅 Vault Coach 插件本地运行
B. Engine Standalone：用户用 Docker 启动 Knowledge Engine GUI，独立导入资料和训练
C. Engine Connector：Vault Coach 显式同步授权副本到本机 Engine
D. Cloud Engine：未来由项目方托管，用户显式授权并通过 HTTPS 连接
```

三个项目是：

1. **Vault Coach**：Obsidian 中的知识、学习与证据入口；
2. **Knowledge Engine**：独立知识训练工作台、高性能检索/图谱、考试、受控 Agent、能力画像与异步任务核心；
3. **AI Career Agent**：求职决策、投递管理与面试训练产品。

核心原则是“共享版本化能力，不共享混乱的数据库表或文件系统权限”；Career Agent 只能经由版本化的 Capability API 获取用户明确授权的能力画像，不能直接读取 Obsidian Vault、Engine chunk 或依赖 Obsidian 正在运行。

## 2. 总体拓扑

```text
                         ┌──────────────────────────────┐
                         │      Knowledge Engine         │
                         │ GUI · Retrieval · Graph · ANN │
                         │ Training · Agent · Jobs        │
                         └──────────────┬───────────────┘
                                        │ Capability API
                 ┌──────────────────────┴──────────────────────┐
                 │                                             │
┌────────────────▼──────────────┐             ┌────────────────▼──────────────┐
│          Vault Coach           │             │        AI Career Agent          │
│ Obsidian UX / local facts      │             │ Resume / JD / application flow  │
│ Ask · Exam · Learning Map      │             │ Matching · interview simulation  │
└───────────────┬───────────────┘             └────────────────────────────────┘
                │
                │ optional, explicit, incremental sync
                ▼
    Engine Connector（可选）或 future Cloud Engine
```

Lite 模式中，Knowledge Engine 不运行；现有的本地索引、确定性图谱、语义图谱、掌握度快照继续作为完整且可用的降级路径。Engine Standalone 与 Engine Connector 共享 Core/API，但前者可完全不连接 Obsidian；Local Engine 与未来 Cloud Engine 也应遵循相同 API 契约，而不是两个不同产品。

## 3. 三个项目的责任边界

| 项目 | 必须负责 | 明确不负责 | 对外输出 |
|---|---|---|---|
| Vault Coach | Obsidian 生命周期、Vault 范围选择、文件增量检测、Ask/Exam UI、用户图谱审核、Lite 模式、Vault 内事实文件 | 多租户、支付、跨设备账号、云端职业业务、强制上传整个 Vault | 版本化的内容变更、已确认图谱事实、Assessment 证据、用户选择的 Knowledge Profile |
| Knowledge Engine | 独立 GUI、managed workspace、可扩展索引、ANN、图计算、独立考试/训练、受控知识 Agent、异步任务、能力画像、检索与图谱投影 API | 通用笔记编辑器、职位/投递业务、无授权读取 Vault、Agent 自主写高影响事实 | 有界检索结果、图谱投影、训练/Assessment DTO、Agent trace、能力差距、任务进度 |
| AI Career Agent | 简历/JD/投递管理、职位匹配解释、面试模拟、职业工作流、用户对职业资料的管理 | Markdown 扫描、Obsidian API、重建知识图谱/向量索引、私自读取用户笔记 | 职业任务、匹配结论、学习建议请求、用户授权后的职业上下文 |

### 3.1 Vault Coach 的事实边界

以下数据仍以 Vault 为源头，不能被 Engine 的缓存反向覆盖：

- 原始 Markdown/PDF 与 Obsidian 元数据；
- M1 `AssessmentSessionDocumentV1` 与 append-only `AssessmentEvent`；
- M2 确定性结构图谱来源；
- M3 的用户图谱决策（确认、拒绝、合并、Alias、手工关系）；
- 用户在插件中选择的知识范围与同步授权。

Engine 可以保存这些事实的带 revision 的副本、索引和派生结果，但所有副本均应可通过增量同步或全量重建恢复。

### 3.2 Knowledge Engine 的独立产品与计算边界

Engine 是一个可独立运行的知识训练产品和计算服务，不是“所有用户数据的无边界数据库”。它负责：

- 独立 GUI 中的资料导入、revision/chunk/retrieval/job 诊断、图谱浏览、考试和训练闭环；
- 大规模向量索引、ANN 检索、过滤和批处理 embedding；
- 已确认 Concept 的大图计算、聚类、中心性、路径或学习缺口；
- M4B 掌握度的批量/增量计算与版本化快照；
- 长任务队列、取消、进度、失败重试和结果缓存；
- 将原始图谱事实转换为有节点/边预算的客户端投影。
- 面向开放式学习目标的受控 Agent：只通过有限检索、图谱、掌握度和训练草案工具编排，不直接写高影响事实。

它不应未经请求直接扫描 Vault，也不应让某个产品绕过领域 API 操作另一个产品的表。Engine 独立模式仅处理用户显式导入的 `managed` workspace；Connector 模式仅处理 Vault Coach 通过 revisioned DTO 明确同步的副本。

### 3.3 AI Career Agent 的业务边界

Career Agent 负责职业领域事实：简历、职位描述、投递状态、公司/岗位偏好、模拟面试记录和用户的职业目标。它可请求能力差距分析，但不保存或读取完整 Vault 内容。

职业功能应使用 `KnowledgeProfile`，而不是“Vault 全量同步”这一粗粒度授权。用户可挑选文件夹、项目、概念或已确认能力，并可查看、撤销和删除已共享资料。

## 4. 四类数据必须分离

```text
知识语义图谱（知识本身）
    Concept / typed relation / source evidence / user decision

学习掌握状态（用户与知识的关系）
    AssessmentEvent / mastery / confidence / review recommendation

职业能力画像（跨产品、经授权的发布物）
    skill / project evidence / selected mastery / profile revision

职业业务数据（Career Agent 专属）
    resume / JD / application / interview / preference
```

知识图谱不能因某次考试错误而改变；掌握度也不能被共现、embedding 相似或未确认候选直接污染。`KnowledgeProfile` 是从前两层选择性发布的稳定 DTO，而不是共享数据库表或对 Vault 的文件系统访问权。

建议的最小契约：

```ts
interface KnowledgeProfileV1 {
  profileId: string;
  revision: number;
  selectedSkills: Array<{
    conceptId: string;
    label: string;
    evidence: Array<{ sourceRef: string; excerpt?: string }>;
    mastery?: { level: string; confidence: number; calculatedAt: number };
  }>;
  consent: {
    purpose: "career-personalization";
    grantedAt: number;
    expiresAt?: number;
  };
}
```

Career Agent 必须把每个匹配/建议标为“来自简历”“来自职位描述”或“来自用户授权的 Knowledge Profile”，避免把模型推断伪装成原始事实。

## 5. 运行模式与数据路径

| 模式 | 数据位置 | 用户适用场景 | 产品行为 |
|---|---|---|---|
| Lite | Vault 与插件本地文件 | 小型 Vault、离线、强隐私、零配置 | 继续使用现有索引与有界图谱；超过阈值时提示而不阻断 Ask/Exam |
| Engine Standalone | 用户电脑的 Docker 卷与 `managed` workspace | 不使用 Obsidian、重度训练、需要检索/图谱/考试调试 | 通过 Engine GUI 显式导入资料，独立完成训练闭环 |
| Engine Connector | 用户电脑的 Docker 卷与 `connector` workspace | 大 Vault、希望性能但不愿上传数据 | Vault Coach 仅连接 `127.0.0.1`；通过 health check 与增量 revision 同步，故障立即回退 Lite |
| Cloud Engine | 独立租户的云端存储 | 不愿维护 Docker、跨设备、需要职业联动 | 登录并显式选定同步范围；使用 HTTPS、租户隔离、删除与撤销同步 |

Local Engine 不应要求用户分别部署 Neo4j、Qdrant、Redis。初期应提供一个 Docker Compose 入口或单一桌面服务，内部以模块化单体承载数据和 worker；插件只探测健康状态，例如 `GET http://127.0.0.1:<port>/health`。

## 6. Engine 的初始实现形态

### 6.1 模块化单体，而非立即微服务

推荐初始模块：

```text
knowledge-engine/
├── workbench/          # 独立 Web GUI；只调用版本化 API
├── workspace/          # managed import / connector revision、删除与数据边界
├── sync-ingress/       # Connector revision、hash、upsert/delete、权限校验
├── content-index/      # 文本、chunk、倒排与元数据
├── vector-retrieval/   # embedding、ANN、过滤、rerank 入口
├── graph/              # adjacency、confirmed relation、子图投影
├── training/           # exam、AssessmentEvent → mastery/recommendation
├── agent/              # tool registry、policy、budget、trace、确认边界
├── capability/         # KnowledgeProfile、gap analysis
├── jobs/               # 队列、进度、取消、重试
└── api/                # local/cloud 共用的版本化 HTTP 契约
```

初始持久化可优先使用单一关系数据库加向量扩展，例如 PostgreSQL + pgvector；概念关系用邻接表、递归查询、预计算邻居和子图缓存满足早期需要。只有在多跳路径查询、复杂模式匹配、全局图算法成为已测量瓶颈时，才考虑引入 Neo4j；只有 pgvector 的延迟、过滤或规模不满足时，才评估 Qdrant/Milvus。

### 6.2 可抽取边界

以下边界先以应用内接口存在，未来才按负载拆进程：

- `EmbeddingExtractionWorker`：需要 GPU、模型速率限制或长批处理时优先抽取；
- `RetrievalService`：只有多产品高并发共用或向量库独立扩容时抽取；
- `GraphService`：只有图版本、图算法和路径查询成为主负载时抽取；
- `TrainingService`：保持考试、Assessment 与 mastery 的确定性契约；
- `AgentOrchestrator`：只持有 tool policy 与 trace，不获得领域存储直连；
- `CapabilityService`：保持最稳定的对外契约，供 Career Agent 消费。

## 7. 同步与一致性协议

禁止每次将整个 Vault 快照上传/传入 Engine。沿用 Vault Coach 已有的文件 hash 与变更思路，使用幂等的 revision 协议：

```ts
interface KnowledgeChangeV1 {
  workspaceId: string;
  sourceId: string;
  revision: number;
  contentHash?: string;
  operation: "upsert" | "delete";
  payload?: {
    sections: unknown[];
    confirmedGraphFacts: unknown[];
    assessmentEvents: unknown[];
  };
}
```

- 插件只发送用户授权范围内的变化；
- Engine 按 `workspaceId + sourceId + revision` 去重并拒绝过期写入；
- 内容/索引/图谱/掌握度任务可独立排队，但结果必须标记输入 revision；
- 用户撤销 Cloud 同步时，停止新变更、删除可识别副本，并让插件保留本地事实；
- Cloud 与 Local 都不得以 Engine 缓存覆盖 Vault 事实源。

## 8. 安全、隐私与账号边界

- 本地 Docker 默认只监听 loopback，不暴露 `0.0.0.0`；
- Cloud 只在用户登录、查看同步范围并明确确认后连接；
- Career Agent 获取的是单独授权的 `KnowledgeProfile`，授权可撤销；
- Vault 文件、职业数据、派生索引和匿名产品指标在存储与访问控制上分区；
- 不用“免费功能”交换默认上传 Vault；不以用户内容训练模型；
- 云端上线前单独完成隐私政策、数据删除流程、备份保留策略与专业合规审阅。

## 9. 演进路线与决策门槛

1. **当前**：继续保持 Vault Coach Lite 完整可用；冻结 Engine 的独立工作区、Workbench、Connector、Training 与 Agent 工具契约。
2. **Engine Standalone MVP**：先完成 Docker、GUI、managed import、索引、检索/图谱 Inspector、任务和独立考试闭环；让 Engine 不依赖 Obsidian 即可验证。
3. **受控 Agent MVP**：在已有证据、训练和确定性 workflow 之上增加有限工具编排、trace、预算和确认，不引入高权限通用 Agent。
4. **Connector / Capability MVP**：将 Vault Coach 接入作为可选增强；Career Agent 只读取用户授权的 Knowledge Profile/Gap DTO。
5. **Cloud beta**：当用户对免部署、跨设备或职业联动有明确付费需求，且已掌握每工作区成本和支持负担后上线。
6. **按测量结果拆分**：仅当数据库/worker/图计算已成为确定瓶颈，才将对应模块抽成独立服务。

### 9.1 已冻结的执行顺序

后续工作不再以“先实现服务，再补插件 UI”的顺序推进。具体执行顺序如下：

| 顺序 | 交付物 | 详细计划 |
|---|---|---|
| 1 | Vault Coach Lite：能力地图、自适应考试、复习建议、发布加固 | 【VaultCoach-Lite-后续开发路线图】 |
| 2 | Knowledge Engine Standalone：GUI、导入、检索、图谱、任务、考试与受控 Agent | 【KnowledgeEngine-Local-后续开发路线图】 |
| 3 | Vault Coach Connector 与 Career Agent：分别接入 Engine 能力和授权的 Knowledge Profile / gap 契约 | 【KnowledgeEngine-Local-后续开发路线图】、【AI-Career-Agent-知识接口与数据契约】 |
| 4 | Cloud beta | 在 Standalone/Connector 的性能、成本、安装成功率和付费需求均验证后单独立项 |

## 10. 架构验收标准

- Lite 模式断开 Engine 后，Ask、Exam、现有图谱和本地 Assessment 事实仍可用；
- Local 与 Cloud 的 API 契约一致，切换不改变领域语义；
- Career Agent 无法在没有 `KnowledgeProfile` 授权时读取 Vault 内容；
- 一个 AssessmentEvent、用户图谱决策和 Vault 内容均有明确事实源；
- Engine 可从 revision 流重建索引，不依赖插件进程常驻；
- Engine GUI 不依赖 Obsidian，可独立完成导入、检索、图谱、考试与受控 Agent 的闭环；
- Agent 不具备高权限旁路，所有高影响写入经确定性 workflow 与用户确认；
- 初期部署不要求用户手工组合多种数据库；
- 任意未来服务拆分都不要求在 Career Agent 中复制 Vault Coach 的领域逻辑。
