# 里程碑 2.1：设置页目录选择与信息层级优化

## 1. 目标与结论

本里程碑是 M2 的交互修订，不改变 M2 已建立的设置 schema、provider 独立性和升级保值契约。目标是让用户无需记忆或手写 Vault 相对路径，并能快速理解哪些设置属于日常使用、哪些属于检索与索引调优。

四项需求均可实现。推荐决策如下：

| 需求              | 可行性 | 推荐方案                                                                         |
| --------------- | --- | ---------------------------------------------------------------------------- |
| 目录输入改成交互选择      | 可实现 | 打开可搜索的目录选择弹窗；首项为“整个 Vault”，其后只列出第一、第二层目录                                     |
| 合并“扫描范围”和“指定目录” | 可实现 | UI 合并为一个“知识库范围”设置项；持久化仍映射到现有 `knowledgeScopeMode` 与 `knowledgeFolder`，避免迁移风险 |
| 按标题和类别整理设置      | 可实现 | 一级为“基础设置”“进阶设置”，二级为*功能类别*，具体设置项使用一致缩进和字号                                     |
| 用可展开标题替代开关      | 可实现 | 基础设置始终展开；“进阶设置”使用带箭头的可点击标题，默认折叠并保存展开状态                                       |

### 1.1 本阶段不改变的业务规则

1. 选择“整个 Vault”时，索引所有受支持且不在 Vault Coach 内部目录中的知识文件；
2. 选择某个目录时，继续递归包含该目录下的后代目录和受支持文件；
3. 两层限制只约束**用户可以直接选择的目录入口深度**，不截断已选择目录中的后代文件；
4. 已安装用户保存的第三层或更深目录继续有效，不自动提升到父目录，不自动改成整个 Vault；
5. API key、provider、模型、检索参数和索引格式不因 UI 重排而改变；
6. 修改有效知识范围只把索引标记为 stale，不在设置页中直接开始重建。

## 2. 当前实现与问题定位

### 2.1 当前 UI

`src/settings.ts` 在基础层和完整设置层中分别展示两个控件：

```text
扫描范围：[整个 Vault / 指定目录]
指定目录：[用户手动输入路径]
```

这会产生四个问题：

1. 用户必须知道路径应使用 Vault 相对路径，而不是操作系统绝对路径；
2. 用户可能输入不存在的目录、文件路径、首尾斜杠或错误层级；
3. 选择“整个 Vault”后，“指定目录”仍然出现，两个控件看起来彼此冲突；
4. 目录改名或删除后，文本框无法主动说明当前配置已经失效。

### 2.2 当前持久化契约

M2 已在 `data.json` 中保留以下两个字段：

```ts
type KnowledgeScopeMode = "wholeVault" | "specificFolder";

interface VaultCoachSettings {
  knowledgeScopeMode: KnowledgeScopeMode;
  knowledgeFolder: string;
}
```

运行时在 `src/knowledge-base.ts` 中先判断 `knowledgeScopeMode`。当值为 `specificFolder` 时，使用 `knowledgeFolder + "/"` 作为文件路径前缀，因此目录范围天然包含全部后代文件。

结论：本里程碑只需更换 UI 表达和输入方式。无需重命名字段、升级 settings schema 或迁移索引。

### 2.3 已核实的 Obsidian API 能力

工程当前安装的 `obsidian` 类型版本为 1.13.0，公开类型已经提供：

- `Vault.getAllFolders(includeRoot?)`：读取 Vault 中的目录；
- `SettingFolderControl`：带 Vault 目录建议的声明式控件，可设置 `filter` 与 `includeRoot`；
- `FuzzySuggestModal<T>`：构建可搜索、可键盘操作的自定义选择弹窗；
- `SettingDefinitionGroup` / `SettingGroup`：组织一组设置项；
- `SettingDefinitionBase.visible`：根据状态显示设置项，并在状态变化后通过设置页 `update()` 重新计算。

项目的 `minAppVersion` 仍是 1.11.4，因此不能只实现 1.13 的声明式目录控件。推荐让 1.13 声明式设置和旧版命令式设置共用同一个目录表、选择弹窗和保存用例。

## 3. 知识库范围的统一交互

### 3.1 设置页只显示一个设置项

基础设置中的“知识库”类别显示：

```text
知识库范围
决定 Vault Coach 可以索引哪些笔记和 PDF。

[整个 Vault                                      选择范围]
```

选择具体目录后显示：

```text
[项目/机器学习                                  更改范围]
```

目录不存在或来自旧版深层配置时，可在当前值旁显示状态文字：

```text
[研究/课程/2025/强化学习                         更改范围]
 当前旧配置：超过新的两层选择限制，仍会继续使用。
```

```text
[Archive/Old                                    更改范围]
 需要处理：该目录当前不存在。配置已保留，请重新选择范围。
```

不要同时保留“扫描范围”下拉框和“指定目录”文本框。两个持久化字段属于实现细节，不应继续成为两个用户任务。

### 3.2 选择弹窗

点击“选择范围”或“更改范围”后，打开 `KnowledgeScopePickerModal`：

```text
选择知识库范围
[搜索目录……]

▣ 整个 Vault                         推荐
📁 工作
📁 项目
  📁 项目/AI
  📁 项目/Vault Coach
📁 学习
  📁 学习/德语
  📁 学习/机器学习
```

交互要求：

1. “整个 Vault”固定为第一项，不参与按路径排序；
2. 第一层目录按本地化名称排序；其第二层子目录紧随父目录并增加一级视觉缩进；
3. 搜索同时匹配目录名称和完整 Vault 相对路径；
4. 当前选择使用勾选图标或 `aria-current="true"` 标识；
5. 鼠标、触控、方向键、Enter 和 Escape 均可完成操作；
6. 弹窗每次打开时重新读取目录，不缓存跨会话的目录列表；
7. 不显示 `.vault-coach` 及其后代目录；其他排除规则必须复用知识库范围规则，不能在 UI 里另写一套不一致的字符串判断；
8. 空 Vault 仍显示“整个 Vault”，并提示当前没有可选子目录；
9. 目录很多时只渲染匹配结果，不在设置页常驻完整目录树。

### 3.3 为什么推荐弹窗而不是常驻目录树

Obsidian 1.13 的 `SettingFolderControl` 已能提供目录建议，并支持 `includeRoot` 与 `filter`。它适合快速原型，但本需求还要求固定的“整个 Vault”文案、父子缩进、旧配置状态和统一的新旧版本体验。自定义 `FuzzySuggestModal` 可以使用公开 API 完整表达这些状态，并能同时服务声明式和命令式设置页面。

不建议把所有目录长期展开在设置页中。大型 Vault 会让页面过长，目录改动后还要维护监听器，并会干扰设置分类和移动端触控。

`SettingFolderControl` 可以保留为备选方案或无障碍回退，但首选实现应只有一个用户可见入口，避免同一功能出现两种不同选择器。

## 4. 两层目录限制的精确定义

### 4.1 深度规则

以 Vault 根目录为深度 0：

| 示例 | 深度 | 新选择器是否显示 |
| --- | ---: | --- |
| 整个 Vault | 0 | 是，固定第一项 |
| `项目` | 1 | 是 |
| `项目/AI` | 2 | 是 |
| `项目/AI/论文` | 3 | 否 |
| `项目/AI/论文/2026` | 4 | 否 |

目录深度应由规范化后的 Vault 相对路径片段数计算：

```ts
function getVaultFolderDepth(path: string): number {
  const normalized = normalizeVaultPath(path);
  return normalized.length === 0 ? 0 : normalized.split("/").length;
}
```

不要按字符串中斜杠数量直接判断，因为首尾斜杠、重复斜杠和 Windows 路径分隔符会造成偏差。

### 4.2 选择深度与索引深度必须分开

用户选择 `项目/AI` 后，`项目/AI/论文/2026/note.md` 仍属于该范围。否则 UI 中显示一个目录，实际却只索引其中两层文件，会形成难以察觉的数据缺失。

如果产品未来希望严格排除第三层后的内容，应新增独立的“最大遍历深度”产品决策和索引 fingerprint，不能借用目录选择器的展示限制实现。

### 4.3 已安装用户的深层目录

新的限制只能约束**新选择**。加载旧设置时：

1. 若 `knowledgeFolder` 为第三层或更深且目录仍存在，将其作为额外的 `legacy-folder` 当前项放在“整个 Vault”之后；
2. 文案说明“当前旧配置仍会使用；选择其他范围后，将只能从两层内目录中选择”；
3. 若旧目录不存在，保留原字符串并显示 `needs-attention`；
4. 不在启动、打开设置页或保存其他设置时修改该路径；
5. 用户主动选择新范围后，才用新值替换旧路径。

这样既能收紧未来选择，也不会让旧用户更新插件后突然扩大或清空知识库。

## 5. UI 合并后的存储映射

UI 使用一个联合类型表达选择：

```ts
export type KnowledgeScopeSelection =
  | { kind: "whole-vault" }
  | { kind: "folder"; path: string };
```

保存时映射到现有字段：

| UI 选择 | `knowledgeScopeMode` | `knowledgeFolder` |
| --- | --- | --- |
| 整个 Vault | `wholeVault` | 保留上一次目录值 |
| 目录 `项目/AI` | `specificFolder` | `项目/AI` |

选择“整个 Vault”时建议保留 `knowledgeFolder`，理由是：

- 运行时在 `wholeVault` 模式下不会读取该字段；
- 用户切回目录范围时可以恢复上一次选择；
- 老版本回退后仍能看到原目录；
- 避免仅因 UI 切换而销毁用户配置。

读取时由一个纯函数还原 UI 选择：

```ts
function toKnowledgeScopeSelection(
  settings: Pick<VaultCoachSettings, "knowledgeScopeMode" | "knowledgeFolder">,
): KnowledgeScopeSelection {
  return settings.knowledgeScopeMode === "wholeVault"
    ? { kind: "whole-vault" }
    : { kind: "folder", path: normalizeVaultPath(settings.knowledgeFolder) };
}
```

### 5.1 原子保存与索引失效

新增一个设置页用例，不让弹窗直接改两个字段：

```ts
interface KnowledgeScopeSettingsApi {
  getKnowledgeScopeSelection(): KnowledgeScopeSelection;
  listKnowledgeScopeOptions(): KnowledgeScopeOption[];
  updateKnowledgeScope(selection: KnowledgeScopeSelection): Promise<void>;
}
```

`updateKnowledgeScope()` 的顺序：

```text
规范化并验证新选择
  → 与当前有效范围比较
  → 一次性更新两个内存字段
  → saveSettings() 一次
  → 仅在有效范围变化时 markKnowledgeBaseDirty() 一次
  → 刷新设置页状态
```

若保存失败，应恢复两个字段的旧值并显示错误，不能出现 mode 已变、folder 未变的半更新状态。

## 6. 设置页信息架构

### 6.1 一级结构

设置页固定使用两个一级区域：

```text
基础设置
  知识库
  回答模型
  界面与回答

进阶设置  ›
```

基础设置始终完整显示。进阶设置默认仅显示标题、摘要和展开箭头。

### 6.2 基础设置分类

| 二级类别 | 设置项 | 放在基础层的原因 |
| --- | --- | --- |
| 知识库 | 知识库范围、Markdown/PDF 是否参与索引、语义检索只读状态 | 决定插件能读什么以及当前是否可用 |
| 回答模型 | 聊天 provider、对应 URL、模型名、Secret 引用 | 完成首次问答所必需 |
| 界面与回答 | 助手名称、默认问候语、启动时打开侧栏、来源默认折叠 | 常见且可直接理解的产品偏好 |

PDF 文件大小、页数限制属于异常保护参数，放入进阶设置的“索引与同步”，不要和“是否索引 PDF”混在基础层。

### 6.3 进阶设置分类

| 二级类别 | 现有字段 |
| --- | --- |
| Embedding 与语义检索 | `embeddingProvider`、`embeddingModel`、`cloudEmbeddingBaseUrl`、`cloudEmbeddingModel`、`enableVectorRetrieval` |
| 检索、重排与生成 | `retrievalPreference`、`enableQueryRewrite`、`enableRerank`、`rerankBaseUrl`、`rerankModel`、各 TopK、`answerSourceLimit`、`generationTemperature` |
| 索引与同步 | `chunkSize`、`chunkOverlap`、PDF 大小/页数限制、`enableAutoIndexSync`、debounce、max wait、file threshold |
| 对话与长期记忆 | `enableLongTermMemory`、`memoryTopK`、`memoryMaxItems`、`maxConversationMessages` |
| 考试 | `examExcludePathPatterns`、`enableExamSmartFiltering` |
| 语义概念图 | `enableSemanticGraph` 及其同步、批次、窗口、相似度参数 |
| Learning Map 自动关系 | 自动关系开关、阈值、规则关系与相似关系开关 |

`defaultRetrievalMode` 是兼容迁移字段，不得出现在设置页。

### 6.4 视觉层级

建议层级：

| 层级 | 元素 | 表现 |
| --- | --- | --- |
| 一级 | 基础设置、进阶设置 | `h2` 语义，最大字号；进阶标题可点击 |
| 二级 | 知识库、回答模型、索引与同步等 | `h3` 语义或 `SettingGroup` heading，中等字号 |
| 三级 | 具体设置项 | Obsidian 标准 `Setting` 字号；在类别容器中统一缩进 |
| 状态 | Ready、Needs attention、旧配置 | 使用文字和图标，不只依赖颜色 |

缩进使用插件自己的类，例如：

```css
.vault-coach-settings__category-body {
  padding-inline-start: var(--size-4-4);
}
```

不要覆盖 Obsidian 全局 `.setting-item`，也不要依赖未公开的主题 DOM 层级。使用 Obsidian CSS 变量，并在窄屏下减小或取消缩进，防止控件区域过窄。

## 7. 进阶设置的折叠交互

### 7.1 替代开关的标题按钮

删除当前“Show advanced settings”开关。基础设置之后渲染一个真正的按钮式标题：

```text
进阶设置                                      ›
Embedding、检索、索引和诊断选项
已启用 3 项自定义设置
```

展开后：

```text
进阶设置                                      ⌄
  Embedding 与语义检索
    ...
  检索、重排与生成
    ...
```

交互要求：

1. 整个标题区域可点击，不要求用户精确点击小图标；
2. 使用原生 `<button type="button">`，而不是给普通 `div` 添加点击事件；
3. 提供 `aria-expanded` 和 `aria-controls`；
4. 箭头旋转只表示状态，不承担唯一的状态信息；
5. 保留 M2 的“已自定义 N 项”摘要；
6. 点击后调用设置页更新，不重新加载插件；
7. 动画遵守 `prefers-reduced-motion`；
8. 折叠只影响显示，不改变任何运行时配置。

### 7.2 展开状态兼容

继续使用 M2 已有的：

```ts
uiPreferences.advancedSettingsExpanded: boolean;
```

- 全新安装默认 `false`；
- M2 用户已经保存为 `true` 时，升级到 M2.1 后仍保持展开；
- 不新增第二个折叠字段；
- 不把折叠状态混入 `VaultCoachSettings` 业务配置；
- 点击标题后只保存 UI preference，不使知识索引失效。

### 7.3 设置搜索

Obsidian 1.13 的 `visible: false` 会在当前渲染周期同时隐藏设置并排除搜索，因此不能声称折叠的具体条目仍可直接被搜索命中。

M2.1 的稳妥方案：

1. 折叠标题本身保持可搜索；
2. 为标题添加 `embedding`、`检索`、`rerank`、`索引`、`chunk`、`记忆`、`考试`、`图谱` 等 aliases；
3. 搜索这些术语时至少能定位“进阶设置”入口；
4. 展开后，各设置项恢复正常搜索；
5. 手工验证 Obsidian 1.13 的真实设置搜索行为，不通过 CSS 隐藏内容来绕过公开 API。

未来若 Obsidian 提供公开的折叠 group API，再替换此策略。不要读取设置搜索框的内部 DOM 或未公开状态。

## 8. 模块与接口设计

### 8.1 领域无关的数据模型

建议新建 `src/app/knowledge/knowledge-scope-types.ts`。该类型会同时被应用层目录表服务、
`VaultCoachPluginApi` 和设置页使用，因此不能放在 `presentation` 后再让 `app` 反向依赖展示层：

```ts
export type KnowledgeScopeSelection =
  | { kind: "whole-vault" }
  | { kind: "folder"; path: string };

export interface VaultFolderSnapshot {
  path: string;
  isRoot: boolean;
}

export type KnowledgeScopeOption =
  | {
      id: "whole-vault";
      kind: "whole-vault";
      depth: 0;
      selected: boolean;
    }
  | {
      id: `folder:${string}`;
      kind: "folder" | "legacy-folder";
      path: string;
      depth: number;
      exists: boolean;
      selected: boolean;
    };
```

`KnowledgeScopeSelection`、`KnowledgeScopeOption` 和 `VaultFolderSnapshot` 均放在该文件。类型不引用
DOM、Obsidian 类或翻译函数；“整个 Vault”等显示文案由 presentation 层根据 `kind` 生成。这样既便于
测试排序、深度、旧配置和缺失目录，也保持 `presentation → app` 的单向依赖。

### 8.2 目录表服务

建议新建 `src/app/knowledge/knowledge-scope-catalog.ts`：

```ts
import type {
  KnowledgeScopeOption,
  KnowledgeScopeSelection,
  VaultFolderSnapshot,
} from "./knowledge-scope-types";

export function buildKnowledgeScopeOptions(input: {
  folders: VaultFolderSnapshot[];
  current: KnowledgeScopeSelection;
  maxSelectableDepth: 2;
}): KnowledgeScopeOption[];
```

纯函数负责：

- 路径规范化；
- 深度过滤；
- `.vault-coach` 排除；
- 父目录优先排序；
- 当前深层旧配置补位；
- 当前缺失目录状态；
- 去重。

Obsidian adapter 只负责把 `app.vault.getAllFolders(true)` 转换为 `VaultFolderSnapshot[]`。这样单测无需启动 Obsidian。

### 8.3 选择弹窗

建议新建 `src/presentation/settings/knowledge-scope-picker-modal.ts`：

```ts
export class KnowledgeScopePickerModal
  extends FuzzySuggestModal<KnowledgeScopeOption> {
  constructor(
    app: App,
    private readonly options: KnowledgeScopeOption[],
    private readonly onChoose: (selection: KnowledgeScopeSelection) => Promise<void>,
    private readonly onError: (error: unknown) => void,
  ) {
    super(app);
  }
}
```

弹窗只渲染和返回选择，不读写 plugin settings，不调用 `markKnowledgeBaseDirty()`。

### 8.4 设置分区注册表

当前 `getSettingDefinitions()` 与 `renderSettings()` 分别维护一份顺序，已经出现重复。不要在 M2.1 里再复制第三份分类列表。

建议扩展 `src/presentation/settings/settings-section-model.ts`：

```ts
type SettingsTier = "basic" | "advanced";

interface SettingsCategoryDefinition {
  id: string;
  tier: SettingsTier;
  titleKey: TranslationKey;
  itemKeys: readonly (keyof VaultCoachSettings | "knowledgeScope" | "semanticStatus")[];
}
```

声明式和命令式渲染都从同一注册表读取类别顺序，但具体 Obsidian 组件创建仍放在 adapter 中。不要把业务保存逻辑塞进注册表。

## 13. 性能、隐私与故障处理

### 13.1 性能

- 目录列表只在打开选择器时读取；
- 使用 `getAllFolders()`，不读取文件正文；
- 深度和排序是目录数量级，不扫描内容；
- 不为设置页注册长期 Vault 事件监听器；
- 如果真实大型 Vault 测试显示卡顿，再增加按需 memoization，并以 Vault 目录事件显式失效。

### 13.2 隐私

- 目录路径只在本机设置页展示，不发送给模型或远程服务；
- 日志只记录选择种类和深度等诊断信息，不记录完整用户目录路径；
- 选择知识范围不触发模型调用；
- 原有外部 embedding/聊天服务披露继续保留在对应设置类别。

### 13.3 故障

| 故障 | 处理 |
| --- | --- |
| 当前目录不存在 | 保留值，显示 needs-attention，等待用户主动重选 |
| 选择后保存失败 | 恢复内存旧值，显示 Notice，不标记索引 stale |
| 设置页更新 API 不可用 | 调用现有命令式 `renderSettings()` fallback |
| 目录在选择后、建索引前被删除 | 建索引前再次解析范围并给出明确空范围错误 |
| 目录列表异常为空 | 保留 whole Vault 和当前旧配置，不覆盖设置 |

## 14. 风险与取舍

### 14.1 两层限制会隐藏合法目录

部分用户使用一个大型 Vault，并把课程或项目放在第三层以后。新选择器不展示这些目录，会降低他们精细选择的能力。M2.1 按当前产品决策执行两层限制，但保留旧配置；真实用户反馈若显示这一限制过强，可把深层目录放到 Advanced 的搜索入口，而不是重新引入自由文本框。

### 14.2 同时维护两套 Obsidian 设置渲染路径

当前既有声明式 `getSettingDefinitions()`，也有旧版 `display()`。如果只修改一处会产生版本差异。分类模型、选择弹窗和保存用例必须共享；渲染 adapter 可以分别存在。

### 14.3 折叠内容与设置搜索

公开 API 明确把 `visible=false` 与搜索排除绑定。M2.1 使用可搜索的 Advanced 入口和 aliases，避免依赖内部 DOM。接受“折叠时先定位入口，展开后搜索具体项”的行为，并把它列入手工验收。

### 14.4 `settings.ts` 体积

当前文件同时承担类型导出、声明式定义、命令式 fallback 和所有回调。M2.1 应提取目录选择器、分类模型和 disclosure 组件，但不要在同一 PR 重写全部设置保存逻辑。每次提取后保持测试和构建通过。

- `src/i18n.ts`、`styles.css`：新增中英文状态文案和插件命名空间内的层级、选择器、focus 与响应式样式。

设置页使用的范围接口为：

```ts
getKnowledgeScopeSelection(): KnowledgeScopeSelection;
listKnowledgeScopeOptions(): KnowledgeScopeOption[];
updateKnowledgeScope(selection: KnowledgeScopeSelection): Promise<void>;
```

`updateKnowledgeScope()` 先比较有效范围；重复选择不会保存。新目录必须来自当前 Vault 的第一层或第二层；
旧的深层或缺失当前配置可以继续读取和显示，但只有用户主动选择一个合法新值后才会被替换。切换到 whole
Vault 时保留上一次 `knowledgeFolder`。保存失败会同时恢复 mode 与 folder，且不会把索引标记为 stale。

### 16.4 与原方案的差异

- 没有先增加临时按钮再删除旧文本框，而是在原子更新 API 和 modal 测试通过后直接切换最终入口，减少中间 UI；
- 旧版命令式路径没有继续维护第二套 `render*Section()`。`display()` 解释与 Obsidian 1.13 相同的
  `SettingDefinitionItem[]`，类别、provider 条件、控件 key 和保存回调只有一份来源；
- 对新 folder selection 增加了应用层存在性和最大深度校验。即使未来出现非 modal 调用方，也不能绕过两层规则；
- 目录为空时，whole Vault 项会同时显示“当前没有可选子目录”，而不是创建第二个空状态行。
