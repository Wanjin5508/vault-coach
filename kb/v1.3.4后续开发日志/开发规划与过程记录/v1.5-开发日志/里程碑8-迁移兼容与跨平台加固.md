# 里程碑 8：迁移兼容与跨平台加固

## 1. 交付目标

每次增量发布都证明：老用户的设置仍按偏好工作，索引不混用不同向量空间，设备不支持新能力时仍能使用已有功能。当前 manifest 声明 isDesktopOnly=false；桌面实验通过不能作为移动端支持证据。

M8 是增量 A/B/C 共同门禁，按本次新增角色扩大矩阵。没有经过真实设备验证的运行组合保持不可默认启用，并在能力矩阵标明。

## 2. 依赖与变更位置

| 文件/模块 | 本阶段职责 |
| --- | --- |
| src/app/config/settings-types.ts、settings-defaults.ts | 每角色配置与明确的新旧用户默认规则 |
| src/app/config/settings-schema.ts、settings-migrations.ts | 验证、版本迁移、异常值和未知版本处理 |
| src/app/config/settings-repository.ts | loadData/saveData 的持久化边界与恢复；复用当前实现，避免并行覆盖 |
| src/vault-coach-plugin.ts | 启停生命周期、初始化顺序和资源释放 |
| src/app/application-container.ts | 能力检测、旧 provider 兼容装配 |
| M3 索引存储与 fingerprint 模块 | 旧索引读取、失效、重建与中断恢复 |
| M5/M6 local-ai 模块 | 缓存完整性、平台能力、资源释放和失败归因 |
| src/presentation/settings/、M7 setup | 解释降级，保留 advanced 等 UI 偏好 |
| tests/config/、tests/local-ai/、兼容性报告（拟新增或扩充现有） | 固定迁移 fixtures 与实机矩阵 |

外部依赖包括实际支持的 Obsidian/Electron/WebView、浏览器存储/Worker 能力、模型与 ORT 已验证构建。测试 fixture 必须去除密钥、私人路径、笔记和聊天内容。

## 3. 按顺序实施

### Step 1：先建立迁移表，再写迁移函数

从当前 data.json 结构和 Repository 读写链建立合成 fixture。用户设置通过插件 loadData/saveData 保存；模型文件缓存、索引数据、UI 偏好应明确各自落点，不能将大模型塞进设置 JSON。

| 原状态 | 新状态要求 |
| --- | --- |
| 无任何持久化数据 | 采用已通过 Gate 的新安装默认策略；未授权不下载 |
| 老用户 Ollama/OpenAI-compatible | 保留服务地址、模型、密钥及 Embedding 选择 |
| 旧重排开关与远程配置 | 保持原启用语义和候选上限；不自动改成 builtin |
| 旧 rewrite/memory | 通过 legacy adapter 保留原行为；关闭项仍关闭 |
| advanced 展开、范围目录等 UI/业务偏好 | 原样保留；与新增 runtime readiness 分离 |
| 新字段缺失/部分配置 | 按版本和已有选择推导，不以“字段缺失”一律认定新用户 |
| 未知未来 schema | 阻止破坏性覆盖，提示升级或恢复；不能降级保存 |
| 模型缓存已清除 | 配置保留，运行状态重新检测为未准备 |

迁移为确定性、幂等的纯转换；校验成功后一次性提交。失败保留原数据，不能先写默认值再尝试恢复。备份方式沿现有 Repository 的实际安全边界设计，避免在日志或 fixture 输出原始配置。

### Step 2：验证三类身份与索引安全

按共用契约分别测试资源身份、embedding fingerprint、任务策略版本。

- embedding 模型/revision/dtype/pooling/归一化/维度/目的等变化，走 M3 不兼容流程；source/chunker/parser/scope 变化按各自索引规则处理。
- 重排或 Utility 模型改变只影响其资源/任务策略，不使向量索引失效。
- backend 切换是否兼容不能凭 dtype 相同下结论；M4 的数值与检索一致性证据决定 provider descriptor/策略。
- 旧索引缺 fingerprint、重建中断、切换模型时有检索任务，均不得混读 generation。
- 模型缓存损坏或被系统回收时重新校验，不信任 persisted ready。

**交付：** 一张状态转移矩阵和可重放的崩溃/取消测试，不只验证 happy path。

### Step 3：平台检测用能力结果驱动

先探测 Worker/存储/WebGPU 等，再进行轻量实际会话创建；存在 navigator.gpu 不等于设备能运行选定模型。WASM 回退也要验证算子、内存、线程隔离条件与延迟。

| 组合 | 必测内容 |
| --- | --- |
| 桌面 macOS/Windows/Linux | 最低支持和当前 Obsidian；GPU 可用与不可用；干净安装 |
| 移动 iOS/Android | 实际 WebView、前后台切换、内存限制、缓存回收、触摸流程 |
| 网络/存储 | 无网络、下载中断、配额不足、损坏缓存、模型来源不可达 |
| 并发与生命周期 | 索引+前台搜索、跨模型切换、卸载重载、重复打开设置 |
| 旧路径 | 本地模型完全不可用时，已有外部 provider/启发式功能仍可使用 |

每行填设备/系统/Obsidian/后端/模型/dtype/测试时间/结论。没有设备的组合写未验证；不可把“有条件支持”写成全平台已支持。移动端若暂不开放内置模型，用能力限制具体功能，是否修改插件总体平台声明需要独立产品决定。

### Step 4：注入故障并检查数据提交点

验证 prepare 中断、Worker crash、超时、OOM、取消后迟到回包、设备休眠/恢复。重点检查：未验证资源不标 ready、过期 epoch 不提交索引、清空记忆后旧任务不写回、用户切换 provider 后旧任务不覆盖新状态。

对存储清理检查引用计数：清理某角色不能删除另一角色仍使用的共享文件；清理失败可重试且状态一致。

### Step 5：用实际升级包完成回归

从当前基线版本准备测试 Vault 与去敏配置副本，安装候选发布资产，走一次升级、重启、搜索、主回答和设置保存。不要在真实日用 Vault 上首次验证迁移。

回退不是任意安装旧二进制都安全：记录旧版本是否理解新 schema；需要回退时优先关闭新能力并发修复版，或使用升级前备份恢复测试过的数据组合。不能让旧代码覆盖未知新格式。

## 4. Gate 与工程学习目标

- [ ] 迁移 fixtures：重复执行、损坏输入、缺失字段、未知版本、旧偏好全部通过。
- [ ] 索引代际、模型身份与任务策略的失效边界有测试。
- [ ] 每个拟发布平台至少有规定范围的实机证据；未验证组合不会默认开放。
- [ ] 网络/缓存/调度故障可恢复，日志无正文与凭据。
- [ ] 升级安装和资源清理通过，无自动下载、无静默外部请求。
- [ ] 回退条件与恢复手册可由另一位开发者执行。

新人重点学习“数据契约比 UI 默认值更长寿”：迁移不是补字段，必须保护用户选择、异步任务提交和旧版本恢复边界。
