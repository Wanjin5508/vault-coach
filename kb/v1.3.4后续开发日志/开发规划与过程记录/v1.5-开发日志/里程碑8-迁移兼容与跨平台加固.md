# 里程碑 8：迁移兼容与跨平台加固

## 1. 目标

把 1.5 从“干净安装可运行”提升为“真实升级安全”：区分新安装与旧安装、保留现有 provider 和学习数据、迁移索引 fingerprint、处理缓存损坏/离线/设备差异，并完成 Desktop/Mobile 回归矩阵。

学习重点：schema migration、兼容性测试、故障注入、数据恢复、移动端远程调试和发布候选管理。

## 2. 不可破坏的数据

- Vault Coach 设置与已配置 provider；
- API key 的既有保存语义；
- 聊天、考试和学习记录；
- Assessment/mastery 数据；
- 语义图治理决策与现有容量保护；
- keyword 索引和可重新生成的 chunk metadata；
- 用户手工选择的 Advanced 参数；
- 当前命令 ID、View ID 和插件 ID。

迁移前先列出实际存储文件、key、schema version 和所有读取入口。可重建数据也不能直接删除；需要先确认可重建、给出状态并保持 keyword 可用。

## 3. 新安装与旧安装策略

| 场景 | 1.5 行为 |
| --- | --- |
| 全新安装 | setup required；embedding preference 为 builtin/auto；首次准备时显式下载 |
| 旧用户已配置 Ollama | 保留 Ollama，不静默下载 builtin；提示可选迁移 |
| 旧用户已配置 OpenAI compatible | 保留原 provider；提示可选本地语义搜索 |
| 旧用户无完整设置但已有索引/学习数据 | 识别为升级，避免误入清空式向导 |
| 已有可用工作流但无 setup state | 生成 completed migration state，可从设置主动重开向导 |
| 向量 manifest 无完整 fingerprint | 保留文字索引，向量标记 stale，安排重建 |
| 缓存有同 fingerprint 模型 | 验证资源后复用 |
| 缓存 marker 存在但资源缺失 | 显示 needs download，不循环加载 |

不要用“新字段缺失”单独判断新用户，因为旧版本当然没有新字段。综合设置、已有数据、索引和版本 migration marker。

## 4. 设置与存储迁移框架

建议引入：

```ts
interface PersistedSettingsEnvelope {
  schemaVersion: number;
  data: unknown;
}

type Migration = {
  from: number;
  to: number;
  migrate(input: unknown): unknown;
};
```

流程：parse unknown → validate old schema → sequential migrations → validate current schema → apply runtime defaults。不要用一次 `Object.assign(DEFAULT_SETTINGS, saved)` 代替迁移。

原则：

1. migration 是纯函数，可用 fixture 测试；
2. 每步只处理相邻版本；
3. 未知未来版本拒绝覆写并提示备份；
4. 迁移成功后原子保存；失败保留原数据；
5. 默认值只补缺失字段，不覆盖用户显式值；
6. 日志记录版本和结果，不记录秘密；
7. 数据 downgrade 不承诺，需在 release notes 说明备份/回滚限制。

## 6. 手动实施顺序

### Step 1：采集脱敏历史 fixture

从 1.3.4、1.4.x 的真实结构制作最小 fixture。去掉 API key、路径和用户内容。每个 fixture 写明来源版本、预期保留字段和预期失效数据。

### Step 2：实现 settings schema 与相邻迁移

先测试未知/损坏数据，再测试正常版本。迁移运行两次应得到同样结果。不要让 migration 调网络、读 Vault 或启动模型。

### Step 3：迁移 setup 状态

如果用户已有有效知识范围、聊天设置和使用证据，则生成 completed/needs-review，而不是强制首次向导。提供 **Run setup again** 入口。

### Step 4：迁移 provider 默认

只有确定的全新安装使用 builtin 默认。旧用户保留 Ollama/OpenAI。迁移 builtin 必须是明确操作，并显示下载与重建成本。

### Step 5：迁移索引

旧向量缺 fingerprint 时不参与检索。保留 chunk/keyword 数据，根据 scope 和 provider 状态安排后台重建。写入采用新临时目录/文件，成功后切换；失败可继续用旧 keyword。

### Step 6：恢复异常存储

覆盖：损坏 JSON、partial index、orphan temp、cache manifest/resource 不一致、存储配额不足。每类给出 error code、自动动作、用户动作和数据影响。

### Step 7：平台回归

Obsidian Mobile 没有 Node/Electron API。用 `rg` 审查新代码中的 `node:*`、`fs`、`path`、`electron`、`process`、`Buffer`，并在实际 iOS/Android 至少验证一类设备；另一类若不可得需标记未验证。

### Step 8：移除 feature flag 前做 release candidate

只有回归矩阵通过才使全新安装默认 builtin。旧用户路径保持迁移选择。保留 kill switch 需说明作用域、默认值和移除日期，避免永久隐藏分支。

## 7. 回归矩阵

| 维度 | 样本 |
| --- | --- |
| 安装 | clean、1.3.4 upgrade、1.4.1 upgrade |
| Provider | Ollama、OpenAI compatible、builtin |
| 索引 | none、keyword only、旧 vector、当前 vector、partial/corrupt |
| 网络 | online、offline warm、offline cold、下载中断 |
| 设备 | desktop WebGPU、desktop WASM、mobile WASM、低内存 |
| Vault | current note、folder、entire vault、rename/delete |
| 生命周期 | reload plugin、close view、restart Obsidian、cancel job |
| 数据 | chat/exam/assessment/graph governance present |

不要做所有笛卡尔组合。按风险选 pairwise 场景，并为最高风险的“旧版本 + 旧向量 + 外部 provider + 离线”单独完整验证。

## 8. 故障注入与恢复标准

| 故障 | 必须观察到 |
| --- | --- |
| 设置 JSON 损坏 | 不覆写原文件；提示恢复/备份路径 |
| 未知 schema version | 拒绝向下写入 |
| fingerprint mismatch | 禁止向量检索，keyword 可用 |
| cache 文件缺失 | 回到 needs-download，不显示 ready |
| WebGPU init/device lost | 一次 WASM fallback，诊断可见 |
| WASM 失败 | auto 使用 keyword，不外发 embedding |
| 存储配额不足 | 临时数据清理，active index 保留 |
| app 在写入时关闭 | 下次识别 temp，不读取半索引 |
| selected note 删除 | scope needs-attention，要求重选 |
| mobile 内存压力 | 安全 batch/停止并解释，不 crash loop |

恢复成功需要验证数据和状态，而不只是 UI 消失错误。

## 9. 移动端与性能检查

- 不使用 Node/Electron API；
- 监听 `visibilitychange`/平台生命周期时避免重复恢复；
- 降低默认 batch 或按 M4 证据设安全配置；
- 模型与向量内存不可同时无限保留；
- 长列表和图视图不因索引事件高频重渲染；
- 进度事件节流但不丢最终状态；
- touch target、软键盘、窄屏和 orientation 可用；
- 缓存清理与 Storage estimate 在平台缺失时有兼容路径；
- 记录最大已验证规模，避免把安全上限说成文件数承诺。

## 10. 隐私与文案验证

设置页与 README 说明：

- builtin 模型首次从何处下载；
- 权重保存在本地缓存，可手工清除；
- embedding 在本机计算；
- 聊天 provider 可能接收问题和检索上下文；
- 外部 Ollama/OpenAI compatible provider 的数据边界；
- 不含隐藏遥测；未来可选 analytics 必须 opt-in。

用 Network panel 验证 builtin 索引期间只有模型资产请求，没有笔记请求。此检查需在模型已缓存和未缓存两种状态执行。

## 11. 工程实践与原因

- sequential migration 可定位每次 schema 改变；
- runtime validation 防止 TypeScript 类型掩盖磁盘未知数据；
- 新旧安装分开，避免升级时意外下载大模型；
- 高风险矩阵使用真实旧 fixture，避免只测试人工构造 happy path；
- index/cache/业务记录分开恢复，缩小损坏范围；
- mobile 以实际 API 和资源约束验证，不能由桌面浏览器推断；
- rollback 先保护不可再生学习数据，再处理可重建索引。

## 12. 完成标准

- [ ] 历史 fixture 通过顺序、幂等迁移；
- [ ] 旧 provider 和 Advanced 设置不被默认值覆盖；
- [ ] 旧用户不被静默下载 builtin 模型；
- [ ] 旧向量不会与新 query vector 混用；
- [ ] Assessment、考试、聊天、图治理数据回归通过；
- [ ] 缓存/索引损坏与离线路径可恢复；
- [ ] Desktop 与至少一个实际 Mobile 完成记录；
- [ ] 无 Node/Electron 新依赖破坏 mobile；
- [ ] 隐私文案与 Network 证据一致；
- [ ] release candidate 矩阵通过后才翻转新安装默认值。
