# 里程碑 0：基线冻结与产品契约

## 1. 目标

在修改产品行为前建立可复现的 1.4.1 基线，把“Zero-Setup Semantic Search”转换成可测的产品契约。这个里程碑不实现内置模型。

学习重点：需求拆解、Git 隔离、测试基线、可观测指标、问题复现文档。

## 2. 交付物

1. v1.5 traceability matrix：产品目标 → 用例 → 模块 → 测试 → 里程碑；
2. clean install、已有用户、离线、模型失败、移动端五类基线记录；
3. time-to-first-value 的手工测量方法；
4. 当前 bundle、索引耗时、内存、向量体积基线；
5. 每个里程碑的 feature branch 与 PR 顺序；
6. 已知风险清单和 M4 GO/NO-GO 判据草案。

## 4. 产品契约拆解

### 4.1 核心用户故事

```gherkin
Given 我第一次安装 Vault Coach
When 我选择一个知识范围并配置聊天 LLM
Then 插件应在可见进度下准备本地语义搜索
And 我无需填写 embedding model 或 TopK
And 完成后能选择 Ask my notes 或 Test my knowledge
```

```gherkin
Given 内置模型不可用或向量索引失败
When 我提问
Then 插件明确显示降级状态
And 使用关键词检索继续工作
And 不把内容静默发送到其他 embedding endpoint
```

```gherkin
Given 我从 1.4.1 升级且已有 Ollama/OpenAI embedding 索引
When 1.5 首次启动
Then 插件保留原 provider 选择
And 不静默下载内置模型
And 不混用不同 fingerprint 的向量
```

### 4.2 建议测量指标

这些指标本地记录，不引入 telemetry：

| 指标 | 定义 | 采集方式 |
| --- | --- | --- |
| TTFV-Ask | 打开 setup 到第一个带来源回答完成 | 屏幕录制 + 时间戳 |
| TTFV-Exam | 打开 setup 到第一次生成考试 | 屏幕录制 + 时间戳 |
| Required fields | 首次成功前用户必须填写的字段数 | 流程审查 |
| Main-thread long task | 准备阶段超过 50ms 的 UI 主线程任务 | Performance panel |
| Model download | 冷缓存实际字节与耗时 | Network/Cache panel |
| Warm query latency | 缓存模型下单条 query embedding p50/p95 | benchmark harness |
| Retrieval quality | Recall@5、Recall@10、MRR，按中/英/德分别报告 | M4 数据集 |
| Upgrade safety | 旧索引是否正确保留或失效 | migration fixtures |

先记录基线，再在 M4 固定 release gate。不要在看到候选模型结果后临时改变质量指标。

## 5. 手动实施步骤

### Step 1：隔离工作

1. 检查 `git status --short`；
2. 记录并保护当前未提交修改；
3. 从确认过的 1.4.1 commit 建 `feature/v1.5-m0-baseline`；
4. 执行 `npm ci`，不要用 `npm install` 随意刷新 lockfile；
5. 记录 Node、npm、OS、Obsidian 版本。

### Step 2：建立自动验证基线

```bash
npm run lint
npm test
npm run build
git diff --check
```

记录测试文件数、测试数、build 时间、`main.js` 大小。失败时先证明失败是否存在于基线，不要把旧失败归因于 v1.5。

### Step 3：建立手工场景 Vault

准备三个不含隐私数据的小 Vault：

- `clean-small`：中/英/德 Markdown 各若干，适合首次成功；
- `upgrade-1.4.1`：已有 settings、text/vector snapshot、Assessment、M3 decisions；
- `stress-medium`：足以观察 embedding 批处理、取消和内存。

Fixture 不提交真实私人笔记。可提交的内容使用自编或许可明确的短文，并记录来源。

### Step 4：画出现状数据流

至少画出：

```text
Settings → Runtime → AdvancedRagEngine → LocalModelClient.embedTexts
                              ↓
                   EmbeddedExactVectorStore
```

标出当前 provider 判断、fingerprint、busy/progress、fallback 和持久化位置。M3 后用同一张图对比。

### Step 5：建立 issue/PR 切片

每个里程碑一个主 issue，子任务按“测试 → 接缝 → 实现 → UI → 文档”拆分。PR 不跨越两个独立里程碑，M4 benchmark 报告单独审查。

## 6. 调试练习

主动制造并记录：

1. Ollama 未启动时重建向量；
2. embedding model 不存在；
3. 向量 manifest 与 shard 长度不一致；
4. 索引中途点击 Stop；
5. 修改 embedding provider 后不手工重建，观察 dirty 状态；
6. 插件关闭期间修改知识范围文件，再启动观察 inventory。

对每个场景写：触发条件、Console、UI、磁盘状态、是否可恢复、预期与实际差异。

## 7. 自动测试计划

本里程碑原则上不改生产代码。可以新增测试辅助说明，但不要为“统计测试数量”写测试。

需要确认现有关键守卫存在：

- `tests/architecture/import-boundaries.test.ts`；
- Runtime 的 snapshot/fingerprint/inventory tests；
- vector store 损坏恢复 tests；
- Application 事件和 fallback tests。

缺失项进入后续里程碑，不在 M0 一次补完。

## 8. CI/CD 练习

阅读两条 workflow 并写审查记录：

- PR CI 已在 Node 20/22 执行 build、lint、test；
- Release 使用旧版 action/Node 18，只执行 build 后直接 release；
- `version-bump.mjs` 当前按 `versions.json` 的 value 判断，可能漏写新版本 key；
- Release 必须验证 tag、manifest、package、versions 一致；
- 真实模型 benchmark 不应进入普通 PR CI。

这里只记录改进方案，M9 再修改 workflow，避免产品开发中途改变发布路径。
