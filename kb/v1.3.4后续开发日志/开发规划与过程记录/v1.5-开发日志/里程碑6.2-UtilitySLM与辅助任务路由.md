# 里程碑 6.2：Utility SLM 与辅助任务路由

## 1. 本阶段做什么

让本地小型生成模型承担查询改写、长期记忆候选抽取两项有限任务。主回答仍使用用户选择的 ChatProvider。意图分类、工具路由和关系抽取留作后续独立需求，不随本次顺带启用。

200M–600M 是候选规模范围；q4/q8 是否可用、中文质量与实际内存均须验证。模型下载小不代表能正确理解对话，也不代表多个模型能同时常驻。[量化方式与模型支持：Transformers.js](https://huggingface.co/docs/transformers.js/v3.8.1/en/guides/dtypes)

## 2. 内部与外部依赖

| 依赖 | 输入与检查 |
| --- | --- |
| M3 | QueryRewritePort、MemoryExtractionPort 与 legacy chat adapter；保持当前消费者的数据语义 |
| M4–M6 | 可运行生成模型的资产/Worker 支持证据，共用 scheduler 与取消机制；encoder 成功不能直接推定生成成功 |
| M6.1 | 复用多模型切换与端到端评测经验；重排 NO-GO 时可用已定义的启发式路径继续本阶段 |
| 当前代码 | ChatProvider 的 rewriteQuery/extractMemoryStatements，RagEngine 的 prepareAnswer，MemoryService 的 updateFromAssistantTurn |
| 外部模型/框架 | 固定 revision、chat template、tokenizer、量化、算子、许可和上下文上限 |
| 评测数据 | 去隐私、可版本化的查询/对话样本，预期改写要素、禁止新增事实、有效/无效记忆标签 |

先读 [[01-LocalAIRuntime架构与跨里程碑契约]]。本地 Utility 不接管考试评价、概念抽取等现有生成职责。

## 4. 逐步实现

### Step 1：画清现有调用链并冻结输出契约

查询路径：prepareAnswer → ChatProvider.rewriteQuery → retrieve → rerank → 上下文 → 主回答。记忆路径：回答后 → MemoryService.updateFromAssistantTurn → RagEngine.extractMemoryStatements → ChatProvider。

目前 QueryRewriteResult 是 originalQuery/rewrittenQuery/useRewrite，记忆消费者接收字符串列表。首版保持这些消费语义，不直接把源想法中的 queries 数组替换进去。若要多查询检索，需要额外设计合并、去重和预算，独立评审。

先用 legacy adapter 接上新端口，确认关闭改写、关闭长期记忆、历史会话均无行为变化；再接本地 adapter。这样能区分架构重构与模型质量问题。

### Step 2：实现受限生成与真实校验

为两个任务分别定义模板、输入长度、max_new_tokens、超时和输出 schema。例如改写为单个 rewritten_query 字符串；记忆为限定条数的 statements 字符串数组，禁止额外字段，去空项并限制单条长度。

- 当前 structured-output-service 的泛型转换不会验证运行时字段；JSON 能解析也不等于结构正确。新增 validator，返回明确错误类型。
- 依据锁定版本使用贪心/关闭采样等配置；不要声称 temperature=0 就能跨设备完全确定。
- 只解码生成的新 token，防止把输入中的 JSON 示例当输出。
- 首版格式失败直接回退；若实验支持一次修复，修复次数和总体时间仍受同一预算约束，不能递归重试或暗中调用外部 LLM。
- 将 prompt/schema/生成参数计入任务策略版本。升级这些配置不会重建 embedding 索引。

**交付：** 不依赖真实模型的格式/边界测试，以及真实模型对同一 schema 的成功率报告。

### Step 3：先接查询改写，再检查是否改善检索

改写必须保留实体、范围、否定条件与时间限定；对话上下文按预算选取，不把整个聊天历史无界塞入。指代不明时允许使用原问题。

超时、取消、空输出或无效结构时用原 query；回答生成始终保留原用户问题。结构校验无法证明语义忠实，因此需要离线标注与回归；高风险改写样本不靠“合法 JSON”放行。

使用同一 embedding/rerank 和语料对比“原问题检索”与“改写检索”，测 Recall/NDCG、实体保留、否定丢失、无依据扩写率及端到端耗时。实验前填好数字门槛。无显著收益时允许默认关闭改写，不强行本地化一个有害步骤。

**调度注意：** Utility 改写 → Embedding → Reranker 会发生模型切换，p95 必须包含权重恢复成本。

### Step 4：再接记忆候选抽取和受控提交

- enableLongTermMemory=false 时不调度、不下载、不生成。
- 输入明确标注 user/assistant 角色，候选需能对应用户明确陈述；不能把助手的推测存成用户事实。将来源位置等暂存元数据用于校验，最终经 adapter 兼容现有字符串与 MemoryStatement。
- 纯抽取阶段不修改存储。验证完成后，在 MemoryService 的提交点再次检查开关、会话/turn ID、任务 epoch 和取消状态。
- 同一 turn 的重试幂等；失败或无候选不清空已有记忆。按当前规范去重、更新上限和时间字段。
- 抽取时用户清空记忆、关闭功能或切换会话，应使旧任务失效，避免后台结果重新写回。
- 通过现有状态持久化链保存，避免绕过 Repository 单独覆盖 data.json；真正的存储落点在实现时沿应用快照链核对。

先测“候选→校验→提交”状态机，再连真实模型。记忆不能可靠确认时跳过保存，主回答仍正常完成。未来若持久化来源证据，必须单独迁移 schema，不临时向旧记录塞未定义字段。

### Step 5：明确路由与隐私边界

分别设置 rewrite 和 memory 的 preferred route；一次任务冻结所选策略。老用户继续按原选项工作，新用户只有在模型已准备且质量 Gate 通过后才使用本地辅助能力。

| 情况 | 处理 |
| --- | --- |
| 本地改写不可用 | 原问题检索 |
| 本地记忆不可用 | 跳过本轮抽取 |
| 老用户已选择外部辅助 | 继续原授权路径，UI 标明会发送对话/问题 |
| 本地路径失败 | 不自动外发正文 |
| 用户选择禁用 | 不创建对应任务 |

只有 Embedding、重排、改写都使用本地路径或明确禁用外部步骤，才可描述“检索前处理本地完成”。主回答、考试与概念抽取的数据去向另行披露。

### Step 6：用事实风险与性能共同决定 GO

除 JSON 通过率，还测改写忠实度、记忆准确率、错误写入、漏提取、跨轮冲突、提示注入样本、中文/英文切片。宁可少写记忆，也不能用条数增长代表质量。

验证低配设备、模型反复切换、生成超时、OOM、卸载和断网。日志只记录任务类别、版本、耗时、计数和错误码，不记录 prompt/记忆。达到预登记门槛后分别为 rewrite/memory 作 GO/NO-GO，不要求一起开启。

## 5. 验收、发布与回退

- [ ] legacy adapter 回归；主回答 provider 选择未改变。
- [ ] 输出合法性与语义质量分别有证据。
- [ ] 关闭/清空/取消后无迟到记忆写入；重试不会重复保存。
- [ ] 改写失败用原问题，记忆失败不影响回答。
- [ ] 无静默云端降级，日志无正文。
- [ ] 全链路延迟和内存包含模型切换；设备范围写清。
- [ ] 接入 M7，并重新执行 M8/M9 受影响门禁。

回退路由时保留已验证的现有记忆，不清空用户历史。对已写入的错误记忆提供用户可查看/删除的现有入口；若缺少入口，应作为启用本地自动抽取前的验收项补齐。
