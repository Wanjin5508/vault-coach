# 里程碑 4.1-hotfix：Embedding 运行时按需交付与发布瘦身

## 1. 为什么新增这个 Hotfix 里程碑

Vault Coach 1.5.3 为了提供零配置的内置 Embedding，把 ONNX Runtime WASM 转为 Base64，并连同 Transformers.js Worker 一起写入 `main.js`。功能链路可以运行，但生产构建达到 `21,886,715 bytes`，触发 Obsidian Community Directory 的 `main.js > 5 MB` 警告，也使 Obsidian Sync Standard 用户无法同步这个文件。

这次问题不是“内置 Embedding”产品方向错误，而是**把产品内置能力错误地等同于把全部推理二进制内嵌到插件入口文件**。用户真正需要的契约是：不安装 Ollama、不填写 Embedding 地址或模型名称、首次准备后可以离线使用。这个契约并不要求 ONNX Runtime WASM 位于 Release 的 `main.js` 中。

本里程碑负责修复发布架构，不改变上层 RAG、EmbeddingProvider、向量指纹和索引事务设计。目标是：

1. 从 `main.js` 移除 ORT `.wasm` 二进制和 Base64 展开内容；
2. 保留内置 Embedding 的零配置体验；
3. 首次准备时下载**版本锁定且经过 SHA-256 校验**的 runtime 与模型资源；
4. runtime 和模型准备完成后可离线使用；
5. 将 `main.js` 控制在 Community Directory 的 5 MB 警告线以下，并设置更严格的 CI 预算；
6. 保留旧用户设置、已生成向量以及现有模型缓存；
7. 补齐发布说明、构建来源证明和 Community Directory Preview 验证。

> 证据边界：1.5.3 的大体积明确触发了警告，但审核页面没有给出 Error。因此不能把“自动审核未完成”完全归因于文件体积。本 Hotfix 仍然必要，因为 21 MB 入口文件已经构成确定的同步、安装和维护问题。

## 2. 外部先例：Smart Related Notes 实际采用了什么方案

本次重新调研了已经进入 Obsidian Community Directory 的 [Smart Related Notes](https://community.obsidian.md/plugins/smart-related-notes)。审计快照为其 `4.0.20` 源码和 README，访问日期为 2026-10-24。

### 2.1 已确认的源码事实

| 事实 | 源码位置 | 对 Vault Coach 的启示 |
| --- | --- | --- |
| 社区安装只携带 `main.js`、`manifest.json`、`styles.css` | [README](https://github.com/Saiki77/smart-related-notes#development) | 不需要让 Community Directory 安装额外 WASM 文件 |
| 构建期读取 Transformers.js 实际依赖的 ORT 版本 | [`gen-ort.mjs`](https://github.com/Saiki77/smart-related-notes/blob/main/gen-ort.mjs) | runtime 版本必须跟 JS glue 精确配对，不能独立猜版本 |

| Release CI 验证 runtime 文件存在，并对标准 Release 资产生成 attestations | [`.github/workflows/release.yml`](https://github.com/Saiki77/smart-related-notes/blob/main/.github/workflows/release.yml) | runtime 可下载性和 Release provenance 都应成为发布 Gate |

Smart Related Notes 的 README 明确写明：模型权重首次从 Hugging Face 下载并缓存，ORT runtime 也会按固定版本首次下载到 `ort/`，之后离线运行。它目前已在 Community Directory 发布，这证明“标准三文件 Release + 首次获取固定 runtime + 本地缓存”至少存在可被社区目录接受的真实先例。

### 2.2 可以借鉴但不能照抄的部分

Smart Related Notes 当前声明 `isDesktopOnly: true`，并把 ORT runtime 写入插件目录。Vault Coach 当前声明 `isDesktopOnly: false`，已有模型缓存也使用 Cache Storage。因此本项目不能直接复制它的全部实现：

- Vault Coach 第一阶段继续只启用 WASM CPU，不同时引入 WebGPU/Asyncify runtime；
- runtime 默认缓存到独立的 Cache Storage namespace，避免 14 MB WASM 进入 Vault 和 Obsidian Sync；
- 下载后不仅检查文件大小，还验证 SHA-256；
- 保留独立 `RuntimeAssetStore` 端口，以便真机证明 Cache Storage 不可靠时再增加受控的 Vault adapter；
- 移动端未验证前保持 `pending`，不能用另一个桌面插件的成功推导移动端成功。

实施时还做了一个比 Smart Related Notes 更小的资产边界：**只按需下载 WASM，不下载 `.mjs` glue**。`onnxruntime-web/wasm` 的 JavaScript factory 随 Worker 一起编译进 `main.js`，Worker 通过 `wasmBinary` 接收已校验的外置二进制。这保留了上游 JS 代码的编译期可审查性，也避免执行从 CDN 获取的 JavaScript。

## 3. 本次失误复盘

### 3.1 错误发生在哪里

错误发生在发布资产边界，而不是 RAG 领域层：

```text
正确的领域边界
RAG -> EmbeddingProvider -> LocalAIRuntimePort

错误的发布决策
LocalAI Worker + Transformers.js + 14 MB ORT WASM
                    ↓ 全部字符串化
                 main.js 21 MB
```

`EmbeddingProvider`、fingerprint、keyword fallback、Worker 隔离和模型缓存仍然有价值。需要替换的是 LocalAIRuntime 下方的 runtime bootstrap 与构建策略。

### 3.2 直接导致体积膨胀的现有代码

当前 [`esbuild.config.mjs`](../../../../esbuild.config.mjs) 在构建时读取 WASM：

```js
const localAiWasm = await readFile(
  "node_modules/onnxruntime-web/dist/ort-wasm-simd-threaded.wasm",
);
```

随后把二进制转为 Base64 编入 Worker：

```js
define: {
  process: "undefined",
  __VAULT_COACH_ORT_WASM_BASE64__: JSON.stringify(
    localAiWasm.toString("base64"),
  ),
},
```

Worker 又把字符串恢复为字节：

```ts
declare const __VAULT_COACH_ORT_WASM_BASE64__: string;

wasmBackend.wasmPaths = undefined;
wasmBackend.wasmBinary = decodeBase64(
    __VAULT_COACH_ORT_WASM_BASE64__,
);
```

最后，整个 Worker 源码再次作为字符串写入主 bundle：

```js
define: {
  __VAULT_COACH_LOCAL_AI_WORKER_SOURCE__: JSON.stringify(
    localAiWorkerSource,
  ),
},
```

这一组合产生两层字符串化，并且 Base64 自身约有 `4/3` 的体积膨胀。当前实际测量为：

```text
ort-wasm-simd-threaded.wasm       14,264,838 bytes
Vault Coach main.js               21,886,715 bytes
```

### 3.3 五个为什么

#### 为什么 1：为什么 `main.js` 达到 21 MB？

因为 14 MB ORT WASM 被 Base64 编入 Worker，Worker 又被内嵌到 `main.js`。

#### 为什么 2：为什么选择把 WASM 编入 `main.js`？

因为当时把“Obsidian 只自动安装三个标准文件”推导成“所有执行资源必须位于 `main.js`”。前半句正确，后半句缺少证据。

#### 为什么 3：为什么没有考虑首次下载 runtime？

因为架构评审过早把 runtime 归入“绝不能下载的远程代码”，没有先调查 Community Directory 中已经发布的同类插件，也没有区分以下两类行为：

- 危险行为：从可变 URL 获取任意脚本、`eval`、静默自更新插件逻辑；
- 可审计资产：由当前插件版本固定 URL、版本、大小和 hash 的 runtime 二进制，用户触发后下载并只作为固定推理后端使用。

Smart Related Notes 的社区发布先例说明，第二类方案可以进入实际审核流程，但 Vault Coach 仍需通过自己的 Preview 和正式扫描，不能把先例当成自动批准保证。

#### 为什么 4：为什么 M4 没有阻止这个决定？

M4 原本要求验证发布形态、真实 Obsidian、缓存和离线恢复，但为了尽快发布内置 Embedding，真实设备复测被暂停，M5 提前实现了生产 Worker。我们保留了“尚未验证”的文字说明，却仍然把未经验证的资产交付假设固化到代码。

这是流程上的关键错误：**风险被记录为 pending，不代表可以绕过 Gate 进入 Release。**

#### 为什么 5：为什么 CI 没有阻止 21 MB Release？

当前 CI 只证明 TypeScript、lint、测试和 esbuild 成功，没有以下发布质量门槛：

- `main.js` 最大字节数；
- bundle metafile 中的大文件来源；
- 标准 Release 资产的 artifact attestations；
- 非空 Release notes；
- Community Directory branch preview；
- 冷缓存、暖缓存和断网恢复的真实安装记录。

因此“构建成功”被错误地带入了“适合发布”的结论。

### 3.4 责任边界和经验

这次失误应归因于架构验证不足，而不是某个库本身：

1. Transformers.js 和 ONNX Runtime 能完成本地推理；
2. Base64 内嵌也能解决资源路径和 ABI 配对问题；
3. 但它不满足本项目的发布体积和 Sync 约束；
4. 在确定交付方式前，必须同时验证功能、平台、发布和运维四条链；
5. 同类社区插件源码应成为架构调研的输入，而不是发布失败后的补充材料。

## 4. 从产品需求重新推导架构

### 4.1 第一步：冻结用户可感知契约

用户看到的“内置 Embedding”只要求：

- 默认提供经过验证的模型；
- 不要求用户安装 Ollama；
- 不要求填写 endpoint、模型名或 API Key；
- 首次准备时清楚显示下载来源、大小和进度；
- 准备完成后不上传笔记并可离线检索；
- 下载失败时仍可使用关键词检索；
- 用户可以清除缓存并重新准备。

这里没有“runtime 必须存在于 `main.js`”这一产品要求。

### 4.2 第二步：列出实际资产

| 资产 | 属性 | 新交付方式 |
| --- | --- | --- |
| Vault Coach UI、RAG、Provider 和状态机 | 插件业务代码 | 编入 `main.js` |
| Local AI Worker/RPC shell | 项目业务代码 | 编入 `main.js`，以 Blob Worker 启动 |
| Transformers.js orchestration 与 ORT JavaScript factory | 固定 npm 依赖代码 | Tree-shake 后编入 Worker bundle |
| ORT `.wasm` | runtime 执行资产 | 首次准备时按固定版本下载、校验和缓存 |
| 模型 config/tokenizer/ONNX 权重 | 模型数据 | 保持固定 Hugging Face revision 下载与 SHA-256 校验 |
| 向量索引 | 用户派生数据 | 保持现有本地持久化与 fingerprint 管理 |

### 4.3 第三步：应用 Obsidian 发布约束

Obsidian 社区安装只主动获取标准三个文件。新设计不依赖它安装额外资产；插件在用户首次准备内置 Embedding 时自行获取 policy 中声明的 runtime 和模型资源。

这不是插件自更新：下载内容不能替换 `main.js`、命令、UI 或 RAG 逻辑；它只能满足当前已安装版本中固定的 runtime policy。更新 runtime policy 必须发布新的 Vault Coach 版本。

### 4.4 第四步：定义信任边界

每个 runtime 资产必须绑定：

```text
Vault Coach version
  -> Transformers.js exact version
    -> onnxruntime-web exact version
        -> exact WASM filename
          -> immutable versioned URL
            -> expected bytes
              -> SHA-256
```

任意一项不匹配都不能执行。禁止使用：

- `latest` URL；
- 未带版本的 CDN 路径；
- 只检查 HTTP 200；
- 只检查缓存文件存在；
- hash 失败后继续执行；
- 远程返回的 JS 直接 `eval`；
- 通过服务器响应改变模型或 runtime policy。

### 4.5 第五步：得到目标架构

```text
Community Directory 安装
  main.js + manifest.json + styles.css
                 │
                 ▼
       BuiltinEmbeddingProvider
                 │
                 ▼
          LocalAIRuntime
          │             │
          │             └── ModelAssetCache
          │                   固定 HF revision
          │                   config/tokenizer/ONNX
          │
          └── RuntimeAssetStore
                固定 ORT version
                .wasm
                bytes + SHA-256
                Cache Storage
                 │
                 ▼ transfer ArrayBuffer
        内嵌 Worker RPC shell
                 │
                 ▼
       内嵌 JS factory + wasmBinary
                 │
                 ▼
          ONNX 本地推理
```

第一次准备需要网络。runtime 和模型全部通过验证后，后续启动从本机缓存恢复，不再请求 CDN 或 Hugging Face。

## 5. 目标接口与代码结构

### 5.1 新增 runtime policy

新增 `src/app/local-ai/runtime-registry.ts`，其内容由构建脚本根据实际安装的 `onnxruntime-web` 生成：

```ts
export interface RuntimeArtifactPolicy {
    file: string;
    urls: readonly string[];
    bytes: number;
    sha256: string;
    mediaType: string;
}

export interface LocalAiRuntimePolicy {
    id: string;
    engine: "onnxruntime-web";
    version: string;
    backend: "wasm";
    cacheName: string;
    artifact: RuntimeArtifactPolicy;
}
```

候选生成结果形态：

```ts
export const BUILTIN_ORT_RUNTIME_POLICY = {
    id: "onnxruntime-web-1.31.0-dev.20260914-8d85527a0-wasm-v1",
    engine: "onnxruntime-web",
    version: "1.31.0-dev.20260914-8d85527a0",
    backend: "wasm",
    cacheName: "vault-coach-local-ai-runtime-v1",
    artifact: {
        file: "ort-wasm-simd-threaded.wasm",
        urls: [
            "https://cdn.jsdelivr.net/npm/onnxruntime-web@1.31.0-dev.20260914-8d85527a0/dist/ort-wasm-simd-threaded.wasm",
            "https://unpkg.com/onnxruntime-web@1.31.0-dev.20260914-8d85527a0/dist/ort-wasm-simd-threaded.wasm",
        ],
        bytes: 14_264_838,
        sha256: "06ba057753da3847e4c24f02d91ab133455b0817c69a44993a9a53a2146df9e3",
        mediaType: "application/wasm",
    },
} as const satisfies LocalAiRuntimePolicy;
```

严禁手写 hash。`scripts/generate-local-ai-runtime-policy.mjs` 必须从 Transformers.js 实际解析到的 `onnxruntime-web` 包目录读取版本和文件，并计算字节数与 SHA-256。

### 5.2 新增 RuntimeAssetStore 端口

新增 `src/domain/local-ai/local-ai-runtime-assets.ts`：

```ts
export interface PreparedRuntimeAssets {
    policyId: string;
    wasmBinary: ArrayBuffer;
    source: "cache" | "download";
}

export interface RuntimeAssetProgress {
    artifact: "runtime-wasm";
    loadedBytes: number;
    totalBytes: number;
}

export interface RuntimeAssetStore {
    prepare(options: {
        allowDownload: boolean;
        signal?: AbortSignal;
        onProgress?: (progress: RuntimeAssetProgress) => void;
    }): Promise<PreparedRuntimeAssets>;
    clear(): Promise<void>;
}
```

领域端口不导入 Obsidian，也不知道 CDN、Cache Storage 或 Worker。

### 5.3 实现可审计缓存

新增 `src/infrastructure/local-ai/cache-storage-runtime-asset-store.ts`：

```ts
async function readVerified(
    cache: Cache,
    artifact: RuntimeArtifactPolicy,
): Promise<Uint8Array | null> {
    const response = await cache.match(cacheKey(artifact));
    if (!response) return null;
    const bytes = new Uint8Array(await response.arrayBuffer());
    if (bytes.byteLength !== artifact.bytes
        || await sha256(bytes) !== artifact.sha256) {
        await cache.delete(cacheKey(artifact));
        return null;
    }
    return bytes;
}
```

下载流程必须先验证，再写正式缓存：

```ts
const bytes = await downloadFromPinnedSources(artifact, signal, onProgress);
assertByteLength(bytes, artifact.bytes);
await assertSha256(bytes, artifact.sha256);
await cache.put(cacheKey(artifact), new Response(bytes, {
    headers: { "content-type": artifact.mediaType },
}));
```

建议 namespace：

```text
vault-coach-local-ai-runtime-v1/<policy-id>/<filename>
```

它必须与模型缓存 `vault-coach-local-ai-v1` 分开，以便：

- 清 runtime 不误删模型；
- runtime 升级不强制重新下载模型；
- 模型切换不重复下载相同 runtime；
- 诊断界面能分别报告 runtime 和模型占用。

### 5.4 修改 LocalAIRuntime

当前 `LocalAIRuntime` 只依赖 Worker factory。Hotfix 后增加 `RuntimeAssetStore`：

```ts
constructor(
    private readonly runtimeAssets: RuntimeAssetStore,
    private readonly createWorker: LocalAiWorkerFactory = createEmbeddedWorker,
) {}
```

`prepare()` 的顺序调整为：

```ts
async prepare(allowDownload: boolean): Promise<void> {
    const assets = await this.runtimeAssets.prepare({
        allowDownload,
        onProgress: (progress) => this.publishRuntimeProgress(progress),
    });
    await this.request("prepare", {
        allowDownload,
        runtime: {
            policyId: assets.policyId,
            wasmBinary: assets.wasmBinary,
        },
    }, undefined, [assets.wasmBinary]);
}
```

`postMessage` 增加 transfer list，避免把 14 MB WASM 再复制一份：

```ts
worker.postMessage(message, transfer);
```

注意：transfer 后原 `ArrayBuffer` 会 detached。Worker 重启或单线程重试必须重新从缓存读取，不能复用已经 transfer 的对象。

### 5.5 修改 Worker runtime 配置

从 `local-ai.worker.ts` 删除：

```ts
declare const __VAULT_COACH_ORT_WASM_BASE64__: string;
decodeBase64(...);
```

Worker 接收经过主线程验证的 WASM，并复用 Worker bundle 内的 ORT JavaScript factory：

```ts
function configureRuntime(runtime: PreparedWorkerRuntime): void {
    const wasmBackend = env.backends.onnx.wasm;
    if (!wasmBackend) throw new Error("ONNX Runtime WASM backend is unavailable.");
    wasmBackend.numThreads = 1;
    wasmBackend.proxy = false;
    wasmBackend.wasmPaths = undefined;
    wasmBackend.wasmBinary = runtime.wasmBinary;
}
```

`wasmPaths = undefined` 禁止 ORT 根据相对路径再发起请求；`wasmBinary` 成为唯一二进制来源。`esbuild.config.mjs` 在 Worker 构建中使用 browser conditions、将 `onnxruntime-web/webgpu` 别名到 `onnxruntime-web/wasm`，并定义 `process: undefined`，避免 Electron Worker 被识别为 Node 后再解析 `worker_threads`。

### 5.6 修改 esbuild

删除 WASM 读取与注入：

```diff
- const localAiWasm = await readFile(
-   "node_modules/onnxruntime-web/dist/ort-wasm-simd-threaded.wasm"
- );

  define: {
    process: "undefined",
-   __VAULT_COACH_ORT_WASM_BASE64__: JSON.stringify(
-     localAiWasm.toString("base64")
-   ),
  },
```

继续保留：

- 独立 Worker bundle；
- `onnxruntime-web/webgpu -> onnxruntime-web/wasm` alias；
- Worker 中的 browser platform 与 `process: undefined`；
- Worker source 内嵌到 `main.js`。

这样 `main.js` 仍包含受版本控制的 Worker 逻辑，但不再包含 14 MB 二进制。

## 7. 按顺序实施

### Step 0：冻结故障快照并修正文档

记录 1.5.3：

```text
main.js bytes: 21,886,715
ORT wasm bytes: 14,264,838
Transformers.js: 4.3.1
onnxruntime-web: 1.31.0-dev.20260914-8d85527a0
release scan: >5 MB warning; automated review incomplete
```

把原 ADR 改为 superseded，并链接本文。不得直接删除原结论，因为保留错误决策及其证据有助于复盘。

Gate：其他开发者能从文档定位 1.5.3 的构建决策、结果和替代方案。

### Step 1：先生成 runtime policy，不改运行代码

实现生成脚本并验证：

1. 解析 `@huggingface/transformers` 实际使用的 `onnxruntime-web`；
2. 读取 `ort-wasm-simd-threaded.wasm`；
3. 写入 exact version、文件名、bytes、SHA-256 和两个固定 CDN URL；
4. 同一 lockfile 重复生成必须 byte-for-byte 一致；
5. upstream 文件缺失或改名时构建失败。

Gate：policy 的版本与 `npm ls onnxruntime-web` 一致，hash 与本地文件一致。

### Step 2：实现 RuntimeAssetStore

先用 fake Cache 和 fake transport 完成测试，再接入 `requestUrl`。必须覆盖：

- 冷缓存允许下载；
- 冷缓存禁止下载；
- 暖缓存完全断网；
- 文件大小正确但 hash 错误；
- 主 CDN 失败、备用源成功；
- 两个源都失败；
- 下载取消；
- 清缓存；
- 两个并发 prepare 合并为一个任务。

Gate：任何损坏缓存都不能进入 Worker；暖缓存测试把所有网络请求设为抛错仍能返回资产。

### Step 3：扩展 Worker 协议

把当前松散的 `{ id, type, payload }` 提取为显式 discriminated union。增加 runtime 资产 payload 和 transfer list。Worker 初始化前验证 `policyId` 与期望值一致。

Gate：fake Worker 能断言 WASM 使用 transfer；dispose/abort 后迟到响应不能改变状态。

### Step 4：切换 Worker 初始化方式

删除 Base64，保留 bundle 内的 ORT JavaScript factory，改为主线程 transfer `wasmBinary`。保留当前 WASM CPU 范围，不顺便加入 WebGPU、多线程或 reranker。

执行真实离线 smoke：

1. 由开发脚本使用本地 `node_modules` 资产填充 cache；
2. 禁止网络；
3. 新建 Worker；
4. 创建 ONNX session；
5. 输出一条 384 维向量；
6. terminate Worker；
7. 确认没有 `worker_threads`、ABI mismatch 或 backend unavailable。

Gate：真实 session 通过，不能只验证“到达 Cache API”。

### Step 5：处理升级兼容和 UI

升级到 Hotfix 后：

- 旧用户 `embeddingProvider` 原值保持；
- 已缓存的四个模型文件继续使用原 `vault-coach-local-ai-v1` namespace；
- embedding fingerprint 不变，不要求重建已有向量；
- 第一次运行新版本时只额外准备 ORT runtime；
- 用户更新后处于离线且 runtime 尚未缓存时，明确提示联网准备一次，并回退关键词检索；
- **清除内置 Embedding 缓存**需要说明会同时清除 runtime 和模型；
- 下载提示显示 runtime 与模型的总量和当前文件，不再只写“下载模型”。

Gate：从带旧 `data.json`、旧模型缓存和旧向量索引的 1.5.3 测试 Vault 升级，设置与索引均保留。

### Step 6：建立发布体积 Gate

生产构建后执行：

```bash
npm run build
npm run release:verify
```

`release:verify` 至少检查：

```text

manifest/package/versions 版本一致
main.js 不包含 __VAULT_COACH_ORT_WASM_BASE64__
main.js 不包含构建期 WASM Base64 长字符串
runtime policy 版本/文件/hash 与 node_modules 一致
```

4.5 MB 是项目预算，为 Community Directory 的 5 MB 警告线保留增长空间。若移除 WASM 后仍超过预算，先使用 esbuild metafile 定位大依赖，再决定是否精简 PDF.js 或 Transformers.js；不得擅自调大预算。

### Step 7：真实 Obsidian 手工验证

在独立测试 Vault 依次执行：

1. 全新安装，确认插件启动不自动联网；

### 13.2 实施的交付链

1. `generate-local-ai-runtime-policy.mjs` 从实际安装的 `onnxruntime-web` 生成 exact version、URL、bytes 和 SHA-256；
2. `VerifiedRuntimeAssetStore` 先检查独立 Cache Storage，命中后重新校验 bytes/hash；
3. 未命中时仅在用户点击准备后请求主 CDN，失败后尝试固定备用源；
4. 下载字节通过大小和 SHA-256 双重校验后才写入缓存；
5. `LocalAIRuntime` 使用 transfer list 把 `ArrayBuffer` 交给 Worker；
6. Worker 使用 bundle 内的 ORT JavaScript factory 和外置 `wasmBinary`，不下载或执行远程 JavaScript；
7. 模型仍使用原有固定 Hugging Face revision 和 `vault-coach-local-ai-v1` 缓存，因此 fingerprint 和旧向量不变。

## 14. 本次架构复盘结论

`1.5.3` 证明了内置 Embedding 的功能链可以贯通，但也暴露了发布资产设计缺陷。正确的修复不是取消内置 Embedding，而是把“产品内置”重新定义为由插件管理完整生命周期：固定 provider、固定版本、明确下载、完整性验证、本地缓存、离线恢复、可清理和可诊断。

Smart Related Notes 提供了一个已经进入 Community Directory 的工程先例。Vault Coach 应吸收它的 runtime bootstrap、版本配对和 Worker transfer 思路，同时保留本项目更严格的 SHA-256、现有模型 fingerprint、keyword fallback 和跨平台证据要求。
