# 里程碑 3：语义概念图谱开发日志

## 1. 文档目的

本文将《v1.3.4 后续规划》的“里程碑 3：语义概念图谱”转换为一次性实施的工程计划。

里程碑 2 已交付确定性结构事实：Document、Section、Tag，以及 `contains`、`links_to`、`embeds`、`tagged_with`。里程碑 3 在其之上增加可学习、可追溯、可人工修正的 **Concept** 层；它不是把 Tag 当作 Concept，也不把模型猜测直接当作事实。

本阶段完成后，插件将能：

1. 从有实际 Chunk 证据的 Section 中抽取 Concept 候选；
2. 以规则、Alias 与受控的向量近邻生成 `same_as` 候选；
3. 以有限关系集合生成带证据的语义关系候选；
4. 在主工作区的可编辑 Concept 审核图中确认、拒绝、合并或手工关联 Concept；
5. 按受影响 Section 增量更新，而不是每次重算整个 Vault；
6. 为里程碑 4 的 Assessment Event → Concept Mastery 链路提供稳定的 Concept ID 与证据引用。

本日志按实现顺序列出步骤，但**不再要求每个子步骤暂停等待维护者验收**。本里程碑将作为一个完整实现批次开发；完成后统一执行自动化、性能、隐私和 Obsidian 手动验收。

## 2. 基线、前置条件与不可破坏的边界

开始日期：2026-07-21。

```text
里程碑 0：已完成
里程碑 1：已完成（Assessment Session / Event JSON 事实源）
里程碑 2：代码完成，待最终 Obsidian 手动验收
当前分支：feature/kg-mvp
```

开始编码前必须确认：

- 里程碑 2 的结构快照可由“重建索引”成功生成，且 `.vault-coach/graph/graph-snapshot-v1.json` 通过完整性检查；
- 现有 Ask、Exam、Assessment、文本索引、向量索引、自动同步和清除索引的测试基线通过；
- 不修改 `GraphSnapshotV1` 的含义，不把 M3 的可变语义数据混入其确定性结构快照；
- 不修改既有 Assessment Session/Event schema，也不让 Markdown 考试报告成为事实源；
- 任何概念抽取、embedding 或关系抽取均不得在 `onload` 自动执行，也不得绕过用户的模型/隐私设置。

里程碑 3 的依赖边界：

```text
M2 GraphSnapshotV1（确定性、完全本地）
  + 当前 Document Index / IndexedChunk
  + M1 Assessment Event 可引用的稳定 Chunk ID
                  ↓
M3 Semantic Concept Graph（候选、证据、人工决策、有效投影）
                  ↓
M4 仅消费有效 Concept 与 Assessment Event，计算 Mastery
```

## 3. 范围与非范围

### 3.1 本阶段必须完成

1. Section 级 Concept 候选抽取、严格 schema 校验、缓存与失效；
2. Concept、Alias、证据、关系候选、人工决策、有效投影的版本化领域契约；
3. 名称规则归一化与既有 Alias 精确匹配；
4. 基于独立 Concept 向量索引的 Top-K 相似候选，禁止默认全量两两比较；
5. `same_as`、`part_of`、`prerequisite_of`、`used_for`、`contrasts_with`、`related_to` 的受限候选关系；
6. 所有模型生成 Concept/关系都有 Section 与至少一个 Chunk 证据；
7. 用户确认、拒绝、合并、撤销合并、Alias 编辑与手工关系的持久化事实；
8. 主工作区标签页中的局部 Concept 审核图与右侧 Inspector；
9. 文件/Section 变更后的增量抽取、候选索引更新和有效图投影更新；
10. 完整测试、性能预算、隐私说明与迁移/恢复策略。

### 3.2 本阶段明确不做

- 不计算 `ConceptMasteryState`、掌握等级、遗忘曲线、弱项、Dashboard、复习计划或自适应考试；

- 不让 LLM 自由发明 relation type，不把“语义相似”自动视为“同一 Concept”；
- 不自动合并不满足确定性规则的 Concept；
- 不将模型候选、向量索引缓存或用户决策写入 `runtime-state.json`、M2 结构快照或 Assessment JSON；
- 不向开发者服务器上传笔记、Chunk、Concept、向量、候选或用户决策；
- 不把 Concept 审核画布塞入现有 Ask/Exam 侧栏。

## 4. 核心设计决策

### 4.1 结构快照与语义图分离

`GraphSnapshotV1` 是可确定重建的结构事实，必须保持 M2 的 schema、排序和不变式。M3 使用独立的语义存储，候选模型、人工修正与 Concept 生命周期不会污染 M2。

建议目录：

```text
.vault-coach/graph/
├── graph-snapshot-v1.json                 # M2 结构事实；保持不变
└── semantic/
    ├── semantic-manifest-v1.json          # schema、统计、分片表、模型签名、任务状态
    ├── sections/<document-key>.json       # 按文档分片的 Section 输入哈希、抽取缓存与证据
    ├── concepts/<prefix>.json              # 按稳定 ID 前缀分片的 Concept / Alias / redirect
    ├── candidates/<prefix>.json            # 未确认 same_as / 语义关系候选
    ├── decisions-v1.json                   # 用户确认、拒绝、合并、撤销、手工关系的追加式事实
    ├── embeddings/<model-key>.json         # Concept 文本到 embedding 的可重建缓存
    └── ann/<model-key>.*                   # ANN 加速缓存；不是事实源，可删除重建
```

JSON 仍可作为事实存储，但不再把所有语义数据放入单一大文件。分片、manifest 和内存索引避免每次变更都反序列化或重写整个 Concept 图。ANN 索引是性能缓存，不是权威事实；损坏时从 Concepts 与 embeddings 重建。

### 4.2 模型候选、用户决策与有效图分层

```text
Section 抽取结果 / 向量近邻 / 关系模型输出
                  ↓
             Candidate layer
                  +
用户确认、拒绝、合并、Alias、手工关系、撤销
                  ↓
             Effective concept graph
```

- **Candidate layer** 可因 Section 内容、prompt 或模型版本变化而重算；默认不参与后续掌握度计算。
- **Decision layer** 是用户事实，优先级高于任何模型结果；重跑模型不得覆盖或忽略它。
- **Effective graph** 是查询和审核图渲染使用的投影：candidate 被确认后出现为有效边；被拒绝后被稳定抑制；被合并的 Concept 经 redirect 解析到主 Concept。

### 4.3 稳定 ID、候选指纹与可逆合并

M2 的节点 ID 是确定性的；M3 的 Concept 名称可被人工修改，且需要跨 Alias/合并保持稳定，因此采用不同策略：

| 对象 | 标识策略 | 原因 |
|---|---|---|
| Concept | `concept:<persistent-id>`，仅在首次提升为有效 Concept 时创建 | 改名、增加 Alias、合并后 ID 不变；未来 Assessment Event 可稳定引用 |
| Section extraction | `section:<M2 section id>:<inputHash>` | 同一输入可命中缓存；内容、prompt、模型或解析版本变化会失效 |
| Concept candidate | `candidate:concept:<stableHash(sectionId + normalizedName + extractionVersion)>` | 重跑可识别同一候选，不产生重复审核项 |
| `same_as` candidate | 无向规范化 pair：较小 Concept ID 在前，再加算法/模型签名 | A/B 与 B/A 是同一候选 |
| 定向 relation candidate | `candidate:relation:<type>:<sourceConceptId>:<targetConceptId>` | `prerequisite_of(A,B)` 与反向关系不同 |
| 用户决策 | 追加式 `decision:<persistent-id>`，可用 `supersedesDecisionId` 撤销/覆盖 | 保留审计与可逆性 |

合并不删除旧 Concept：

```text
concept:old  ──redirectsTo──►  concept:canonical
```

旧证据、旧候选和未来的 Assessment 引用保持可追溯；有效查询解析 redirect。撤销合并仅追加一条撤销/替代决策，并重新投影，不破坏历史。

## 5. Section 级概念抽取：技术细节

### 5.1 为什么抽取单位必须是 Section

任意 Chunk 太短会导致同一标题下反复产生概念、丢失标题上下文并提高模型调用次数；整篇文档又会超出上下文且难以定位证据。M2 已经给出稳定的 Section、heading path、Chunk ID 和 locator，故 M3 只从 Section 读取语义单元。

### 5.2 Section 输入构造

对 M2 中每个 `SectionGraphNode` 执行：

1. 从当前 `DocumentIndexReader` 按 Section 的 `chunkIds` 取得 Chunk；按原始文档位置/Chunk ID 规范排序；
2. 仅保留该 Section **直接拥有**的 Chunk，不把子 Section 的正文重复并入父 Section；标题路径作为上下文单独提供；
3. 去重 Chunk ID，过滤已移除、空文本、范围外或 `.vault-coach/` Chunk；
4. 若 Section 没有可用 Chunk，跳过模型抽取。无正文标题可继续存在于 M2 结构图，但不能成为没有来源证据的 Concept；
5. 建立不可变的 excerpt 映射，例如 `E1 → chunkId + locator + 可发送文本`；模型只能引用 `E1...En`；
6. 给模型的上下文为：文档标题、heading path、有限长度的编号 excerpt。不能传入未映射到 `E*` 的正文；
7. 若 Section 超过模型输入预算，按 Chunk 边界切成连续窗口 `window 0..n`。每个窗口仍带同一 Section ID 和自己的 excerpt 映射；窗口结果回到同一 Section 后再进行确定性去重。

概念抽取输入的逻辑形态：

```text
Document: test/A.md
Section: A 一级标题 > A 二级标题
E1 [chunk-...]：...
E2 [chunk-...]：...
```

模型必须返回严格 JSON：

```json
{
  "concepts": [
    {
      "name": "Reciprocal Rank Fusion",
      "aliases": ["RRF"],
      "description": "按排名融合多个检索结果的方法。",
      "source_excerpt_ids": ["E1", "E2"]
    }
  ]
}
```

### 5.3 输出验证、缓存与失效

抽取器在持久化前必须：

- 解析 JSON 或受控代码块 JSON；拒绝自由文本、未知字段、空名称、超出数量/长度的输出；
- 验证每个 `source_excerpt_ids` 都存在于本次输入，且至少有一个证据；
- 将每条证据还原成真实 `chunkId`、`DocumentLocator`、Section ID 和输入哈希；
- 对候选名称/别名做 Unicode NFC、空白、标点、大小写等规则规范化；
- 保存模型提供商、模型名、prompt/extraction schema 版本、输入哈希、生成时间和失败状态；
- 绝不把模型没有引用的 Chunk 伪造为证据。

缓存键至少包含：

```text
sectionId
+ ordered chunk IDs / content hashes
+ heading path
+ extraction prompt version
+ extraction model signature
+ extraction schema version
```

当文件变更导致 Chunk、heading path、模型签名或 prompt 变化时，只失效对应 Section；删除/移出范围时删除该文档的 Section cache、证据和由其唯一支持的候选。模型请求失败保留最后一次有效结果并记录 dirty/error，不影响 M2 检索、Ask 或 Exam。

## 6. 防止 embedding 与相似性计算爆炸

### 6.1 明确禁止的实现

下列逻辑禁止成为默认路径：

```text
for each Concept A:
  for each Concept B:
    cosineSimilarity(A.vector, B.vector)
```

10,000 个 Concept 会产生约 5,000 万对比较；768 维向量意味着数百亿级乘加操作。现有文本 Chunk 精确向量检索不能直接复用于大型 Concept 去重。

### 6.2 独立 ConceptSimilarityIndex

新增应用端口 `ConceptSimilarityIndex`，语义上独立于 RAG 文本 Chunk 向量库：

```ts
interface ConceptSimilarityIndex {
  upsert(items: readonly ConceptEmbeddingRecord[]): Promise<void>;
  remove(conceptIds: readonly string[]): Promise<void>;
  findNearest(vector: number[], limit: number): Promise<ConceptSimilarityHit[]>;
  rebuild(items: readonly ConceptEmbeddingRecord[]): Promise<void>;
}
```

生产实现使用浏览器/移动端兼容的 HNSW 或等价 ANN 索引。该库必须可随插件 bundle、可释放资源、可持久化为可丢弃缓存；不能使用 Node 原生二进制依赖或启动时加载整个 Vault 图。

候选生成规则：

1. 先走零模型成本的规则归一化与已确认 Alias 精确匹配；
2. 对新/变化 Concept 的 `canonicalName + aliases + short description` 生成或命中 embedding 缓存；不重复发送完整 Section；
3. 仅查询 ANN 的有限 Top-K，例如 20～50 个邻居；
4. 以相似度、名称/语言 guard、Alias、来源重叠等条件过滤；
5. 仅把通过条件的少数记录写为 `same_as` candidate；相似度本身从不自动 merge；
6. 初次建立大库索引时分批插入，并限制每轮 embedding/ANN 工作预算；后续只处理变更 Concept。

初始全量建索引的成本是“生成 N 个 Concept embedding + 构建 ANN 索引”，而不是 N² 次比较。每个后续变更只会产生少量 embedding 与 Top-K 查询。若当前平台无法加载合规 ANN 实现，插件只能保留规则/Alias 候选并提示用户，**不得退化为无上限的全量两两比较**。

### 6.3 调度、预算与隐私

- 默认关闭自动语义抽取；用户在设置中显式启用并选择模型提供商后才可运行；
- 任务由 `SemanticIndexCoordinator` 串行或低并发执行，可取消、可恢复、显示已处理 Section/队列/失败数；
- 不在 `onload` 扫描、不阻塞 Ask/Exam、不与文本向量索引争抢无限并发；
- 配置单次最大 Section 数、最大待处理文件数、每个 Concept 的最大候选数与总工作时间预算；
- Ollama 仅接收用户本地配置地址；使用 OpenAI-compatible provider 时，设置页必须明确提示会发送 Section excerpt 或 Concept 文本；
- embeddings、ANN 与候选缓存都在当前 Vault `.vault-coach/graph/semantic/` 中；不包含遥测。

## 7. 受限关系抽取与证据

除 `same_as` 外，模型只能从以下有限集合选择：

```text
part_of
prerequisite_of
used_for
contrasts_with
related_to
```

模型输入只包含同一 Section 内已验证的 Concept 候选及其 excerpt 映射。每条关系必须带至少一个 `source_excerpt_id`，并在写入前校验端点、关系类型、证据 ID 和方向性。

- `same_as` 是无向候选对；
- `prerequisite_of`、`part_of`、`used_for` 是有向关系；
- `contrasts_with`、`related_to` 在存储前使用固定端点排序，避免 A/B 与 B/A 重复；
- 模型不能创建无来源 Concept、未知 relation type、悬空端点或只有“因为模型这么说”的边。

## 8. 用户确认、拒绝、合并与手工关联

### 8.1 持久化规则

用户交互不直接修改模型 cache，而是追加 `UserSemanticDecision`：

```ts
type UserSemanticDecision =
  | { kind: "confirm-candidate"; candidateFingerprint: string }
  | { kind: "reject-candidate"; candidateFingerprint: string; reason?: string }
  | { kind: "merge-concepts"; canonicalConceptId: string; mergedConceptIds: string[] }
  | { kind: "undo-merge"; supersedesDecisionId: string }
  | { kind: "add-alias" | "remove-alias"; conceptId: string; alias: string }
  | { kind: "create-manual-relation"; type: SemanticRelationType; sourceConceptId: string; targetConceptId: string; evidence?: ConceptEvidenceRef[]; note?: string }
  | { kind: "remove-manual-relation"; relationId: string };
```

确认将 candidate 提升为有效关系；拒绝以稳定指纹抑制未来同一候选，即使模型重新运行也不会反复弹出。手工关系必须引用至少一个已有 Chunk 证据，或显式填写用户说明并标记 `origin: "user"`，从而保证关系来源可解释。

### 8.2 主工作区 Concept 审核图

用户不可能逐个审核数千个候选，因此交互不能只是长列表。M3 在 Obsidian **主工作区标签页**创建轻量 `Concept review` View；它是后续 M5 Learning Map 的可复用基础，但不包含 Mastery Dashboard。

它只向渲染器传递局部投影：

```text
搜索的 Concept
+ 一跳已确认关系
+ Top-K 未确认候选
+ 当前重复/相似簇
```

不得默认传入或绘制整个 Vault 图。候选边使用虚线，已确认边使用实线，被拒绝边默认不显示。

右侧 Inspector 展示名称、Alias、置信度、模型信息、Section/Chunk 证据和决策历史，并提供：

| 操作 | 图形交互 | 持久化结果 |
|---|---|---|
| 确认候选 | 点击虚线边 → Confirm | `confirm-candidate`，边进入有效图 |
| 拒绝候选 | 点击虚线边 → Reject，可选原因 | `reject-candidate`，当前边消失并被抑制 |
| 合并概念 | 多选节点 → Merge → 选择主节点 → 查看影响预览 | redirect + `merge-concepts`；旧证据保留 |
| 撤销合并 | Inspector 的决策历史 → Undo | `undo-merge`，重新投影 |
| 手工关联 | 选中两个节点 → 关系类型白名单 → 选择证据或写说明 | `create-manual-relation` |
| 编辑 Alias | 节点 Inspector 添加/删除 Alias | Alias decision，重新运行精确归一化 |

为减少人工负担，审核视图支持搜索、只看未确认候选、按簇查看、按置信度/来源筛选和多选合并；“不处理”不是错误，未确认候选默认不会进入 M4 的高影响计算。

View 通过 `VaultCoachApplication` 的语义 Graph API 工作；不得直接访问 JSON Store、ANN 索引、Obsidian metadata cache 或模型 client。关闭标签页必须释放 renderer、ResizeObserver、DOM listener、动画与临时布局任务。

## 10. 一次性实现步骤

以下步骤按顺序一次性完成；中间不要求维护者逐项测试、提交或合并。

### 步骤 1：冻结 M2/M1 接口并建立语义图 fixture

- 新增小型/大型 Concept fixture：重复术语、缩写、中文/英文名称、同名不同义、Section 超长窗口、无 Chunk 标题、无效 evidence、关系方向、已拒绝候选、可逆 merge；
- 为 1,000+/10,000 Concept synthetic 数据建立性能基线，记录 ANN 建索引、Top-K 查询、单 Section 更新；
- 扩展架构测试：semantic domain 零 Obsidian/模型/DOM 依赖，presentation 不直接导入 Store 或 ANN。

### 步骤 2：建立纯领域契约、指纹、投影与完整性

- 定义 Concept、Alias、Evidence、Section extraction、Embedding record、Candidate、Decision、redirect、有效 relation 和统计 schema；
- 实现名称规范化、无向/有向关系 key、redirect 无环校验、每条模型关系的 evidence 校验、用户决策优先级；
- 实现 `SemanticGraphProjector`，从持久化候选和决策产生不可变有效投影。

### 步骤 3：实现分片 JSON Store、manifest 与恢复

- 实现 manifest、文档 Section 分片、Concept 分片、candidate 分片和追加式 decision log；
- 使用临时文件、验证、备份/恢复策略；单分片写入失败不得覆盖上一次有效事实；
- ANN 缓存作为可重建附属文件处理，损坏不得损坏 Concept/Decision 事实。

### 步骤 4：实现 Section 输入读取、窗口化、缓存与模型 schema

- 由 M2 Section node + 当前 Document Index 创建可验证 `SectionExtractionInput`；
- 实现直接 Chunk 选择、excerpt 编号、窗口拆分、inputHash、模型/prompt/schema 版本 cache；
- 实现受控模型请求、JSON schema 验证、evidence 回填、失败隔离与结构化诊断；
- 在设置中加入显式语义抽取开关、发送范围说明和任务预算。

### 步骤 5：实现规则归一化、Concept 生命周期与 Alias

- 先处理同一规范化名称和已确认 Alias，不调用 embedding；
- 创建/更新 Concept、证据引用、alias candidate；Concept ID 与显示名称解耦；
- 实现同名不同义保护：词面相同但证据/用户决策冲突时保留为独立候选，禁止静默 merge。

### 步骤 6：实现独立 ANN ConceptSimilarityIndex

- 接入跨平台 HNSW/等价 ANN 实现并封装为端口；
- 按模型签名缓存 Concept embedding，批量、低并发、可取消生成；
- 实现 Top-K 查询、阈值/词面 guard、候选去重和候选工作预算；
- 禁止任何未设上限的 N² 回退；无法建立 ANN 时仅保留规则/Alias 候选并给出可操作诊断。

### 步骤 7：实现受限关系候选与来源审计

- 对已验证的同 Section Concept 调用关系抽取；
- 限制 relation type，验证 evidence、端点、方向和重复；
- 将模型来源、prompt、置信度和 Chunk 证据写入 candidate layer；不满足证据条件的结果直接拒绝持久化。

### 步骤 8：实现用户决策、有效投影与应用 API

- 实现确认、拒绝、merge、undo merge、Alias、手工关系的追加式 decision use case；
- 以决策重投影有效图，确保用户决定优先且关系拒绝可抑制重跑候选；
- 在 `VaultCoachApplication` 增加语义图查询、审核、任务状态和取消 API；不得破坏 M2 `graph` API。

### 步骤 9：接通增量任务与持久化恢复

- 在 M2 文本/结构图同步成功后，仅排队受影响的 Section；删除/rename 失效相关 evidence 与 candidate；
- 引入 `SemanticIndexCoordinator`，实现分批、预算、取消、恢复、dirty/error 状态；
- 默认不自动调用模型；用户显式重建或启用受控自动更新后才运行；模型/ANN 失败不得回滚 M2、Ask、Exam 或 Assessment。

### 步骤 10：实现主工作区 Concept 审核图

- 注册稳定命令与 View type，在普通 Workspace Leaf 打开，不改变 Ask/Exam 侧栏布局；
- 实现局部投影、搜索、筛选、候选虚线、确认关系实线、Inspector 与决策动作；
- 多选 Concept merge、手工 relation、决策历史和撤销；
- 对 renderer 进行筛选上限、按需展开与 unload 清理。此步骤只做审核图，不做 M5 掌握度 Dashboard。

### 步骤 11：统一验证、迁移与文档

- 运行领域、store、模型 schema、ANN、投影、增量、应用 API、View 生命周期和现有功能回归；
- 测量 1,000+/10,000 Concept 的初建、单 Section 更新、Top-K 查询、内存与持久化大小；
- 更新 README 中模型发送范围、语义缓存、用户决策与 Concept 审核图的隐私说明；
- 执行 `npm ci`、`npm run build`、`npm run lint`、`npm test` 与专用 Vault 手动验收。

## 11. 测试与性能策略

### 11.1 必须自动化覆盖

| 层级 | 覆盖重点 |
|---|---|
| domain | 名称归一化、候选指纹、无向 pair、定向关系、redirect 无环、merge/undo、用户优先级 |
| extraction | direct Chunk 选择、超长窗口、inputHash、JSON/schema 拒绝、没有证据的候选拒绝 |
| store | 分片、manifest、decision append、tmp/bak 恢复、ANN 缓存损坏可重建 |
| ANN | Top-K 限制、缓存命中、增量 insert/remove、绝不调用全量 N² fallback |
| projector | candidate + decision 的有效图、拒绝抑制、合并 redirect、手工边来源 |
| runtime | 单文件变化只抽取受影响 Section、删除/rename 清理、取消与失败隔离 |
| view | 只请求局部投影、Confirm/Reject/Merge/Undo、unload 资源清理 |
| regression | Ask、Exam、Assessment、M2 graph、索引/清除/自动同步与设置 |

### 11.2 性能门槛与可观测性

性能测试不使用用户真实 Vault，不将真实概念、向量或快照提交仓库。开发记录至少包含：

- 1,000、10,000 Concept 的 ANN 建索引耗时、峰值内存和缓存大小；
- 单个 Section 修改后的抽取、embedding、Top-K、投影与分片写入耗时；
- 每次任务实际处理 Section 数、embedding 数、候选数、被预算跳过数和失败数；
- 是否使用本地 Ollama、云端 provider 或纯规则路径。

若性能超出预算，优先降低批量大小、候选 K、自动队列和渲染投影范围；不得以恢复 N² 全库比较来“保证结果”。

## 12. 隐私、安全与恢复

- M2 结构图谱始终本地；M3 的模型调用必须有显式开关；
- 使用 Ollama 时请求仅发向用户配置的本地地址；使用云端时显示被发送的 Section excerpt / Concept 文本范围；
- `.vault-coach/graph/semantic/` 可能包含笔记路径、标题、Chunk 证据、Concept、Alias、embedding 和用户决策，必须被 `.gitignore` 排除；
- 用户决策是私有 vault 数据，不得作为遥测；
- 删除 ANN 缓存只能触发重建，不能删除 Concept、证据或 decision log；
- 若 semantic store 不兼容或损坏，保留原文件、标记 semantic graph dirty，并允许从 M2 + 当前索引重新建立候选；不影响 M2 图、Ask、Exam 或 Assessment。
