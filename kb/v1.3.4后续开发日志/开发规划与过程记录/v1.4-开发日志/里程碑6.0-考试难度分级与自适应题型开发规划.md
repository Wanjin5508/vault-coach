# 里程碑 6.0：考试难度分级与自适应题型开发规划

## 1. 定位、背景与结论

本里程碑是正式进入 VC-L6 前的独立前置交付。它只改变**一场新考试的出题方式与作答界面**；不实施 Wiki、不实施学习推荐、不重建知识图谱，也不调整既有自由文本评分算法或 Mastery 算法。

关联 Issue [#62](https://github.com/Wanjin5508/vault-coach/issues/62) 的截图显示：用户回答自由文本题后，界面给出 `0 / 100`、`25 / 100` 等分数与较长的模型评分说明。即使模型给出了理由，用户仍无法像核对标准答案一样判断评分是否可靠。Issue 提出的方向是：

1. 简答题不应是唯一默认形式；
2. 用户应能选择【简单模式】或【挑战模式】；
3. 简单模式应以选择题、判断题等客观题提供可核验的评价；
4. 简答题保留为可选能力，而不是删除。

本规划采用以下产品结论：

> 简单模式只生成可由程序确定判分的客观题；挑战模式由受约束的 LLM 规划题型，但其输出必须落在受版本控制的题型契约内。二者都写入同一种 `ExamSession → ExamEvaluation → AssessmentEvent` 事实链，因此不会改变既有评分语义或知识图谱的构建链路。

这里的“难度模式”是用户选择的体验策略，代码名称使用 `ExamMode` 或 `assessmentMode`，取值为 `simple | challenge`。它**不能复用**已有 `ExamDifficulty = basic | intermediate | advanced`：后者是单道题的认知难度字段，二者混用会让历史、提示词、评分和统计失去明确语义。

## 2. 当前基础与问题边界

当前考试链路已经分层：

~~~text
范围选择 / 智能筛选
  → ExamBlueprintService（规划 topic、questionType、difficulty、sourceChunkIds）
  → ExamQuestionGenerator（生成题干、参考答案、rubric、来源）
  → ExamQuestionValidator（确定性结构与质量校验）
  → ExamSession（作答）
  → ExamEvaluationService（LLM 自由文本评分）
  → AssessmentEventFactory（不可变 Assessment 事实）
  → Mastery（消费 Assessment）
~~~

现有 `ExamQuestionType` 为 `explanation | comparison | application | reasoning | process`，所有题目均使用文本框作答，评分服务按题目、参考答案、rubric 和用户文本调用模型。它适合解释、推理与应用，但无法为“答对/答错”提供用户可见的确定性保证。

已经成立、且本里程碑必须继续保护的事实边界如下：

| 事实                    | 所有者                            | M6.0 的处理                                                        |
| --------------------- | ------------------------------ | --------------------------------------------------------------- |
| 原始笔记、chunk、索引         | Index / Vault                  | 仅按既有范围读取；不写回笔记。                                                 |
| 知识图谱 Concept/Relation | M2/M3 semantic graph           | 只读既有 `sourceChunkIds → conceptIds` 映射；不调用图谱抽取、确认、合并、重建或写 store。 |
| 已有自由文本题评分             | `ExamEvaluationService`        | Prompt、温度、100 分制归一化、缺项回退和总分算法保持不变。                              |
| 新客观题评分                | 新的、隔离的确定性 evaluator            | 仅为新题型提供 `0` 或 `100` 的逐题结果；输出仍是既有 `ExamEvaluation` 契约。           |
| 考试历史/Assessment       | Session JSON 为事实源，Markdown 为投影 | 仅向新 session 增加可选模式与题型数据；旧记录不迁移、不改写。                             |
| Mastery               | `AssessmentEvent[]`            | 继续只消费已评分事件；不读取 `ExamMode`，不改权重、时间衰减、等级或关系。                      |

因此“不得影响评分以及后续知识图谱”具体表示：

- 挑战模式的自由文本题仍走原有 `ExamEvaluationService`，并以 golden test 锁定当前结果归一化；
- 简单模式不把选择结果交给 LLM 评分，答案键由已校验题目决定，评分结果再适配为原有 `ExamEvaluationItem`；
- 图谱从不因模式选择而新增、删除或修改节点与关系；考试完成后仍按现有规则创建 Assessment evidence，供 Mastery 消费；
- 考试题只能读取由自己 `sourceChunkIds` 证明的 Concept ID，不能让模型临时发明图谱概念。

## 3. 用户需求拆解与验收行为

### 3.1 考试设置页

在范围、文件和题数之后增加必选模式卡片，首次默认选中【简单模式】；模式选择仅对将要创建的一场考试生效。

| 模式 | 用户文案 | 可生成作答形式 | 判分方式 |
| --- | --- | --- | --- |
| 简单模式 | “选择题与判断题。答案明确，可立即核对。” | 单选题、判断题 | 本地确定性判分，不调用评分模型。 |
| 挑战模式 | “根据笔记内容选择合适题型，可能包含解释、比较、流程、推理或应用题。” | 客观题与自由文本题 | 客观题确定性判分；自由文本题沿用原有 LLM 评分。 |

开始生成前要清晰显示模式将影响“题目形式”，而非夸大为对用户能力的精确诊断。模式可在生成前切换；一旦生成 Session，不能中途切换，否则必须重新生成，避免一份考试混入来源不一致的题目策略。

### 3.2 简单模式的题目与结果

1. 只允许单选和判断，禁止简答、比较、应用、推理、流程等自由文本表单；本里程碑不引入多选、填空或拖拽排序，避免部分得分、输入归一化和无障碍复杂度同时膨胀。
2. 单选题必须有 3–5 个稳定 option ID；判断题有且只有“正确/错误”两个选项。UI 保存 ID 而非选项文本，换语言或改显示文案不会改变已提交答案。
3. 每题必须有唯一正确 option ID、可追溯来源和完整参考解释；缺任一项即拒绝题目，不能以猜测的默认答案补齐。
4. 选择正确得 `100 / 100`，选择错误或未作答得 `0 / 100`；反馈分别说明正确性、给出参考解释和来源路径。`evaluationConfidence = 1`，评分 metadata 明确标记为 deterministic，不伪装成模型评分。
5. 提交页使用 radio 控件而非 textarea；结果页仍沿用现有“用户答案、参考答案、评分标准、反馈、改进建议、来源路径”的阅读结构。

### 3.3 挑战模式的题目与结果

1. 不把“代码 → 流程题”“定义 → 选择题”等主题映射写死在 TypeScript 中。模型应根据受选范围中的实际证据、文档结构和学习目标选择适合的形式。
2. 模型只能选择系统实现过的封闭枚举：`single-choice`、`true-false`、`free-response`；`free-response` 继续使用已有 `explanation | comparison | application | reasoning | process` 认知题型。不能让模型发明 UI、评分器或 schema 不支持的题型。
3. 挑战模式可混合客观题和自由文本题。针对过程、代码设计、条件比较、因果推理等需要解释的内容，允许自由文本；对具有唯一、可由来源直接判断的命题，允许客观题。
4. 计划结果必须记录“为何此题型适合该证据”的简短 rationale，作为生成诊断，不向 Assessment 或 Graph 传播。用户可在生成完成后的诊断/开发日志中查看。
5. 若模型规划、生成、验证或修复后仍没有合法题目，明确报告范围/内容不足；不得把自由文本题偷偷降级到简单模式，也不得用未验证的干扰项凑数。

## 4. 领域模型：把“认知目标”与“作答形式”分开

新增类型应是向后兼容的可区分联合，而不是给现有 `ExamQuestion` 堆叠大量可选字段。

~~~ts
type ExamMode = "simple" | "challenge";

type ExamAnswerForm = "single-choice" | "true-false" | "free-response";

interface ExamChoiceOption {
  id: string;                 // 稳定键，例如 option-a；不保存显示索引
  text: string;
}

interface ObjectiveExamQuestion extends ExamQuestionCommon {
  answerForm: "single-choice" | "true-false";
  options: ExamChoiceOption[];
  correctOptionId: string;
}

interface FreeResponseExamQuestion extends ExamQuestionCommon {
  answerForm: "free-response";
}

type ExamQuestion = ObjectiveExamQuestion | FreeResponseExamQuestion;
~~~

`ExamQuestionCommon` 保留既有题干、referenceAnswer、rubric、sourceChunkIds、evidenceExcerptIds、sourcePaths、conceptIds 与生成 metadata。`ExamBlueprintItem` 新增 `answerForm` 和可选 `selectionRationale`，已有 `questionType` 继续描述考察目标。`ExamSession` 新增可选 `examMode` 与版本化 `generationPolicy`；旧 JSON 缺字段时标为 `legacy-free-response` 读取，不反写也不重评。

`userAnswers` 可在 M6.0 暂保持 `string[]`，其中客观题保存 option ID，自由文本题保存原字符串，避免无关的持久化格式大迁移。解析与显示必须通过 `answerForm` 分流，不能依靠“字符串看起来像 A/B”猜测题型。

## 5. 技术方案：受约束的 LLM 工作流，而不是通用 Agent

### 5.1 结论

本功能**不需要 Agent，也不需要 LLM tool calling**。它需要的是有上限、可审计的三段式 workflow：范围与证据已由插件掌握，模型既不需要浏览文件系统，也不需要搜索网络、修改文档、创建任务或决定何时停止。引入可自主循环和工具调用的 Agent 会带来不可预测的 token、时延、权限与数据外发范围，且与 Vault Coach Lite 的本地优先边界不匹配。

LLM 在这里负责的是*有限的语义判断*：“给定这些可用证据，哪一种已实现的题型最能测试它”；程序负责范围、来源、Schema、判分、重试上限与持久化。这是避免硬编码主题规则、同时保持可靠性的正确分工。

### 5.2 工作流

~~~text
现有 Scope / Smart filtering / Content profile
  → 受限题型规划器（LLM JSON）
  → 题目生成器（LLM JSON，带证据）
  → 确定性 schema 与 provenance validator
  → 客观题唯一性 verifier（LLM JSON，最多一次修复）
  → Session
  → 按 answerForm 路由到确定性或既有 LLM evaluator
~~~

#### A. 内容信号准备（不调用 Agent）

现有 `ExamContentProfiler` 已能给出 include/partial/exclude、标题路径、topics 和可出题容量。M6.0 在进入蓝图前补充只读的 `ExamContentSignals`，由 chunk 内容和 Markdown 结构计算，例如：标题层级、步骤列表、表格、代码块、定义句、条件词、对比连接词、公式/命令以及文本长度。它们是**提示上下文**，不是“信号到题型”的硬编码决策表。

输入仍严格局限在用户选定范围、通过现有筛选的 chunk。没有新增网络请求；模型提供方、隐私设置和取消信号均沿用当前考试生成链路。

#### B. 受限题型规划器

扩展 `ExamBlueprintService` 的 JSON schema。每个 item 至少返回：

~~~json
{
  "id": "bp1",
  "topic": "…",
  "learning_objective": "…",
  "answer_form": "single-choice | true-false | free-response",
  "question_type": "explanation | comparison | application | reasoning | process",
  "selection_rationale": "由来源中的步骤与条件判断，采用…",
  "source_chunk_ids": ["真实 chunk id"]
}
~~~

规划器 system prompt 要求它：只选给定 ID、优先跨文件和跨主题、说明选择依据、内容不足时减少题量。`simple` policy 在 schema 之外再由 TypeScript validator 强制 `answer_form ∈ {single-choice, true-false}`；`challenge` 则允许三种形式。无论模型怎样输出，非法 type、无来源、重复来源和超量 item 都会被丢弃。

不能把“没有明确硬编码”误解成允许任意字符串进入运行时。题型枚举、来源 ID、选项数量、唯一答案、分数范围和最大重试次数必须由程序硬约束；只有“本段内容适合哪一种已实现题型”的判断交给模型。

#### C. 题目生成与有界修复

`ExamQuestionGenerator` 根据 `answerForm` 使用区分 schema：

- 对自由文本题，继续使用既有题干、参考答案、100 分 rubric、来源 excerpt 的结构，Prompt 与 validator 的旧路径保持可比较；
- 对单选/判断题，要求返回 options、correct_option_id、reference_answer、简短确定性 rubric、source_chunk_ids 与 evidence_excerpt_ids；禁止“以上皆是”、多正确项、依赖来源外常识和在题干中泄露答案；
- `ExamQuestionValidator` 确定性检查 option ID 唯一、数量、正确键存在、文本非空、来源合法、题目与选项不暴露内部标记、同一场考试不重复；
- 新增 `ObjectiveQuestionVerifier`，用一个严格 JSON 判定“正确选项是否能由证据唯一支持、干扰项是否与证据冲突或缺乏支持、题干是否无歧义”。失败项只允许针对该项修复一次；修复后仍失败即丢弃并显示题数减少原因。

Verifier 是一个固定一次调用的质量关卡，不是可以无限反思的 agent loop。若用户设置的是本地模型，所有三次有限模型调用仍在本机；若用户显式配置云端 provider，则沿用当前考试功能已披露的发送边界。

#### D. 评分路由

新增 `ExamEvaluationRouter`（或等价应用层 port），其唯一职责是按 `answerForm` 分派：

- `single-choice` / `true-false` → `ObjectiveExamEvaluationService`，本地依据 `correctOptionId` 产生既有 `ExamEvaluationItem` 形状；
- `free-response` → 现有 `ExamEvaluationService.evaluate()`，不修改其 prompt、temperature、JSON 归一化、缺项回退和总分算法；
- 汇总仍使用现有总分口径。若一场 challenge exam 混合题型，router 按题收集 items 后交由与现有行为等价的汇总器处理，不得改变旧“纯自由文本”session 的计算结果。

确定性 evaluator 生成的 metadata 应明确为 `evaluatorKind: deterministic` 与版本如 `exam-objective-evaluation/v1`。若现有 metadata 类型假定所有 evaluator 都是模型，应以可区分联合扩展，而不是伪造 `modelProvider` / `modelName`。

## 7. 数据兼容、评分与图谱不变量

### 7.1 保存与回读

- 新 Session JSON 写入 `examMode`、policy/prompt version、blueprint answer form、客观题选项及正确 ID；答案键只存于既有受保护的考试记录，不能暴露给答题 UI。
- Markdown 报告将客观题投影为可读选项，并在**评分后**显示正确答案/解释；未评分报告绝不写出正确 ID 或参考答案中可直接泄题的内容。
- 缺少新字段的历史 JSON 和 Markdown 一律按旧自由文本显示；不批量 migration、不重新调用模型、不补写 answer key。
- mode 是审计 metadata，不作为 Mastery、Progress 或 Graph 的领域输入。

### 7.2 必须成立的评分不变量

1. 既有自由文本题的 `ExamEvaluationService` 输入、Prompt 版本、分数截断、缺项补齐和总分结果不变。
2. 客观题评分绝不调用 LLM；任意合法 option ID 的结果是可重复的。
3. 每题都产出一条 `ExamEvaluationItem`，包含 `0..100` 的 score、feedback、improvement、错误码、confidence 与 evaluator metadata；缺失答案仍是完整 item。
4. 一次保存仍按“Session JSON 事实先写入 → AssessmentEvent 幂等写入 → Markdown 投影”的既有事务原则执行；重评继续使用 `supersedesEventId`，不能原地篡改旧 event。
5. 评分模式不同不改变同一自由文本答案的评分；模式只能决定题目生成，不是对分数施加隐藏系数。

### 7.3 必须成立的图谱不变量

1. 创建、提交和保存考试不得调用任何 graph build、semantic extraction、concept merge、relation decision 或 graph store write API。
2. 出题时可只读查询“该 source chunk 已确认的 Concept IDs”；没有确认映射时保持现有 provisional topic fallback，不让 LLM 新建 Concept。
3. AssessmentEvent 仍以 question 的已验证 `sourceChunkIds` 和 `conceptIds` 追溯；`examMode`、`answerForm` 和题型 rationale 不进入 Concept/Relation schema。
4. 考试结果可以像现在一样影响 Mastery evidence，但绝不能反向修改知识图谱本身。

## 8. 测试矩阵与验收

| 层级 | 必测场景 |
| --- | --- |
| Domain policy | simple 只允许两种客观 form；challenge 允许三种；旧 session 默认 legacy free-response；非法 mode/form 不穿透。 |
| Blueprint | 模型正确选择 form/rationale；simple 中模型输出自由文本被拒绝；无效 chunk、重复 chunk、未知 type 被拒绝；内容不足时减题而非凑题。 |
| Generator/validator | 单选 3–5 项、判断 2 项、唯一正确 ID、无答案泄露、来源合法；验证失败只修复一次；自由文本旧 schema 的 golden fixture 不变。 |
| Objective evaluator | 正确、错误、未答、未知 option ID、混合 challenge session；结果是稳定的 100/0，且模型 client 零调用。 |
| Legacy evaluator | 现有 explanation/comparison/application/reasoning/process 的固定模型响应、总分、缺项/非法分数回退全部保持。 |
| Presentation | mode 默认 simple、切换时清除旧 analysis、客观题 radio 的 option ID 提交、自由文本 textarea 不回归、结果页和未评分导出不泄题。 |
| Persistence | 新 session JSON/Markdown round-trip；旧 JSON、旧 Markdown、未评分 Markdown 继续可读；重复保存与重评 event 语义不变。 |
| Assessment/Mastery | 每个新题产生可追溯事件；同一 source/concept 的 event 映射稳定；Mastery 仅消费事件，不读取 mode。 |
| Graph/architecture | 考试模块无 graph 写端口 import；创建/提交考试后确定性图与语义图快照字节级不变；不触发语义重建任务。 |
| 用户手工验证 | 对 HTML、代码、流程笔记各生成 simple/challenge 两场；核对每道客观题的答案唯一、证据可回跳、自由文本仍按旧方式评分。 |

## 9. 非目标、风险与降级

本里程碑明确不做：

- 不做用户知识库 Wiki、自动整理、目录移动或原文改写；
- 不做 L6 的自适应选题、基于 Mastery 的复习编排或推荐；
- 不做任意自定义题型、动态表单、工具调用 Agent、网络搜索或多轮无限自我修复；
- 不修改知识图谱容量策略、语义窗口、证据投影或评分模型配置；
- 不把“挑战”解释成更高分权重或对用户作出能力判断。

主要风险和处理方式：

| 风险 | 处理 |
| --- | --- |
| 模型生成多个正确项或含糊干扰项 | 严格 schema、确定性 validator、唯一答案键和选项数量约束；结构不合格时使用来源绑定的客观题回退。语义 verifier 仅在后续质量数据证明必要时再独立引入。 |
| 小范围内容不足以构造可靠客观题 | 允许少于请求题数；提示扩大范围或使用挑战模式，绝不伪造干扰项。 |
| LLM 输出格式不稳定 | 复用 `generateParsedJsonAnswer`、版本化 schema、unknown 归一化和确定性拒绝。 |
| 新类型破坏旧历史 | 所有新字段可选；以 fixture 固定旧 JSON/Markdown；不做后台迁移。 |
| 模式改动意外改变 Mastery/Graph | 以 Application API 和 import-boundary 测试保护单向链路；检查 graph snapshot 不变。 |
| 生成时间、成本增加 | planner、generator 都有固定上限；simple 评分零模型调用；沿用 abort/progress。若后续引入一次性 semantic verifier，必须单独评估其时延与成本。 |

## 11. 进入 VC-L6 前的接口承诺

M6.0 完成后，VC-L6 可以把 `ExamMode`、蓝图 rationale、题型 coverage 与评估 evidence 作为**只读输入**，以实现后续的考试规划或自适应选题。但 L6 必须继续遵守本文件的边界：它可以决定“下一场考什么”，不能重写历史评分、不能把模型建议直接写进知识图谱，也不能绕过已验证的题目/评分契约。

M6.0 的代码实现与自动化验证已完成；在真实 Vault 完成人工验收前，不应进一步扩大该里程碑范围或改变其评分、图谱隔离边界。

## 12. 实现记录（2026-07-25）

### 12.1 已交付的领域契约与评分隔离

- `ExamMode` 以 `simple | challenge` 独立于既有的单题 `ExamDifficulty`；创建的 session 会写入 `examMode`，旧 JSON 缺少该字段时仍按旧自由文本记录读取。
- `ExamBlueprintItem` 增加可选 `answerForm` 与 `selectionRationale`；新蓝图使用 `single-choice | true-false | free-response`，但旧 fixture/历史蓝图没有该字段仍可生成原有自由文本题。
- 新客观题携带稳定 option ID、显示文本和唯一 `correctOptionId`；答题 UI 只保存 option ID，结果与 Markdown 投影转换为用户可读的选项文本。
- `ObjectiveExamEvaluationService` 不调用模型，根据答案键给出 100 或 0 分，且明确写入 `evaluatorKind: deterministic` 和 `evaluationConfidence: 1`。
- `ExamEvaluationRouter` 保留纯自由文本 session 对原 `ExamEvaluationService` 的直接调用。混合挑战模式只将自由文本子集交给既有模型评分，再按原有 `ExamEvaluation` 契约合并；没有修改旧 Prompt、温度、分数归一化或回退规则。

### 12.2 受约束的出题工作流

- `ExamBlueprintService` 将当前模式、允许的 answer form 和来源 chunk 送入结构化 JSON 规划；simple policy 在 TypeScript 中再次强制拒绝 `free-response`，challenge policy 才允许模型在三种已实现形式中选择。
- `ExamQuestionGenerator` 按蓝图 `ANSWER_FORM` 要求模型输出选项与答案键；`ExamQuestionValidator` 检查来源、100 分 rubric、选项数量、唯一 ID 和答案键。若模型输出缺少客观题结构，会回退到来源绑定的客观题，而不会将简单模式降级为简答题。
- 第一版没有加入第二个 LLM semantic verifier：它会额外增加模型调用、时延和不确定性，但不能替代最终的来源/答案键校验。当前以严格 schema 与确定性 validator 建立可审计底线；若人工验收显示干扰项质量仍不足，再单列小版本加入一次性 verifier，而不是引入 Agent 循环。

### 12.3 不变量与验证结果

- 图谱只通过既有的只读 `sourceChunkIds → conceptIds` 映射参与出题；M6.0 未新增 graph write 端口、重建调用或语义抽取调用。
- Assessment 的 session JSON、event factory、保存顺序和 Mastery 消费路径未改；模式和作答形式不进入 Concept/Relation schema。
- 分析成功后，controller 与界面会同时锁定模式、范围、文件、题量和智能筛选设置；操作区只保留“开始生成测试”与“返回并修改设置”。必须先返回，分析结果才会被显式丢弃并允许切换模式，避免分析结果与实际出题策略不一致。
- 已新增客观题生成、确定性评分、旧自由文本路由，以及“分析后锁定模式、返回后才可切换”的 controller policy 测试。
- 自动验证已通过：`npm test -- --run`（47 files / 188 tests）、`npm run lint`、`npm run build` 与 `git diff --check`。真实 Vault 的手工验收仍待进行。
