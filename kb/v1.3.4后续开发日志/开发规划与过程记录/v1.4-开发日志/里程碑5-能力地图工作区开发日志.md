# 里程碑 5：能力地图工作区开发日志

## 1. 目标与阶段范围

里程碑 5 将 M4A 的 Learning Graph 和 M4B 的 Mastery snapshot 转换为用户可理解的主工作区能力地图，但不把图谱画布塞回 Ask/Practice 侧栏。本里程碑的最终用户路径是：

~~~text
发现薄弱知识 → 查看证据与原因 → 启动定向考试
~~~

本次已完成 VC-L5.1 至 VC-L5.4：先为后续 Dashboard 与 Learning Map 建立只读的 Progress 查询契约和应用层聚合服务，再补齐惰性缓存、失效、既有事件链、独立主工作区入口与按需加载的 Dashboard。Dashboard 不改变任何图谱、掌握度或考试事实，也不把大图放入 Ask/Practice 侧栏。

## 3. L5.1 实现记录

### 3.1 新增契约

新增【src/app/progress/progress-types.ts】：

- 【ProgressSnapshot】：不可持久化的 Dashboard 读模型；
- 【ProgressGraphSummary】：effective Concept 数量、图谱来源可用性和消息；
- 【ProgressMasterySummary】：掌握度状态、各等级计数、已评估 Concept、覆盖率、算法版本和数据新鲜度；
- 【ProgressAssessmentSummary】：结构化 Assessment Session 数量、已评分数量和最近考试时间；
- 【ProgressRecommendationPreview】：为 M7 预留的稳定展示契约，L5.1 固定返回空数组。

【ProgressSnapshot】只包含聚合值和状态，不泄漏 JSON Store、图谱 renderer projection、pending candidate 或可变领域对象。

### 3.2 聚合服务

新增【src/app/progress/progress-service.ts】。它组合三个既有且职责明确的数据入口：

| 数据 | 读取接口 | 使用原因 |
|---|---|---|
| effective Concept catalog | 【LearningGraphQueryService.getConceptCatalog】 | 只包含经 M3 决策后的有效概念，不受渲染节点预算影响。 |
| Mastery snapshot | 【MasteryService.getState / getSnapshot】 | 保留算法版本、dirty/busy 状态和可追溯考试证据。 |
| Assessment history | 【AssessmentSessionStore.listHistory】 | 结构化 JSON 是考试事实源；不使用可能重复、可重建的 Markdown 报告。 |

在 L5.1 交付时，服务不缓存快照、也不写入任何数据；L5.2 随后在同一服务中补齐了惰性缓存、失效和刷新策略，详见第 5 节。

### 3.3 Application Facade 与装配

- 【src/app/application-api.ts】将占位的 Progress API 扩展为【isAvailable】和异步【getSnapshot】；
- 【src/app/application-container.ts】创建并装配 ProgressService；
- 【src/app/vault-coach-application.ts】仅通过 Facade 暴露服务，不向 Presentation 暴露具体实现；
- 在缺少 ProgressService 的兼容性构造路径中，Facade 返回明确的 unavailable snapshot，不抛出无意义的空对象错误；
- 【src/presentation/controllers/progress-controller.ts】仅将 availability 类型从固定 false 放宽为 boolean，仍未加载或渲染 Dashboard 数据。

### 3.4 统计规则

1. 覆盖率为“当前 effective Concept 中，拥有至少一条有效 Mastery evidence 的数量 / 当前 Concept 数量”。
2. 没有当前 catalog 或 Mastery snapshot 时，覆盖率为 null，而不是 0；这避免把“尚未计算”误报为“用户不会”。
3. Mastery snapshot 中已不在当前 catalog 的旧 Concept 不计入等级和覆盖统计；若 snapshot dirty，仍展示上一次快照，但其状态为 stale。
4. Assessment 统计只统计结构化 Session；旧 Markdown 历史不会伪装成可用于掌握度的证据。
5. M7 之前 recommendations 始终为空，不能在 L5.1 根据分数猜测学习任务。

## 5. L5.2 实现记录：失效通知与订阅

### 5.1 惰性缓存

ProgressService 现在保存最后一次成功的【ProgressSnapshot】以及只读【ProgressStateView】：

- 第一次【getSnapshot】才读取 catalog、Mastery snapshot 和 Assessment history；
- 缓存有效时，重复的 View refresh 不会再次读取 Assessment history；
- 【invalidate】只将快照标记为 dirty，不主动扫描 Vault、不主动读取 JSON；
- 下一次显式读取才重建快照，因此插件启动、文件事件和后台索引事件均保持轻量；
- 返回值会深拷贝，调用者无法修改服务缓存。

### 5.2 并发与 revision 保护

多个 View 同时请求 dirty snapshot 时，共享同一个 in-flight Promise，只执行一次 history 读取。若读取期间图谱、Mastery 或 Assessment 事实发生变化：

1. 【invalidate】递增内存 revision；
2. 旧读取可以完成，但不会写入缓存；
3. 原调用自动按最新 revision 再读取一次后返回。

这避免将“文件变更前开始计算、文件变更后才返回”的旧数据作为新的能力地图结果。

### 5.3 失效来源与现有订阅

没有新增独立的 UI 轮询器或全局 timer。Progress 使用已有【VaultCoachApplication】事件链通知 Runtime/Plugin 刷新 View：

| 事实变化 | 失效位置 | 已有通知 |
|---|---|---|
| 索引构建、增量同步、文件变更、清除索引 | 【notifyIndexStateChanged】 | index-state-changed |
| M2 图谱重建 | Graph Application API | graph-state-changed、mastery-state-changed |
| M3 effective graph 变更（确认、拒绝、合并、Alias、手工关系） | Semantic Graph invalidate helper | semantic-graph-state-changed、mastery-state-changed |
| M4B 显式重建/清除 | Mastery Application API | mastery-state-changed |
| 新建或重新评分的结构化 Assessment facts | saveExamSession 在 JSON 保存成功后 | exam-history-changed，必要时 mastery-state-changed |

因此 Progress 不需要订阅 Obsidian Vault 事件，也不需要知道具体 View；Runtime 已经订阅 Application 事件并调用安全的【refreshAllViews】。仅 Markdown 投影保存、旧 Markdown 历史删除和幂等自动保存不会让 Progress 误以为学习事实发生变化。

### 5.4 L5.3 实现记录：稳定的主工作区入口

L5.3 的目标是让用户可以从多个 Obsidian 原生入口打开能力地图工作区，而不是把 Dashboard 或大图渲染进 Ask/Practice 侧栏。

#### View Type 与叶子生命周期

- 新增稳定 View Type【vault-coach-progress】以及显示名【Learning dashboard】；稳定字符串会写入 Obsidian 工作区布局，因此后续不能随意重命名；
- 新增【ProgressWorkspaceView】，它是普通【ItemView】，可关闭、重新打开，也可由 Obsidian 分屏；
- 新增【src/plugin/main-workspace-view.ts】中的【activateMainWorkspaceView】。它先复用同类 View 的已有 leaf；没有时才调用【workspace.getLeaf(true)】创建普通工作区标签页，再聚焦该 leaf；
- Concept Review、Learning Map 和 Progress 统一复用该激活器，避免未来三处对“是否新建叶子、是否聚焦”的行为逐渐分叉；
- 【refreshAllViews】已识别 Progress leaf，但 L5.3 的 refresh 仅刷新轻量 shell，不读取 Progress snapshot，不产生 history I/O。

#### 用户入口与范围控制

【open-learning-dashboard】命令和【chart-line】Ribbon 直接打开 Progress View；Ask/Practice 侧栏仅增加紧凑的【Learning dashboard / Open】入口。主工作区 shell 提供到既有 Learning Map 的跳转，因此本步骤已经形成“打开 Dashboard → 查看已确认关系”的可用路径。

L5.3 的初始 shell 在【onOpen】中只调用【ProgressController.getState】确认服务可用性。L5.4 已在用户打开该工作区后按需调用【getSnapshot】；工作区恢复本身不会主动读取，只有 View 完成打开生命周期后才开始异步读取。当前 Dashboard 仍不创建图谱 renderer、listener、timer 或持久化布局状态，这些分别属于 L5.5/L5.7。

### 5.5 L5.4 实现记录：按需本地 Dashboard

#### 数据读取与生命周期

【ProgressController】现在完整转发只读【ProgressApplicationApi】的【getState】和【getSnapshot】；它不 import Store，也不判断掌握度算法。打开 ProgressWorkspaceView 后才发起【getSnapshot】读取，后续来自既有 application event 的 refresh 会再次请求同一接口；L5.2 的缓存、in-flight 合并与 revision 保护负责避免重复 history I/O 和旧结果覆盖。

View 自身额外保留一个短生命周期的最近成功 snapshot 和 refresh revision：新请求开始时先显示 loading 或旧卡片；旧请求在新请求之后完成时不再回写 DOM；读取错误时保留最后成功卡片并显示 retry，若没有成功卡片则显示明确错误状态。关闭 View 时递增 revision、释放 controller 并清空 DOM，异步返回不能再渲染已关闭叶子。

#### 指标范围与缺失值规则

新增【ProgressDashboardModel】作为纯 Presentation read model，将 snapshot 和容量评估转换为固定数量的卡片与分布行：

| 面板 | 唯一事实源 | 关键规则 |
|---|---|---|
| Confirmed concepts | effective Concept catalog 聚合 | 只统计有效 Concept，不把 pending candidate、节点预算或 renderer 状态算入。 |
| Assessment coverage | Mastery snapshot | 【coverageRatio=null】显示【Not calculated】，绝不显示 0%。 |
| Mastery state / distribution | Mastery snapshot | 显示 current/stale/missing/calculating/unavailable，并完整展示五级数量。 |
| Structured assessments | Assessment Session JSON history | 显示已评分/总数和最近结构化记录；不读取 Markdown 报告。 |
| Evidence quality | Mastery unbound issues | Mastery 缺失或不可用时显示【Not calculated】，不能把 0 issue 误说成健康。 |
| Local data health | SemanticGraphApplicationApi capacity | 仅展示当前 Lite 容量建议；不连接服务、不上传数据。 |

RecommendationService 尚未存在，因此 Dashboard 只明确提示“建议将在后续阶段提供”，不以分数或相似度临时生成伪建议。

#### UI 范围

主工作区增加数据新鲜度条、五个有色状态卡、掌握度分布、容量/最新考试摘要以及既有 Learning Map 跳转按钮。卡片仅使用本插件 CSS class，不覆盖 Obsidian 全局主题。L5.4 不改动 Learning Map renderer、Focus neighborhood、关系方向或 Inspector；这些交互问题仍严格留给 L5.5/L5.6。

## 8. L5.2 测试修复记录

新增的 Application 事件测试首次失败，原因是测试中的 MasteryService fake 只提供了【rebuildAll】和【clear】，但图谱重建路径还会调用【markDirty】。这不是产品代码问题，而是 mock 没有实现实际调用的 port。

修复方式是补齐 fake 的【markDirty】。随后定向测试通过。该问题提醒后续测试不要用“仅满足测试最终断言”的不完整 fake；应用协调器测试必须提供当前操作链会触达的完整最小端口。

## 9. L5.3 测试修复记录

首次为主工作区激活器编写单元测试后，产品代码与 Vitest 均通过，但 ESLint 报告测试直接访问【workspace.getLeaf】、【leaf.setViewState】等 mock 方法可能丢失【this】绑定，同时把 Obsidian 的过时方法签名带入断言类型。

修复方式不是关闭规则，而是把每个【vi.fn】保存到独立局部变量；构造 workspace fake 时再把它们挂到对象上，断言也只引用局部 spy。这样测试仍验证真实调用参数，又不会把类型系统的 API 迁移提示误判为产品缺陷。

## 10. L5.4 测试修复记录

L5.4 将【ProgressWorkspaceView.refresh】从同步重绘改为异步按需读取。原【refreshAllViews】调用仍按同步方法处理，ESLint 因此报告 Promise 未处理。产品行为并未失败，但这种提示若被忽略，会让读取异常成为未观察的 Promise。

修复为在 composition root 的 View refresh 循环中使用【void leaf.view.refresh()】明确标记后台刷新。View 内部已捕获读取错误并渲染 retry/旧快照状态，因此这不会吞掉错误；它只是保留既有“事实变化不阻塞 Runtime”的事件链语义。

另一个编译修复来自【coverageRatio】的 nullable 类型：即使先计算了布尔变量，TypeScript 不会把该变量反向收窄原字段。模型最终直接在格式化表达式处分支，并加入缺失 Mastery evidence 的回归测试。

## 13. L5.4 补充修复：考试证据与已确认概念的可追溯绑定

### 13.1 现场问题与根因

在测试 Vault 的【.vault-coach】目录中检查到：最新空白考试已写入 5 条 0 分 Assessment event，且 evidence/evaluation confidence 均为 1；但掌握度快照包含 143 个 unknown、0 个 weak，30 条历史 event 全部被记录为【unknown-concept】。因此问题不在空白答案、评分或权重为零。

根因是旧考试生成器仍把每道题的【conceptIds】固定写成【exam-topic:*】临时主题 ID。MasteryBindingResolver 只接受“已确认概念 ID 直接相同”或“主题名与显示名/别名唯一精确相同”；蓝图主题通常是章节级短语，不能稳定等同于语义概念名称，故所有事件被安全拒绝。该临时 ID 设计来自 M1，在 M4B 后尚未完成与语义图谱的接线。

### 13.2 解决方案与兼容原则

1. 扩展 effective Concept catalog：每个已确认概念除 ID、名称、别名和路径外，还暴露只读【sourceChunkIds】。这些 ID 来自概念抽取时的原始 evidence，不使用 embedding 或模糊相似度。
2. 新生成的考试题在生成完成时，以题目的【sourceChunkIds】查找同一来源 chunk 上的已确认概念，将所得稳定【concept:*】ID 直接写入【question.conceptIds】。没有命中时才保留【exam-topic:*】兼容回退。
3. MasteryBindingResolver 增加最后一级的“source-chunk-evidence”精确回退：仅当旧 event 的临时 ID/名称无法绑定时，按其持久化的 sourceChunkIds 解析当前 catalog。这样历史 Assessment JSON 保持不可变，但重建掌握度后可利用原始来源重新绑定。
4. 一个题目可能引用同一 chunk 中多个已确认概念时，分数会作用于这些均有直接来源证据的概念。这是保守的 provenance 归因，不会对不在题目来源 chunk 中的概念扩散，也不会沿图谱关系传播分数。
5. 若 source chunk 没有已确认概念，事件继续显示为 unbound/unknown；不能用词面、ANN 或模型猜测补齐，因为掌握度中的错误归因比未知更有害。

### 13.3 预期结果

修复后，重新计算掌握度时，测试 Vault 中已有的 30 条历史 event 会优先按 source chunk 重新解析。空白考试所覆盖的概念将成为【weak】，其余未覆盖的已确认概念仍为【unknown】；未来新考试会把真实概念 ID 直接持久化，不依赖兼容回退。

### 13.4 实现与验证记录

- 【LearningGraphQueryService】现在从 effective Concept evidence 构造一次性【chunkId → concept IDs】只读索引；ExamEngine 在每次生成考试时只读取一次该索引。
- 【ExamQuestionGenerator】优先持久化该索引给出的已确认【concept:*】ID；图谱缺失、语义图谱未启用或题目来源尚无概念 evidence 时保持旧的【exam-topic:*】回退。
- 【MasteryBindingResolver】在直接 ID 和唯一名称/别名均失败后才使用 source chunk evidence；不会重写旧 Assessment JSON，也不会做 embedding、相似度或关系传播。
- 掌握度算法版本从【mastery/v1】升为【mastery/v2】；旧快照在加载后会显示为“需要重建”，不能继续被当作按旧绑定规则计算出的 current 数据。下一次提交新考试或执行“重建概念掌握度”都会触发全量重算。
- 新增回归覆盖：新题写入稳定 concept ID、catalog 的 chunk 索引确定性、旧 provisional event 的 0 分证据会使同源概念成为 weak。

## 14. L5.5：正式 Learning Map 画布与可逆探索

### 14.1 用户反馈与交付边界

此前 Learning Map 使用确定性规则网格，其优点是渲染开销低，但视觉上更像调试投影，无法表达关系图谱的聚簇与邻接；点击【聚焦邻域】后只有【重置探索】，也无法回到用户刚才的搜索或上一级邻域。本步骤将它升级为正式的只读图谱浏览器。

本步骤仍不编辑任何 semantic candidate、confirmed relation 或用户决策；确认、拒绝、合并、关系编辑继续属于 Concept review。Learning Map 只消费已经由 M2 + M3 决定的有界 projection。

### 14.2 实现方案

1. 【LearningGraphRenderer】以稳定节点 ID 作为初始种子，在现有 `maxNodes=150` 的 projection 内执行一次确定性力导向布局。节点排斥、最小碰撞距离、关系弹簧和向中心的弱回归共同形成接近 Obsidian 原生关系图的空间分布；不新增第三方图库，也不把 catalog 全量交给 renderer。
2. 力导向布局仅在 View 创建时同步计算一次，当前上限下约为 150 次 × 150² 的纯视觉运算；没有动画循环、后台 timer、embedding 或磁盘 I/O，因此不会与语义图谱构建竞争，也不会产生“等待后随机跳动”的画面。
3. 图谱支持背景拖拽平移、滚轮缩放、【适配视图】、节点拖拽和键盘 Enter/Space 选择。边连接到节点圆周而非圆心；有方向的 confirmed/user/structural relation 使用箭头，检查器仍以 `source → target` 显示事实方向。
4. 为避免 150 个标签互相覆盖，连接节点、选中节点、悬停节点及其一跳邻居显示名称；孤立节点仍可通过鼠标悬停的原生 SVG title 与点击发现。选中/悬停时非邻域节点和边淡出，关系局部结构更易辨认。
5. 【LearningMapController】新增内存中的 focus history。每次进入新的 Focus neighbourhood 都保存完整的上一个 query（搜索词、关系筛选和结构上下文）；工具栏在有历史时显示【返回上一步】。全局搜索或【重置探索】会清空历史，避免回到已失效的探索分支。

## 15. L5.5 补充：关系可见性、自动候选与正式 Canvas 画布

### 15.1 反馈与事实核查

现场 Learning Map 出现“150 个节点、0 条关系”。实现核查表明，Learning Map 过去只读取 `SemanticGraphProjector.project()` 的 effective relations：候选关系必须经过确认才会进入该集合。因此，未确认候选不会连线是原设计；但已经保存的确认决策也显示为 0 条关系则不符合预期。

## 16. L5.5 布局修复：高 degree 留白与稳定首帧

### 16.1 现场问题

自动关系开启后，150 节点投影包含约 200 条以上关系。旧 Canvas 实现从哈希散点启动 96 帧动画；节点圆形虽然通常不会完全重叠，但所有已连接节点都会在概览缩放下显示文本，形成“标签重叠、虚线箭头堆叠、重新打开大幅跳动”的视觉问题。该动画也会使用户误以为每次打开都在随机重新计算。

### 16.2 修复方案

1. 首次绘制前同步完成确定性布局，不再运行自动 requestAnimationFrame 位移动画；相同节点/边输入每次打开得到相同坐标。仅保留显式 reheat 的 18 步微调，且当前 UI 不会在打开时调用它。
2. 统计每个节点的入边与出边总数作为 degree。degree 越高，显示圆点略大、布局碰撞半径越大、弹簧目标长度越长；高连接 hub 周围因此会留下可读的关系扇区，而不是把叶子压在箭头终点附近。
3. 每步力导向运算后额外执行两次直接碰撞分离。该约束比单纯的排斥力可靠，专门保证星形 hub、密集候选图中节点圆形不会重合。
4. 概览缩放只显示选中节点、悬停节点及其一跳邻居的标签；用户放大到 1.35 倍后才显示完整局部名称。这使默认全图保留原生图谱式的“点和线优先”阅读层级。
5. 自动候选边进一步降低不透明度，并默认不画箭头；选中或聚焦其端点时才显示候选方向。confirmed/user relation 的箭头始终可见。背景由方格改为稀疏点阵，避免画布像调试网格。
6. 布局迭代数随节点数按 pair-operation 预算自适应：典型 150 节点概览获得充分求解，500 节点完整模式也不会因 O(V²) 计算卡住主线程。

【tests/presentation/learning-graph-renderer.test.ts】现验证：布局确定性、画布边界、二维分布、任意节点的最小间距，以及高 degree hub 与最近叶子节点之间的留白。完成后执行完整 build、lint、test 与 diff check。

## 17. L5.5 布局深化：椭圆星系与社区聚类

### 17.1 设计调整

上一轮只是在单一力导向空间中为 hub 增加留白，仍会把所有节点钳制在画布的矩形世界坐标内，无法表达“多个核心知识点及其各自关联圈”。本轮将 Canvas 明确为观察窗口，而非世界边界：节点世界坐标不再被矩形钳制，用户可平移浏览，点击【适配视图】后会将所有星系整体纳入当前窗口。

### 17.2 星系算法

1. 先对当前有界 projection 计算每个节点的总 degree（入边 + 出边）；`degree=0` 使用基础半径，degree 越大半径单调增大，最高额外增加 18 个世界坐标单位。
2. 根据无向邻接关系拆分连通分量；每个较大分量选取约 `sqrt(V)/2` 个高 degree hub。优先选取相距超过两跳的 hub，稠密图中再稳定补齐种子，避免所有候选都坍缩到同一个中心。
3. 对 hub 执行多源 BFS；每个节点被分配给最近 hub，平局时按稳定 ID 决定。因此连接到相同核心知识点的节点成为一个社区。
4. 社区中心沿椭圆黄金角分布形成多个星系；星系内部以 hub 为中心按 hop/ring 初始化。跨社区关系的弹簧目标长度比社区内部关系更长，所以星系间仍能以桥接边关联，但不会挤为同一团。
5. 力导向阶段保留社区中心的轻微世界坐标吸引，不引入画布边界；碰撞分离继续保护高 degree 节点周围的可读留白。

### 17.3 回归验证

新增 renderer 测试覆盖：degree 半径单调增长、两个由桥接边连接的 hub 社区形成分离星系、叶子节点仍更接近自己的 hub。最终 `npm run build`、`npm run lint`、`npm test`（44 个文件、162 项）与 `git diff --check` 均通过。

### 17.4 Hub 视觉强化

验收反馈表明原半径增量在密集自动候选图中仍不够醒目。本次将 degree 半径映射从“基础半径 + 最多 18”提高为“基础半径 + 最多 32”，并提高平方根系数。以 degree 25 为例，hub 相比 degree 0 节点至少额外增加 30 个世界坐标单位；碰撞半径继续由显示半径派生，因此增大不会导致邻居压到 hub 上。

## 18. L5.5 交互与页面空间修复

### 18.1 触控板缩放

旧实现每个 wheel event 固定乘以 1.12/0.88。触控板会连续发出大量极小事件，因此视觉上放大过快。现在改为将 `deltaY` 统一换算为像素并使用指数倍率 `exp(-delta × 0.00045)`；小 delta 只产生极细微变化，鼠标行滚动和页面滚动也有统一且被限制的最大步长。新增单元测试覆盖触控板小 delta、正反方向和 line mode。

## 22. L5.5 悬浮标签与图例字号对齐

## 23. L5.6 Inspector、来源跳转与定向考试入口

### 23.1 边界与交互

Learning Map 仍是只读投影；不会因查看节点而写入 Concept、关系、Mastery 或考试记录。概念检查器在固定高度内补充以下可追溯摘要：名称和稳定 Concept ID、单行简介、Alias、当前 Mastery 等级/分数/置信度/趋势、已绑定评估证据数量，以及当前投影中的出入关系数。没有 Mastery snapshot 时明确显示“尚未计算/需要重建/计算中”，不把没有证据解释为答错。

### 23.2 “按此知识考试”不是提前实现 L6

L6 才会引入基于弱项、前置关系与 Assessment history 的自适应 `ExamPlan`。本步骤只复用已经稳定的手动考试流程：

1. 从选中 effective Concept 的 `sourcePaths` 与来源 evidence 去重取得 Vault 文件路径；

## 25. Learning Map 画布填充与完整投影默认值

### 25.1 问题与原因

图谱容器会随主工作区高度增长，但 Canvas 仍以固定 `23 / 16` 宽高比渲染。容器高于该比例时，Canvas 只占据上半区域；下半部分只是同色的空容器，而图例又绝对定位到容器底部，造成“图谱不能显示在下半部分”的错觉。

此前 Learning Map 初始 query 固定使用 150 节点 / 300 边概览预算。对于当前 334 节点、388 边的测试库，这不是容量限制，而是 UI 默认值造成的静默隐藏；用户必须识别图标化的【显示全部】才会看到完整图。

### 25.2 修复

1. Canvas 改为 `width: 100%; height: 100%`，填满 Learning Map 已分配的图谱容器。renderer 已按实际 `getBoundingClientRect()` 分别换算 X/Y 指针坐标，因此非固定宽高比不会破坏平移、缩放、命中测试或适配视图。
2. Learning Map 初始 query 改为本地 renderer 的硬上限：500 节点 / 2,000 边。低于该阈值的 Vault（包括当前测试库）首次打开就展示所有节点和关系；用户仍可通过【显示概览】回到 150 / 300 的轻量投影。
3. 超过 500 / 2,000 的 Vault 仍被有界投影保护，信息面板明确显示截断原因；不会显示一个无法真正“显示全部”的切换按钮。

### 25.3 回归

LearningMapController 新增默认完整投影断言；renderer 的布局和缩放定向测试继续通过。最终交付前执行完整 build、lint、test 与 diff check。

### 25.4 修复：填满容器不能靠 CSS 拉伸

验收发现上一版 `height: 100%` 只是把固定 `920 × 640` backing canvas 拉到更高的 CSS 盒子。浏览器对 X/Y 使用不同显示倍率，节点圆形变为椭圆；且 renderer 仍以旧 `640` 高度计算 `fit()`，额外区域没有增加可见世界空间。

现在 renderer 在 Canvas 挂载后和每次容器 resize 时读取实际尺寸，并同步更新：backing store（含 device pixel ratio）、逻辑 viewport 宽高、坐标换算、平移增量、wheel page delta、网格和 `fit()` 中心/缩放。ResizeObserver 触发后仅重新适配当前图，不重新执行 force layout；所以节点坐标稳定、圆形保持圆形，新的垂直空间确实纳入图谱视口而非被拉伸像素填充。

## 26. L5.7 每叶状态、资源回收与回归

### 26.1 每个工作区标签页的可恢复状态

Learning Map 现在实现 Obsidian `ItemView.getState/setState`，状态版本为 1，并且只保存 Presentation state：当前 query（搜索、关系筛选、来源/自动关系开关、完整/概览）、focus history、选中节点/边，以及用户拖动后固定的节点坐标。

固定布局只保存 `pinnedPositions`，不会保存所有 force-layout 中间坐标：未拖动节点继续由确定性布局计算，已拖动节点才以有限、校验后的坐标恢复。恢复时会过滤掉已经不存在的节点、非数值/无穷坐标和超过 500 条的异常状态。图谱事实、Mastery、考试、设置和 JSON Store 不会因关闭/打开 leaf 而被写入。

### 26.2 生命周期

1. renderer 在每次重绘前先导出 pinned layout、再 `destroy()`；`destroy()` 会断开 `ResizeObserver` 并移除 Canvas DOM。
2. View 关闭或刷新失败时取消 search popover 的延迟 focus timer、递增 refresh revision，并释放旧 renderer；晚到的 projection Promise 不再写入已经关闭或已被新请求替代的 View。
3. 容器 resize 只重新适配视口，不重新运行 force simulation；用户固定的节点坐标仍被恢复。
4. 重新打开同一个 Workspace leaf 时，Obsidian 恢复该 leaf 自己的状态；不同分屏 leaf 不共享筛选或选择。

### 26.3 回归

新增测试覆盖：controller 的搜索、关系筛选、显示开关、概览/完整模式和 focus history 可序列化后恢复；损坏 workspace state 保持安全默认；pinned layout 只恢复当前 projection 中具有有限坐标的节点。最终检查见本轮完整 CI。

## 28. 来源节点图例与“概念—来源”关系边界

Learning Map 的【显示来源结构】开启后，除了灰色的文档/章节节点，还会按需显示橙色的标签节点。图例现在将两类来源节点分别说明：灰色圆点代表文档或章节，橙色圆点代表来自 frontmatter 或行内 `#tag` 的标签；灰色带箭头线仍表示确定性来源结构连接。它们都不是语义 Concept，不能参与 Mastery、考试范围决策或自动关系置信度。

当前版本刻意不在画布上把每一个 Concept 直接连到所有 evidence section：Concept 已保留可追溯证据，但若把这类多对多证据全部画为普通边，中大型 Vault 会迅速成为以文档为中心的星状噪声图，挤压学习关系的阅读空间。后续如需增强来源追溯，应添加单独的只读 `evidenced_by` provenance 边，并限制为“选中/聚焦 Concept 时按需展开”，而不是把它和 `prerequisite_of` 等学习事实混为同一层。
