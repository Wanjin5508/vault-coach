# 里程碑 1：结构化考试证据开发日志

## 1. 文档目的

本文将《v1.3.4 后续规划》的“里程碑 1：结构化考试证据”转换为可逐项实施、审查、测试和提交的开发日志。

里程碑 1 的唯一业务目标是：把一次已经评分的考试，稳定保存为可供后续掌握度引擎消费的、可追溯且不可被 Markdown 报告误删的事实证据。

本里程碑完成后，考试仍保持现在的生成、作答、评分、保存、导出和历史查看体验；改变的是其内部事实源：新考试的事实源从单一 Markdown 文件升级为 Assessment Session JSON，Markdown 仅作为人可读投影。

强制规则：

- `AssessmentEventFactory` 必须是纯函数式领域服务：输入题目、评分结果、会话和时间/ID 依赖，输出事件；不读文件、不调用 LLM、不生成 DOM；
- `ExamEvaluationService` 只负责“请求模型并归一化结果”，不得保存文件或创建事件；
- `VaultCoachApplication` 只编排“保存事实 → 投影报告 → 通知历史变化”，不拼接 Markdown、不解析 JSON；
- JSON 与 Markdown 存储只能由 `infrastructure/storage` 接触 `App`、`VaultAdapter`、路径和文件 API；
- 现有 `ExamSessionStore` 在迁移期可以保留为 facade，但其 `save()` 不得再次成为唯一事实写入点；
- `AssessmentEvent` 一旦成功写入 JSON 不得原地修改；重新评分只能追加新事件，并填写 `supersedesEventId`。

## 5. 数据契约

### 5.1 `ExamQuestion` 的扩展

在 `src/domain/exam/exam-types.ts` 把当前轻量题目扩展为下列语义。类型名保持不变，避免扩大调用方改动面。

```ts
export type ExamQuestionType =
    | "explanation"
    | "comparison"
    | "application"
    | "reasoning"
    | "process";

export type ExamDifficulty = "basic" | "intermediate" | "advanced";

export interface ModelPromptMetadata {
    modelProvider: string;
    modelName: string;
    promptVersion: string;
}

export interface ExamQuestion {
    id: string;
    blueprintItemId: string;
    question: string;
    referenceAnswer: string;
    rubric: string;
    questionType: ExamQuestionType;
    difficulty: ExamDifficulty;
    sourceChunkIds: string[];
    evidenceExcerptIds: string[];
    sourcePaths: string[];
    conceptIds: string[];
    generationMetadata: ModelPromptMetadata & { generatedAt: number };
}
```

字段来源必须确定，不能由另一次 LLM 调用补齐：

| 字段 | 唯一来源 | 实现位置 |
|---|---|---|
| `blueprintItemId` | `GeneratedExamQuestionCandidate.blueprintItemId` | `ExamQuestionGenerator.convertCandidateToQuestion()` |
| `questionType`、`difficulty` | 与 candidate 匹配的 `ExamBlueprintItem` | 同上；找不到蓝图项视为生成失败，不得静默猜测 |
| `sourceChunkIds`、`evidenceExcerptIds` | 已经验证过的 candidate | 同上；去重后保留原顺序 |
| `sourcePaths` | `sourceChunkIds → IndexedChunk.filePath` | 维持当前逻辑 |
| `conceptIds` | 本文 5.2 的确定性 provisional binding | 同上 |
| `generationMetadata` | 当前配置的 provider/model、问题生成 Prompt 常量版本和生成时间 | `ExamQuestionGenerator` 的一次生成上下文 |

为降低一次性升级的破坏性，读取旧的 session JSON/测试 fixture 时应在存储反序列化边界补默认值；领域代码内部禁止长期使用 `undefined` 代替上述字段。

### 5.2 里程碑 1 的 Concept ID 策略

里程碑 1 需要事件可追溯到 Concept，但语义图谱要到后续里程碑才建立。因此本阶段不能让 LLM 临时“发明”概念，也不能依赖尚不存在的 Graph Store。

采用确定性的 provisional topic binding：

```text
blueprintItem.topic
  → trim + Unicode 规范化 + 小写 + 压缩空白
  → stableHash(normalized topic)
  → exam-topic:<hash>
```

要求：

- 每个蓝图项至少产生一个 `conceptIds` 条目，值为上述稳定 ID；
- 在 Assessment Session JSON 的 `conceptBindings` 中保存 `{ id, label, sourceBlueprintItemId, kind: "provisional-topic" }`，以便事件 ID 可回查为人类可读主题；
- 相同规范化 topic 在同一次或不同次考试中产生相同 provisional ID；
- 不在本里程碑做别名归并、跨语言匹配、关系推断或概念编辑；
- 后续语义概念图谱必须通过显式映射或迁移将 provisional ID 对应到正式 Concept，不能改写既有事件。

该策略使 M1 已满足“事件可追溯到 Concept”的证据要求，同时不越界实现图谱。

### 5.3 评分结果与错误分类

在 `exam-types.ts` 增加：

```ts
export type AssessmentErrorCode =
    | "missing-key-point"
    | "concept-confusion"
    | "incorrect-causal-relation"
    | "incorrect-definition"
    | "incomplete-process"
    | "incorrect-application"
    | "unsupported-claim"
    | "irrelevant-answer"
    | "no-answer"
    | "other";

export interface ExamEvaluationItem {
    questionId: string;
    score: number;
    maxScore: number;
    feedback: string;
    improvement: string;
    coveredKeyPoints: string[];
    missingKeyPoints: string[];
    errorCodes: AssessmentErrorCode[];
    evaluationConfidence: number;
    evaluator: ModelPromptMetadata & { evaluatedAt: number };
}
```

归一化规则必须写成测试：

| 输入情况 | 归一化结果 |
|---|---|
| 缺少 `covered_key_points` / `missing_key_points` | 空数组 |
| 字符串、数组或混合值 | 修剪、过滤空值、保序去重为字符串数组 |
| 未知、重复或格式错误的 error code | 已知代码保留且去重；未知值折叠为一次 `other` |
| 用户答案为空白 | 强制加入 `no-answer`，不能完全依赖模型判断 |
| `evaluation_confidence` 非数值或越界 | 截断至 `0..1`；缺失时为 `0` |
| `score` / `max_score` 异常 | 沿用现有 `0..100`、整数、`maxScore = 100` 的行为 |
| 模型漏掉题目 | 仍产生一条该题评分，分数和文本使用当前回退文案，证据字段取安全默认值 |

评分 Prompt 只增加输出字段及其 JSON schema，不改变现有评分目标、温度、100 分制、总分算法或现有回退文案。新增常量，例如 `EXAM_EVALUATION_PROMPT_VERSION = "exam-evaluation/v2"`，并在提交通用例中把当前模型信息作为显式元数据传入服务；领域服务不得读取设置对象。

### 5.4 `AssessmentEvent` 与不变性

在 `src/domain/assessment/assessment-types.ts` 定义：

```ts
export interface AssessmentEvent {
    id: string;
    eventType: "exam-answer";
    sessionId: string;
    questionId: string;
    conceptIds: string[];
    sourceChunkIds: string[];
    rawScore: number;
    normalizedScore: number;
    difficulty: ExamDifficulty;
    questionType: ExamQuestionType;
    errorCodes: AssessmentErrorCode[];
    evidenceConfidence: number;
    evaluationConfidence: number;
    occurredAt: number;
    evaluator: {
        provider: string;
        model: string;
        promptVersion: string;
    };
    supersedesEventId?: string;
}
```

事件不应重复保存任何可由 session/question 读取的大段题干、答案或模型输出。事件保存最小事实引用与评分证据；详细可读内容由 session JSON 承担。

事件不变式：

1. 仅当 `session.evaluation !== null` 时产生事件；
2. `evaluation.items` 中每一道匹配题目必须产生一条事件；若评分项缺失，由评分服务先补齐再创建事件；
3. `rawScore` 为归一化前的有效题目分数，`normalizedScore = rawScore / maxScore`，范围固定为 `0..1`；
4. `evidenceConfidence` 由来源完整度确定：有 Chunk 且有证据摘录为 `1`，有 Chunk 无摘录为 `0.7`，没有 Chunk 为 `0`；该规则必须是纯确定性函数；
5. `occurredAt` 使用该评分项的 `evaluator.evaluatedAt`，而非 Markdown 写入时间；
6. 新事件 ID 由注入的 ID 生成器生成，测试使用固定生成器；
7. 重评时新增事件，其 `supersedesEventId` 指向同一 `sessionId + questionId` 最近一条未被替代的事件；不得覆盖旧 event。

### 5.5 Assessment Session JSON

JSON 文件的根对象必须有 schema 版本，且保存完整会话与事件，不依赖 Markdown 恢复任何事实：

```ts
export interface AssessmentConceptBinding {
    id: string;
    label: string;
    sourceBlueprintItemId: string;
    kind: "provisional-topic";
}

export interface AssessmentSessionDocumentV1 {
    schemaVersion: 1;
    sessionId: string;
    savedAt: number;
    examSession: ExamSession;
    assessmentEvents: AssessmentEvent[];
    conceptBindings: AssessmentConceptBinding[];
}
```

文件布局固定为：

```text
.vault-coach/
├── assessments/
│   ├── sessions/
│   │   └── <session-id>.json
│   └── index-v1.json
└── exams/
    └── <session-id>-<human-readable-title>.md
```

`index-v1.json` 仅保存历史列表所需的摘要和 JSON 相对路径，例如 `sessionId`、`reportPath`、`title`、`createdAt`、`score`、`maxScore`、`updatedAt`。它不是事件副本，也不是新的真相来源；读索引失败时应能扫描 `assessments/sessions/*.json` 并重建索引。

### 5.6 写入、投影和失败语义

一次已评分会话的保存顺序必须固定：

```text
评分完成的 ExamSession
  → AssessmentEventFactory
  → 写入并校验 Assessment Session JSON
  → 更新 index-v1.json
  → 写入 Markdown 投影
  → 发送 exam-history-changed
```

具体约束：

- JSON 写入采用“临时文件 → 校验 JSON → rename/replace”的单文件提交策略；若当前 Obsidian Adapter 不支持原子 rename，则把兼容降级封装在 JSON Store 内，并保留可恢复的 `.tmp` 文件规则；
- JSON 写入或索引写入失败时，不写 Markdown、不发成功通知、不把会话标为 `saved`；
- JSON 成功而 Markdown 投影失败时，结构化事实必须保留，应用层返回可定位的“报告投影失败”错误，并提供下一次保存/历史读取时的重试投影路径；
- 重新生成 Markdown 只能读取 `AssessmentSessionDocumentV1` 并调用纯 formatter，绝不能重新运行评分或事件工厂；
- 导出到用户目录仍是独立副本，仅写导出的 `.md`，不修改 JSON、索引或既有事件；
- 删除当前报告和按路径删除历史都只删除 `.vault-coach/exams/*.md`，绝不删除 `assessments/sessions/*.json` 或其中的事件；结构化事实的清除/撤销策略留给后续版本设计。

## 6. Markdown 投影与旧历史兼容

### 6.1 新报告格式

保留 `formatExamSessionMarkdown()` 作为纯 formatter，并保持当前 front matter 键 `vaultCoachExam`、`examId`、`createdAt`、`score`、`maxScore`、`scope` 和既有标题/题目/评分章节可读。

新报告可以额外增加不影响旧解析的投影元数据：

```yaml
vaultCoachAssessmentProjection: true
assessmentSchemaVersion: 1
assessmentSessionPath: ".vault-coach/assessments/sessions/<session-id>.json"
```

这些字段只是定位线索，不能替代 JSON；Markdown 正文可以展示“关键点”“待补足关键点”“错误分类”，但不应为了展示而改写 JSON 事件。

### 6.2 历史读取策略

历史列表要合并两种来源，并以 JSON 为优先：

| 历史类型 | 识别条件 | 列表与打开行为 | 是否创建/修改事件 |
|---|---|---|---|
| 新结构化会话 | `assessments/index-v1.json` 或 session JSON 存在 | 用 JSON 摘要列出；报告不存在时按 JSON 重建后显示 | 否 |
| 新结构化会话的残留报告 | Markdown 存在且 front matter 指向 JSON | 与 JSON 条目按 `sessionId` 去重，JSON 优先 | 否 |
| 旧 Markdown 历史 | 仅存在 `.vault-coach/exams/*.md`，无 JSON | 使用现有 `parseExamHistoryItem()` 列出和读取 | 否 |
| 损坏 JSON | 有文件但无法解析或 schema 不支持 | 列出可诊断错误；不删原文件、不以空数据覆盖 | 否 |

禁止在后台批量迁移旧 Markdown：旧记录缺少 `sourceChunkIds`、`blueprintItemId`、模型版本和可靠的逐题评分依据，自动补出事件会污染后续 Mastery 数据。后续若提供迁移工具，必须由用户明确确认，并把结果标为低置信度导入记录。

### 6.3 保持现有 UI 行为

`ExamController`、`ExamView` 和 `LegacyPluginApiAdapter` 继续使用现有 API 名称和返回类型：

```ts
evaluateExamSession(session, userAnswers): Promise<ExamSession>
saveExamSession(session): Promise<ExamSession>
listExamHistory(): Promise<ExamHistoryItem[]>
readExamHistoryContent(path): Promise<string>
deleteExamSession(session): Promise<void>
deleteExamHistory(path): Promise<void>
```

第一版实现不要把 `AssessmentEvent` 暴露给 UI，也不要增加 Progress Tab。应用层在 `saveSession()` 内部完成事件创建与“JSON 事实优先”保存，从而保持目前“评分后自动保存”的时序与按钮文案不变。

为支持报告已被删除的结构化会话，需要在不改变 UI 接口的前提下定义稳定的虚拟历史路径：`ExamHistoryItem.path` 对 JSON 条目使用其可再生 Markdown 路径；`readHistoryContent(path)` 首先查找该路径关联的 JSON，报告缺失则重建并返回。旧 Markdown 仍按原路径直接读取。

## 9. 手动验收脚本

在测试 Vault 中按下列顺序验证，过程中不要修改现有的真实 Vault 考试文件：

1. 选择若干含多个 Chunk 的笔记范围，生成一场考试，确认题干、题数、来源链接和原有界面无变化；
2. 提交一题完整答案、一题错误答案和一题空白答案，确认评分页面、分数和错误提示符合原行为；
3. 等待自动保存，检查同时生成：

   ```text
   .vault-coach/assessments/sessions/<session-id>.json
   .vault-coach/assessments/index-v1.json
   .vault-coach/exams/<session-id>-<title>.md
   ```

4. 打开 JSON，确认每一道评分题都有一个 event，且 event 可经 `sessionId`、`questionId`、`sourceChunkIds` 和 `conceptIds` 回溯；确认 evaluator 有 provider、model 和 Prompt 版本；
5. 保存一份 JSON 内容副本，删除对应 Markdown，重新打开考试历史；确认记录仍存在、报告可重建，且 JSON 逐字节不变；
6. 再次保存未重评的同一会话，确认没有多出 event；执行明确重评，确认旧 event 保留、新 event 带 `supersedesEventId`；
7. 打开预先准备的旧中文、英文和无 front matter Markdown，确认均可列出和读取，且不会生成 `assessments/sessions` JSON；
8. 删除一份新报告，确认只删除 Markdown；确认结构化会话仍在历史中可恢复；
9. 导出报告到普通 Vault 目录，确认导出文件可读，且隐藏目录 JSON/index 未被改写；
10. 重启 Obsidian，确认历史、报告重建和现有 Ask/Exam/设置/索引功能均正常。

## 10. 风险、决策与回滚边界

| 风险 | 预防措施 | 回滚策略 |
|---|---|---|
| 新字段导致旧测试或旧 session 不可读 | 反序列化边界默认值、legacy fixture、分步骤提交 | 回退到步骤 2 前；旧 Markdown 不受影响 |
| LLM 不返回新字段 | 强制 Prompt schema + 安全归一化 + 契约测试 | 保持评分可用，证据字段用安全默认值 |
| JSON 写入中断 | 临时文件、读回校验、索引可重建 | 保留原 JSON，清理/恢复临时文件，不覆盖事实 |
| Markdown 删除被误解释为删除考试 | 明确 delete 只作用报告、测试 JSON 仍存在 | 从 JSON 重建报告 |
| 重复保存产生重复事件 | 评分 fingerprint 与 active-event 查询 | 删除重复报告无效；事件修复只能追加撤销/替代，不原地改写 |
| provisional concept ID 未来无法对齐图谱 | 保存 binding label/blueprint 关系，后续显式映射 | 保留旧 ID，新增映射，不改写 event |
| 迁移扩大 UI 改动面 | 保留 Application API 和 Legacy Adapter 形状 | 停在 facade 层，不迁移 UI |

回滚时只回滚程序代码，不删除用户已经生成的 `.vault-coach/assessments` 文件。未知 schema 文件必须保留；后续版本可选择读取或提供导出工具。

## 12. 与后续里程碑的接口

里程碑 1 只产出 Assessment 事实，不计算学习结论。后续模块必须遵守：

```text
ExamSession JSON + AssessmentEvent[]
             ↓
（里程碑 2/3）Concept/Graph 映射
             ↓
（里程碑 4）MasteryEngine 只消费 AssessmentEvent[]
             ↓
ConceptMasteryState[]
             ↓
（里程碑 5/7）Progress 与 Review UI
```

`MasteryEngine` 不得读取 Markdown 报告，也不得直接调用 LLM。Markdown 可以被删除和再生成；Assessment Event 才是后续掌握度计算的证据边界。
