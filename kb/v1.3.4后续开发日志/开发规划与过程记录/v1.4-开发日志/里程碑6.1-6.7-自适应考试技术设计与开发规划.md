# 里程碑 6.1–6.7：自适应考试技术设计与开发规划

> 实施状态（2026-07-25）：本规划的 M6.1–M6.7 主链路已落地并通过全量自动化回归。下面的设计章节保留为决策依据；第 12 节记录实际模块、边界和验证结果。

## 1. 定位与已知基线

M6.0 已解决一次考试的**作答形式与评分路由**问题：用户可在 `simple` 与 `challenge` 中选择；simple 只产生单选/判断题并由本地答案键确定性评分，challenge 才允许既有自由文本题与客观题共存。分析完成后，范围、文件、题量、智能筛选和 `ExamMode` 被锁定；用户只能生成，或显式返回设置页、丢弃分析结果后重新修改。

M6.1–M6.7 不推翻上述实现，而是在其之上解决另一件事：**根据可追溯的学习证据，选择为什么考、优先考哪些知识。**

~~~text
M6.0：用户选择如何作答、如何评分
        simple / challenge
                 ↓ 固定为本场策略
M6.1–M6.7：系统根据有效图谱、掌握度与 Assessment 选择考什么、为什么考
        diagnostic / weak-review / prerequisite / mixed
                 ↓ 产生可审计 ExamPlan
既有 ExamEngine：在限定来源内生成题目、评分、保存和导出
~~~

两个维度必须正交：

| 维度 | 值 | 负责的问题 | 明确不负责 |
|---|---|---|---|
| 自适应目标模式 | `diagnostic`、`weak-review`、`prerequisite`、`mixed` | 为什么考、哪些 effective Concept 优先 | 不选择 UI 题型、不改变评分规则 |
| 考试模式 `ExamMode` | `simple`、`challenge` | 用户如何作答、使用本地还是既有模型评分路由 | 不代表能力等级、不改变 Mastery 权重 |

因此，challenge 中取得高分不天然比 simple 中取得高分“更有价值”；两者都仅以已保存的题目、来源、评分和 confidence 形成 Assessment 事实。后续若需要研究不同题型的校准问题，应另开里程碑，不能暗中塞入 L6 的排序逻辑。

## 2. 技术决策与不可破坏的边界

### 2.1 采用受限的确定性 Planner，不引入通用 Agent

本阶段的选题是一个有限排序问题，输入与输出都有完整 schema，不需要 Agent、多轮 workflow 或工具调用：

1. 读取已确认的 effective Concept、确认的前置关系、Mastery 快照和已保存 Assessment 事实；
2. 过滤当前用户范围外、没有可证明来源 chunk、pending/rejected 的对象；
3. 对剩余候选按版本化规则计算理由、优先级和冷却期；
4. 以稳定排序截取有限 `ExamTarget`；
5. 将目标与已锁定的 `ExamMode` 交给既有考试蓝图与题目生成流程。

该过程使用 **TypeScript strict + 纯领域函数 + 显式依赖注入 + 稳定排序** 即可实现。它不发送额外模型请求，不读取网络，不循环“自我修复”，也不会让模型直接决定 Concept、关系、分数或 Mastery。LLM 仍只在 M6.0 已有的蓝图/题目生成与自由文本评分位置工作，且继续受 schema、来源范围、取消信号和既有上限约束。

### 2.2 分层与依赖方向

~~~text
Presentation（Exam View / Controller）
  ↓ 仅调用
Application（AdaptiveExamPlanner / Exam Application API）
  ↓ 读取 ports；组合快照
Domain（adaptive-exam 纯规则、验证、fingerprint）
  ↓ 只依赖 domain types
Infrastructure（Assessment JSON、graph/mastery/query adapter、Obsidian）
~~~

- `src/domain/adaptive-exam/` 不导入 Obsidian、Store、Model client 或 DOM；其输入是已归一化的值对象。
- `src/app/exam/` 通过窄 port 获得 Learning Graph、Mastery、Assessment 覆盖和范围解析结果；不直接读取 JSON 文件。
- `src/exam/` 只接受已验证的计划/目标/来源，不反向查询图谱或掌握度。
- Presentation 不保存计划事实、不读取 Store；只拥有可丢弃的界面状态。
- Graph、Concept Review 和语义重建是只读输入。M6 不新增 graph write 端口、语义抽取调用或重建任务。

### 2.3 复用技术与新增技术

| 需要 | 采用技术 | 复用/落点 |
|---|---|---|
| 领域契约和校验 | TypeScript `strict`、判别联合、只读数组、纯函数 | 新建 `src/domain/adaptive-exam/` |
| 可重复计划 | canonical serialization、`stableGraphHash` 风格的浏览器兼容稳定 hash、`localeCompare` 排序 | 参考 `src/domain/graph/graph-id.ts`；不得使用 Node `crypto` |
| 去重与候选聚合 | `Map`、`Set`、显式 tie-breaker | planner 内存计算，输入规模受现有图谱/考试预算限制 |
| 读取知识证据 | Application port/adaptor、effective Learning Graph、Mastery snapshot、Assessment history | `src/app/learning-graph/`、`src/app/mastery/`、Assessment Store facade |
| 取消与进度 | 既有 `AbortSignal`、`ExamGenerationProgress`、controller busy state | 不再新建后台队列或轮询器 |
| 持久化与兼容 | 可选 JSON 字段、schema/version 校验、Markdown projection version | `AssessmentSessionDocumentV1`、Exam Session Markdown |
| 题目/评分 | M6.0 `ExamMode`、蓝图 schema、答案键、`ExamEvaluationRouter` | 不另造评分器或第二个模型 verifier |
| UI | Obsidian 原生 DOM、Controller state machine、i18n、CSS | `ExamController`、`ExamView`，不引 React/状态库 |
| 验证 | Vitest、ESLint、`tsc -noEmit -skipLibCheck`、esbuild、`git diff --check` | 现有 npm scripts |

### 2.4 全局不变量

1. 只有 effective Concept、确认关系、可追溯 source chunk 和已保存 Assessment event 可以进入 Planner。
2. `ExamPlan` 只是一份可再生的派生规划；Exam Session、Assessment JSON、原始 Markdown/PDF 和用户图谱决策才是事实源。
3. 无法从目标 Concept 证明 source chunk 时，Planner 不得把名称相似或 embedding 相近的内容强行绑定为目标；应降级、减题或说明缺证据。
4. 输入的范围/索引/图谱/Mastery/Assessment revision 任一变化，都使旧计划不可用于静默生成；必须明确重新分析/规划。
5. `ExamMode` 在范围分析或计划预览后不可改变。改变模式必须执行返回设置页的既有动作，清空 analysis 与 plan，再重新开始。
6. L6 的任何失败不能阻断现有手动范围考试、提交评分、保存 Session、Markdown 导出或历史读取。
7. Planner 不根据模型提供商、`evaluatorKind`、simple/challenge 或自由文本长度调整 Mastery 权重；这些只可用于审计、呈现或后续独立校准研究。

## 3. 目标数据流与版本策略

### 3.1 端到端数据流

~~~text
用户：范围 + 题数 + adaptive target mode + ExamMode
  → 现有范围分析（锁定输入）
  → L6.2 读取 effective graph / Mastery / Assessment
  → L6.1 纯函数生成并验证 ExamPlan
  → UI 展示目标、理由、降级原因
  → L6.3 将 target source chunks + ExamMode 交给 ExamEngine
  → M6.0 蓝图 / 出题 / 本地或模型评分路由
  → L6.4 保存 ExamSession + plan audit snapshot
  → L6.6 基于题目已证明的 concept/source 生成 Assessment event
  → 既有 Mastery 只消费 Assessment event
~~~

### 3.2 Revision 与 stale-plan 规则

计划输入需要携带以下只读 revision/signature，而不是把整份图谱、历史或原文重复写入计划：

| 字段 | 来源 | 用途 |
|---|---|---|
| `scopeSignature` | 已规范化的范围选择、排除/强制包含与 analysis eligible chunks | 防止范围或文件变化后复用计划 |
| `indexRevision` | 已有知识索引/来源 inventory 有效 revision | 防止知识库变更后继续使用旧 chunk |
| `effectiveGraphRevision` | effective Concept/confirmed relation 查询快照 | 防止图谱治理变化后选择过时目标 |
| `masteryRevision` | Mastery snapshot 生成 revision/时间 | 审计排序依据 |
| `assessmentRevision` | 已保存 Assessment history 的 revision 或稳定 fingerprint | 防止冷却期/覆盖判断过时 |
| `planningAt` | controller 显式注入、按秒/毫秒规范化的时间 | 使到期和冷却期判断可复现 |

`ExamPlan.inputFingerprint` 由算法版本、上述 signature、模式、题数和稳定排序后的目标候选摘要产生。提交“按计划生成”时，Application 层必须重新比较 revision：匹配才继续；不匹配则返回可本地化的 `plan-stale` 结果，UI 显示“知识状态已变化，请返回并重新分析”。不得后台静默重算，因为用户需要看到新的目标和理由。

## 4. M6.1：自适应考试领域模型与确定性规则

### 4.1 交付目标

新建 `src/domain/adaptive-exam/`，在不依赖 Application/Obsidian 的前提下定义输入、输出、理由代码、稳定 fingerprint、完整性校验和纯 Planner 算法。此步骤不读取 Store、不调用模型、不渲染 UI。

建议模块划分：

~~~text
src/domain/adaptive-exam/
  adaptive-exam-types.ts            # public value objects and discriminated unions
  adaptive-exam-planner.ts          # pure rank/select algorithm
  adaptive-exam-integrity.ts        # plan/input validation and failure codes
  adaptive-exam-fingerprint.ts      # canonical serialization and browser-safe hash
  adaptive-exam-policy.ts           # bounded constants, mode and cooldown policy
~~~

### 4.2 核心契约

建议的关键类型（名称可在实现时按项目命名规范微调，但语义不可省略）：

```ts
export type AdaptiveTargetMode =
  | "diagnostic"
  | "weak-review"
  | "prerequisite"
  | "mixed";

export type AdaptiveReasonCode =
  | "unassessed"
  | "low-confidence"
  | "weak-mastery"
  | "developing-mastery"
  | "review-due"
  | "confirmed-prerequisite"
  | "recently-covered"
  | "insufficient-evidence"
  | "scope-capacity-limited";

export interface ExamPlanningInput {
  algorithmVersion: "adaptive-exam/v1";
  planningAt: number;
  scope: AdaptiveExamScopeSnapshot;
  examMode: ExamMode;
  targetMode: AdaptiveTargetMode;
  requestedQuestionCount: number;
  revisions: AdaptiveExamRevisions;
  concepts: readonly PlanningConcept[];
  confirmedPrerequisites: readonly ConfirmedPrerequisite[];
  coverage: readonly ConceptAssessmentCoverage[];
}

export interface ExamTarget {
  conceptId: string;
  sourceChunkIds: readonly string[];
  reasonCodes: readonly AdaptiveReasonCode[];
  priority: number;
  expectedQuestionCount: number;
  prerequisiteOfConceptIds: readonly string[];
}

export interface ExamPlan {
  id: string;
  algorithmVersion: string;
  inputFingerprint: string;
  planningAt: number;
  examMode: ExamMode;
  targetMode: AdaptiveTargetMode;
  scopeSignature: string;
  targets: readonly ExamTarget[];
  appliedFallbacks: readonly AdaptiveReasonCode[];
  diagnostics: AdaptivePlanDiagnostics;
}
```

`PlanningConcept` 必须只包含 id、经确认的来源 chunk id、可供排序的 Mastery 摘要、confidence 和稳定 label；不能含模型原始响应、embedding 向量、待审核候选或整段笔记正文。`ConfirmedPrerequisite` 必须来自 effective graph 中方向明确且已确认的关系。`ConceptAssessmentCoverage` 仅保留最近评估时间、次数、最近得分摘要及可验证 event id。

### 4.3 纯算法与确定性

候选计算分为以下固定阶段：

1. **范围交集**：只保留有至少一个 `sourceChunkId ∩ eligibleChunkIds` 的 effective Concept。
2. **证据过滤**：去除无来源、悬空关系、重复 Concept 和无效 confidence；将原因记入 diagnostics，而非猜测补全。
3. **模式规则**：
   - `diagnostic`：优先从未评估、低 confidence 的范围内 Concept 中选取；
   - `weak-review`：优先 weak/developing、复习到期的 Concept；
   - `prerequisite`：仅从目标的确认前置节点中选取；没有有效边时降级为 diagnostic；
   - `mixed`：以固定配额在上述集合轮转；内容不足时记录实际采用的集合。
4. **冷却与覆盖**：最近已评估的 Concept 降权或排除；窗口与权重由 `adaptive-exam-policy.ts` 的版本化常量定义，时间来自 `planningAt`，不得在函数内读取 `Date.now()`。
5. **排序与截断**：按 `priority DESC → 最久未评估 ASC → conceptId ASC` 等公开 tie-breaker 排序。题数不足时宁可减题并返回 `scope-capacity-limited`，不以相似名称补足。
6. **来源选择**：每个 target 的 chunk id 使用字典序去重并截取预算；source 必须同时属于当前范围和该 Concept 的已证明来源。

优先级可使用可读的整数/定点权重，避免浮点微差污染测试。例如先按 `reasonTier`、再按 `masteryBand`、再按 `daysSinceLastAssessment` 分桶，而不是把多个未校准的小数相乘。所有权重、冷却期和最大目标数都必须在 policy 文件中带 `algorithmVersion`，并在 plan 中保存该版本。

### 4.4 Fingerprint、完整性和失败模型

- 采用当前项目 `stableGraphHash` 风格的 FNV-1a 浏览器兼容 hash；输入先递归规范化对象 key、数组顺序与字符串空白，不能依赖对象插入顺序。
- `validateExamPlanningInput()` 返回结构化失败码，例如 `empty-scope`、`stale-revision`、`no-effective-concepts`、`no-source-backed-target`，不直接抛出展示给用户的中文错误。
- `validateExamPlan()` 要验证：target 唯一、每个 target 有 source、source 都在 scope、reason code 与模式相容、数量未超过请求/容量、排序符合 policy。
- 重复调用 `buildExamPlan(input)` 的 JSON 结果必须字节级一致；测试中注入相同 `planningAt`，不使用随机 ID。`plan.id` 从 fingerprint 派生。

### 4.5 M6.1 验收

- 纯 domain 单元测试不需要 Obsidian、Model client、Store 或网络 mock。
- 每个模式都有范围不足、没有 Mastery、没有确认前置、最近重复、并列排序和无 source 的 fixture。
- 输入不变时 fingerprint/targets/diagnostics 完全一致；任一 revision 或 `ExamMode` 改变时 fingerprint 改变。
- pending/rejected、embedding-only、模糊 label 的 fixture 绝不成为 target。

## 5. M6.2：Application Planner、快照组装与降级

### 5.1 交付目标

新建 `src/app/exam/adaptive-exam-planner.ts`。它负责把多个现有只读服务的输出归一化成 M6.1 输入，然后调用纯 domain Planner；不把排序逻辑散落在 controller 或 View。

建议定义窄依赖接口：

```ts
interface AdaptiveExamPlannerDependencies {
  getScopeSnapshot(selection: ExamScopeSelection): Promise<ResolvedExamScope>;
  getEffectiveConceptCatalog(): Promise<EffectiveConceptCatalog>;
  getConfirmedPrerequisites(): Promise<readonly ConfirmedPrerequisite[]>;
  getMasterySnapshot(): Promise<MasterySnapshot | null>;
  getAssessmentCoverage(): Promise<readonly ConceptAssessmentCoverage[]>;
  getRevisions(): Promise<AdaptiveExamRevisions>;
  now(): number;
}
```

依赖由 `application-container.ts` 装配现有 Learning Graph、Mastery、Assessment 和范围服务；测试只替换这些 port，不实例化 Obsidian `App`。这保持 Application 层能处理异步读取、source lifecycle gate 和错误分类，而领域层保持同步纯函数。

### 5.2 读取、归一化与降级规则

| 外部状态 | Application 行为 | 传给 domain 的结果 | UI 文案方向 |
|---|---|---|---|
| Mastery 尚未构建 | 不阻塞计划 | 所有 Concept 视作 unassessed/unknown | “暂无掌握度，按范围进行诊断” |
| effective graph 不可用 | 不读 pending 语义候选 | 若有确定性 source 则做范围基础计划；否则停止 | “缺少可验证概念来源” |
| Mastery/graph dirty 或 revision 不一致 | 不复用旧 plan | 返回 stale/needs-refresh | “知识状态已变化，请重新分析” |
| Assessment history 为空 | 不虚构复习到期 | `diagnostic` 降级 | “尚无历史评估，先建立基线” |
| 容量不足 | 不扩大范围 | 计划减题并说明实际容量 | “可生成 N 道，而非请求的 M 道” |
| 某 target 没有范围内来源 | 排除 target | diagnostics 记录 `insufficient-evidence` | “该概念缺少当前范围证据” |

适配器输出进入 Planner 前必须排序、去重、冻结为只读 snapshot。Application 层只将必要 metadata 传递到 Presentation，不传递完整笔记、embedding 或模型输出。

### 5.3 性能与并发

- 计划计算本身是 O(C log C + R)，其中 C 为范围内 effective Concept 数、R 为确认前置关系数；使用已有 graph-capacity 的投影预算限制输入。
- 读取使用已有缓存的 Mastery/graph query 服务；不得在每次 radio 切换时重扫 Vault、重建索引或调用 LLM。
- `AbortSignal` 贯穿 scope 解析和 Planner 请求；纯函数在大数组循环中可按批次检查 signal，或 Application 在调用前后检查。
- controller 使用 request/revision token，只有最新一次分析/计划请求可以写回 state；返回设置页或取消后旧 Promise 的结果必须被忽略。
- 不持久化 Planner cache 作为事实。可在单次 View 生命周期内用 `inputFingerprint → ExamPlan` 做只读 memoization，但 revision 改变立即失效。

### 5.4 M6.2 验收

- port mock 能证明 planner 不调用 Model client、不写 Store、不触发 graph rebuild。
- 错误/降级结果是结构化状态，View 不需解析异常消息。
- 多个并发计划请求、取消、scope 变化和 source lifecycle gate 都不会把旧计划显示为当前计划。
- 200–500 个可见 Concept 的典型输入在本地 UI 可接受预算内完成；性能测试以确定性 fixture 和相对阈值记录，而非依赖机器绝对毫秒数。

## 6. M6.3：ExamEngine、蓝图与题目生成桥接

### 6.1 交付目标

让既有 `ExamEngine` 接收**已验证的** `ExamPlan` 或最小 `ExamTarget` 列表，而不是让它自行访问 Mastery 或图谱。既有手动范围考试继续传空计划，行为保持不变。

建议新增一个跨层但只读的值对象，例如：

```ts
interface AdaptiveExamGenerationContext {
  planId: string;
  algorithmVersion: string;
  inputFingerprint: string;
  targetMode: AdaptiveTargetMode;
  examMode: ExamMode;
  targets: readonly ExamTarget[];
}
```

它作为可选字段进入 `ExamGenerationOptions` 或专用 `createExamFromPlan()` 入参；不能把 Application service、Store、Mastery snapshot 或 graph object 传入 `src/exam/`。

### 6.2 蓝图映射技术

1. Engine 先以当前 scope/analysis 得到 eligible chunk；对每个 target 执行 `target.sourceChunkIds ∩ eligibleChunkIds`。
2. 交集为空时拒绝该 target 并在生成 diagnostics 中记录，不改为按 concept 名称搜索。
3. 对有效 target，以 `conceptId + source chunk` 建立 blueprint item 的额外 audit 字段，例如 `plannedTargetConceptIds?`；它不替代现有 `questionType`、`difficulty` 或 `sourceChunkIds`。
4. `ExamBlueprintService` 的提示词只获得 target 的稳定 label、学习目标和已经允许的 source chunk，不获得 Mastery 原始事件、用户行为或全图。
5. M6.0 的 `ExamMode` 原样传入蓝图：simple 强制 `single-choice | true-false`；challenge 才允许 `free-response`。Adaptive target mode 不得覆盖这个 policy。
6. `ExamQuestionGenerator` 继续验证来源、客观题 option/answer key、唯一性与回退。若某 target 的模型输出无效，使用同一 target/source 的既有确定性回退；不能回退到范围外题目。

为避免一次 target 被多个 blueprint item 无限制重复，使用 `Map<conceptId, assignedCount>` 和计划中的 `expectedQuestionCount` 上限。题目数不足时保留已通过题目并报告，不添加无证据的干扰项。

### 6.3 兼容性与边界

- 保留现有 `ExamBlueprintItem`、`ExamQuestion` 新字段可选的兼容策略；旧 Session 缺少 adaptive metadata 时仍按旧自由文本记录读取。
- `EXAM_QUESTION_GENERATION_PROMPT_VERSION` 只在 prompt 契约真实改变时升级；旧题目/报告不重写。
- 无 adaptive context 时，所有 legacy golden tests 必须保持原输出；不得因新增字段强制 M1/M5 历史数据迁移。
- 本步骤不添加模型自检 Agent。结构不合格仍由既有 deterministic validator + source-bound fallback 处理。

### 6.4 M6.3 验收

- 自适应 target 的每题 `sourceChunkIds` 是 target 与 scope 的交集，且题目审计字段能回链 plan。
- simple + 任意 adaptive target mode 从不产生自由文本题；challenge 仍遵守 M6.0 支持的封闭 answer form 枚举。
- 模型失败、无效 option、无来源 target、题数减少和取消均不越界、不会中断历史手动考试。
- ExamEngine 编译依赖中不存在 Mastery/graph service import。

## 7. M6.4：Application API、Session 审计与持久化

### 7.1 交付目标

新增预览计划和按计划创建考试的 Application API，同时将“当时依据什么生成”以可选 audit snapshot 保存在 Exam Session 中。计划并不是新的事实源，但保存最小快照可让历史考试解释为什么选中某个 Concept。

建议 API 形态：

```ts
previewAdaptiveExamPlan(request: AdaptiveExamPlanRequest): Promise<AdaptiveExamPlanResult>
createAdaptiveExamSession(request: CreateAdaptiveExamRequest): Promise<ExamSession>
```

`AdaptiveExamPlanResult` 是判别联合：`ready`、`degraded`、`stale`、`unavailable`、`cancelled`。它携带 i18n key/参数、plan 摘要和 diagnostics，而非预格式化 HTML/中文长文本。

### 7.2 Session 与报告契约

在 `ExamSession` 新增可选 `adaptivePlan` audit 块：

```ts
interface AdaptivePlanAuditSnapshot {
  planId: string;
  algorithmVersion: string;
  inputFingerprint: string;
  targetMode: AdaptiveTargetMode;
  examMode: ExamMode;
  scopeSignature: string;
  targetConceptIds: string[];
  reasonCodesByConceptId: Record<string, AdaptiveReasonCode[]>;
  appliedFallbacks: AdaptiveReasonCode[];
}
```

- 只保存 ID、版本、理由代码和范围 signature；不保存 embedding、整段 source、模型 prompt 或 Mastery 全快照。
- 新字段全部可选。`AssessmentSessionDocumentV1` 可接受加性字段；只有出现不兼容语义变更时才提升 schema version 并写迁移。
- JSON store 的 runtime validator 对 optional 字段做严格枚举/数组/字符串检查，未知字段保持前向兼容。
- Markdown report 只在用户需要审计时增加“考试计划”摘要；增加 frontmatter/projection 合约时提升 `EXAM_MARKDOWN_PROJECTION_VERSION`，旧报告仍可读取。
- `examMode` 与 plan audit 必须匹配；保存前由 domain integrity 检查。若不匹配，拒绝保存而不是修正其中一个字段。

### 7.3 Stale-plan 与幂等保存

- `createAdaptiveExamSession()` 在生成前复核 input fingerprint/revision；不匹配返回 `stale`，不调用模型。
- Session 创建后保存/重新评分仍按现有 questionId 和 Assessment event fingerprint 幂等；同一计划不应导致重复 event。
- 重新评分可以生成 superseding event，但不重新运行 Planner 或改变原 session 的 plan audit。
- Exam history 与导出继续以 Session/Assessment 事实显示；计划预览本身不写入历史。

### 7.4 M6.4 验收

- 旧 JSON、旧 Markdown、旧自由文本 Session 与未评分 Session 均可读。
- 新 Session round-trip 后 plan id、两种模式、理由代码和 source linkage 不丢失。
- stale request 不产生模型调用、不创建半成品 Session；取消不会保存 plan 或报告。
- API 只暴露需要的 DTO，不泄露 Store/Obsidian/Model client 类型。

## 8. M6.5：考试界面、Controller 状态机与可访问性

### 8.1 交付目标

在现有原生 DOM `ExamView` 与 `ExamController` 中加入自适应目标模式、计划预览和“为什么考它”，但不引入 React、全局状态库或 modal workflow。现有手动范围考试仍是首要可用路径。

推荐的可见状态机：

~~~text
setup（可改范围/题数/ExamMode/target mode）
  → analyzing（busy，可取消）
  → plan-ready（锁定输入：Generate / 返回并修改设置）
  → generating（busy，可取消）
  → taking → evaluating → review

返回并修改设置：清空 analysis + plan + request token；重新开放所有设置
~~~

`targetMode` 与 `ExamMode` 都属于 setup input：用户必须在分析前选择。plan-ready 状态沿用 M6.0 已实现的配置锁定，不允许在同一份 analysis/plan 上切换 simple/challenge、切换目标模式、修改范围、修改文件或题数。这样计划的理由、source scope 与实际生成策略永远一致。

### 8.2 UI 技术细节

| 区域 | 技术实现 | 关键交互 |
|---|---|---|
| 目标模式选择 | 原生 radio group + `AdaptiveTargetMode` 状态 | 选择变化清空旧 analysis/plan；默认 `diagnostic` |
| 考试模式选择 | 复用 M6.0 radio group | 默认 simple；分析后 disabled |
| 分析/计划预览 | controller 请求 token + `AdaptiveExamPlanResult` | 显示目标数量、原因、降级、实际题量和两种模式，不显示内部 score |
| 每题理由 | question ↔ plan target audit mapping | 显示 Concept、理由代码本地化、来源跳转；缺失映射显示“范围基础题”，不猜测 |
| 返回 | `returnToSetup()` | 清空 plan、analysis，恢复可编辑状态；不删除已保存历史 |
| 无障碍 | semantic `button`/`input`、`disabled`、可见状态文本、焦点恢复 | 不能只依赖颜色；键盘能选择模式、查看理由、返回 |

现有 View 是全量重渲染模式，因此 controller 的 `getState()` 要返回不可变的 plan summary。DOM listener 继续由 View 生命周期清理；不要让 plan 结果闭包持有旧 View 或旧 AbortController。

### 8.3 M6.5 验收

- 用户能在三步内理解“考什么、为什么、如何作答”：选择设置 → 分析查看计划 → 生成。
- plan-ready 只允许生成或返回；测试通过直接调用 controller setter 也无法变更锁定输入。
- 计划不存在、不可用、stale、降级、取消和题数减少都具有明确且不误导的 i18n 状态。
- 从 Learning Map/Recommendation 启动来源范围考试时，可预填 target/mode，但用户仍能在分析前修改；不能静默跳过确认。
- Ask、历史、手动范围考试、M6.0 客观题 radio 和旧 textarea 不回归。

## 9. M6.6：Assessment 绑定、Mastery 接缝与评分不变量

### 9.1 交付目标

让自适应计划选中的目标可以被审计，同时只把**题目已证明的** Concept/source 作为 Mastery 输入。不能因为 Planner 希望考一个 Concept，就把没有证据的 id 写进 Assessment event。

当前 `AssessmentEventFactory` 以 `question.conceptIds` 与 `question.sourceChunkIds` 创建 immutable event；该路径应继续是 Mastery 的唯一考试事实输入。M6.6 在此基础上增加 audit 信息和更严格的交叉校验。

### 9.2 绑定策略

1. Planner target 只能携带范围内、有效 Concept 已证明的 source chunk。
2. Engine 生成题目后，以 `question.sourceChunkIds` 查询 confirmed `conceptIdsByChunk`；只有交集中的 target Concept 可进入 `question.conceptIds` 和 Assessment event。
3. 建议为 event/session 添加可选 `adaptive` audit 块（plan id、target mode、`plannedTargetConceptIds`），但 Mastery engine 继续只读取 `conceptIds`、分数、confidence、时间和既有字段。
4. target 无法安全绑定时，在 plan/session diagnostics 标记 `insufficient-evidence`，题目可作为范围基础题存在，但不得以该 target 更新 Mastery。
5. `ExamEvaluationMetadata.evaluatorKind` 应在 Assessment audit 中以可选字段保留为 `model | deterministic`；现有 `provider/model/promptVersion` 保持兼容。它用于解释评分来源，不用于自动加减分。

必要时将 `AssessmentEvent.evaluator` 扩展为加性字段：

```ts
evaluator: {
  provider: string;
  model: string;
  promptVersion: string;
  kind?: "model" | "deterministic";
}
```

JSON validator、event fingerprint、supersession、Mastery binding resolver 和现有 fixture 必须同步审查：新增 audit 字段不能使旧 event 重复写入，也不能令 re-evaluation 丢失 supersedes 关系。

### 9.3 不变量与验收

- simple 的 100/0 分和 challenge/legacy 的模型分数均沿用现有 normalized score 算法；M6.6 不设置题型系数。
- pending/rejected、label 相似、source 交集为空的 Concept 不进入 `event.conceptIds`。
- 一个已保存 Session 的重新评分只 supersede 同一 question 的旧 event；不会重新规划、不会重新绑定无关 Concept。
- 图谱快照在创建、作答、评分、保存自适应考试前后保持不变；只允许 Assessment/Mastery 既有失效通知。
- Assessment 读取失败时，用户仍能看到已生成考试和评分结果；保存失败走既有错误提示，不污染图谱。

