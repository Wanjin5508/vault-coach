# Vault Coach 代码注释规范

## 1. 目标

代码注释用于保存无法从类型、命名和控制流直接看出的协作知识，包括业务约束、架构边界、数据一致性、失败策略和兼容原因。注释应帮助维护者安全地修改代码，而不是逐行复述实现。

## 2. 语言与术语

- 说明性文字统一使用简体中文；
- 类名、类型名、字段名、协议名、错误码和第三方产品名保留原文，例如 `KnowledgeBaseSnapshot`、`AbortSignal`、WebGPU；
- 同一概念使用固定译法：应用层、领域层、基础设施层、展示层、知识范围、向量索引、语义图、掌握度；
- 用户可见文案进入 `src/i18n.ts`，不要写在注释里代替本地化；
- 不翻译标准工具指令，例如 `eslint-disable`、`@deprecated` 和 URL。

## 3. 应当注释的内容

### 3.1 模块和类

说明三个问题：

1. 该模块负责什么；
2. 明确不负责什么；
3. 有哪些必须维持的生命周期、数据或依赖边界。

```ts
/**
 * 协调知识索引的重建、取消和状态发布。
 *
 * 该类只管理应用层任务，不读取 DOM，也不直接写入 Obsidian Notice。
 * 新索引完整落盘前必须保留最后一个可用快照。
 */
```

### 3.2 公共接口与领域类型

说明字段语义、单位、取值边界、旧版本兼容和不变量。类型已经表达清楚的信息不重复描述。

```ts
interface IndexProgress {
    /** 当前任务已完成的 chunk 数；总数未知时允许为空。 */
    completed?: number;
}
```

### 3.3 非直观分支

解释为什么必须这样处理，以及删除该分支会破坏什么。注释放在决策前，而不是在代码后补一句同义描述。

```ts
// 旧索引没有完整的 embedding 指纹，不能证明与当前查询向量兼容。
// 保留文字索引供关键词检索使用，仅将向量部分标记为过期。
```

### 3.4 失败、降级与一致性

写清失败是否可重试、是否允许部分成功、保留哪些旧数据，以及哪个上层负责向用户展示错误。

### 3.5 兼容与迁移

说明兼容对象、移除条件和替代入口。废弃 API 必须包含迁移目标。

```ts
/**
 * @deprecated 仅用于兼容旧导入路径；新代码从 `presentation/plugin-api` 导入。
 */
```

## 4. 不应保留的注释

- 逐字复述下一行代码；
- 已失效的实现历史和个人讨论；
- 没有负责人、条件或追踪入口的模糊 TODO；
- 用“临时”“以后优化”代替明确约束；
- 注释掉的旧代码；
- 与实现不一致的参数、默认值或版本号；
- 重复类型定义的 `@param`、`@returns` 文本。

实现能通过命名直接表达时，优先重命名或提取函数。

## 5. TODO 格式

只有存在明确触发条件或跟踪入口时才使用 TODO：

```ts
// TODO(#123): 当索引格式 v2 完成迁移后，删除 v1 读取分支。
```

没有 issue 时写清移除条件：

```ts
// TODO: 等最低支持版本提供该 API 后，移除兼容探测。
```

## 6. 分层要求

| 层级 | 注释重点 |
| --- | --- |
| `domain/` | 业务不变量、确定性、证据边界、不可变事实 |
| `app/` | 用例编排、事务边界、失败与降级、端口职责 |
| `infrastructure/` | 外部格式、存储原子性、资源释放、平台限制 |
| `presentation/` | View 生命周期、交互状态、可访问性、渲染规模 |
| `plugin/` | Obsidian 注册与清理、稳定 ID、宿主适配 |

## 7. 公共声明的覆盖优先级

导出并不等于必须逐项添加注释。审查时按协作风险决定注释粒度：

1. 优先说明跨层 API、存储端口、持久化格式、组合根、生命周期对象和领域不变量；
2. 算法入口应说明确定性、排序、版本和失败语义；
3. 一组语义紧密且名称清楚的枚举、联合类型或纯函数，可以用模块级注释统一说明；
4. 仅在字段存在单位、边界、可空语义、兼容要求或安全含义时添加字段注释；
5. 不为 getter、简单适配器、自解释常量和重复类型信息机械补注释。

代码审查不能只统计注释覆盖率。应检查维护者是否能够判断变更影响、数据归属、调用边界和不变量。

`src/main.ts` 是架构测试锁定的最小 Obsidian 入口，只保留导入和默认导出；入口职责记录在
`vault-coach-plugin` 和架构文档中，不在该文件增加说明文字。

## 8. 审查清单

- [ ] 新增公共类型或服务是否说明职责和边界？
- [ ] 非直观分支是否解释原因和被保护的不变量？
- [ ] 失败路径是否说明数据保留、重试和展示责任？
- [ ] 注释是否与当前实现、版本和默认值一致？
- [ ] 是否泄露 API key、笔记正文、用户路径或模型输出？
- [ ] 是否可以通过改进命名删除这条注释？
- [ ] 废弃入口是否给出迁移目标？
- [ ] TODO 是否有追踪入口或可验证的移除条件？
